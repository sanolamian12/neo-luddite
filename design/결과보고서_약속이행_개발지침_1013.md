# 결과보고서 약속 이행 — 개발 지침 (10/13 작성 · 11/2 기능 동결까지 유효)

> **모든 개발 세션은 시작할 때 이 문서부터 읽는다.** 로드맵(`design/데모대비_챗품질_개선로드맵_1010.md`)보다 우선한다.
> 상태 원본은 `docs/doing/최종결과보고서_작업기지_1012.md`의 §4-1 약속 장부이고, 보고서 원고는 `docs/final/원고/원고_1-6_ch2.md`다.

## 0. 왜 이 문서가 있나

- 결선 최종결과보고서(10/23 17시 제출)는 **11/3~5 시연 시점의 시스템**을 결과로 적는다. 사용자가 10/13에 정했다.
- 심사위원은 이 보고서를 들고 킨텍스 부스에 와서 실물과 맞춰 본다. 양식에는 "보고서 내용 = 결선 시연 내용, **허위 기재 시 수상 취소**"라고 되어 있다.
- 그래서 **보고서에 적힌 것은 11/2까지 전부 실제로 동작해야 한다.** 이 문서는 보고서에 적은 문장마다 무엇을 구현하고 무엇으로 합격을 판정하는지 정리한 것이다.

## 1. 모든 세션이 지킬 규칙

1. **보고서가 약속한 동작을 깨지 않는다.** 백엔드를 배포할 때마다 `backend/eval/run_demo_eval.py`로 회귀 계측을 돌린다. §3의 수치가 나빠지면 배포를 되돌리거나 그날 안에 고친다.
2. **약속을 지킬 수 없겠다고 판단되면 즉시 사용자에게 알린다.** 몰래 범위를 줄이지 않는다.
   - 10/22까지는 보고서 문구를 고칠 수 있다(작업기지 §4-1 상태 갱신 + 원고 수정).
   - 10/23 제출 후에는 구현으로만 메울 수 있다.
3. **우선순위는 약속 장부(P1~P10) 항목 > 그 밖의 개선**이다. 장부 밖 기능은 보고서 6장 "향후 계획" 몫이니 11/2 전에는 손대지 않는다.
4. **세션을 끝낼 때마다 작업기지 §4-1의 상태 칸과 아래 §2 표의 "현재" 칸을 갱신한다.** 커밋 해시와 측정 파일 경로도 함께 적는다.
5. 데이터 출처 정직성:
   - 세무사 평가 점수는 세무사가 직접 준 값만 쓴다.
   - 평가 질문 세트는 "내부 제작"이라고 밝힌다.
   - Claude가 만든 산출물(감사 모드, LLM1 derived 데이터)을 사람 평가나 제품 자산으로 쓰지 않는다.
6. 기존 운영 제약은 그대로 지킨다.
   - 국내 모델만 쓴다. 제품 경로에서는 Upstage만 호출한다.
   - Supabase egress와 DB 크기를 아낀다. 배포는 모아서 하고, 로컬 개발은 `VEC_MEMORY=off`로 띄운다.
   - 운영 마이그레이션은 사용자가 직접 실행한다.
   - 프론트 dev 서버가 떠 있으면 build하지 않는다.
7. **11/1에 기능을 동결한다.** 11/1~11/2에는 리허설(R6)과 버그 수정만 한다.

### 6-2. 배포할 때마다 (규칙 1)
```
cd backend
.\.venv\Scripts\python.exe -m eval.run_demo_eval --tag <이름>        # 운영 데모 세트(전체 또는 --only)
.\.venv\Scripts\python.exe -m eval.report_check --tag <이름>         # 보고서 §2-B 수치에 자동 대조
```
- `report_check` 가 ❌·⚠ 를 내면: 이번 배포 탓이면 되돌리거나 그날 고친다. 원래 미달이던 항목(출처 80%·A4 등)은 그 항목을 맡은 세션의 일 — 악화만 없으면 된다(직전 회차 report_check 와 비교).
- 지연 판정은 웜업 1~2회 뒤, 같은 세트 2회 이상(Solar 흔들림).
- 목표값은 `backend/eval/report_check.py` 의 `TARGETS` 한 곳. 보고서 숫자가 바뀌면 같은 날 고친다(§5).
