## 0. 진단 — 지금 상태

### 0.1 세무사 계정은 지금 어떻게 생기나
- 실제 계정은 **`supabase/seed.sql` 직접 insert 로만** 생긴다(auth.users + identities + `public.auditors`). Admin API 스크립트 없음.
  운영 = 데모 8계정(user 4 · auditor 3 · admin 1), 전부 email provider.
- 관리자 "새 평가자 등록"(`/admin/auditors/new` → `services/auditor.ts:77-113`)은 **`public.auditors` 행만 insert** — 로그인 계정·profiles·역할은 안 생김(화면 문구도 "PoC").
- 연결 키 = `auditors.id = profiles.domain_id`(FK 없음, 텍스트). 소셜 가입자의 domain_id = auth uid 문자열.
- `expert_profiles` 는 트리거·시드 없음 — 세무사 본인이 `/audit/profile` 에서 upsert. 카드 노출 = `auditors.status='active' and expert_profiles.listed`(0034 `list_experts`).
- 역할 결정: 로그인 후 `lib/live-auth.ts` 가 **profiles.role** 을 읽음(JWT 아님) → DB 에서 role 만 바꾸면 다음 세션 동기화 때 `/audit` 로 간다.
- 0047 `guard_profile_identity`: admin 이 아니면 role·domain_id 변경 불가. security definer RPC 안에서도 `auth.role()='authenticated'` 라 **호출자가 admin 이어야 통과** → 승인 RPC 를 admin 전용으로 두면 그대로 맞물린다.

- 사용자 목록·가입 경로·최근 접속 — 없음(프론트에서 `profiles` 전체를 읽는 코드 0).

- `rag.chat_turns`(463건, 9/16~)는 RLS 켜짐·정책 0·authenticated 권한 0 → **관리자 집계는 security definer RPC 필요**.
  사용자 컬럼 없음, `conversation_id` 로 `conversations.owner_id` 조인. **463건 중 444건은 대화 행 없음** = 비회원 턴(+삭제분) → 회원/비회원 구분 근거.

## 1. 설계 결정 (사용자 확인 필요 표시 = ❓)

### D1 ❓ 세무사의 로그인 수단 — **권장: 소셜 계정으로 먼저 가입 → 그 계정으로 신청 → 승인 시 같은 계정의 role 을 auditor 로**
| | A. 소셜 가입 후 신청(권장) | B. 계정 없이 신청서 → 관리자가 이메일 계정 발급 |
|---|---|---|
| 계정 생성 | 이미 있음(0047 경로) | Admin API(service role) 필요 → 백엔드 엔드포인트 신설 |
| SMTP | **불필요**(알림은 앱 안 우편함 `public.mail`) | 필수(초대·비밀번호 설정 메일) |
| 본인 확인 | 소셜 로그인 + 신청서 | 이메일 소유 확인뿐 |
| 팀장 화면 | 안 건드림(진입 링크만 협의) | 로그인 화면에 세무사 이메일 로그인 상시 노출 필요 |
| 단점 | 고객으로 쓰던 계정이면 고객 대화가 세무사 계정에 남음 → 신청 조건에 "상담 기록이 있으면 경고" 정도 | 공사 큼, 전시 전 SMTP·도메인 일정 의존 |

→ A 면 **운영 SMTP 는 이번 범위에서 빠진다**(재설정 메일은 데모 이메일 계정만 해당).

### D2 ❓ 신청 화면 위치 — **권장: 새 경로 `/expert/apply`(내 소유) + 진입은 계정 메뉴 "세무사로 신청"**
- 로그인·가입 화면(`components/auth/auth-screen.tsx`, 팀장)은 **코드로 안 건드린다**.
- 가입 화면 안내문(auth-screen.tsx:87 "전문가·운영자 권한은 승인된 계정에만 부여됩니다") 옆에 "세무사이신가요? → 신청 방법" 링크 한 줄을 넣으면 발견성이 좋아지는데, **이건 팀장 화면이라 협의 대상**. 넣지 않아도 흐름은 완결된다.
- 비로그인으로 `/expert/apply` 진입 → `/login?next=/expert/apply` (destinationAfterLogin 의 viewer 허용 경로에 추가 필요 — `lib/account-route.ts`, 이것도 PR #5 계열 파일이라 한 줄 수정이면 알림).

### D3 ❓ 신청서 항목 — **권장 최소: 이름 · 세무사 등록번호 · 사무소명 · 사무소 소재지(시·구까지) · 연락 이메일 · 휴대폰 · 경력 연수 · 전문 분야 · 자기소개(선택)**
- 자격증 사본 업로드는 **안 받는 것을 권장**(민감 서류 보관 부담·Storage 정책 추가). 관리자가 등록번호·이름으로 한국세무사회 회원 조회를 **수작업**으로 확인하고, 확인 결과를 체크·메모로 남긴다(자동 검증 없음).
- 이메일은 카카오 가입자가 이메일 없이 올 수 있어 신청서에서 따로 받는다(`auditors.email` not null).

### D4 ❓ 반려·철회 신청서 보유 — **권장: 반려·철회 후 30일 보관 뒤 파기**(재신청 대응), 승인되면 신청서 원본은 `auditors`·`expert_profiles` 로 옮기고 등록번호·확인 메모만 유지
- 처리방침 §1·§3 갱신 필요. 회원 탈퇴 시 신청서도 함께 삭제(`_purge_account` 에 추가).

### D5 승인 시 하는 일 (DB 단일 전이, 0035 방식)
한 트랜잭션에서: 신청서 `approved` → `profiles.role='auditor'`(domain_id 는 그대로 uid) → `auditors` 행 insert(id=domain_id, 이름·이메일·전화·qualifications=['세무사', 등록번호 표기]) → `expert_profiles` 행 insert(**listed=false**, 신청서의 전문분야·경력·소개 복사 — 세무사가 프로필을 확인하고 직접 공개) → 신청자에게 앱 안 우편함 알림.

### D6 ❓ 세무사 해제 — 이번 범위에 넣을지
- 승인 취소(auditor → user 강등)는 진행 중 상담방·원장이 걸려 복잡 → **이번엔 "정지"(기존 auditors.status=suspended)로 대신**하고 강등은 안 만든다(권장).

## 2. DB — 마이그레이션 0049 (적용은 확인 후)

### 2.1 `public.expert_applications`
```
id text pk ('app-'||uuid)
applicant_domain text not null  -- = current_domain_id(), profiles 삭제 시 _purge_account 가 지움
name, registration_no, office_name, office_region, email, phone text
years_experience int, specialties text[], bio text
status text check in ('pending','approved','rejected','withdrawn')
review_note text        -- 관리자 확인 메모(신청자 비공개)
reject_reason text      -- 신청자에게 보이는 사유
status_history jsonb    -- [{status, at, actor, note?}] (0035 형식)
created_at, updated_at, decided_at bigint
unique (applicant_domain) where status='pending'   -- 진행 중 신청 1건
```
RLS: 신청자 = 본인 행 select(단 `review_note` 는 RPC 로만 감추거나 뷰로 분리), admin = 전부 select. **insert/update 정책 없음** — 아래 RPC 가 유일한 경로.

### 2.2 RPC (전부 security definer, `revoke from public, anon` · `grant to authenticated`)
| 함수 | 호출자 | 하는 일 |
|---|---|---|
| `submit_expert_application(jsonb)` | role=user 만 | 항목 검증(길이·등록번호 형식) → pending 1건 생성 → 관리자 우편함 알림 |
| `withdraw_expert_application(p_id)` | 신청자 | pending → withdrawn |
| `review_expert_application(p_id, p_decision, p_reason, p_note)` | admin 만 | `for update` 잠금 → pending → approved/rejected → (승인 시 D5) → 신청자 우편함 |
| `admin_list_users(p_limit, p_offset, p_role, p_q)` | admin 만 | profiles + auth.users(email·created·last_sign_in) + identities.provider + 대화 수·마지막 대화 |
| `admin_usage_overview(p_days int default 30)` | admin 만 | 아래 2.3 |

### 2.3 모니터링 지표 (`admin_usage_overview` 반환 jsonb)
- 사용자: 역할별 수 · 가입 경로별(google/kakao/email) · 기간 내 신규 가입 일별 · 7일/30일 활성(last_sign_in_at 기준)
- 사용: 일별 챗 턴(`rag.chat_turns`, **회원/비회원 분리** = 대화 행 존재 여부) · 처리 결과(outcome) 분포 · 일별 새 회원 대화(conversations) · 상담 신청 수·상태별(consultation_requests) · 대기 중 세무사 신청 수
- 한계(문서·화면에 명시): 비회원 턴은 대화 행이 없어 "삭제된 회원 대화"와 구분 불가(탈퇴 시 chat_turns 도 지우므로 실제론 거의 비회원) · 방문자 수(PV)는 수집 안 함.

### 2.4 함께 고칠 것
- **P2**: `admin_delete_account` 대상이 auditor 면 `expert_profiles` 삭제 + `auditors` 를 `status='suspended'`·이메일/전화 비우기·이름 "탈퇴한 세무사"(행 삭제는 consultation_*·ledger FK 때문에 불가) + 신청서 삭제. `_purge_account` 에 `expert_applications` 추가.
- **P1** ❓: `auditors_read` 를 staff(auditor·admin)로 좁히고, 고객 화면이 쓰는 이름은 `list_experts`/상담 RPC 가 이미 주는 값 또는 `id·display_name` 만 담은 뷰로 대체. **고객 화면 2곳(owner-consultations·owner-offers) 수정 필요** — 이번에 같이 할지 확인.
