## 이번 범위(§12 #1)
1. **제안·방 집계**: 제안(상태별 수 — pending·approved·declined·withdrawn·expired(읽을 때 판정)), 방(열림·닫힘, 메시지 수, 마지막 메시지 시각).
2. **브레이크**: 방 강제 종료(`close_room`), 동의 강제 철회(`revoke_pool_consent`), 대기 중 제안 거절·철회(`transition_offer`). 전부 확인 단계를 거친다.
3. **풀 열람 기록**(`pool_case_views`) 보기 — 어느 세무사가 어느 사례를 언제 열었나(사용자 결정 2026-09-21: 기록만, 고객엔 비공개 → admin 전용 화면).
4. 모바일 412px 컨벤션(테이블 → 카드, 다중 패널 → 탭).

## 하지 않을 것
마감 지난 일감 닫기(#3), 채널 묶기(#2), 만료 행 정리(#6 — 화면은 만료로 표시만), 메시지 페이지네이션(#7), 풀 새 사례 뱃지(#8), 동의만 하는 경로(#9), 방 안 대화 RAG·첨부(#10), 신고 기능(§4.3 에 적혀 있지만 신고 데이터가 없다 — 필요하면 따로 설계).
**DB 변경은 없어야 한다 — 필요해 보이면(예: 강제 조치 알림 메일, 강제 조치 사유 기록) 멈추고 묻는다.**

## 착수 전에 사용자에게 물을 것
- **화면 자리**: `/admin/consultations` 에 탭 추가(원안 — 신청 / 제안 / 채팅방 / 풀 동의·열람) / admin 사이드바에 새 메뉴.
- **admin 이 방 메시지 본문을 보는가**: RLS 는 열려 있다(`consultation_messages_admin_read`). 집계만(수·시각) / 본문까지(신고·분쟁 대응). 사장님·세무사 사이 사적 대화다.
- **강제 조치 뒤 알림**: 지금 함수는 사장님이 닫든 admin 이 닫든 같은 결과다. 당사자에게 "운영자가 닫았다"를 알릴지 — 알리려면 DB(메일·사유 컬럼) 변경이라 범위가 바뀐다.
- **풀 열람 기록의 보기 단위**: 사례별(이 사례를 누가 봤나) / 세무사별(이 세무사가 몇 건 봤나) / 둘 다.
