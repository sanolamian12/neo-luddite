## 1. 목표 흐름

```
[경로 A — 고객이 고른다]                    [경로 B — 풀에서 손을 든다]

AI 챗 중 연결 트리거(기존 (a))
  ↓
세무사 카드 목록에서 1명 선택
  ↓
③ 동의 시트: "이 대화를 비식별 처리해
   상담사 풀에 올려도 될까요?"  ──────────→  ⑤ 풀에 비식별 사례 등재(7일)
  │  (동의 없이도 ④는 진행된다)                        ↓
  ↓                                          ⑦ 풀을 본 세무사가 연결 요청
④ 신청(pending) → 그 세무사에게 알림              (프로필 + 메시지 1건 동봉)
  ↓                                                  ↓
⑥ 세무사 수락                                 ⑧ 고객이 설정 메뉴에서 확인
  ↓                                             → 승인 / 거절
  └──────────────→ 채팅방 개설 ←──────────────────────┘
                      ↓
     ⑨ 같은 대화에 대해 방이 여럿일 수 있다(세무사별 1:1, 상한 3)
```

- **경로 A의 동의는 선택**이다. 동의를 거절해도 고른 세무사에게 가는 신청(④)은 그대로 진행된다.
  동의는 "내가 고르지 않은 세무사에게도 보여도 되는가"에 대한 답이지, 신청의 전제 조건이 아니다.
- **채팅방은 두 경로의 합류점**이다. 경로 A의 수락(⑥)과 경로 B의 승인(⑧)이 같은 방을 연다.
- 방은 **대화(conversation) 단위가 아니라 (대화, 세무사) 쌍 단위**다. 한 대화에 세무사 3명이 붙으면 1:1 방이 3개다.

## 3. 데이터 설계

새 마이그레이션 `0037` ~ `0040`. 기존 `consultation_requests`(0034/0035)는 **경로 A 신청으로 그대로 유지**하고,
방·메시지·풀·제안은 새 테이블로 붙인다(기존 상태 기계를 건드리지 않는다).

### 3.1 `public.conversation_pool_consents` — 동의와 비식별 사본이 한 행에

| 컬럼 | 뜻 |
|---|---|
| `conversation_id` text PK → conversations(id) on delete cascade | 동의 단위 = 대화 1건 |
| `viewer_id` text | 동의한 사장님 domain_id |
| `granted_at` / `expires_at` bigint | 부여 시각 / +7일 |
| `revoked_at` bigint | 철회(= 즉시 풀에서 내려감) |
| `masked_payload` jsonb (nullable) | 마스킹된 Conversation — **풀에 보이는 전부**. **철회 시 null 로 비운다** |
| `mask_report` jsonb | `{규칙: 건수}` — 무엇을 몇 개 지웠는지(**messages 안에서만** 센다, §3.2) |
| `masked_at` bigint | 마스킹 시각(= 얼린 시점) |
| `occupation` / `tax_category` / `title` | 목록 메타. 원문 테이블을 조인하지 않으려고 동의 시점에 함께 얼린다(`title` 은 마스킹 후) |

- RLS: 사장님 = 본인 행 select 만, admin = 전체. **세무사는 정책이 없어 직접 조회 0행** — RPC 로만 본다.
  insert/update 정책 없음 — 쓰기는 `grant_pool_consent`/`revoke_pool_consent` 로만.

- **풀 노출 조건** = `revoked_at is null and expires_at > now`. 별도 플래그를 두지 않는다(어긋날 자리를 없앤다).
- 원문(`conversations.payload`)과 **분리 저장**한다. 풀은 이 테이블만 읽는다 → 마스킹 누락이 있어도
  "원문이 통째로 새는" 사고는 구조적으로 안 난다.
- 동의는 그 시점의 대화를 얼린다. 동의 후 이어진 턴은 풀에 안 올라간다(재동의로만 갱신).

### 3.2 마스킹은 **DB 함수 안에서** (`mask_conversation_payload(jsonb) returns jsonb`)

동의·마스킹·등재를 한 트랜잭션에 둔다. 클라이언트가 마스킹을 건너뛰고 등재할 경로 자체를 없애기 위해서다
(0034 에서 연락처 공개 범위를 `list_experts()` 로 강제한 것과 같은 판단).

| 규칙 | 패턴(요지) | 치환 |
|---|---|---|
| 전화 | `01[016-9]`+3~4자리+4자리, 지역번호형 | `[전화]` |
| 이메일 | RFC 근사 | `[이메일]` |
| 사업자등록번호 | 3-2-5 | `[사업자번호]` |
| 주민등록번호 | 6-7(성별자리 1~4) | `[주민번호]` |
| 계좌번호 | 2~6-2~6-2~8 (은행명 근접 시) | `[계좌]` |
| 카드번호 | 4-4-4-4 | `[카드]` |
| 주소 | 시/도 + 시·군·구 + 로/길 + 번지 근사 | `[주소]` |
| 상호·병원명 | `○○의원/병원/치과/한의원/약국/세무사무소` 접미 | `[상호]` |
| 사람 이름 | ① 성 + **2자** + (띄움?) + `원장/대표/실장/사장/과장/부장/팀장/차장/이사/씨` ② 직함 + 띄움 + 성 + 2자 + `입니다/님/씨/께서…`·문장부호 | `[이름]` (이름만 바꾸고 직함은 남김, 같은 이름은 전역 치환) |

**구현에서 정해진 것 (2026-09-21, 0037 실측)**
- **음성 장치**: 숫자 규칙은 앞뒤가 숫자·점이거나 `숫자,` 모양이면 안 잡는다(`1,000-2,000`·`0.010` 보호, 문장 속 쉼표 뒤 전화는 잡힘).
  계좌는 은행명·계좌·통장이 12자 안에 앞설 때만, 날짜(YYYY-MM-DD) 모양 제외. 상호는 후보를 찾은 뒤 일반명사 앞말(종합·대학·국회·치과·우리…)을 거른다.
  이름은 후보의 끝 글자가 조사면 명사+조사로 본다(띄운 경우 `이가는과와도만`, ②방향은 용언 어미 `해하한…`까지).
- **`persona.label`·`businessType` 은 규칙과 무관하게 `[고객]` 으로 바꾼다** — 계정 표시명("사장님2", 실가입자는 이름)이라 어느 계정의 사례인지 드러난다.
- 구조 키(`id`·`type`·`kind`·`role`·`occupation`·`taxCategory`…)는 건드리지 않는다(세그먼트 id 는 앵커, enum 은 스키마 검증).
- 리포트는 `messages` 안에서만 센다. 제목은 첫 질문의 사본이라 같이 세면 번호 하나가 "전화 3건"으로 부풀었다(E2E 발견).
- **알려진 한계(고지로 감당)**: 2자 이름("김철")·직함 없는 이름 미탐 / 대표번호(1588-…)는 연도 범위와 모양이 같아 미탐 /
  "인정은 원장" 류(명사+은) 과잉 마스킹 — 은은 이름 끝(지은·하은)에 흔해 빼면 실명이 새므로 감수. 실데이터 218건 기준 오탐 2건이 전부 이 유형.
- 단위시험: `supabase/tests/test_0037_pool_masking.py` (양성 22·음성 21 + json 재귀 + 역할별 RLS, 전부 롤백). 규칙을 고치면 여기에 사례를 더한다.

- **지울 수 없는 것이 남는다**: "강남에서 15년 된 치과", 금액대, 직원 수 같은 문맥 단서는 규칙으로 못 지운다.
  → 동의 시트와 풀 화면 양쪽에 **그대로 고지한다**("완전한 익명은 아닙니다"). 날조하지 않는 원칙과 같은 태도다.
- **동의 시트는 마스킹 결과를 먼저 보여 주고 동의를 받는다.** 안 보여 주고 받는 동의는 동의가 아니다.
- 규칙은 단위시험으로 양성·음성 둘 다 건다(전화번호처럼 생긴 금액 `1,000-2,000` 을 지우면 안 된다).

### 3.3 `list_pool_cases()` / `open_pool_case(id)` — 풀 조회 RPC (security definer)

세무사·admin 만 실행. 유효 동의만. **원문 테이블을 조인하지 않는다.**

- `list_pool_cases()` — **본문 없이** 요약 메타만: 업종·세목·마스킹된 제목·첫 질문·질문 수·등재/만료 시각·리포트·`viewed_by_me`
  · **`my_offer_status`**(0039 — 내 제안 상태, 없으면 null. 기한 지난 pending 은 `expired` 로 돌려준다. `drop function` 후 재생성).
- `open_pool_case(id)` — 마스킹 사본 전문 + **열람 기록** 1건. 상세는 이 함수로만 열린다.
- `public.pool_case_views (conversation_id, auditor_id, first/last_viewed_at, view_count)` — §10-1 결정(기록만, 고객엔 비공개).
  쓰기는 `open_pool_case()` 안에서만, 읽기는 admin 만. 대화 삭제 시 cascade.
- 사장님 쪽: `preview_pool_mask(id)` — 본인 대화의 지금 payload 를 같은 함수로 마스킹해 보여 준다(저장 안 함).

### 3.4 `public.consultation_offers` — 경로 B: 세무사 → 고객 연결 요청

`id, conversation_id, expert_id, viewer_id, message(≤300자, 옵셔널 1건), status, status_history, created_at, updated_at, expires_at`
· `status`: `pending | approved | declined | withdrawn | expired` · `unique (conversation_id, expert_id)`

- 기존 `consultation_requests` 를 재사용하지 않는 이유: **방향과 승인 주체가 반대**다(세무사가 걸고 고객이 승인).
  같은 테이블에 방향 컬럼을 붙이면 0035 의 전이 함수가 두 갈래로 갈라진다.
- insert 는 `make_offer()` RPC 로만(세무사 본인 + 유효 동의 존재 + 상한 검사). 전이는 `transition_offer()` 하나로.
- 상한: **대화당 pending 제안 5건, 열린 방 3개.** 고객이 요청 더미에 깔리지 않게.

**구현에서 정해진 것 (2026-09-22, 0039)**
- §10-3 결정: **재제안 없음** — `unique (conversation_id, expert_id)` 그대로. 거절·철회·만료 뒤에도 같은 대화에 다시 못 건다.
  §10-4 결정: pending **5**, 만료 **7일**(설계값 유지).
- `message` ≤ 300자(선택, 앞뒤 공백 제거·빈 문자열은 null). `status_history` 는 생성 때 pending 1건부터 쌓는다.
- RLS: 세무사 = 본인 제안, 사장님 = 본인 앞 제안, admin = 전체 — **select 만**. 정책은 `current_domain_id()`/`is_admin()` 만 쓴다(둘 다 anon 실행 가능, §7).
- `make_offer` 가드(설계에 더한 것): ① **공개 프로필(`expert_profiles.listed`)·활성 세무사만** — 사장님이 받는 것은 프로필 카드라서
  ② 같은 대화에 그 세무사와 **이미 열린 방**이 있으면 불가 ③ 그 세무사 앞으로 **대기 중인 경로 A 신청**이 있으면 불가(수락하면 된다).
  admin 은 제안 불가(호출자 역할이 세무사여야 한다). 같은 대화의 제안은 advisory lock 으로 직렬화.
- `transition_offer` 권한: 승인·거절 = 사장님, 철회 = 제안한 세무사, **admin 은 거절·철회만**(승인 불가 — 사장님 대신 방을 열지 않는다).
  권한 검사를 상태 검사보다 먼저 한다(남의 제안은 만료 확정조차 못 건드린다).
- **만료는 pg_cron 없이**: 목록·화면은 `pending && expires_at <= now` 를 만료로 보고, 그 행에 전이를 걸면 요청한 전이 대신
  **`expired` 로 확정해 그 행을 돌려준다**(예외로 올리면 확정이 롤백되므로). 프론트 service 는 돌려받은 status 가 요청과 다르면 오류로 알린다.
  대기 상한 5 는 만료 전 pending 만 센다.
- 승인 → `open_room(..., 'offer', id)`. 방 상한 3 초과면 예외 → **승인 자체가 롤백**(제안 pending 그대로, 메일 없음).
- 동의 철회(`revoke_pool_consent`) 뒤: 새 제안 불가, 풀에서 빠짐, **이미 열린 방은 유지**(D4), 대기 중 제안은 사장님이 여전히 승인·거절할 수 있다.
- 단위시험: `supabase/tests/test_0039_offers.py` 76건(드라이런·`--applied`·`--fresh`·`--refn`). 임시 세무사는 `profiles` 를
  `session_replication_role=replica` 로 auth.users 없이 넣는다(롤백).

### 3.5 `public.consultation_rooms` — 채팅방

`id, conversation_id, viewer_id, expert_id, origin('request'|'offer'), origin_id, status('open'|'closed'),`
`created_at, closed_at, last_message_at, viewer_last_read_at, expert_last_read_at` · `unique (conversation_id, expert_id)`

방 개설 경로는 **`open_room()` 하나**로 모은다. 경로 A 수락(`transition_consultation` 의 `accepted`)과
경로 B 승인(`transition_offer` 의 `approved`)이 각각 이 함수를 호출한다.

**구현에서 정해진 것 (2026-09-21, 0038)**
- `open_room()` 은 **사용자 실행 불가(내부 전용)** — 전이 함수 안에서만 부른다. 출처를 검증한다:
  `origin='request'` 면 같은 (대화·사장님·세무사)의 `accepted|completed` 신청이 있어야 한다.
  `origin='offer'` 면 같은 (대화·사장님·세무사)의 `approved` 제안이 있어야 한다(0039 가 `create or replace` 로 더함).
- 같은 쌍의 방이 이미 **열려 있으면 그 방**, **닫혀 있으면 다시 연다**(같은 방·이전 메시지 유지, origin 은 최신 출처로 갱신).
- 상한: **대화당 열린 방 3**(닫힌 방은 안 셈). 초과하면 예외 → 경로 A 에선 **수락 전이 자체가 롤백**된다(신청은 pending 그대로).
  같은 대화의 개설은 advisory lock 으로 직렬화.
- 신청이 `completed` 가 돼도 방은 **열린 채**다(닫기는 `close_room` 만).
- `close_room(id)` — **양쪽 참여자 누구나 + admin**(§10-2 결정). 이미 닫혔으면 그대로 돌려준다. 닫힌 방은 읽기만.
- `mark_room_read(id)` — 호출자 쪽 `*_last_read_at` 갱신 + **그 방 알림 메일(ref room)도 읽음**(사이드바 뱃지가 함께 준다).
- 방 테이블엔 쓰기 정책이 없다. RLS 는 참여자 select + admin select.

### 3.6 `public.consultation_messages` — 메시지

`id, room_id → rooms(id) on delete cascade, sender_id, sender_role('user'|'auditor'), body(1~4000자), created_at, edited_at, deleted_at`
· 인덱스 `(room_id, created_at)`

- RLS: **방 참여자(viewer/expert)** 가 select/insert(insert 는 **열린 방**에만), **admin 은 select 만**
  (`sender_role` 에 admin 이 없어 쓰기는 뺐다 — 개입은 §4.3 강제 종료로). update 는 본인 메시지의 `deleted_at` 만
  (정책 + **컬럼 권한** `grant update (deleted_at)`), delete 없음. 지운 시각은 서버 시각, 되살리기 불가.
- `sender_id`·`sender_role`·`created_at` 은 **BEFORE INSERT 트리거가 호출자로 덮어쓴다**(클라이언트 값 무시 — 사칭 불가).
  AFTER INSERT 트리거가 방의 `last_message_at` 과 **보낸 쪽 읽음**을 갱신한다.
- Realtime publication 에 `consultation_rooms`·`consultation_messages` 추가.
- **읽음**은 메시지별이 아니라 방의 `*_last_read_at` 한 칸으로. 메시지마다 읽음 행을 쌓지 않는다.
  안 읽음 수 = 상대 메시지 중 `created_at > 내 last_read_at` 이고 안 지운 것(프론트에서 센다).
- **정책에 쓰는 함수는 anon 실행 권한을 빼면 안 된다**(`is_room_member`). Realtime 은 로그인 전 anon 구독자에게도
  정책을 평가하고, 그 평가가 권한 오류를 내면 **그 이벤트가 모든 구독자에게서 사라진다**(방 참여자도 못 받음, §7).

  경로 B(offer) → `/offers`("세무사 연결 요청으로"). 브라우저 기록에 기대지 않아 메일 링크·새로고침으로 들어와도 같다. 방을 못 찾으면 "세무사 상담으로".

### 4.2 세무사

- `/audit/pool` — **비식별 사례 풀**. 카드 목록(업종·세목·요약 첫 줄·경과일), 상세에서 마스킹된 대화 전문.
  상단 고지: "개인정보는 규칙으로 가렸습니다. 완전한 익명은 아닙니다. 사례 밖 용도로 쓰지 마세요."
  `[연결 요청]` → 메시지 1건(선택) → `make_offer()`
  **구현(0039)**: 상세 아래 "연결 요청" 패널(상한·1회·7일 안내, 300자 카운터). 보낸 뒤엔 상태 배지 + 대기 중 `[요청 철회]` /
  승인 `[채팅방 열기]` / 거절(사유 표시)·철회·만료 = "사례당 1회라 다시 요청 불가". 목록 카드에도 내 요청 상태 배지(스토어 우선, 없으면 `my_offer_status`).
- `/audit/rooms` — 내 채팅방 목록 + 방 화면(사장님 쪽과 같은 컴포넌트, 역할만 다름)
  - 방 헤더의 원 대화 링크: 경로 A → `/audit/consultations/<신청id>`("신청·AI 상담 원문 보기"),
    경로 B → `/audit/rooms/<방id>/conversation`("AI 상담 원문 보기", 후속1). 뒤의 것은 목록 옆 오른쪽 칸에 방 대신 뜨는 **읽기 전용 원문**
    (정지 스냅샷 우선, 헤더에 "읽기 전용 · <시각> 정지 스냅샷", ← 는 그 방으로). 코멘트·평가를 달 수 없다 — 일감 밖에서 검수 기록이 생기지 않게.
- `/audit/consultations`(기존) — 수락 시 방이 열리므로 `[채팅방 열기]` 추가
- 사이드바 뱃지: 내 방 안 읽음 수(+ 선택적으로 풀 새 사례 수)

### 4.3 관리자

`/admin/consultations` = **탭 4개**(후속 2단계, 2026-09-23). 셸 머리는 `상담 운영` 하나, 탭 본문은 **고른 탭만 그린다**.

| 탭 | 보는 것 | 브레이크 |
|---|---|---|
| **신청** | 경로 A 신청 전체 · 상태별 집계 · 세무사별 필터(기존 화면 그대로) | 없음(전이는 당사자가 한다) |
| **제안** | 경로 B 제안 상태별 집계(만료는 읽을 때 판정) · 세무사 → 사장님 · 동봉 메시지 · 만료일 | 대기 제안 **거절·철회** (`transition_offer`) — **승인은 없다** |
| **채팅방** | 열림·닫힘 수 · 방별 메시지 수 · 마지막 메시지 시각 · 출처(경로 A/B) | 방 **강제 종료** (`close_room`) |
| **풀 동의·열람** | 동의(공개 중·만료·철회) · 마스킹 리포트 칩 · 열람 기록 **사례별/세무사별 전환** | 동의 **강제 철회** (`revoke_pool_consent`) |

- **대화 본문은 admin 에게 그리지 않는다**(2026-09-23 결정). RLS 는 `consultation_messages_admin_read` 로 열려 있지만 화면은
  건수·시각까지만 쓴다 — 사장님·세무사 사이 사적 대화다. 분쟁 대응이 필요해지면 그때 따로 설계한다.
- **강제 조치 알림 없음**(2026-09-23 결정). 세 함수 다 사장님·세무사가 한 것과 결과가 같고, 당사자에게 가는 메일·알림에
  "운영자가 했다"는 표시가 없다. 알리려면 메일 kind·사유 컬럼이 필요해 DB 변경이 된다 — 그때 다시 정한다.
  대신 **브레이크마다 화면 안 확인 단계**를 둔다(`ConfirmAction` — 경고 문구에 결과를 쓰고 [확인]/[취소]).
- **열람 기록은 두 집계**(2026-09-23 결정): 사례별 = 이 사례가 누구에게 열렸나(유출 추적), 세무사별 = 이 세무사가 얼마나 뒤지나(과열람 감시).
- 링크는 `/admin/*` 안에서 닫는다 — admin 은 `RoleGuard role="auditor"` 때문에 `/audit/*` 에 못 들어간다(후속1 에서 죽은 링크를 하나 고쳤다).
- 신고 처리는 **넣지 않았다** — 신고 데이터가 없다. 필요하면 따로 설계한다.
- 화면: `components/consultation/admin-consultations-view.tsx`(탭 셸 + 신청 탭) ·
  `admin-offers-panel.tsx` · `admin-rooms-panel.tsx` · `admin-pool-panel.tsx` · `admin-ops-parts.tsx`(집계 타일·확인 단계·카드 줄).
- **새 Realtime 채널 0개**: 제안·방 컬렉션은 계정 버튼 뱃지·사이드바 뱃지 때문에 이미 첫 화면부터 붙어 있고,
  `conversation_pool_consents`·`pool_case_views` 는 **publication 에 없어** 풀 탭을 열 때 화면이 직접 당긴다(`services/case-pool.ts`).

## 5. 상태 기계

```
consultation_offers:  pending ─승인→ approved ─┐
                        ├─거절→ declined        ├→ open_room()
                        ├─세무사 철회→ withdrawn │   (admin: 거절·철회만)
                        └─7일→ expired          │   (pg_cron 없음 — 읽을 때 판정, 전이 시 확정)
consultation_requests: pending ─수락→ accepted ─┘   (기존 0035 그대로)
consultation_rooms:    open ─(양쪽 누구나 | admin)→ closed ─(같은 쌍 재수락·재승인 → open_room)→ open
pool_consent:          granted ─7일→ expired | ─철회→ revoked
```

원칙(0035 계승): **전이는 함수 하나로만.** 테이블에 update 정책을 열지 않는다.

| 위험 | 대비 |
|---|---|
| 규칙 마스킹이 문맥 단서를 못 지운다 | 고지 + 7일 만료 + 철회 + admin 강제 철회(`revoke_pool_consent` 가 admin 허용 — 화면은 §4.3 단계), 풀 열람 로그(`pool_case_views`, (a) 구현) |

(b)에선 채팅방·메시지만 켰고 **(c)에서 전 컬렉션(14개)에 켰다**(2026-09-21 사용자 결정). 늦어진 첫 적재는 `components/ui/spinner.tsx`(동그라미, `role=status`, 움직임 줄이기면 정지)로 보여 준다 — "불러오는 중…" 20곳 + **"로딩 중…" 40곳**(목록 적재 대기는 대부분 이 문구였다), 문구는 그대로 두고 스피너만 붙였다. 페이지를 연 직후 생긴 신청·메일이 새로고침 없이 뜨는 것을 E2E 로 확인. |
| **준비 신호는 채널당 ~250ms 씩 직렬** ((c) 실측) | Realtime 서버는 `"Subscribed to PostgreSQL"` 을 채널마다 순서대로 보낸다 → 채널이 많을수록 뒤 컬렉션의 준비가 늦다. 게다가 **새 페이지마다 모든 컬렉션이 두 번 구독**되고 있었다(모듈 로드 때 1번 + 세션 복원이 쏘는 SIGNED_IN 에 또 1번) → 채널 27개, 마지막 준비 6.6초 → 대시보드·명부가 5초 타임아웃에 걸렸다. → `sync.ts`: 첫 구독 전 세션 복원을 기다리고, **같은 사용자의 SIGNED_IN 이면 다시 붙지 않는다**(로그인·로그아웃·토큰 갱신은 그대로) → 채널 13개, 마지막 준비 2.6초. **첫 화면 실측(새 페이지, 3회 중앙값, 켜기 전→후)**: 목록 0.4~1.4초 → 2.2~4.9초(신청·우편함·대기열 +1.7초, 작업·방·사장님 신청 +3~4초), 로그인 직후 첫 화면 사장님 3.0→1.0 · 세무사 3.5→3.7 · admin 3.6→6.4초. 영원히 도는 스피너 0(20화면 × 데스크톱·412px). 더 줄이려면 **컬렉션을 채널 하나에 묶기**(준비 신호 1번) — 미착수 |
| **anon 구독자의 정책 평가 오류가 이벤트를 지운다** ((b) E2E 실측) | 비로그인 페이지도 모든 테이블을 anon 으로 한 번 구독한다. 정책 함수가 anon 에게 실행 불가면 평가 오류 → **그 이벤트가 방 참여자에게도 안 간다**(A/B 확인). 정책에 쓰는 함수는 anon 실행 허용 + null 이면 false 로 |
