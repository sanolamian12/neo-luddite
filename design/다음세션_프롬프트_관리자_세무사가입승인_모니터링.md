## 0. 상황

- 소셜 로그인(Google 게시 완료·카카오) · 비밀번호 찾기/재설정 · 개인정보처리방침 `/privacy` · 회원 탈퇴(0048) · KB 비식별이 운영에 있다(`2ffee6c`).
- 가입 정책: 공개 가입 = role user 만. **세무사 = 신청서 → 정보 확인 → 관리자 최종 승인**, 관리자 가입 차단(0047 이 역할 변경을 관리자로 제한).
- 관리자 화면(사용자·사용 현황) = 내 소유. 로그인·가입 화면 = 팀장 소유.

## 1. 할 일 후보 (단계마다 내 확인)

1. 진단(코드 0·DB 쓰기 0): 기존 관리자 화면(`frontend/app/admin`)·`public.auditors`/`expert_profiles`(0034) 와 세무사 계정이 지금 어떻게
   만들어지는지(seed·app_metadata) · 세무사 계정의 로그인 수단(이메일+비밀번호 → 비밀번호 재설정 메일 = 운영 SMTP 필요).
2. 세무사 가입 신청: 신청서(이름·자격번호·사무소·연락처…) 저장 테이블 + RLS · 신청 화면 위치(공개 페이지? 소셜 로그인 후 "세무사로 신청"?) — 팀장 화면과 겹치면 협의.
3. 관리자 승인: 신청 목록 → 확인 → 승인 시 계정 역할 부여(auditor) + `auditors`·`expert_profiles` 행 생성. 반려 사유.
4. 관리자 모니터링: 사용자 수·가입 경로(google/kakao/email)·최근 접속·상담 건수, 사용 현황(챗 턴 `rag.chat_turns`), 계정 삭제(`admin_delete_account`).
5. 운영 SMTP(세무사 이메일 계정 안내·재설정 메일) — 도메인 없으면 Gmail SMTP.

## 2. 함정

- 처리방침 §1·§5 에 새로 받는 항목(자격번호 등)·위탁이 생기면 `/privacy` 갱신.
- 승인 RPC 는 DB 단일 전이(0035 방식) — 클라이언트가 role 을 직접 쓰지 않게. `guard_profile_identity` 는 관리자만 role 변경 허용.
- 로컬 `.env.local` 은 프로덕션 Supabase · 로컬은 DATA_MODE 덧씌워 실행 · 운영 CORS 는 localhost 미허용.
- 시험 계정은 `/account/delete` 또는 `admin_delete_account` 로 정리.
