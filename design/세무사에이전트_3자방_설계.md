**작성 2026-10-06 밤.** 출발점 = `design/다음세션_프롬프트_세무사에이전트_3자방.md` §2-2·2-3.

## 1. 사용자 결정 (10/6, 재논의 금지)

| # | 결정 |
|---|---|
| U1 | 고객이 말하면 agent 가 답한다. 세무사가 **'고객에게 답하기'** 를 끌 때까지 — **기본 ON** |
| U2 | 세무사가 말하면 agent 는 반응하지 않는다. 세무사가 **'세무사에게 답하기'** 를 켤 때까지 — **기본 OFF** |

## 2. 지금 코드가 막고 있는 것 (진단)

| 자리 | 사실 | 결과 |
|---|---|---|
| `consultation_messages.sender_role` | check `('user','auditor')` | agent 메시지를 넣을 수 없다 |
| `_room_message_before_insert` | sender 를 `current_domain_id()` 로 덮어쓰고 역할을 viewer/expert 대조로 정한다 | 서버(서비스 연결, uid 없음)가 넣으면 역할 null → 거부 |
| `_room_message_after_insert` | user 가 아니면 상대 = 사장님, 방당 첫 메시지에 메일 | agent 메시지가 사장님에게 '세무사가 보냈다' 메일을 쏜다 |
| 방 `expert_id` | `auditors.id` = **domain id** | `kb3.documents.expert_id` 는 **auth uid** — 서버가 `profiles(domain_id → id)` 로 바꿔야 한다 |
| `/api/chat` | 인증 없음(전시회, 메모리 `project_chat_no_auth_exhibition`) · expert 인자 없음 | 여기에 expert 범위를 열면 아무나 남의 게시분을 검색 — **열지 않는다** |
| 쓰기 미들웨어 `WRITE_ROLES` | `("auditor","admin")` | 사장님(viewer) 토큰은 새 쓰기 API 에서 403 — 방 경로만 viewer 허용 필요 |
| `run_clinic` | 명시 연결 요청 → 연결 카드, 막히면 `_offer` 연결 카드, 판정 → verdict·체크리스트 블록 | 방에서는 연결 카드가 무의미(이미 연결됨), 블록은 U5 로 버린다 |
| 에이전트 설정 | `localStorage` `neo-agent-studio-v1:<owner>` (에이전트 최대 30개, 사례·질문·원칙 전부) | 서버가 원칙·질문을 못 읽는다 · **발견 1**: 다른 브라우저에선 서버 사례가 지식 모음에 0건 |

## 3. 전체 흐름

```
고객/세무사 브라우저                       백엔드(seam-a)                         Supabase
─────────────────────                     ─────────────                          ────────
① 메시지 insert (RLS, 지금 그대로) ───────────────────────────────────────────▶ consultation_messages
② POST /api/rooms/{room}/agent-reply ───▶ ③ 토큰 → domain_id · 방 참여 확인
   { triggerMessageId }                    ④ 트리거 메시지가 이 방의 것 · 보낸 역할 ↔ 스위치 확인
                                           ⑤ 선점(claim) insert … on conflict do nothing ──▶ room_agent_runs
                                              └ 못 잡으면 = 이미 누가 돌리는 중 → 202 {status} 반환(아무것도 안 함)
                                           ⑥ 방 메시지 전부 → history, run_clinic(room_mode,
                                              agent_expert_id = 방 세무사 auth uid, agent_profile)
                                           ⑦ 3분 안에 끝나면 agent 메시지 insert ──────────▶ consultation_messages(agent)
                                              run = done / 넘으면 run = expired(답 버림)
⑧ Realtime: run 행(대기 표시) · agent 메시지 수신 ◀────────────────────────────── publication
```

- 브라우저는 **"이 메시지에 답해 달라"만** 말한다. 누가 답할지·답해도 되는지·검색 범위는 전부 서버가 DB 에서 읽어 정한다
  → 본문 값(expertId 등)을 받지 않는다(U7, 프롬프트 §5 "연결 확인 없이 expert 범위 열기 금지").
- `/api/chat` 은 손대지 않는다.

## 4. 중복 방지 (U3)

**선점 테이블 `public.room_agent_runs`** — 트리거 메시지 하나에 행 하나.

| 칸 | 뜻 |
|---|---|
| `trigger_message_id` PK | 답할 메시지. **PK 라서 두 브라우저가 동시에 불러도 insert 는 하나만 성공** |
| `room_id` | |
| `status` | `running` · `done` · `expired`(3분 초과, 답 버림) · `failed`(Upstage 오류 등) · `skipped`(스위치 꺼짐 등) |
| `started_at` · `finished_at` · `reply_message_id` · `caller_id`(누가 불렀나, 계측) · `error` | |

- **방당 동시 1개**: `unique (room_id) where status = 'running'` 부분 인덱스. 고객이 연달아 두 번 보내면 두 번째 선점은 실패 →
  첫 run 이 끝난 뒤 서버가 **"트리거 이후에 온, 아직 run 이 없는 자격 메시지"** 가 있으면 그 최신 것 하나로 한 번 더 돈다
  (연달아 보낸 질문은 마지막 것 기준으로 한 번 답한다 — 앞 메시지는 history 로 들어간다). 그 사이 메시지들은 `skipped`.
- **누가 부르나** (§9 D1): 보낸 쪽 브라우저가 insert 직후 바로 부른다. 상대 브라우저는 **백업** — 자격 메시지를 Realtime 으로
  받고 10초 안에 run 행이 안 보이면 부른다(보낸 사람이 탭을 닫은 경우). 둘 다 불러도 PK 가 하나만 통과시킨다.
- **재시도**: `failed`·`expired` 행은 "다시 시도" 때 `update … set status='running' where status in ('failed','expired')` 로 다시 잡는다
  (조건부 update 라 이것도 하나만 성공).
- 서버가 재시작돼 `running` 이 고아가 되면: `started_at` 이 4분 넘은 `running` 은 선점 시 `expired` 로 간주하고 다시 잡는다.

## 5. 3분 타이머 · 대기 표시 (U6)

- **대기 표시는 run 행에서 나온다** — 양쪽 화면 모두 `room_agent_runs` 를 Realtime 으로 받아, `running` 이면 방 아래에
  "세무사 AI 가 답을 쓰는 중… 0:42 / 3:00" (경과는 `started_at` 기준, 두 사람이 같은 시계를 본다).
- **서버 마감 = 시작 후 180초.** `run_clinic` 은 동기 호출이라 중간에 끊지 못한다 → 끝났을 때 180초를 넘었으면
  답을 **넣지 않고** `expired` (§9 D2 — 늦은 답을 올리면 '중단됐습니다' 화면 뒤에 답이 튀어나온다).
  지금 최악 ≈ 245초(작문 폴백)라 실제로 걸릴 수 있다.
- 화면: 180초가 되면 대기 표시 → "답이 늦어 멈췄습니다 · 다시 시도". 다시 시도 = 같은 트리거로 §4 재선점.
- Upstage 혼잡(`UpstageCongested`, 줄 대기 30초 초과)은 `failed` + 혼잡 안내 문구를 화면에만 보인다(방 메시지로 안 남김).

## 6. agent 가 보는 것 · 쓰는 것 (U4·U5·U7)

**history 변환** (방 메시지만, 지운 메시지 제외, 최근 N=20개):

| 방 메시지 | run_clinic history |
|---|---|
| 고객(`user`) | `role=user` |
| agent | `role=assistant` |
| 세무사(`auditor`) | 트리거가 고객일 때: `role=assistant`, 본문 앞에 `[세무사 직접 답변] ` · 트리거가 세무사일 때(세무사 응답 ON): 그 메시지가 `user_text`, 이전 세무사 메시지는 `role=user` + `[세무사] ` |

**`run_clinic(room_mode=True, agent_expert_id=…, agent_profile=…)`** — 방 전용 인자. 기존 경로(`/api/chat`·스튜디오)는 바이트 불변.
- ⓪ 명시 연결 요청 갈래 건너뜀(이미 연결된 방). `_offer` 연결 블록 안 붙임.
- 판정·자문·되묻기 갈래는 그대로 탄다(엔진 권위 그대로). 응답의 **segments 텍스트만** 줄바꿈으로 이어 방 메시지 1건
  (4000자 상한 — 넘으면 마지막 문장 경계에서 자르고 "…(이하 생략)"). uiBlocks 는 버린다.
- 판정 갈래에서 카드가 빠지면 '인정/부인' 결론이 카드에만 있어 텍스트가 덜 말할 수 있다 → 방 모드에서는
  판정 라벨 한 줄(`판정: 조건부 인정 (규칙엔진)`)을 맨 앞 문장으로 넣는다(엔진 결과에서 결정적으로, LLM 아님).
- 계측: `conversation_id = room_<room_id>` 로 `rag.chat_turns` 에 남는다(실사용이라 지우지 않음, 접두로 구분).
- **D9**: 원칙·질문·사례는 세무사가 쓴 원문, 작문은 Upstage. 외산 모델 없음.

**agent_profile (항목 3 — 원칙·확인 질문 → 프롬프트)**, 10/4 결정 "원칙·되묻기 = 프롬프트, 사례 = RAG" 그대로:
- 서버 저장된 그 세무사 '방 에이전트'(§9 D4)의 `policy.scope`·`exclusions`·`rules`·`introduction`·`voice` + 켜진 확인 질문 목록.
- 작문 시스템 문구 끝에 `[이 세무사의 상담 원칙 — 세무사가 직접 쓴 문장]` 블록으로 붙인다. 규칙엔진 판정·근거 규칙보다 **아래** 서열
  ("원칙이 판정과 부딪히면 판정이 우선"). 되묻기(`write_followup`)에는 확인 질문 목록을 "가능하면 이 질문으로" 로 준다.
- `exclusions`(다루지 않는 상담)에 걸리면 → 답 대신 "이 부분은 세무사님이 직접 답변드릴게요" 한 줄(판단은 solar 몫, 감수).
- 참여 기준 토글(`onMissing`·`onConflict`·`onException`)의 방 동작은 §9 D6.

## 7. 데이터 — 마이그레이션 0044

1. `consultation_messages.sender_role` check 에 `'agent'` 추가.
   - before insert 트리거: **호출자 uid 가 있으면 지금처럼 덮어쓴다**(로그인 사용자는 agent 를 사칭할 수 없다).
     uid 가 없고(서비스 연결) `sender_role='agent'` 면 그대로 둔다. `sender_id = 'agent:' || expert_id`.
   - after insert 트리거: agent 는 **메일 없음**, 읽음 칸 안 건드림, `last_message_at` 만 갱신.
2. `consultation_rooms` 에 `agent_reply_customer boolean not null default true` · `agent_reply_expert boolean not null default false`.
   쓰기는 RPC `set_room_agent_switches(p_room_id, p_customer, p_expert)` 로만 — **그 방 세무사만**(사장님·admin 불가).
   기존 열린 방에 기본값을 그대로 줄지는 §9 D3.
3. `room_agent_runs` (§4) + RLS: 방 참여자·admin 읽기(`is_room_member`, **anon 실행권 유지** — Realtime 함정 ①), 쓰기 정책 없음(서버만).
   publication 추가. → Realtime 바인딩 +1(준비 대기 ~60~90ms, 후속4 실측 규칙).
4. `expert_agents` (항목 3·발견 1) — `(expert_id auth uid, agent_id)` PK, `name`, `practice jsonb`, `is_room_agent boolean`,
   `updated_at`. RLS: 본인 읽기·쓰기(Supabase 직접, 기존 스토어처럼), `is_room_agent` 는 세무사당 1개(부분 유니크).
   서버는 서비스 연결로 방 세무사의 `is_room_agent` 행만 읽는다. 범위는 §9 D5.

## 8. 화면

- **방(사장님·세무사 공통)**: agent 말풍선(이름 "○○ 세무사 AI", 다른 색) · 대기 표시·3분 · "다시 시도". 메시지 보낸 뒤 자동 호출.

- 사장님 화면에는 스위치 대신 상태 한 줄("이 방은 세무사 AI 가 먼저 답합니다 · 세무사가 직접 볼 수 있습니다").
- **스튜디오**: 에이전트 설정을 `expert_agents` 로 서버 저장(상단 '변경 저장' = 서버) · '방에서 쓸 에이전트' 지정 ·
  지식 모음 목록은 서버 사례 기준(발견 1 해소 — 다른 브라우저에서도 보인다).
- 문구: 스튜디오의 "게시 = 나에게 연결된 상담의 AI 답변" 이 이때부터 사실이 된다. 10/6 밤에 넣은 "질문·원칙은 아직 상담 AI 에 반영되지
  않습니다" 문구는 이 공사에서 걷어낸다.
