## 3. 괴리 — 영역별

### A. 입구 챗 답변 화면 — 작음

- 우리 live: `local-chat-experience.tsx` 가 답을 `messageText` 로 이어 붙이고 카드만 따로(`UiBlocks readOnly`). 출처·프레임워크 배지가 **안 보인다**.
- 그쪽: `EntryResponse` 로 다 보인다. **live 에 그대로 쓰면 메일이 말한 화면이 실제 AI 답에서도 나온다.**
- 할 일 = 충돌 1덩어리씩(entry-chat.ts·local-chat-experience.tsx·entry-owner-handoff.tsx) + `withSampleResponseUi` 는 **프로토타입에서만**(live 실제 답에 가짜 "판정 표시 예시" 카드를 씌우면 안 된다).

### B. 상담에서 가르치기 — 중간

- 그쪽 원천: 끝난 채팅(사람 세무사 답이 있는 것) · 참여 리허설 · 붙여넣기/TXT·MD · 샘플. 정리는 결정적 규칙(LLM 없음) — **D9 와도 맞다**.
- live 원천으로 바로 쓸 수 있는 것: **우리 채팅방(0038) 메시지** — 세무사는 자기 방을 RLS 로 이미 읽는다. 3자 방이 생겼으니 agent 답도 섞여 있다(그쪽 스키마에 "AI 발화는 따로 표시"가 있어 맞는다).
- 저장: 그쪽은 세션·녹취를 `practice` 안에 둔다 → 우리 `expert_agents.agent`(jsonb) 에 **그대로 실려 서버 저장된다**(0044, 2MB 상한 — 그쪽 한도 녹취 4만 자 × 20개 = 약 80만 자라 들어간다).
- 남는 백엔드 결정: 상담 원문을 가르치기에 쓰는 **동의**(그쪽 문서 "Private sources" — 고객 동의·보관·삭제). 지금 0037 풀 동의(대화 1건·7일)와는 다른 동의다.
- 가르친 사례는 지금처럼 '서버에 저장 → 게시'(0043)로 kb3_expert 에 들어간다 — 그쪽 "적용" 버튼과 우리 서버 초안 저장을 한 동작으로 묶을지가 화면 결정.

### C. 공용 지식 기여 원장 · 관리자 검토 — 큼 (핵심 괴리)

| | 우리 0043 (지금 운영) | 그쪽 프로토타입 |
|---|---|---|
| 공용으로 보내는 것 | **같은 문서**의 share_state 를 pending 으로 | **별도 제안서**(비식별 payload) — 개인 사례는 그대로 |
| 상태 | pending · approved · rejected | 초안(자동 저장) · 검토 요청 · 수정 요청 · 게시 · 거절 · 철회 |
| 개정 | 내용 바뀌면 초안으로(다시 공유) | 같은 제안 id 아래 **불변 제출본** 1·2·3… |
| 검토 | admin 승인/거부 + 메모 | 4개 점검값 + 사유, **저자 ≠ 검토자** |
| 크레딧 | 승인 때 ledger `bonus` 0원 1행 | 게시 때 저자 크레딧 1건 · 중복 게시 거부 · **철회 시 자격 취소**(기록은 남김) |
| 질문 기여 | 없음(KB3 는 사례만) | 있음(기록·검토만, 검색엔 안 씀) |
| 개인정보 | 세무사 원문 그대로(D9) | 제출마다 비식별·공유 허락 확인 + 식별자 패턴·중복 검사 |
| 검색 반영 | 승인 → kb3 `match_chunks` 공용 범위 | 게시된 제출본으로 겹쳐 보기, 철회 시 빠짐 |

→ 그쪽 화면을 live 로 붙이려면 **둘 중 하나**(§6 D-B).

### D. 내비게이션 · 스튜디오 구조 — 중간 (충돌 대부분)

- 충돌 파일: agent-library · agent-practice · practice-knowledge · practice-teaching · audit-shell · expert-sidebar (+ entry 쪽 4개).
- **오늘 우리가 스튜디오에 넣은 것**(그쪽에 없음)을 새 구조에 다시 끼워야 한다:
  `expert_agents` 서버 저장(라이브러리 save) · '연결 상담방에서 이 에이전트 쓰기' · 서버에만 있던 사례 불러오기 · 지식 모음의 서버 상태·게시·내리기·공용 보내기(`ServerCasePanel`·`ShareBar`) · 실제 AI 시험칸(`RealPreview`) · live 안내 문구.

### E. 그쪽이 모르는 우리 기능 (팀장에게 알릴 것)

- **3자 방**(고객·세무사·세무사 AI, 스위치 2개, 대기 표시 3분) — 그쪽 '참여 요청'(리허설 인박스) 개념과 이어 붙일 자리. 지금 방 화면은 그쪽 디자인 시스템 밖(옛 shadcn 톤 + 보라색).
- **에이전트 설정 서버 저장 · 방 에이전트 지정.**
- **세무사 사례 서버 상태**(초안 → 게시 → 공용 승인 대기 → 공용) · 관리자 승인 화면 `/admin/pipeline/kb3-share`.

## 4. 앞으로 계속 맞추는 방식 (구조 제안)

그쪽이 UI 를 계속 바꾸고 우리가 뒤에서 맞추는 관계라, 매번 같은 파일에서 부딪히지 않게 **경계를 정해 두는 것**이 이번 반영보다 오래 간다.

1. **그쪽 = UI 원본, 우리 = live 연결층.** live 전용 코드는 별도 파일에 두고(이미 그렇게 한 것: `expert-server.tsx`·`room-agent.tsx`·`services/*`), 그쪽 파일에는 **한두 줄 훅만** 꽂는다. 이번 충돌 16덩어리도 대부분 "그쪽 파일 한복판에 우리가 조건문을 넣은" 자리다.
2. **서비스 경계 합의 제안**: 화면은 `services/*`(예: `expertAgents.save()`, `contributions.submit()`)만 부르고, 그 안에서 `isPrototype` 이면 브라우저 저장 · live 면 서버. 그쪽이 새 화면을 만들 때 이 인터페이스에 맞춰 주면 우리는 live 구현만 채운다. → 팀장과 한 번 합의할 일.
3. **정기 병합**: `ugproto/main` 새 커밋이 오면 worktree 에서 `import-credigraph` 로 병합 → 프로토타입 모드 동작은 그쪽 것 그대로, live 모드는 우리 연결 → tsc·test·live build·Playwright 회귀 → 배포.

## 6. 결정 (10/6 밤 사용자)

- **D-A · D-B · D-D = 추천안 확정.**
- **D-C = 입력 방식에 따라 갈린다(사용자 수정):** 주 경로는 **세무사가 직접 타이핑·붙여넣기**로 사례를 적는 것 — 고객은 세무사의 스튜디오 화면을 보지 않으므로 **고객 동의 불필요**.
  **방 세션 자체를 불러오는 경로**(채팅방 원문을 그대로 가져오기)를 열 때만 **방 단위 고객 동의 1회**가 필요하다.
