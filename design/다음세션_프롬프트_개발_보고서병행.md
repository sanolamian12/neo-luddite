# 개발 세션 시작 프롬프트 — 결과보고서 병행 (10/13 ~ 11/2, 매번 같은 블록)

결선 최종결과보고서(10/23 제출)는 **11/3 시연 시점의 시스템**을 결과로 적었다. 그래서 11/2까지의 개발 세션은 전부
"보고서에 적힌 약속을 사실로 만드는 일"이다. 아래 블록을 **새 개발 세션 첫 메시지로 그대로 붙여 넣는다.**
이번에 무엇을 할지는 블록이 아니라 지침 문서의 **§6-4 "다음 세션 할 일"(바통)** 이 정한다 — 세션마다 끝낼 때 갱신된다.

구조:
- 지휘 = `design/결과보고서_약속이행_개발지침_1013.md` (규칙 §1 · 약속 A1~A14 §2-A · 수치 §2-B · 일정 §3 · 절차 §6 · 바통 §6-4)
- 상태 원본 = `docs/doing/최종결과보고서_작업기지_1012.md` §4-1 약속 장부(P1~P10) — docs/ 는 git 밖, 이 PC 에만 있다
- 보고서 원고 = `docs/final/원고/원고_1-6_ch2.md`
- 수치 대조 = `backend/eval/run_demo_eval.py` → `backend/eval/report_check.py`(보고서 §2-B 목표에 자동 판정)
- 실행 기록 = 로드맵 `design/데모대비_챗품질_개선로드맵_1010.md` 맨 아래 진행 기록 · `history/`

---

```
결과보고서 병행 개발 세션이야. design/결과보고서_약속이행_개발지침_1013.md 를 열고 §1 규칙과 §6 절차를 먼저 읽어 줘.
이번 세션의 일은 §6-4 "다음 세션 할 일"(바통)이야 — 내가 다른 일을 따로 주지 않으면 그걸 해.

시작할 때(§6-1):
- 작업기지 docs/doing/최종결과보고서_작업기지_1012.md §4-1 약속 장부에서 그 항목(P#)의 상태·마감을 확인하고,
  이번 일이 §2-A 의 어느 A# 이고 §2-B 의 어느 수치를 움직이는지 한 줄로 말한 뒤 시작해.
- 장부(P1~P10) 밖의 일이면 11/2 전에 할지 먼저 물어봐(규칙 3).

하는 동안:
- 배포할 때마다 run_demo_eval → report_check 로 보고서 수치에 대조해(§6-2). 이번 배포로 나빠진 게 있으면 되돌리거나 그날 고쳐.
- 보고서 약속을 못 지킬 것 같으면 바로 말해 줘(규칙 2). 10/22 까지는 원고 문구를 고칠 수 있어.
- 운영 제약(규칙 6): 제품 경로는 Upstage 만 · 로컬 백엔드는 VEC_MEMORY=off · 배포는 모아서(Supabase egress·DB 크기) ·
  운영 마이그레이션·DB 적재는 내가 터미널에서 실행 · 프론트 dev 가 떠 있으면 build 금지.
- 11/1 기능 동결(규칙 7).

끝낼 때(§6-3): 지침 §2 "현재" 칸 · 작업기지 §4-1 상태 · §6-4 바통(다음 사람이 바로 시작할 수 있게) · 로드맵 진행 기록을
갱신하고, 큰 묶음이 끝났으면 history 에 기록한 뒤 커밋·push 해.
```
