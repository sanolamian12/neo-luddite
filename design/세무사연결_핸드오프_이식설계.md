## 1. 전체 흐름 (원본 기준, 목표 상태)

```
채팅(owner)                      세무사(auditor)               관리자(admin)
AI가 연결 카드 발행
  ↓
티저: 얼굴 3개 + "N명 상담 가능" + [전문가 보기]
  ↓
팝오버: 세무사 카드 목록 → 1명 선택 → [상담 신청]
  ↓
확인 시트: 추가 메시지(선택) → 신청하기
  ↓
"신청 완료"          ──────→  대기(pending) 신청 수신        전체 신청 목록
  ↓                             수락/거절/완료 + 메일 발송     상태 뱃지·집계
/consultations 에서 추적  ←──  상태 변경 + 메일
```

상태: `pending → accepted | declined`, `accepted → completed`, `pending → cancelled`(사용자).
전이는 한 함수(`transition`)로 모으고, 매 전이마다 `statusHistory`에 {status, at, actor, note} 를 쌓는다.

## 2. 세션 분할 (사용자 결정 2026-09-18)

| 단계 | 범위 |
|---|---|
| **(a) 이번 세션** | ① 세무사 쪽 "상담 프로필" 편집 페이지(연락처 공개 범위 포함) → ② 채팅 연결 카드(티저→팝오버→시트) + 신청을 Supabase 에 저장 → ③ 백엔드 트리거 |
| **(b) 다음 세션** | 받는 쪽: 사용자 `/consultations`(추적·취소), 세무사 `/audit/consultations`(수락/거절/완료), 관리자 `/admin/consultations`, 메일 kind `consultation`, 사이드바 대기 뱃지, "수락 후 공개" 연락처 실제 공개 |

순서 근거(사용자): 카드에 뜰 정보를 세무사가 직접 기입하는 공간을 먼저 만들고, 그것을 사용자 쪽에 붙이는 게 자연스럽다.

## 3. 결정 사항

### 3.1 트리거 = (b) 명시 요청 + 엔진이 못 푸는 자리에서 자동 제안
백엔드 `api/pipeline.py run_clinic` 에서 결정적으로 판단한다. LLM 의도 판단(c)은 오탐 위험으로 배제.

| 조건 | 동작 | meta.handoff |
|---|---|---|
| 사용자가 세무사/전문가/사람 연결을 명시 요청 (정규식) | 추출·엔진을 건너뛰고 짧은 안내 + 카드. **Upstage 호출 0** | `explicit` |
| 자문 경로(엔진 규칙 밖, 선례 있음) | 자문 답변 뒤에 카드 부착 | `advisory` |
| 자문 경로인데 선례 없음 | 미지원 안내 뒤에 카드 부착 | `no_precedent` |
| 판정 없는 되묻기가 연속 누적(직전 2턴도 판정 없음) | 되묻기 뒤에 카드 부착 | `stalled` |

- 자동 제안은 **대화당 1회**(history 에 이미 `expert_handoff` 가 있으면 생략). 명시 요청은 매번.
- 카드는 세무사 명단을 담지 않는다 — `{kind, reason, note?}` 만. 명단은 렌더 시점에 DB 에서 조회.
- 판정 카드와 공존하지 않는다(판정은 엔진 권위 — 판정이 난 턴에는 붙이지 않음).
- 모델: 트리거 자체는 LLM 무관. 국내 AI 트랙 조건과 충돌 없음.

### 3.2 세무사 상담 프로필 (세무사가 직접 기입)
`public.auditors` 를 넓히지 않고 **별도 테이블** `public.expert_profiles` (auditor_id PK = domain_id).
이유: `auditors` 는 인증자 전원이 읽을 수 있어(0002 `auditors_read`), 여기에 연락처 공개 범위를 두면 DB 단에서 못 막는다.

필드: 공개 여부(listed), 한 줄 소개(bio), 전문 분야(specialties[]), 경력 연수, 상담 가능 상태(available/busy/offline), 아바타(프리셋 경로), 연락처 채널별 값 + 공개 범위.

연락처 공개 범위(채널별: 전화 / 이메일 / 카카오톡 오픈채팅 링크):
- `public` — 카드에 바로 표시
- `after_accept` — 카드엔 "상담 수락 후 공개"만 표시. 실제 공개는 (b)에서 수락된 신청의 신청자에게만.
- `hidden` — 표시 안 함

강제 지점: owner 는 테이블을 직접 못 읽고, `security definer` 함수 `public.list_experts()` 로만 조회 → 함수가 공개 범위대로 연락처를 null 처리해서 반환.

### 3.3 원본과 달리 하는 것
- **좋아요(하트) 수 제외** — 우리 DB 에 근거 데이터가 없다. 지어낸 수치는 넣지 않는다(날조 수치 원칙). 대신 실제 검수 이력에서 계산한 "누적 검수 N건" 뱃지(원본의 achievement badge 로직)를 쓴다.
- **아바타** — 원본 일러스트 7장 중 3장을 압축해 프리셋으로 제공, 세무사가 고른다. 없으면 이니셜 원(avatar_color). 업로드(Supabase Storage)는 이후 과제.
- **직종 필터(occupations)** — 지금 clinic 만 살아 있어 생략.
- **모바일** — 팝오버 360px 고정 대신, 좁은 화면(`md` 미만)에선 Dialog/시트로 연다(모바일 컨벤션).
- **채팅 식별자** — `useReplayStore.script` 대신 `useRemoteChatStore.conversationId`.

### 3.4 상담 신청 저장 (이번 세션은 insert 까지)
`public.consultation_requests`: id, conversation_id, viewer_id, expert_id, message, status(default pending), status_history jsonb, created_at, updated_at (epoch ms).
RLS: 사용자 = 본인 행 insert/select, 세무사 = 본인 앞 행 select, admin = 전체. 상태 전이(update)는 (b).

### 3.5 하트 (사용자 결정 2026-09-18 — 원본의 좋아요 수를 실데이터로)
- 채팅 카드의 하트를 사장님이 누른다. `expert_likes` (세무사, 대화 세션, 사용자)당 1행 — 누르면 +1, 다시 누르면 행 삭제로 −1. 시작 0.
- 수치는 행 개수(`list_experts()` 에서 count). 카운터 컬럼이 없어 저장값과 실제가 어긋날 수 없다.
- 검수 기록과 무관 — 상담받은 사람이 세무사에게 주는 값. "누적 검수 N건" 뱃지는 별개(audits 에서 계산).
- 쓰기는 `toggle_expert_like()` RPC 로만(원자적 토글 + 새 수치 반환). 재생 모드(대화 id 없음)에선 누를 수 없다.
