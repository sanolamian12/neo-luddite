## 0. 한 문단 요약

KB2 완성 목표 셋 중 **G1(재현성)을 닫았고 G3(임팩트)의 계측을 깔았다.** G1 에 남아
있던 단 하나가 합성 타임아웃 값이었는데, 직전 세션이 원시 소요 목록을 안 남겨
"벽 아래의 진짜 p90"을 모르는 상태였다. 원시값 저장 + **SDK 내부 재시도 제거**로 한
회차 더 재니 분포가 두 덩어리로 갈렸고 — 정상 호출 48건이 **전부 15초 이하**, 실패
2건만 240초 벽에 붙어 있었다 — 상한을 낮춰도 자를 정상 호출이 없음이 확정됐다.
`TIMEOUT_SYNTHESIZE` **240 → 60**. G3 는 지표에 필요한 값이 이미 `ChatMeta` 에 다
있는데 **아무데도 안 남는다**는 것이 진짜 문제여서, 필드 추가가 아니라 **남길 자리**를
만들었다(`rag.chat_turns`).

## 1. 작업 ① — 합성 타임아웃 값 결정 (G1 마감)

### 1.1 직전 세션이 남긴 숙제

분포는 이미 나와 있었다(job `e6af3b47`):

```
성공 48회: min 0.71s  p50 3.54s  p90 243.2s  max 248.3s
실패  1회: 480.7s ( = 240s × 2, SDK 내부 재시도 )
```

그런데 **원시 목록을 저장하지 않아** p90 이 이미 240초 벽에 붙어 있었고, 그래서
"상한을 낮추면 정상 호출을 자르는가"에 답할 근거가 없었다. 값을 박지 않고 회차를
하나 더 돌기로 한 판단이 옳았다.

### 1.2 처방 둘 — 원시값 보존 + SDK 재시도 제거

**① 원시 목록 저장**(`coverage.synthesisSuccessMsRaw` / `FailedMsRaw`). 요약은 원시에서
언제든 다시 나오지만 그 반대는 안 된다. 호출 수십 개짜리 int 리스트라 jsonb 비용은
무시할 만하다.

**② 합성 호출만 SDK 내부 재시도 0** — 이쪽이 결정적이었다. 이 호출은 재시도가 **두
겹**이었다(SDK `DEFAULT_RETRIES=1` + 호출측 `CHUNK_ATTEMPTS=3`). 대가가 둘이다:

- **체감 상한이 240초가 아니라 480초**다(직전 실패 1건이 정확히 480.7초).
- **계측이 오염된다.** SDK 재시도는 우리 눈 밖에서 일어나므로 "240초 물렸다가 재시도로
  3초 만에 성공"이 `successMs` 에 **243초 한 건**으로 찍힌다. 직전 측정의
  `p90 243.2s / max 248.3s` 가 정확히 그 모양이었다.

재시도 자체는 잃지 않는다 — `CHUNK_ATTEMPTS` 루프가 하고, 그쪽은 `failedCalls` 로
**세어진다**. 여기서만 끄면 **한 번의 호출 = 한 개의 소요값**이 된다.

### 1.3 실측 — 분포가 두 덩어리로 갈렸다

job `9da37290`:

```
성공 48회  min 1.042s  p50 2.897s  p90 4.870s  max 15.000s  (2위 7.238s)
실패  2회  240.068s · 240.092s                              ← 정확히 상한
```

**240초 근처의 성공이 0건이다.** 느린 생성이면 연속 분포여야 하는데, 재시도를 걷어내니
정상 호출이 **1~15초 한 덩어리**로 모였다. 직전 회차의 243s·248s 는 모델이 느렸던 게
아니라 **재시도 성공이 한 건으로 접혀 있던 것**이었다.

잃었던 값을 되찾았다 — **'벽 아래의 진짜 p90' = 4.87초.** 상한 240초는 그 **49배**,
관측 최대 15.0초의 **16배**였다.

상한 후보별로 잘리는 정상 호출:

```
20s → 0건   30s → 0건   45s → 0건   60s → 0건   90s → 0건
```

48건 전부 15초 이하라 **어느 후보도 정상 호출을 자르지 않는다** — 직전 세션이 답하지
못했던 바로 그 질문이다.

### 1.4 결정: `TIMEOUT_SYNTHESIZE` 240 → 60

관측 최대의 **4배**. 45초도 0건 절단이지만, 아직 못 본 느린 호출에 여유를 남기는
보수적 선택을 했다(사용자 결정). 절감 효과는 45초와 거의 같다(실패 건당 180s vs 195s).

**부수 효과가 컸다: 완주 35분 → 16분.** 이후 모든 실험이 싸진다. 타임아웃이 2건 났는데도
`lostChunks 0` — `CHUNK_ATTEMPTS` 재시도가 건졌다. **상한을 낮춰도 유실이 늘지 않는다는
근거**가 같은 회차에서 나왔다.

### 1.5 남겨둔 관찰

성공 최대값이 정확히 `15000ms` 다. 나머지 47건은 전부 불규칙한데 이것만 정수라 우연치고
눈에 걸린다. **1건뿐이라 파지 않았다** — 다음 회차에 또 15000 이 나오면 그때 어딘가의
15초 제약을 의심할 것.

## 2. 작업 ② — G3 되묻기율 계측 (마이그레이션 0027)

### 2.1 진짜 문제는 "필드가 없다"가 아니었다

제품 논지는 **"RAG 는 답변 품질이 아니라 '답할 수 있는 범위'를 넓힌다"**(판정은 엔진
권위라 안 바뀐다)인데 kb2 경로에서 숫자로 보인 적이 없었다. 코드를 읽어보니 지표에
필요한 값(`ragSource`/`ragHits`/`followUp`)은 **`ChatMeta` 에 이미 다 있었다.**

문제는 **아무데도 안 남는다**는 것이었다 — 백엔드 `/api/chat` 은 무상태고, 프론트는
`meta` 를 파싱만 하고 버린다(`conversations.payload` 에도 없다). 즉 필드를 더하는 일이
아니라 **남길 자리를 만드는 일**이었다.

### 2.2 L2 결정 (전부 사용자 확인)

**① 적재 위치 = 백엔드 전용 테이블.** 프론트 payload 가 아니라 백엔드를 고른 이유는
**프론트를 안 거치는 호출도 남기 때문**이다 — 논문 세션의 3방향 벤치마크
(`?rag=` on/off × `?ragSource=rag|kb2|hybrid`)는 curl 로 도는데, payload 에 얹으면
그게 통째로 유실된다.

**② 분모를 스키마에 박지 않았다.** 되묻기는 두 종류이고 섞으면 지표가 오염된다:

- `no_precedent` — 자문 경로에 들어왔는데 선례가 없어 되묻음 ← **G3 의 분자**
- `undecided` — 판정형 결정변수 부족(①-b) ← RAG 와 무관. **섞지 말 것**

어느 쪽을 분모로 삼을지 아직 안 정했으므로 **모든 턴을 남기고 `outcome` 으로 구분**하되
분모는 집계 시점에 고른다. 이번 세션의 교훈("요약만 남기고 원시값을 버리지 말 것")을
지표 설계에 그대로 적용한 것이다.

**③ 화면 노출은 범위 밖.** 표본 0으로 시작하는 패널을 만들지 않는다.

### 2.3 구현에서 조심한 세 가지

**`outcome` 을 `meta` 에서 되추론하지 않았다.** 각 return 자리에 손으로 붙인다 —
`followUp=True` 가 **성격이 다른 세 갈래**에서 나오기 때문이다(필수정보 부족·선례
없음·결정변수 부족). 되추론은 그 셋을 한 덩어리로 만들어 지표를 조용히 오염시킨다.

**`rag_searched` 는 nullable.** 되묻기 갈래는 검색 단계에 도달조차 못 하므로 null 이고,
false 로 뭉개면 **"RAG 를 껐다"와 구별이 안 된다.**

**적재 실패는 절대 응답을 막지 않는다**(예외 삼키고 로그). 계측은 응답 경로에 얹힌
곁다리다. 다만 조용히 0줄이 쌓이면 "되묻기가 없었다"로 오독되므로 삼킨 실패는 로그에
남긴다.

### 2.4 프로덕션 실증

curl 3발(검증 후 삭제 — 분모 오염 방지):

```
outcome        요청   실제   검색   hits
advisory       kb2   kb2   true     5     ← 선례 찾아 답함
advisory       rag   rag   true     2     ← 선례 찾아 답함
no_precedent   kb2   none  false    0     ← 검색을 끄니 되묻기
```

세 줄이 이미 논지의 모양이다. 집계 도구는
`docs/doing/kb2_측정자료_260912/scripts/g5_g3_rate.py`(LLM 0회) — 자문 분모와 전체
분모를 둘 다 계산하고, 표본 20 미만이면 비율 인용을 막는다.

⚠️ **이 지표는 낮을수록 좋다고 단정하지 말 것.** 근거 없이 자신 있게 답하는 것보다
되묻는 게 안전하다는 게 원래 설계다. "되묻기가 줄었다"가 "엉터리 답이 늘었다"가 아님을
보이려면 답변 쪽 확인이 따로 필요하다.

```
c6e40c44 수정(locked)   부가가치세    → 부가가치세신고  0.8174  ← 레이블이 바뀌었는데 의미로 따라갔다
```

`reattachFailedToUnsorted` 는 여전히 1이고, 임계값 논의는 회차가 더 쌓인 뒤다.

## 4. ⚠️ 커버리지는 내려갔다 — 기록만 (사용자 결정)

```
직전 e6af3b47:  413 → 배정 305 (73.8%) → 인용 274 (66.3%)   유실 0 / 목차 26
이번 9da37290:  413 → 배정 266 (64.4%) → 인용 220 (53.3%)   유실 0 / 목차 30
```

프로덕션 4회차 배정률: 73.1 / 70.5 / 73.8 / **64.4%** — 앞 셋은 좁고 이번이 낮다.

**이번 세션의 코드 변경과는 인과가 없다.** SDK 재시도 변경은 `synthesize_kb2_sentences`
에만 걸었고, 배정은 그보다 **앞 단계**인 `classify_dynamic_category`(재시도 2회 그대로)
가 한다. 분류 실패 0 · 분류 입력 폴백 0 · 환각 id 0, 가드도 정상 통과(64.4% > 요구 55.4%).

**단정하지 않는 이유가 중요하다**: 측정된 회차 편차 3.8% 는 **목차를 고정하고** 잰
값이다(항목 15·16 실험이 전부 "같은 150건·같은 목차"). **목차까지 새로 뽑는 전체
파이프라인의 편차는 한 번도 측정된 적이 없다** — 64.4% 가 그 편차 안인지 밖인지 가를
데이터가 없다. 커버리지는 목표가 아니라 계기판이므로 숫자를 올리는 작업은 하지 않는다.

→ 다음 세션 후보로 올린다: **"전체 파이프라인(목차 포함) 회차 편차 미측정"** 을 알려진
공백으로 명시할 것. 지금까지의 모든 편차 수치는 목차 고정 조건이다.

## 6. 교훈

**"요약만 남기고 원시값을 버리지 말 것"이 두 번 값을 했다.** 한 번은 직전 세션이 분위수만
남겨 회차를 하나 더 돌아야 했던 자리에서, 또 한 번은 그 교훈을 G3 지표 설계에 적용해
**분모를 스키마에 박지 않은** 자리에서.

**그리고 새 교훈 하나**: 재시도가 두 겹이면 **계측이 조용히 거짓말한다.** SDK 재시도는
호출 바깥에서 일어나 "실패 후 재시도 성공"을 "한 번의 느린 성공"으로 접어버린다. 이번엔
그것이 `p90 243.2s` 라는 **존재하지 않는 정상 호출**을 만들어냈고, 그 숫자 때문에 상한을
못 낮추고 있었다. 소요를 재는 자리와 재시도하는 자리는 같은 층에 있어야 한다.
