## 무엇이 생겼나
사장님이 상담사 풀 공개에 동의한 사례를 **고르지 않은 세무사도 보고 먼저 연결을 요청**할 수 있다(경로 B).
세무사는 `/audit/pool` 상세에서 메시지 한 줄(선택)을 붙여 `[연결 요청]`을 보내고, 대기 중이면 철회할 수 있다.
사장님은 사이드바 아래 계정 버튼에 요청 수가 뜨고, 메뉴의 **"세무사 연결 요청 N건"** → `/offers` 에서 세무사 프로필 카드·메시지·어느 대화 건인지를 보고
**승인하면 바로 그 세무사와의 채팅방으로 이동**한다. 거절은 사유를 골라 세무사에게 알린다. 요청은 7일 뒤 만료된다.

같이 바꾼 것: 모든 목록이 **Realtime 준비 신호를 기다린 뒤 첫 적재**를 하고(페이지를 연 직후 생긴 행이 사라지던 틈을 전부 막음),
그 대기 동안 **동그라미 스피너**를 보여 준다.

## 결정 (사용자, 착수 전)
- §10-3 재제안: **1회만** — 거절·철회·만료된 세무사는 같은 대화에 다시 요청할 수 없다(unique 유지).
- §10-4: 대화당 대기 요청 **5건**, 만료 **7일**(설계값 그대로).

## 설계에 더한 것 (적용 전 사용자 확인)
- `make_offer` 가드: 프로필 비공개 세무사는 요청 불가(사장님이 볼 카드가 없다) / 같은 대화에 이미 열린 방이 있거나 / 내 앞으로 대기 중인 경로 A 신청이 있으면 불가.
- admin 은 거절·철회만(승인 불가 — 사장님 대신 방을 열지 않는다).
- 만료는 pg_cron 없이: 읽을 때 기한으로 판정하고, 기한 지난 요청에 전이를 걸면 요청한 전이 대신 `expired` 로 확정해 돌려준다.

## 도중에 잡은 것
1. **준비 대기를 전면으로 켰더니 대시보드·세무사 명부가 +4초**(정확히 5초 타임아웃). 웹소켓 프레임을 찍어 보니
   Realtime 서버가 "Subscribed to PostgreSQL" 을 **채널당 ~250ms 씩 순서대로** 보내는데, 새 페이지마다 **모든 컬렉션이 두 번 구독**되고 있었다
   (모듈 로드 때 + 세션 복원이 쏘는 SIGNED_IN 때). 채널 27개 → 마지막 준비 6.6초. 전에는 SUBSCRIBED 만 기다려서 안 보이던 낭비였다.
   → `sync.ts`: 첫 구독 전에 세션 복원을 기다리고, **같은 사용자의 SIGNED_IN 이면 다시 붙지 않는다**(로그인·로그아웃·토큰 갱신은 그대로).
   채널 13개, 마지막 준비 2.6초. 지시서에 없던 변경이라 배포 전에 알리고 확인받았다. `e2e/sync-retry.spec.ts` 2/2 로 회귀 확인.
2. **"로딩 중…" 40곳**: 지시서는 "불러오는 중…" 20곳을 바꾸라고 했지만, 대기열·작업·결과·우편함·대시보드·admin 표처럼 스토어 적재를 기다리는 화면은
   대부분 "로딩 중…" 이었다(준비 대기로 실제로 길어지는 자리). 둘 다 스피너로 바꾸고 문구는 그대로 뒀다(총 60곳).
3. **E2E**: 준비 대기로 세무사 명부 적재가 늦어져 `/offers` 카드 제목과 방 헤더에 `auditor2`(id)가 몇 초 보였다 →
   이미 받아 둔 공개 카드 이름을 먼저 쓰고, 둘 다 없을 때만 id.
4. 측정 방법 자체의 허점: 처음엔 "텍스트가 3초 안 바뀌면 완성"으로 쟀는데, 준비 대기가 3초를 넘기면 "로딩 중…" 상태를 완성으로 셌다 →
   로딩 표시가 사라지고 2초 불변까지로 바꾸고, 기준(HEAD)도 별도 worktree 빌드로 같은 스크립트로 다시 쟀다.
