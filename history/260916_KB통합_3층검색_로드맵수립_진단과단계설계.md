## 0. 한 문단 요약

사용자 질문에서 출발했다 — "auditor가 보는 KB(지식베이스)는 질문 없이 정보만 있는
트리인데, 코사인 매칭을 그대로 적용하면 매칭률이 나쁘지 않겠나. 이런 사전형 정보를
참고해 답변하는 구조를 만들 수 있나." 코드를 확인한 결과 **전제부터 달랐다**:
`/audit/knowledge` KB는 매칭이 나쁜 게 아니라 **아예 검색 경로에 없다**. 프론트 정적
시드일 뿐 DB·임베딩이 없고 백엔드가 읽지도 않는다. 반면 적재 함수
`ingest_kb_document()`는 이미 존재하는데 **호출하는 곳이 없다** — 자리는 파였고 배선만
안 된 상태였다. 이 진단 위에서 **3층 구조(L0 규범 상시주입 / L1 사전 검색 / L2 = 현행
KB2) + RRF 순위 융합**을 설계하고 P1~P4 단계로 쪼개 마스터 문서에 고정했다.

## 1. 진단 (코드 근거)

### 1.1 `/audit/knowledge` KB는 검색 경로 밖이다

- 실체: `frontend/data/kb/seeds/*.ts` 6종(마스터/해석론/직업군/판례노트/용어집/오류패턴),
  합계 1,165줄. 스키마 `frontend/lib/kb-schema.ts`(`KbDocument`).
- 소비처: `frontend/lib/kb-seeds.ts` → `/audit/knowledge` 트리 UI **뿐**. DB에 없고,
  임베딩 없고, 백엔드 grep 무결과.
- 즉 답변 품질 기여도가 0이다. 사용자의 우려(매칭률)보다 **한 칸 앞선 사실**이다.

### 1.2 배선 자리는 이미 있었다

- `backend/api/rag/ingest.py:190` `ingest_kb_document()` — `source_kind="kb_document"`,
  멱등 키 `kb:<id>`. **레포 전역에 호출자 없음**(`scripts/rag_ingest.py`는 `case_seed`만
  호출).
- `frontend/components/admin/rag-overview-view.tsx:34` — "큐레이션 문서" 라벨 이미 존재.

### 1.3 비대칭 문제는 절반만 맞다

Upstage는 이미 `embedding-query` / `embedding-passage` 비대칭 쌍을 쓴다
(`backend/api/rag/embeddings.py`) — 질문↔서술문 격차를 줄이도록 학습된 모델이다.
KB2 점수가 0.5 미만으로 깔리는 실측 원인은 `retriever.py:154` 주석대로 **문장이 짧고
응축돼서**지 서술문이라서만은 아니다. 그래서 `KB2_MIN_SCORE=0.35`를 따로 뒀던 것이다.

### 1.4 지금 `HybridRetriever`는 융합이 아니라 경쟁이다

`retriever.py:103` — "kb2에 결과 있으면 kb2, 없으면 rag" 하드 폴백. **코퍼스마다 임계값을
따로 튜닝하는 것 자체가 이 구조의 증상**이다. 코퍼스가 셋이 되면 못 버틴다.

## 2. 설계 결론

### 2.1 3층 분리

시드 6종은 성격이 전혀 다른 두 덩어리다. 한 코퍼스로 뭉쳐 검색하면 둘 다 망가진다.

| 층 | 내용 | 취급 |
|---|---|---|
| L0 규범 | 해석론 결정트리, 오류패턴, 면책 | **검색 안 함 — system prompt 상시 주입** |
| L1 사전 | 용어집, 판례노트, 직업군, 마스터 | 검색. doc2query 증강 후 임베딩 |
| L2 경험 | 세무사 코멘트 응축 문장 | 현행 KB2 그대로 |

**L0을 검색에서 뺀 근거**: 해석 원칙은 질문마다 top-k로 뽑을 성질이 아니라 어떤 질문에든
적용되는 판단 규칙이다. 부수 효과로 `llm.py`의 하드코딩 프롬프트가 KB 문서에서 빌드되면
**"세무사가 KB를 고치면 AI 사고방식이 바뀐다"** 가 제품적으로 성립한다.

**권위 서열**: `엔진 판정 > L0 규범 > L2 검수 선례 > L1 일반 정보`. 판정은 여전히 엔진
권위(마스터 §2)이고, 이 서열은 설명·자문 문장의 근거 우선순위다.

### 2.2 RRF 순위 융합

점수 대신 **순위**로 합산하면 코퍼스별 스케일 차이(§1.4)가 자동 소멸한다. 자리 쿼터로
한 코퍼스의 top-k 독식을 막는다. BM25/`pg_trgm` 병행은 조문번호·사건번호에 유효하며
**모델 호출이 아니라 국내 AI 트랙 제약과 무관**하다. 외산 리랭커는 제품 경로 금지.

### 2.3 doc2query 채택, HyDE 보류

역질문 생성은 오프라인 1회 비용에 런타임 0. HyDE는 챗 턴마다 LLM 1회라 지연 비용이
있어 P3 실측 후 재검토로 미뤘다.

### 2.4 출처 라벨 분리는 필수

`llm.py:310` `write_advisory`가 passage를 평평하게 이어붙이는데, 여기에 성격이 다른
코퍼스를 섞으면 **KIIS 실험에서 이미 관찰한 맥락 혼입이 악화된다**. 블록을 갈라
"검수 선례(세무사 확인됨)" vs "참고 사전(미확인)"으로 주입하고 충돌 시 우선순위를 명시한다.

## 3. 단계 (사용자 승인 2026-09-16)

| 단계 | 내용 | 비고 |
|---|---|---|
| P1 | L0 규범층 주입 | 코퍼스·마이그레이션 불필요. 미해결 결정 하나 있음(§4) |
| P2 | RRF `FusionRetriever` (rag + kb2 둘만으로) | `?ragSource=fusion` 신설. 4-way 벤치로 판정 |
| P3 | L1 사전층 적재 (`kbdict` 스키마 + doc2query) | 마이그레이션 + 적재 스크립트 → **별도 세션** |
| P4 | 출처 라벨 분리 프롬프트 | P2·P3와 함께 |

**P1+P2를 먼저 묶는 이유**: P3(사전층)를 먼저 만들어도 융합기가 없으면 결국 KB2와
경쟁만 시키게 된다. 그릇을 먼저 만든다.

**불변 원칙**: 기존 디폴트 경로(`?ragSource=rag`)는 어느 단계에서도 안 바꾼다. KB2가
그랬듯 병렬로 얹고 A/B로 비교한다. graceful·엔진 권위·Upstage 단독도 그대로.

## 4. 착수 전 미해결 결정 (P1)

규범층 원문인 시드가 `frontend/data/kb/seeds/*.ts` — **타입스크립트라 백엔드가 직접 못
읽는다.** 셋 중 하나를 골라야 한다.

- (a) 빌드 시 JSON 내보내기 → 백엔드가 읽기
- (b) 시드를 DB로 이관 → P3의 사전층 적재와 겹침
- (c) 백엔드에 md로 복제 → 동기화 부채 발생

P1 착수 세션에서 P3를 어디까지 당겨볼지와 함께 판단한다.

## 5. 코퍼스 확장 규칙 (사용자 지시로 메모리 고정)

**현 시점 투입 가능한 정보 풀은 시드 1,165줄이 전부**이며 더 넣을 외부 정보가 없다.
향후 외부 소스(국가법령정보센터 Open API·국세청 상담사례·조심 결정문 등) 투입 시 6규칙:
① 계측 먼저(`rag.chat_turns` 0027 + `testset.json` before/after) ② precision 감시
(커버리지만 보지 않는다 — KB2 천장 63~65% 사례) ③ 한 번에 한 소스 ④ 라이선스 확인
⑤ 권위 등급 부여 ⑥ 소급 가능(status 전환, 삭제 아님).

**근거**: 대량 투입은 양날이다. "정보가 많을수록 좋다"는 직관이 RAG에서는 성립하지 않고,
계측 없이 넣으면 품질이 왜 변했는지 영영 알 수 없게 된다.

## 7. 후속 — §4 미해결 결정 확정 (같은 날, 사용자 지시)

§4에 열어둔 (a)/(b)/(c) 셋을 같은 깊이로 재분석해 **(c) 백엔드 md 로 확정**했다.

**결정타는 실측이다** — `frameworks` 14,602자 + `pitfalls` 2,767자 = **17.4k자**, 현재
시스템 프롬프트는 1,028자. 매 턴 호출되는 작문 프롬프트에 17배를 얹을 수 없다(비용·지연,
그리고 긴 프롬프트는 지시 준수를 희석시킨다). 따라서 **L0는 시드 전문이 아니라 요약 규범
블록**이고, 요약 단계가 반드시 붙는다. 그 순간 (a)의 유일한 편익인 자동 동기화가 끊긴다 —
손으로 요약하면 그게 곧 (c)이고, LLM으로 요약하면 비결정적이라 규범으로 못 쓴다(규범이
배포마다 흔들리면 안 된다). **비용은 지불하고 편익은 못 받는 구조**라 (a) 탈락.

(b)는 P1에서 하면 비싸고 P3에서 하면 거의 공짜라 이월. 상세 비용(프론트 async화,
편집 저장소 이관 연쇄, 요청 경로 DB 왕복, 폴백 문안이 결국 (c)의 복제본)은 마스터 문서
§3 P1에 남겼다.

**(c)의 "두 원본" 문제는 방향을 뒤집어 해소한다** — 복제가 아니라 규범의 원본을 백엔드로
옮기는 것으로 선언한다. 프론트 시드 = 사람이 읽는 해설(길다, 표·예시), 백엔드 md = AI가
따르는 규범(짧다, 명령형). 역할이 다른 두 문서라 동기화 의무가 애초에 없다.

**필수 동반 조치**: `load_norms()` 로더 경계 한 겹. `retriever.py:4`의 관용구와 같다.
이것이 (c)를 막다른 길이 아니라 (b)로 가는 계단으로 만든다 — P3에서 소스만 교체하면
프롬프트 빌더는 한 줄도 안 바뀐다.

**분류 정정 — `master`는 L1이 아니라 L0다.** `frontend/data/kb/seeds/master.ts`는 문서가
자기 정체를 직접 말한다("본 지식 베이스는 당신의 시스템 프롬프트다"). 답변 절차 6단계·
거절 규칙·출력 형식이 들어 있어 사전에 넣고 검색할 물건이 아니다. 최초 작성 시 L1으로
분류했던 것을 정정했다. 확정 배치: **L0 = master·frameworks·pitfalls / L1 = glossary·
cases·occupations**.

**(b)는 P3에서 두 갈래로 갈린다** — L1의 DB화는 **필수**(벡터 검색을 하려면 임베딩이 DB에
있어야 한다), L0의 DB 승격은 **선택**(상시 주입이라 파일로 충분). L0 승격은 세무사 편집분이
`frontend/lib/kb-store.ts:121`의 브라우저 localStorage를 벗어날 때 비로소 실익이 생긴다 —
지금은 **어떤 안으로도 편집분이 서버에 도달하지 않는다.**

**(a) 재오픈 신호**: L0를 요약 없이 전문 주입하는 설계로 바뀌면 (a)가 되살아난다. 지금
실측으로는 해당 없음.
