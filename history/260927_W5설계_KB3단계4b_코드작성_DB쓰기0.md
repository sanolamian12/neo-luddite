## 3. 만든 것

**import-credigraph**
- `supabase/migrations/0041_kb3_schema.sql` — `kb3.documents`(case_id unique, corpus `kb3_prec|kb3_qna`, origin, case_number, content, source_url 필수, law_articles, embedding vector(4096), content_hash, status) + `kb3.match_documents(vec, k)` + 방어적 RLS. **미적용.**
- `api/rag/kb3_store.py`(kbdict_store 모양) · `retriever.py` 의 `Kb3Retriever`(case_refs = 문서번호) · `get_retriever(source="v2")`.
  쿼터 0 인 갈래는 안 붙인다(`FUSION_QUOTA_KB3=0` = 적재 전 v2). **v1 `fusion` 분기는 한 줄도 안 바뀜**(확인).
- `scripts/kb3_ingest.py ingest` — 캐시 벡터만 사용(없으면 멈춤), case_id·content_hash 멱등, 범위 밖은 archived. `--write` 없으면 dry-run(0041 미적용이면 빈 DB 가정).
- `bench_fusion.py --kb3 이름:범위:컷:쿼터[:갈래순서]` — 순서 생략 시 run2 와 같이 kb3 맨 뒤.

**agentic-v2**
- `api/llm2.py` — 근거 4블록 라벨(검수 선례 > 판례 요지 > 국세청 해석 > 참고 사전) + 규칙(판례·해석 충돌 시 둘 다 밝히고 조건부/보류),
  도구 `emit_answer{verdict, verdict_basis, segments}`, `enforce()`(모델 호출과 분리 — 하니스가 그대로 쓴다):
  basis 가 rag·kb3 본문에 없으면 `판정 보류` + 결론·적용 문장 제거 · gap 인데 확정이면 `조건부` · 근거에 없는 `제N조` 문장 제거 · 인용 대조.
  공통 규범은 본문만 빌리고 머리말은 자체 것(`llm._with_norms` 의 "판정은 규칙엔진의 권위"는 v2 에서 거짓).
- `api/engine_contrast.py` — v1 판정 경로와 같은 관문(추출→9유형→필수값→결정변수 검증)을 통과할 때만 `eng.evaluate`, 실패는 전부 삼킴.
- `pipeline_agentic._answer` — `write_advisory` → `llm2.write_answer`, `source="v2"`, 엔진 대조 병렬(답 뒤 5초 대기 상한), `ChatMeta.llm2`.

## 5. 드러난 것 · 함정

1. **openai 지연 import 교착** — 대조 스레드와 본 스레드가 `client.chat`/`client.embeddings` 를 동시에 처음 건드리면 `_DeadlockError`.
   서버 콜드스타트에서도 날 수 있다 → `pipeline_agentic` 로드 때 `openai.resources.chat`·`.embeddings` 선 import.
2. **거짓 출처 문구** — 임시 자문의 선두 "세무사들이 남긴 검수 의견을 근거로"는 kbdict 만 아니면 무조건 붙었다 → KB3 도 세무사 검수라고 부르게 된다. v2 는 corpus 별로 조립.
3. **설계 오류 정정** — "날조 조문은 numeric_guard 가 잡는다"는 틀렸다(조문 번호는 설계상 수치 토큰 제외). llm2 조문 가드로 대체.
4. **M1 구멍** — "소득세법"처럼 숫자 없는 basis 는 아무 근거에나 부분일치 → 숫자 든 인용만 센다.
5. **개인/법인 혼입(O-W5-4)** — 병원 원장 질문에 법인 질의회신만 떠 법인세법 시행령으로 답했다(엔진 판정은 같음).
6. **numeric_guard 가 `N월` 기간을 안 본다(O-W5-5)** — "연말정산 시점(다음 해 2월~5월)" 날조 통과.
7. **밤 프로덕션 DB** — 23시께 벤치 중 `server closed the connection unexpectedly` 반복. 워커 1·2문항에 545초, 접속만 21.8초.
   벤치가 4096차원 exact scan 을 동시에 여럿 던져 DB 를 누른 것일 수도 있다 → 멈췄다. 158문항은 낮에.
