## 1. merge 하한 A/B/C 실험 — 개수 축과 중복 축의 분리

### 설계

지난 세션 §6① 의 설계를 그대로 따랐다. 맵은 결정적이지 않으므로 **후보를 한 번만 뽑아
파일로 굳히고**(413건 → 12배치 → 후보 72개, 고유 61개, 34.4초) 목차 변형만 바꿔 잰다.

| 목차 | 개수 | 중복 | 무엇을 가리나 |
|---|---|---|---|
| A 현행 | 30 | 있음(복리후생 4갈래 등) | 기준선 = 지금 프로덕션 활성 목차 |
| B 채움 | 30 | 없음 | 개수 고정 → **중복만의 효과** |
| C 축소 | 22 | 없음 | 중복 제거에 개수 감소가 딸려온 경우 |

중복 판정은 LLM 이 아니라 **코드가** 했다(대안 (c) 의 시제품). 세 규칙의 합집합:
레이블 임베딩 코사인 ≥ 0.70, 부분문자열 포함(3자 이상), 공통 접두 3자 이상.

코사인만으로는 부족하다는 것이 쌍 목록에서 바로 보였다:

```
0.9091  복리후생비 × 복리후생비처리        ← 진짜 중복
0.8866  접대비 × 접대비인정
0.8358  복리후생비 × 인건비·복리후생
0.8231  업무용승용차 × 업무용승용차특례
0.7046  복리후생비 × 피부시술복리후생비
0.6802  복리후생비처리 × 카드비용처리      ← 첫 오탐('처리' 접미가 같을 뿐)
…
0.5829  인테리어·개인카드 × 인테리어비용처리 ← 진짜 중복인데 오탐보다 아래
```

인테리어 3종을 코사인으로 잡으려고 임계값을 내리면 오탐이 **먼저** 들어온다. 그래서
문자열 규칙을 함께 썼다. 결과 클러스터 4개:

```
[인건비·복리후생] ← 복리후생비(18) 인건비·복리후생(26) 복리후생비처리(10) 피부시술복리후생비(6)
[접대비]          ← 접대비(14) 접대비인정(3)
[업무용승용차특례] ← 업무용승용차(10) 업무용승용차특례(14)
[인테리어비용처리] ← 인테리어·개인카드(0) 적격증빙(11) 인테리어비용처리(12) 인테리어적격증빙(0)
```

30 → 22개(사용자 예측 ~22 와 일치). B 의 채움 8개는 캐시된 맵 후보에서 관찰 횟수순으로,
같은 세 규칙에 안 걸리는 것만: 가족계좌·급여 / 간이과세 / 출장비 / 임차료 / 기부금·후원 /
의료봉사비용 / 폐기물처리비 / 고용증대세액공제.

> 함정 하나: 채움을 **대표 레이블하고만** 대조하면 접힌 멤버(적격증빙, 피부시술복리후생비)가
> 대표와는 규칙에 안 걸려 '새 주제'인 척 되돌아온다. 접힌 멤버 **전부**를 대조해야 한다.

### 결과 (같은 150건 · 순차 · 조건당 3회)

```
A 현행 30개·중복 有 : 54.0 / 52.0 / 49.3%   평균 51.8%   폭 4.7%p (상대 8.6%)
B 채움 30개·중복 無 : 53.3 / 54.0 / 53.3%   평균 53.6%   폭 0.7%p (상대 1.2%)
C 축소 22개·중복 無 : 46.7 / 45.3 / 47.3%   평균 46.4%   폭 2.0%p (상대 4.2%)
```

호출 실패 **0/1350건**(순차라서 — 지난 세션 결론 재현).

- **B ≈ A**: +1.8%p, 상대 +3.5%. 측정된 회차 편차(3.8%) 안이다. → **중복은 범인이 아니다.
  가설 기각.**
- **C < B**: −7.2%p, 상대 −13.4%. 편차 밖이다. → 9/11 오전의 "좁히면 더 나쁘다"가
  **세 번째로 재확인**됐다. **`MERGE_MIN_CATEGORIES=20` 하한은 낮추면 안 된다.**
- 곁가지로 나온 관찰: **A 의 회차 편차(상대 8.6%)가 B(1.2%)보다 훨씬 크다.** 근사 동의어는
  커버리지를 깎지는 않지만 **판정을 흔든다** — 같은 건이 회차마다 `복리후생비`와
  `인건비·복리후생` 사이를 오간다. n=3 이라 결론이라기보다 다음에 확인할 관찰로 남긴다.

### 진짜 발견 — 건 단위로 보면 목차 축은 끝났다

조건별 평균만 보면 셋이 비슷비슷하다. 건 단위로 겹쳐보면 다른 그림이 나온다
(3회 중 한 번이라도 배정되면 '갈 곳 있음'):

```
A 83/150 · B 85/150 · C 75/150
세 조건 모두에서 갈 곳을 찾은 건        64
어느 조건에서도 갈 곳이 없던 건        52 (34.7%)
A 에서만 구제 6 · B 에서만 9 · C 에서만 2
```

**A 미분류 67건 중 52건(78%)은 목차를 어떻게 바꿔도 안 구제된다.** 목차를 더 만지는
것은 남은 미분류의 22% 를 두고 다투는 일이다.

그리고 중복 클러스터가 표를 나눠 먹는 것 자체는 사실이다(A 3회 합산):

```
63표 ← 복리후생비 22 / 인건비·복리후생 29 / 복리후생비처리 8 / 피부시술복리후생비 4
36표 ← 업무용승용차 12 / 업무용승용차특례 24
13표 ← 접대비 9 / 접대비인정 4
```

하지만 그 표들은 **어차피 배정되는 건들**이다. 접어봐야(C) 미분류가 줄지 않는다 —
오히려 늘었다. 즉 **중복은 트리의 가독성 문제이지 커버리지 문제가 아니다.**

또 하나: **세 조건 모두에서 3회 내내 한 표도 못 받은 세목이 6개**다 —
`1세대1주택비과세` `6세이하자녀` `개인부동산임대` `수도권공공기관이전`
`육아휴직수당과세` `카드비용처리`. merge 가 "1회 관찰 후보는 넓은 주제에 흡수시켜라"를
여전히 안 듣고 있다. 목차의 20% 가 빈 칸이다.

## 2. 그래서 52건은 무엇인가 — 미분류의 진짜 정체

원문을 열어보니 **잡담이 아니었다.** 전부 멀쩡한 병의원 세무 질문인데, 번들에 실린
**AI 답변이 엉뚱한 주제**다. 그리고 세무사 코멘트가 바로 그 점을 지적하고 있다:

- 1억짜리 진단기기 리스 질문 → AI 답변: "차량·접대·통신·복리후생 중 무엇인지 알려달라"
- 배우자 주 2회 SNS 관리 급여 질문 → AI 답변: 통신비 업무전용회선 부인 논리
- 진료비 20~30% 할인 질문 → AI 답변: 접대비 부인, 필요경비 0원
- 개인 명의 장비 질문 → AI 답변: 차량 업무사용비율 안분 논리

분류기는 `content[:700]` 을 읽는다. 질문은 대개 한두 줄이라, **읽히는 텍스트의 대부분이
질문과 주제가 다른 답변**이다. 목차에 갈 곳이 없어서가 아니라, **질문이 아닌 것을 읽고
판단**하고 있었다.

이건 지금까지 한 번도 건드리지 않은 축이다 — 맵·리듀스·목차 크기·중복·배치화는 전부
"어떤 선택지를 주느냐"였고, 여기는 "무엇을 읽히느냐"다.

(측정 결과는 §3)

## 3. 분류 입력 실험 — 번들 전체 vs 질문만 vs 질문+코멘트

목차는 A(현행 30개)로 **고정**하고 입력만 바꿨다. 축을 하나만 움직인다. 같은 150건·순차·
조건당 3회:

```
full  입력평균  601자 : 52.7 / 52.0 / 52.0%   평균 52.2%   폭 상대 1.3%
q     입력평균   55자 : 63.3 / 66.7 / 63.3%   평균 64.4%   폭 상대 5.0%
qc    입력평균  390자 : 58.7 / 56.7 / 56.0%   평균 57.1%   폭 상대 4.6%
```

호출 실패 0/1350건. `full` 이 §1 의 A(51.8%)를 그대로 재현해 계측이 정상임을 확인했다.

**질문만 넣으면 +12.2%p(상대 +23%).** 편차(3.8%)의 6배다. 그리고 결정적인 것:

```
A/B/C 어디서도 갈 곳이 없던 52건 중
  full : 1건 구제 (2%)
  q    : 18건 구제 (35%)
  qc   : 9건 구제 (17%)
```

목차 축이 소진된 뒤에 남아 있던 축이 이것이었다. **읽히는 텍스트를 1/10 로 줄였더니
커버리지가 올랐다** — 지금까지 이 프로젝트의 모든 개선이 "더 많이 보여주기"였던 것과
정반대 방향이다.

`qc` 가 `q` 보다 낮은 것도 같은 이치다. 세무사 코멘트는 **지식이 있는 곳**이지만 조문과
다른 주제를 길게 인용해서, 주제 판정에는 소음이다. KB 의 가치와 분류 신호는 다른 자리에
있다.

### 제품 반영

`api/rag/ingest.question_of()` — 번들에서 `[질문]` 절만 떼는 파서를, **조립기
`build_bundle_text` 바로 옆에** 뒀다(떨어져 있으면 형식이 바뀔 때 한쪽만 따라간다).
`kb2_taxonomy._classify_all` 이 이걸 써서 분류하고, 파서가 실패하면 번들 전체로 되돌아가되
**폴백 건수를 세어** `coverage.classifyInputFallbacks` 로 남긴다(조용한 폴백은 위험하다 —
이번 세션이 그 교훈으로 시작했다).

검색과 합성은 **여전히 번들 전체**를 쓴다. 지식은 세무사 코멘트에 있다. 바뀐 건 "이
상담이 무슨 주제냐"를 묻는 자리 하나뿐이고, 그 질문에는 질문이 답한다.

검증: 413건 전량에 대해 제품 파서의 결과가 측정판 파서와 **완전히 일치**하고 폴백 0건.
즉 측정한 그대로가 제품에 들어간다.

### 남은 한계 (정직하게)

배정률은 **커버리지**이지 **정확도**가 아니다. 질문만 읽으면 "갈 곳을 찾는" 비율은 오르지만
"맞는 곳을 찾는" 비율은 이 측정으로 알 수 없다. 다만 이 제품에서 비용은 대칭이 아니다 —
가까운 세목에 잘못 들어가면 세무사가 트리에서 옮길 수 있지만(이제 '기타'도 마찬가지),
미분류는 화면에 나타나지도 않았다. 정확도 측정은 세무사 평가가 필요한 별도 일이다.

## 4. '기타' 세목 (사용자 결정 구현)

**결정**: "트리에는 보이되 `match_sentences` 에서는 빠진다."
구현 전에 판단해 보고한 두 가지와 그 근거:

### (a) status 를 새로 만든다 — `'unsorted'` (마이그레이션 0025)

`'retired'` 재사용은 **위험하다**. `kb2_store.set_document_status` 가
`where status in ('active','retired')` 라서, 세무사가 트리에서 **[세목 재연결] 한 번**이면
미분류 182건이 통째로 검색에 들어온다 — 이번 결정이 막으려던 바로 그 일이다. 새 값은
같은 WHERE 절에 안 걸려 **추가 가드 없이** 그 전환이 거부된다.

또 `'retired'` 는 화면에서 `document_events` 의 사유를 배지로 띄우는데, '기타'는 행위자도
사유도 없어 그 목록을 기계가 만든 문서로 오염시킨다.

`kb2.match_sentences` 가 이미 `d.status='active'` 만 보므로 **SQL 함수 변경은 불필요**
(0022·0024 와 같은 이유). 대신 **눈에 안 띄는 필수 항목**이 하나 있었다:
`archive_all_active_documents()` 가 `status='active'` 만 건드려서, '기타'를 넣지 않으면
세대교체 때 안 내려가고 **회차마다 죽은 '기타'가 하나씩 쌓인다**(0023 이 카테고리에서
고쳤던 그 버그와 같은 모양). `status in ('active','unsorted')` 로 넓혔다.

### (b) 합성은 돌리지 않는다 — 원문 1건 = 문장 1개

합성 프롬프트의 계약이 "같은 주제의 상담 묶음 → 조항 문장"이고, 인용률을 59%→96% 로
올린 처방(커버 규칙 + 청크당 ~9건)이 **그 응집성 위에** 서 있다. '기타'는 정의상 주제가
없어서 무관한 아홉 건을 한 프롬프트에 넣으면 공허한 일반화나 없는 연결이 나온다.

위험이 비대칭이라는 게 결정적이다: '기타'의 존재 이유가 **세무사가 문장을 밖으로 옮기는
것**이고, 옮기는 순간 그 문장은 검색에 들어가고 기여 크레딧을 단다. **조항처럼 생긴 가짜
문장은 옮겨진 뒤엔 진짜와 구별되지 않는다.** 원문 덩어리는 손봐야 한다는 게 눈에 보인다.

부수 효과로 attribution 이 **더 정확해진다** — `source_passage_ids` 가 정확히 한 건이라
원 세무사가 가중치 1.0 을 그대로 받는다(묶음 합성처럼 쪼개지지 않는다).

이력은 손봐야 했다. `create_sentence` 가 v1 을 `'system_synthesis'` 로 박는데 원문 보관에는
거짓말이다. 0025 에서 `'system_unsorted'` 를 추가하고 editor_id 는 `system:kb2_unsorted` —
옮겨진 문장의 이력이 `v1 원문 보관 → v2 moved → v3 auditor_edit` 로 정직하게 읽힌다.

임베딩은 만든다(`kb2.sentences.embedding` 이 not null 이기도 하고, 옮겨지는 순간 검색
대상이 되는데 그때 만들려면 이동 경로에 배관이 하나 더 붙는다).

### 화면

트리 맨 아래 **"기타 (검색 제외)"** 별도 줄(대목이 아니므로 삭제 버튼 없음, 세목 이동
select 의 선택지에도 안 들어간다). 선택하면 편집 줄 대신 설명 — "AI 가 어느 세목에도 넣지
못한 상담입니다. **검색·답변에는 들어가지 않고**, 합성도 하지 않아 원문 그대로 보관돼
있습니다. 알맞은 세목으로 옮기면 그때부터 검색에 포함됩니다."

문장 이동 다이얼로그에서 '기타'는 **목적지에서 제외**했다 — 거기서 꺼내는 게 용도이지
넣는 곳이 아니고, 넣으면 세무사가 방금 한 판단이 검색에서 사라진다.

계측에 `unsortedStored` 가 붙고, admin 깔때기의 "미분류로 **유실**" 줄이 보관 건수가 있을
때 "미분류 → '기타' 보관 · 검색 제외"로 바뀐다. **`cited`(커버리지)에는 일부러 안 더했다** —
검색에 안 잡히는 문장은 답변을 덮지 못하므로, 같이 세면 지표가 스스로를 속인다.

## 5. 합성 단계 가드 (지난 세션 §6③)

분류 가드는 archive **직전**에 서 있어서 멈추면 아무것도 안 건드린 상태다. 그 뒤에 합성이
전량 실패하면 되돌릴 방법이 없어 **빈 세대**가 남는다.

트랜잭션으로 묶는 길은 막혀 있다 — 커넥션이 모듈 캐시 하나(autocommit)이고 archive 부터
적재까지 사이에 LLM 호출로 십수 분이 흐른다. 십수 분짜리 트랜잭션은 그 커넥션을 쓰는 다른
요청까지 함께 붙잡는다.

그래서 **되돌리기**를 준비한다: archive 직전에 내려가는 세대의 `(id, status)` 를 찍어두고,
합성이 문장 0개로 끝나면 이번 회차가 만든 껍데기를 삭제하고 기존 세대를 **원래 status 로**
복구한다(`unsorted` 는 `unsorted` 로 — `active` 로 일괄 복구하면 '기타'가 검색에 들어간다).

**판정선을 문장 0개로만 둔 것은 의도적이다.** "직전 세대의 절반 미만" 같은 상대선이 더
촘촘하겠지만 **합성 단계의 회차 편차를 아직 재본 적이 없다.** 분류 가드의 임계값은 순차
4회 실측(상대 3.8%) 위에 세웠고, 여기서 감으로 숫자를 고르면 이 프로젝트가 여러 번 덴 그
실수를 반복하는 것이다. 0 은 재볼 필요가 없는 유일한 값이고 오탐이 원리적으로 불가능하다.

화면은 분류 가드와 같은 호박색이되, 문구가 다르다 — 여기선 이미 내려갔던 세대를 **되돌려
올렸으므로** "기존 세대 N개 문서를 복구했습니다"를 함께 적는다. 분류 판정은 `guard` 가
아니라 `classifyGuard` 키로 남긴다(`guard` 로 두면 화면이 그걸 중단 사유로 읽어 **사유가
빈 칸인 배정률 표**를 그린다 — 여기서 중단시킨 건 분류가 아니라 합성이다).

## 6. 다음 세션 작업 목록

### ① 합성 인용률 하락(93.1% → 87.4%)의 정체 (최우선)

§8 참조. 커버리지는 올랐지만 인용률은 내려갔다. 두 설명이 가능하고 **아직 갈리지 않았다**:
(a) 새로 배정된 71건이 원래 어려운 건이라 합성이 덜 인용한다, (b) 청크가 41→48 로 늘어난
영향, (c) 그냥 회차 편차 — 합성 편차를 **한 번도 재본 적이 없어서** 셋을 가를 수 없다.

그래서 순서는: **합성 회차 편차부터 재고**(같은 세목·같은 원문 3회), 그 다음에 인용률
하락이 편차 밖인지 판정한다. 부산물로 §5 가드의 상대 임계값 근거도 생긴다.

### ② 브라우저에서 '기타' 실사용 확인

API·DB·검색 배제는 확인했다(§8). 남은 건 사람이 실제로 쓰는 경로다 — 트리 맨 아래
표시, 문장 클릭 → 다른 세목으로 이동, **이동한 문장이 그때부터 검색에 잡히는지**.
Playwright 로 확인(이 레포엔 chromium-cli 가 없고 Turbopack 이 이 환경에서 크래시하니
`next dev --webpack`).

### ③ 맵 단계도 질문만 읽힐지

맵(`propose_categories_batch`)은 `content[:200]` 을 읽는다. 번들이 `[질문]` 으로 시작하니
200자면 대개 질문 + 답변 앞머리다. 분류에서 −12%p 를 만든 오염이 맵에도 있을 수 있다.
맵 후보 캐시 방식으로 싸게 잰다(후보 목록의 질/개수를 비교).

### ④ merge 가 1회 관찰 레이블을 여전히 안 접는다

세 조건 모두에서 3회 내내 **한 표도 못 받은 세목이 6개**다(`1세대1주택비과세`
`6세이하자녀` `개인부동산임대` `수도권공공기관이전` `육아휴직수당과세` `카드비용처리`).
목차의 20% 가 빈 칸이다. 커버리지에는 영향이 없지만(C 실험이 보여줬다) **트리가 지저분**
하고, 세무사가 보는 것은 트리다. 오늘 만든 레이블 코사인+문자열 병합기
(`build_taxonomies.py`)를 merge **뒤에 후처리**로 붙이면 LLM 을 설득하지 않고 접을 수 있다.
단 이건 **가독성 개선이지 커버리지 개선이 아니다** — 그렇게만 기대할 것.

### ⑤ 근사 동의어는 판정을 흔든다 (n=3 관찰)

A 의 회차 편차(상대 8.6%)가 B(1.2%)보다 훨씬 컸다. 같은 건이 회차마다 `복리후생비`와
`인건비·복리후생` 사이를 오간다는 뜻이다. ④ 를 하면 부수적으로 나아질 수 있다. 다음에
④ 를 할 때 편차를 함께 재서 확인할 것.

### ⑥ 사람이 손댄 것이 세대교체 때 사라진다 (새로 드러난 구멍)

세무사가 '기타'에서 문장을 빼내 진짜 세목에 넣어도, 다음 재구조화가
`archive_all_active_documents()` 로 **그 세목까지 통째로 내린다**. 즉 사람의 정리 노동이
회차마다 사라진다. '기타'를 만들면서 이 구멍이 처음으로 **실제 비용**이 됐다
(`locked_by_auditor` 는 레거시 재합성 경로만 보호한다). 설계 판단이 필요한 건이다.

### ⑧ 잔가지 (그대로 이월)

- 의미 중복 문장 dedup — 지금은 정규화 일치만 접는다. ④ 와 같은 도구를 쓸 수 있다.
- `kb2.document_events` 이력 보기 UI.
- 가드가 실제로 중단시킨 적은 아직 없다(오프라인 8개 시나리오로만 검증).

## 7. 측정 방법 — 이번에 더한 것

지난 세션 §7 에 더해:

1. **맵 후보는 파일로 캐시하고 목차 변형만 바꾼다.** 맵은 결정적이지 않아서, 변형마다
   다시 돌리면 '목차 차이'와 '맵 편차'가 섞인다.
2. **조건별 평균만 보지 말고 건 단위로 겹쳐볼 것.** A/B/C 평균은 셋 다 비슷해 보였지만,
   건 단위로 보니 "52건은 어느 조건에서도 갈 곳이 없다"가 나왔다 — 이번 세션의 제일 중요한
   숫자이고, 평균만 봤으면 놓쳤다.
3. **숫자가 막히면 원문을 읽을 것.** 52건이라는 숫자는 "목차를 바꿔도 안 된다"까지만
   말해준다. 왜인지는 원문 15건을 눈으로 읽고서야 나왔다.
4. 임계값(코사인 0.70)도 감으로 고르지 않았다 — 쌍 목록을 전부 찍어 **오탐이 어디서
   시작되는지 보고** 그 직전에 그었다.

   Playwright 를 직접 스크립트로 구동해야 하고, Turbopack 이 이 Windows 환경에서
   크래시하니 `next dev --webpack` 으로 띄울 것. 프로덕션 CORS 는 localhost:3000 만 허용.

3. **맵 단계도 질문만 읽힐지** — 맵(llm.propose_categories_batch)은 content[:200] 을
   읽는다. 번들이 [질문]으로 시작하니 200자면 질문 + 답변 앞머리다. 분류에서 −12%p 를
   만든 오염이 맵에도 있을 수 있다. 맵 후보 캐시 방식으로 싸게 잰다(ingest.question_of
   가 이미 있다).

중요 — 이미 틀린 것으로 확인된 가설(다시 파지 말 것):
- **"미분류 = 근사 동의어 분할"은 기각됐다** (A/B/C 실험). 중복 제거는 배정률을
  편차 안에서만 움직인다. 중복은 **트리 가독성** 문제이지 커버리지 문제가 아니다.
- **목차를 좁히면 더 나쁘다** (세 번 확인: 14개 47%, C 22개 46.4% < B 30개 53.6%).
  MERGE_MIN_CATEGORIES=20 하한은 낮추지 말 것.
- **맵 프롬프트도 맵 maxItems 도 커버리지의 원인이 아니다.**
- **분류 배치화 금지.** 미분류 84% vs 건별 45%.
- **분류 입력에 세무사 코멘트를 붙이지 말 것.** 질문만 64.4% vs 질문+코멘트 57.1%.
  코멘트는 지식이 있는 곳이지만 조문·다른 주제를 길게 인용해 주제 판정에는 소음이다.
  (검색·합성은 여전히 번들 전체를 쓴다 — 거기선 코멘트가 핵심이다.)
