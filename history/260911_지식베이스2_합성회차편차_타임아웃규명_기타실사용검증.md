## 0. 한 줄 요약

직전 세션이 판정을 미뤄둔 **합성 인용률 하락(93.1% → 87.4%)** 의 정체를 규명했다. 셋으로
좁혀둔 설명((a) 어려운 건 (b) 청크 증가 (c) 회차 편차) 중 답은 **넷째**였다 —
`APITimeoutError`. 합성 단계의 회차 편차를 처음 재보니 날것 편차가 상대 7.9% 라 하락은
그 안이었고(→ **"나빠졌다"는 판정 불가**), 그 편차 자체가 **전부 호출 실패에서** 왔다
(실패 세목을 빼면 편차 0.9%). 분류에서 '회차 붕괴'의 정체가 `RateLimitError` 였던 것과
같은 구멍이 합성에도 있었다.

## 1. 측정 설계 — 합성만 흔들리게 고정하기

합성 편차를 재려면 **합성에 들어가는 묶음이 회차마다 같아야** 한다. 그런데 분류는 자체
편차(상대 3.8%)가 있어 매번 다시 돌리면 '합성 편차'와 '분류 편차'가 섞인다. 그래서 맵
후보를 캐시했던 것과 같은 수법으로, 분류 배정을 **한 번만** 돌려 파일로 굳혔다.

```
분류 배정 고정: 304/413 = 73.6%   (실패 0 / 폴백 0)
프로덕션 e1305183:  302/413 = 73.1%   ← 재현됨
```

그 고정 묶음(25세목·304건)으로 합성을 **순차 3회**. 제품과 같은 조건이다 — 세목 순차,
세목 안의 청크는 4워커 병렬(`SYNTHESIS_WORKERS`), 예산 6000, `temperature=0`, 빈 청크
재시도 1회.

⚠️ **계측 사본을 따로 썼다.** `llm.synthesize_kb2_sentences` 는 `except Exception:
return []` 라 **실패가 '인용 0'으로 둔갑**한다. 폴백이 있는 함수로 재면 안 된다는 직전
세션 교훈이 여기서 그대로 값을 만들었다 — 사본이 아니었으면 타임아웃을 "모델이 그 원문을
안 썼다"로 읽고, 인용률이 낮은 원인을 프롬프트에서 찾았을 것이다.

## 2. 결과 — 하락은 편차 안이고, 편차는 타임아웃이다

```
① 날것
   회차 1  258/304 = 84.9%   청크 50   오류 {APITimeoutError: 2}   1558s
   회차 2  245/304 = 80.6%   청크 50   오류 {1, 2, 2}              3002s
   회차 3  266/304 = 87.5%   청크 50   오류 {APITimeoutError: 1}    854s
   평균 84.3% / 절대폭 6.9%p / 상대폭 7.9%

   프로덕션 하락: 93.1% → 87.4% = 절대 5.7%p / 상대 6.1%   ← 편차 안
```

**직전 세션이 단정하지 않은 것이 옳았다.** 1회 측정으로 "나빠졌다"고 했으면 틀렸을 것이다.

```
② 타임아웃이 난 세목(4대보험·임금 / 개원비용 / 광고·경품) 제외
   회차 1  223/255 = 87.5%
   회차 2  221/255 = 86.7%
   회차 3  222/255 = 87.1%
   평균 87.1% / 절대폭 0.8%p / 상대폭 0.9%
```

**모델 편차는 사실상 0이다.** 겉보기 편차 7.9% 는 전부 호출 실패에서 온다. 청크 하나가
죽으면 그 안의 원문 ~10건이 통째로 미인용이 된다:

```
③ 실패한 세목에서 잃은 양 (같은 원문·같은 목차, 회차만 다름)
   4대보험·임금    13/16(81%)   13/16(81%)!  13/16(81%)!
   개원비용        6/16(38%)!   6/16(38%)!   15/16(94%)
   광고·경품      16/17(94%)    5/17(29%)!  16/17(94%)
```

같은 세목이 어떤 회차엔 한 번에 성공한다 → 이 실패는 **원문이 합성 불가라서가 아니라
Upstage 쪽 산발적 정체**다. 재시도가 답이라는 근거가 여기서 나온다. 시간도 같은 원인이다
(회차 2 가 3002s, 회차 3 이 854s — 타임아웃 한 번이 240초씩 먹는다).

### 남은 미인용은 구조적이다 (가설 (a) 부분 지지)

건 단위로 3회를 겹쳐보면:

```
3회 전부 인용  229건 (75.3%)
2회          32건 (10.5%)
1회          18건 (5.9%)
0회          25건 (8.2%)   ← 어느 회차에서도 근거로 안 쓰인다
```

그 25건 중 **8건이 `가족인건비` 한 세목에 몰려 있다.** 프로덕션 e1305183 의 `가족인건비`는
24투입 16인용 — **미인용 8건이 정확히 일치**한다. 우연한 회차 문제가 아니라 고정된 건들
이라는 뜻이다. 다음 세션에서 읽어볼 값어치가 있는 15건짜리 표본이 여기 있다.

### 가설 (b) 청크는 기각

```
④ 청크 크기별 인용률 (오류 없는 청크만, 3회 합산)
   1건 100%   2건 100%   3건 94.4%   4건 100%   5건 88.9%   6건 75.9%
   7건 90.5%  8건 73.6%  9건 92.6%  10건 90.0%  11건 79.1%  12건 90.6%
  13건 79.5% 14건 95.2%
```

단조 관계가 없다. 프로덕션 job 두 개를 청크 수로 묶어봐도 방향이 반대다(da0d2a7d 는 청크
1개 88.4% < 3개 97.8%, e1305183 은 1개 93.6% > 3개 78.8%). **청크 41→48 은 원인이 아니다.**

## 3. 제품 반영 (커밋 `af1c013`)

원인이 "실패를 못 세는 것"이라, 고칠 자리도 거기다.

- **`synthesize_kb2_sentences` 가 `(문장, 실패사유)` 반환.** `classify_dynamic_category`
  를 9/11 오전에 고친 것과 같은 모양이다. `no_tool_call` 도 실패로 센다 — `tool_choice`
  로 강제했는데 안 지킨 것을 모델의 판단으로 볼 근거가 없다.
- **빈 청크 재시도 1 → 2** (`CHUNK_ATTEMPTS = 3`). 근거는 §2③ — 같은 세목이 다른 회차엔
  한 번에 성공하므로 한 번 더 묻는 비용(타임아웃 1회)이 원문 ~10건보다 싸다.
- **`ChunkFailures` 집계** → `coverage.synthesisCalls / FailedCalls / FailureKinds /
  LostChunks / LostPassages` + 세목별 표에 **유실** 열 + 유실이 있으면 붉은 경고.
  `lostChunks` 와 `failedCalls` 를 나눈 이유: 실패해도 재시도로 건진 청크는 결과가
  온전하고, 시도를 다 쓴 청크만 원문이 사라진다 — 인용률로는 둘이 같아 보이는데 처방이
  정반대다.
- **합성 가드 2축** `GUARD_MAX_LOST_CHUNK_RATIO = 0.10`. 관측된 유실은 회차당 1/50·2/50·
  0/50 (0~4%) 이라 10% 는 2.5배 — 이 셋은 어느 것도 막지 않는다(막아서도 안 된다. 청크
  하나 유실은 커버리지 3%p 손실이라 멀쩡한 세대를 되돌릴 사건이 아니다). 기존 '문장 0개'
  판정은 그대로 둔다.

  **인용률에 선을 긋지 않은 이유**가 이번 측정의 핵심이다. 인용률은 상대 7.9% 흔들리는데
  실패 세목을 빼면 0.9% 다 — 즉 인용률의 흔들림은 **결과**이고 원인은 유실 청크다. 결과에
  선을 그으면 촘촘하면 정상 회차를 막고 느슨하면 아무것도 못 막는다. 분류 가드가 배정률
  보다 호출 실패를 먼저 보는 것과 같은 선택이다.

- **덤 — merge 레이블 중복 방어(`_dedup_labels`).** §5 실험 중 merge 가 **같은 레이블
  30개**(`복리후생비` × 30)를 돌려주는 것을 봤다. 목차 30칸이 한 칸이 되는데 선택지가
  하나뿐이라 **배정률은 오히려 높게 나올 수 있어 나쁜 회차 가드가 못 잡는다**. 접은 뒤
  고유 레이블이 하한(20) 미만이면 폴백(관찰 횟수순)으로 넘긴다. n=1 관찰이지만 구조적으로
  열려 있고 방어가 싸다. 근사 동의어 병합(`복리후생비` vs `복리후생비인정`)은 여전히
  여기서 안 한다 — 그건 커버리지가 아니라 트리 가독성 과제다.

## 4. '기타' 실사용 — 사람의 경로까지 성립 (작업 ②)

직전 세션은 API·DB·검색 배제를 확인했다. 남은 고리는 사람이었다. Playwright 로 실제
브라우저에서:

| 고리 | 결과 |
|---|---|
| 트리 맨 아래 "기타 (검색 제외)" | ✅ |
| 문장 카드 | ✅ 111개 |
| 이동 후보에 '기타' 자신 없음 | ✅ (나오는 곳이지 들어가는 곳이 아니다) |
| 이동 실행 | ✅ 111 → 110, 콘솔 에러 0 |
| 이력 | ✅ v1 `system_unsorted` → v2 `moved` / `auditor` |
| **이동 후 검색에 잡힘** | ✅ 자기 질의에 **1위 0.937** |

가장 불리한 조건(문장 자신의 임베딩)으로 양방향이 확인됐다 — '기타'에 있는 동안은 상위
5건에 0건, 옮기는 순간 1위. 옮긴 문장은 `fc17e2f6`(소득세법 시행령 155조 8·16항, 수도권
공공기관 이전)이고 `1세대1주택비과세` 로 갔다. 155조가 1세대1주택 특례 조항이라 주제가
맞는 자리여서 그대로 뒀다(사용자 결정). 활성 문장 407 → 408 / '기타' 111 → 110.

**환경 메모**: 포트 3000 을 다른 프로젝트(STLC_Web) dev 서버가 점유 중이었다. 프로덕션
CORS 는 `localhost:3000` 만 허용하므로, 남의 서버를 죽이거나 프로덕션 설정을 고치는 대신
**로컬 CORS 프록시(3002) + 앱 3001** 로 우회했다. 측정 대상은 CORS 가 아니라 UI 경로라
이 우회가 검증의 의미를 바꾸지 않는다. Playwright 함정 둘: ①하이드레이션 전에 `fill` 하면
값은 들어가도 React state 가 비어 제출 버튼이 계속 disabled 다(타이핑 + 버튼 활성 대기로
해결) ②`router.replace` 는 클라이언트 라우팅이라 `waitForURL` 의 load 대기가 안 풀린다
(`waitForFunction(location.pathname…)` 으로 해결).

## 5. 맵 단계도 [질문]만? — 개선되지만 작다, **보류** (작업 ③)

맵(`propose_categories_batch`)은 `content[:200]` 을 읽으니 분류를 −12%p 만들었던 오염이
여기에도 있을 수 있다. 맵 후보를 두 조건으로 뽑아 **파일로 캐시**하고(맵은 비결정적이라
매번 다시 돌리면 조건 차이와 맵 편차가 섞인다), merge → 같은 150건 순차 3회 분류:

```
A 현행 content[:200]   70.7 / 68.0 / 68.0   평균 68.9%
B 질문만               73.3 / 71.3 / 72.7   평균 72.4%   (+3.5%p)
```

세 회차 구간이 겹치지 않는다(B 최저 71.3% > A 최고 70.7%). 그런데 **분류에서 얻은
+12.2%p 와는 자릿수가 다르고**, 편차의 1.3배에 그친다. 그리고 대가가 있다 — B 의 후보는
눈에 띄게 좁다:

```
A 고유 59개: 복리후생비 / 복리후생비 인정 / 복리후생비인정 …   ← 근사 동의어 중복
B 고유 64개: 추석선물 / 학회등록증 / 진료비할인 / 현금결제 …    ← 1회 관찰 레이블
```

목차는 세무사가 보는 화면이고, 로드맵은 이미 "1회 관찰 레이블이 목차의 20%"를 가독성
과제로 잡아뒀다. 작은 커버리지 개선을 위해 그쪽을 더 나쁘게 만들 이유가 없다 →
**사용자 결정: 보류.** 근사 동의어 병합(레이블 임베딩 코사인 후처리)을 먼저 넣고 그
위에서 다시 잰다. 측정 데이터는 남겨둔다.

## 6. 다음 세션 작업 목록

### ① 세대교체가 사람의 정리 노동을 지운다 — **§8.2 에서 실물로 재현됨**

세무사가 '기타'에서 문장을 빼내 진짜 세목에 넣어도 다음 재구조화가
`archive_all_active_documents()` 로 그 세목까지 내린다. §4 에서 옮긴 한 건이 §8.2 에서
**정확히 한 회차 만에 원상복귀**했다 — 옮긴 문장은 archived 문서 안에서 검색 밖으로
나갔고, 같은 원문은 새 세대에서 다시 '기타'에 담겼다. `locked_by_auditor` 는 레거시
재합성 경로만 보호한다.

이게 왜 최우선인가: KB2 의 제품 논지는 "KB 는 세무사 코멘트로 **자란다**"인데, 지금
구조에서 KB 는 자라지 않고 회차마다 **다시 만들어진다**. 커버리지를 몇 %p 올리는 것보다
이쪽이 크다.

**전략 결정 (2026-09-12, 사용자): 보존 + 의미 기반 재부착.** 사람이 손댄 문장을
archive 하지 않고, 새 세대의 목차 중 **레이블 임베딩이 가장 가까운 세목**에 다시 붙인다.
맞는 자리가 없으면 '기타'로 내리고 계측에 남긴다.

레이블 문자열 매칭을 쓰지 않는 이유는 **측정된 사실**이다 — 목차 레이블은 세대를 넘어
**33~67% 만 남는다**(최근 4회: 67 / 33 / 47 / 60%). 하필 §4 에서 옮긴 문장의 목적지
`1세대1주택비과세` 가 이번 세대에서 사라진 12개 중 하나였다. 그런데 **의미는 대체로
남는다**: `1세대1주택비과세`→`양도소득세비과세`, `감가상각`→`감가상각비`,
`부가가치세`→`부가가치세신고`, `인테리어비용처리`→`인테리어비용`. 문자열은 불안정하고
의미는 안정적이므로 재부착은 임베딩으로 해야 성립한다.

지금 고치는 것이 싸다는 근거: 사람이 손댄 양이 아직 `locked_by_auditor` 1건 /
`auditor_edit` 2 · `moved` 1 · `retired`·`reconnected` 2+2 뿐이다. 소급 보정이 사실상 공짜다.
문장당 원문 수는 1건이 434, 2~5건이 96 이라 원문 id 를 키로 쓰는 재부착이 성립한다
(5건짜리 문장만 판단이 갈릴 수 있다).

**L2 — 코드 만지면서 정할 것**(지금 정하면 추측이다):
1. 매칭 임계값. **감으로 정하지 말 것** — 쌍 목록을 전부 찍어 오탐이 시작되는 지점
   직전에 그을 것(직전 세션이 0.70 을 그렇게 정했다).
2. **중복 정책**: 보존된 사람 문장과, 같은 원문에서 이번 회차에 새로 합성된 문장이 둘 다
   active 가 된다. 접을지(어느 쪽 우선) 둘 다 둘지.
3. **기여·정산**: 같은 원문이 두 문장(보존 + 신규)으로 크레딧을 두 번 만들 수 있다.
   기여 = RAG 존속기간 모델과 충돌하는지 확인 필요.
4. **보존 범위**: `locked_by_auditor`(수정)만인가, `moved`(이동)도인가, `retired`도인가.
   이동은 "사람이 고른 세목"이라 G2 의 핵심이므로 포함이 자연스럽다.
5. **스키마**: 재부착은 문장의 `document_id` 갱신 + `sentence_versions` 에 새 editor_type
   (`regenerated_reattach` 등)이 필요할 수 있다 → CHECK 제약 마이그레이션(0025 선례).
6. **계측 정의**: 보존 문장의 원문을 이번 회차의 '인용'으로 셀지. 안 정하면 깔때기의
   분모·분자가 세대를 넘어 섞인다 — 지표가 스스로를 속이는 자리다.
7. **재부착 실패율**을 coverage 에 남길 것(매칭 없어 '기타'로 내려간 건수).

### ② 근사 동의어 병합 — 트리 가독성, 그리고 ⑤의 전제

레이블 임베딩 코사인(≥0.70) 후처리를 merge 뒤에 붙인다. 도구는 직전 세션의
`build_taxonomies.py` 에 있다. 이게 들어가야 §5 의 맵 입력 변경을 다시 잴 수 있다 —
지금은 "커버리지 +3.5%p vs 가독성 악화"라 교환이 성립하지 않는다.

### ③ `가족인건비` 미인용 8건을 읽는다

3회 내내 인용 안 된 25건 중 8건이 여기 몰려 있고 프로덕션과 정확히 일치한다. 숫자가
막히면 원문을 읽으라는 규칙이 적용될 자리다 — "합성이 왜 이 8건만 안 쓰는가"는 프롬프트
문제일 수도, 그 세목의 묶음이 실제로 이질적인 것일 수도 있다.

### ④ `TIMEOUT_SYNTHESIZE` 하향은 **재고 나서**

타임아웃 한 번이 240초를 먹고, 회차 2 는 그 때문에 3002초였다(회차 3 은 854초). 낮추면
정체를 빨리 포기하고 재시도할 수 있지만, **성공 호출의 소요 분포를 아직 안 쟀다.** 감으로
고르면 이 프로젝트가 여러 번 덴 그 실수다. 다음에 잴 때 호출별 소요를 같이 찍을 것.

### ⑤ 잔가지 (이월)

- merge 가 1회 관찰 레이블을 안 접는다 → ② 와 같은 도구.
- 의미 중복 문장 dedup(지금은 정규화 일치만).
- `kb2.document_events` 이력 보기 UI.
- 합성 가드가 실제로 중단시킨 적은 아직 없다(오프라인 시나리오 + 이번 스모크로만 검증).

## 7. 측정 방법 — 이번에 더한 것

직전 세션 §7 에 더해:

1. **측정하려는 단계의 바로 앞 단계를 파일로 굳힌다.** 합성 편차를 재려면 분류가
   고정돼야 한다(맵 후보 캐시와 같은 수법). 굳힌 값이 프로덕션과 같은지 먼저 확인할 것
   — 304/413 vs 302/413 이라 "측정한 그대로가 도는 판"임이 보장됐다.
2. **편차를 재면 '편차의 원인'도 같이 나온다.** 회차별 총계만 봤으면 84.9/80.6/87.5 에서
   "합성은 원래 흔들린다"로 끝났을 것이다. 실패를 세는 사본이었기 때문에 그 편차가 전부
   타임아웃이라는 게 보였고, 그래서 가드를 **결과(인용률)가 아니라 원인(유실 청크)** 에
   걸 수 있었다.
3. **공짜 분석을 먼저 한다.** 청크 가설은 기존 job 두 개의 `categoryStats` 를 청크 수로
   묶는 것만으로 흔들렸다 — LLM 호출 0회. 비싼 측정을 설계하기 전에 이미 있는 데이터를
   먼저 볼 것.
4. **측정끼리도 겹치면 안 된다.** 합성 3회가 도는 동안 맵 실험을 같이 돌리고 싶었지만,
   429 가 합성 측정을 오염시킨다(그게 바로 9/11 오전에 규명한 사고다). 브라우저 작업처럼
   LLM 을 안 쓰는 일만 병행했다.
5. 제품이 순차면 측정도 순차 — 단, **제품이 병렬인 자리(청크 4워커)는 병렬로** 재야
   한다. "병렬 금지"가 아니라 "제품과 같게"가 규칙이다.

즉 번들에 **확정 지식이 없다** — 있는 것은 "AI 답변이 틀렸다"는 기록뿐이다. 합성이 여기서
조항을 못 뽑는 것은 결함이 아니라 **정상 동작**이다. 태그 분포가 이를 뒷받침한다:


미인용 집단에서 3.6배 몰려 있다. 다만 **완벽한 예측자는 아니다** — 인용된 229건 중에도
