# 7. 평가 · 검증 (공통)

## 무엇을 정리하는가

**"무엇으로 확인했나"의 기록이다.** 특정 포지션이 아니라 모든 포지션에 걸친 공통 섹션이다.
게임 프로젝트(SamChess)에서 가장 비싼 실수는 "조용히 틀리는 것"이었다. 이 프로젝트에서는
**"그럴듯하게 틀리는 것"** 이 가장 비쌌다. LLM 답변은 언제나 그럴듯하고, 채점기도 일반론에 관대하다.
그래서 일반 소프트웨어의 검증(타입 체크, 스모크)과 함께 **평가**(벤치, 계측, 채점)를 같은 곳에 모은다.

포지션 문서에는 "검증했다" 한 줄만 남는다. 상세는 여기에 있다.

## 담는 것

| 소제목 | 내용 |
|---|---|
| **정적 검사·스모크** | `tsc --noEmit`, `npm run build`, FastAPI `TestClient`, Playwright 브라우저 스모크, `/rag/health` 확인 |
| **실측·계측** | 프로덕션 DB에 돌린 결과(클러스터 수, 분류 분포, 커버리지, 혼입률, 동시 부하) |
| **벤치·채점** | n-way 벤치, strict judge, 오라클 천장, 블라인드 기준선 |
| **확인하지 못한 것** | 알면서 남긴 검증 공백. 다음에 누가 무엇을 봐야 하는가 |

## 반복해서 배운 검증 원칙

8~9월 6주의 검증 기록에서 되풀이된 원칙이다. 설명과 사례는 백서 1장 1.1~1.3절에 있다.

- 폴백이 있는 함수로 잴 때는 **폴백이 삼킨 것부터 센다.** 레이트리밋은 "미분류"로, 타임아웃은 "인용 0"으로, 키 미설정은 "0초 폴백"으로 보였다.
- 재시도는 한 층에서만 하고, 측정은 **제품과 같은 동시성**으로 한다.
- 「0건」과 「닿지 않음」은 다른 값이다. 요약보다 원시값을 먼저 남긴다.
- 시험 도구를 먼저 시험한다. 고치기 전의 실패를 보고, 몇 개를 돌았는지 찍는다.
- 유지·후퇴 기준은 **실험 전에 숫자로 선언**하고 그대로 따른다(LLM1의 72% 기준).
- 1회 측정으로 효과를 말하지 않는다. 조건당 세 번 재고, 같은 축인지부터 본다.
- LLM 채점은 **같은 회차 안의 순위**로 읽는다. 기본 채점기는 일반론에 관대하므로 엄격 채점을 따로 둔다. 채점의 방향은 봉인한 사람 대조로 잰다(16/16 일치, 7건 중 4건 누락 → 하한).
- 평균 다음엔 건 단위로 겹쳐 보고, 막히면 원문을 읽는다. 이상한 숫자는 그 숫자를 만든 행을 직접 연다.
- 함께 움직이는 두 변수로 원인을 하나로 단정하지 않는다("채널당"이 아니라 "바인딩당"이었다).
- 확인하지 못한 것은 목록으로 남긴다. 표본 0은 0%가 아니다.
