# 프로덕트 오너 — W07 · 2026-09-13 ~ 09-19

> **이번 주 요지** — 결정이 가장 많았던 주다. 큰 줄기는 넷이다.
> - **KB2 개량을 일단락했다.** 9/13에 트리 가독성 규칙 넷을 확인하고 "다음은 논문"으로 넘겼다.
> - **질문 하나로 새 로드맵이 열렸다.** "세무사가 보는 사전형 KB를 코사인 매칭하면 매칭률이 나쁘지 않겠나"라는 질문이 KB 3층 검색(P1~P8)이 됐다. 단계 승인, 원본 처리 방식, 코퍼스 확장 6규칙을 이 자리에서 정했다.
> - **AI 규범을 사람이 고치는 운영 모델을 세웠다.** 규범은 사람이 확정한다. 초안은 누구나 쓰고 확정은 세무사가 한다. 확정은 즉시 반영된다. 그 위에 인증 → 이의 기간 1일 → admin 브레이크의 순서와, 승인 문턱 2명을 정했다.
> - **프로덕션 디폴트 검색을 fusion으로 바꿨다.** "디폴트는 바꾸지 않는다"는 원칙이 "입증 전까지"의 조건부였음을 확인하고 통과선(fusion ≤ rag)과 되돌리기 조건을 정했다.
>
> 외부로는 세무사에게 규범 검토본 PDF를 보내 "수정 없음"을 받았고, 9/18에는 확인 대기 3건을 PDF + 엑셀 회신표로 묶었다. ICTC 2026 카메라레디는 마감 하루 전에 지면 제한을 4페이지로 정정하고 제출했다.

## KB 3층 검색 — 우선순위와 범위

### 질문에서 로드맵으로 (09-16)
질문은 이랬다. "auditor가 보는 KB는 질문 없이 정보만 있는 트리인데, 코사인 매칭을 그대로 적용하면 매칭률이 나쁘지 않겠나. 이런 사전형 정보를 참고해 답변하는 구조를 만들 수 있나." 답은 한 칸 앞선 사실이었다. 그 KB는 프론트 정적 시드라서 **검색 경로에 아예 없었다**(→ [KE](../3_지식엔지니어/KE_2026-09_W07_0913-0919.md)).

PO가 승인·확정한 것:
- **3층 구조 + RRF 순위 융합.** L0 규범은 검색하지 않고 system prompt에 상시 주입한다. 해석 원칙은 어떤 질문에든 적용되는 판단 규칙이라서다. L1 사전은 검색하고, L2는 현행 KB2다.
- **단계 순서 P1~P4.** P1 L0 규범층 → P2 RRF 융합기 → P3 L1 사전층 → P4 출처 라벨. 융합기 없이 사전층을 먼저 만들면 KB2와 경쟁만 한다.
- **불변 원칙.** 디폴트 `?ragSource=rag`는 어느 단계에서도 바꾸지 않는다. 병렬로 얹고 A/B로 비교한다.
- **P1 원본 처리 = (c) 백엔드 md**(같은 날 후속 지시). 결정타는 실측이었다. 규범 시드 전문이 17.4k자로 시스템 프롬프트(1,028자)의 17배라 요약이 필수다. 요약이 붙는 순간 (a) 빌드 시 JSON 내보내기의 유일한 편익(자동 동기화)이 사라진다. (b) DB 이관은 P3에서 하면 거의 공짜라 이월했다. "두 원본" 문제는 역할을 나눠 풀었다. 프론트 시드는 사람이 읽는 해설이고, 백엔드 md는 AI가 따르는 규범이다.
- **코퍼스 확장 6규칙**(메모리에 고정 지시). ① 계측 먼저 ② precision 감시 ③ 한 번에 한 소스 ④ 라이선스 확인 ⑤ 권위 등급 부여 ⑥ 소급 가능(삭제가 아니라 status 전환). "정보가 많을수록 좋다"는 직관이 RAG에서는 성립하지 않고, 계측 없이 넣으면 품질이 왜 변했는지 영영 알 수 없다.

### 규범은 사람이 확정한다 (09-16)
P1 규범 md 3종(1,314자)은 Claude(개발 도구)가 시드를 요약한 초안이었다. PO는 **"사람이 확정"** 으로 정했다. solar-pro3로 다시 쓰지 않는다. 세무사 검토본 PDF(3장 25항목, M/F/P 번호, 의견란)를 만들어 보냈고, **세무사 회신은 "수정 사항 없음, 확정"** 이었다. 이후 규범을 바꾸는 순서는 세무사 컨펌 → md → 점검 → 배포다. 사람이 규범을 검토·편집하는 화면은 P5로 로드맵에 올렸다. P1·P2 배포도 같은 날 승인했다.

### 엄격 채점 추가, 사전 컷 0.45 포함 (09-17)
- **엄격 채점 모드 추가.** 기본 채점기가 "어느 질문에나 통하는 일반 원칙" 청크에 관대해서, 점수 구간과 상관없이 등급2가 약 40%로 평평했다. 이대로는 사전층의 컷을 정할 수 없었다. 엄격 채점은 등급2를 "질문의 바로 그 지출·제도를 직접 다룸"으로 좁히고, 일반론은 최대 1점이다. 기본 채점은 P2 비교용으로 그대로 둔다.
- **kbdict 컷 0.45로 fusion 기본에 포함.** 어느 컷도 "useful 상승 + precision·noise 비악화"를 동시에 만족하지 못했다. 0.45는 이득 미입증이지만 무해했다. 그래도 넣은 근거는 넷이다. fusion은 디폴트가 아니다. 3층 구조가 실제로 돈다. 고득점 매칭만 들어간다. P4 라벨이 사전을 감싼다. 0.35(precision·noise 악화)와 컷 0(관대)은 기각했다.

### P6 확정 거버넌스 (09-17)
미리 정해 둔 것(재논의 금지): 순서는 **인증 → 이의 기간 → admin 브레이크**다. 이의 기간 1일에 디폴트 승인, 다수 승인이면 즉시 반영하는 빠른 길, 로그인 시 먼저 확인, admin은 경로 밖 브레이크, 인증이 간이 테스트를 번거롭게 하면 안 됨.

이번 세션에 물어 정한 것:

| 항목 | 결정 |
|---|---|
| 인증 범위 | 쓰기 API 전체, **챗 제외** |
| 이의 해제 | **이의 철회 또는 수정(→ 초안·재공개)으로만.** 승인 수는 이의를 이기지 못하고, admin이 판단하는 경로도 없다 |
| 로그인 알림 | **로그인 직후 팝업 + 사이드바 배지.** 대시보드 카드와 메일 발송은 채택하지 않음 |
| admin 권한 | **공개 중 제안 거부 + 확정본 즉시 롤백.** 긴급 단독 확정은 없음 |
| 승인 문턱 | 원래 3명 → **2명.** 데모 세무사 계정의 한계 때문에 낮췄다(설정값) |

엔지니어가 무난한 제안을 그대로 택한 것: 작성자와 공개자는 승인 집계에서 뺀다. 공개 중에 수정하면 결정과 타이머를 리셋한다. 로컬 우회 플래그 없이 토큰 헬퍼로 테스트한다. 세무사 1~2명의 초기 운영은 기한 만료 자동 반영으로 충분하다.

**남은 결정**: 승인 문턱 3으로 돌아갈 시점(세무사 실계정 수와 연동할지), 내 제안에 이의가 달리면 작성자에게 알릴지, 메일·대시보드 카드, 악성 방어(승인 자격·제안 빈도·diff 크기 상한), 챗 인증.

### 재적재 전에 원인부터 (09-18, P7)
- **코퍼스 분포 저장 = 원시 목록 + 개수 둘 다.** 개수만이면 "왜 그 청크가 들어왔나"를 못 되짚는다(0027의 교훈).
- **재적재 전에 혼입원부터 특정하라.** 재적재 안의 비용(retired 116건 부활, LLM 재분류, 벤치 기준선 무효, KB2 입력 변화)을 먼저 보고받은 뒤의 지시다. 결과는 기록된 혼입원이 틀렸다는 것이었고, 재적재는 필요 없어졌다(→ [KE](../3_지식엔지니어/KE_2026-09_W07_0913-0919.md)).
- **긴 지연은 재현까지만.** 120초 멈춤이 동시 호출의 산물로 판정됐고, 단일 사용자 조건에서는 멈춤이 없어 타임아웃 단축은 하지 않았다.
- rag 단독 혼입의 실질 해법인 **디폴트 fusion 전환은 PO 결정으로 넘어왔다.** 불변 원칙 1과 충돌하기 때문이다.

|---|---|
| 판정형 측정 통과선 | **fusion ≤ rag.** 혼입이 rag 이하이고 판정 모순이 fusion 쪽에서 늘지 않으면 전환한다 |
| 되돌리기 | **스모크 이상 즉시.** 배포 직후 스모크에서 오류·빈 근거·판정 불일치가 나오면 서버 설정 한 줄을 지우고 재시작한다. 그 뒤로는 실사용 턴이 쌓일 때 `rag.chat_turns`로 다시 판정한다(자동 조건 없음) |
| 원칙 갱신 | 디폴트 rag 불변 원칙은 "입증 전까지"의 조건부였고 충족됐다. **"디폴트 전환은 벤치·혼입 근거로 판정한다"** 로 바꿨다 |

판정형 192회에서 fusion ≤ rag(혼입 2 vs 2, 법리 모순 2 vs 6)로 통과했고, **9/18 11:09 KST에 프로덕션 디폴트가 fusion이 됐다.** 측정은 → [EV](../7_평가검증/EV_2026-09_W07_0913-0919.md).

「후일담」 10/6 프로덕션 챗은 KB3 단독(`RAG_SOURCE=kb3`)으로 다시 전환됐다.

### 전시 동시 부하 (09-18, P8 B)
- 프로덕션 부하 N=1·2·3·4(배포 전)와 N=4·6·8(배포 후)를 승인했다.
- **챗 턴당 대기 합계 30초.** 넘으면 HTTP 200 + 안내 1문장 + `meta.congested`다. 500이면 프론트가 오류로 던진다.
- **백그라운드 Upstage 호출도 같은 게이트, FIFO.** KB2 재구조화·분류·적재 임베딩에 우선순위를 두지 않는다.
- **쓰기 타임아웃 단축은 안 한다.** 측정을 보고 정하기로 했고, 게이트 후 216턴 멈춤 0으로 근거가 사라졌다.
- **인프라 이전(Oracle A1)은 다음 주 이후로 보류.** → 이어서: 9/24에 이전했다(W08).

### 엔진 복리후생비 — 증빙과 근거 문구 (09-18)
- **필요증빙은 조건부 항목**으로 정했다. 사내규정 / 지급·이용 대장 / 현금·상품권 지급 시 근로소득 원천징수 / 시설·회원권 이용 시 사업자 명의 계약. 엔진이 모든 복리후생비(명절 떡값 포함)에 "회원권 명의"를 요구하던 헬스장 사안 잔재를 걷어 냈다.
- **카드↔본문 불일치는 "맞는 쪽으로 일치".** 법리를 교차확인해 보니 맞는 쪽은 카드의 판정·금액(전부인정)이었다. 엔진 근거 문구가 계정을 "복리후생비"로 단정한 것이 틀렸다. 문구만 고치고 판정·금액은 그대로 뒀다. 이 문구의 법리는 세무사 최종 확인 대기다(요청 02).

### 날조 수치 — 값을 고치지 않고 빼고 묻는다 (09-18, P8 C)
판정형 답변이 접대비 한도를 64회 중 23회 근거 없이, 회차마다 다른 값으로 말했다. 대응은 **사후 검출 + 규칙 한 줄**로 정했고 자문 경로에도 적용했다. 가드는 값을 고치지 않는다. 문장을 빼고 확인 안내를 붙인다. **어느 값이 맞는지는 세무사 몫**이기 때문이다. 필요한 법정 수치(접대비 한도 등)는 세무사에게 받아 L0 규범 초안 → 세무사 승인(P6 절차)으로 넣는다(요청 03). → [AIE](../2_AI엔지니어/AIE_2026-09_W07_0913-0919.md)

### KB2 오류 후보 — 확인분만 은퇴, 나머지는 세무사에게 (09-18)
KB2 문장이 오류로 지적된 [AI 답변]을 옮겨 적은 경우가 최소 30건 나왔다. PO는 법리 오류 1건(업무용승용차 1,500만원 한도를 거꾸로 쓴 문장)을 세무사에게 공유해 수정이 필요하다는 확인을 받았다. 처리는 **확인분만 은퇴 + 목록 전달**로 정했다. 법률 판단은 세무사가 한다. 합성 근본 수정은 어느 쪽이든 한다. 31건 반영(D)은 세무사 회신 뒤 재구조화 시점과 함께 정하기로 하고 대기시켰다.
