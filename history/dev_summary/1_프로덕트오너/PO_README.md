# 1. 프로덕트 오너

## 개요

**무엇을 만들지 정하고, 세무 도메인과 운영 규칙의 주인이 되는 사람이다.**
이 제품은 병의원 사장님이 세무 질문을 하면 AI가 답하고, 세무사가 그 답을 검수해 지식으로 되돌리는 구조다.
그 고리 위의 규칙이 전부 이 자리에서 나온다. 무엇을 판정하고 무엇은 판정하지 않을지, 세무사의 기여를 어떻게 세고
정산할지, 어떤 정보를 누구에게 보여 줄지가 그런 규칙이다.

소규모 팀에서는 **대표가 겸하는 경우가 많다.** 이 프로젝트에서도 원문에 "결정 (사용자)"로 적힌 것과
AskUserQuestion으로 고른 것은 전부 이 자리에서 나왔다.

## 역할

| 축 | 하는 일 |
|---|---|
| **도메인 정책** | 세목 분류 체계, 규범(AI가 지켜야 할 상담 원칙), 판정 범위, 답하지 않을 자리를 정한다 |
| **운영 모델** | 검수 두 게이트, 기여 = RAG 존속기간, 정산 = 수익% × 기여비율, 규범 확정 거버넌스(문턱·이의 기간), 동의·마스킹을 정한다 |
| **우선순위·범위** | 로드맵 순번을 정하고, "그건 묻던 질문이 아니었다"고 정정하며, 지금 안 할 일(은행 연동, 로컬 GPU 등)을 선언한다 |
| **외부 대응** | 대회 인프라 수요조사와 심사에 대응하고, 세무사에게 검토를 요청하고, 팀 공유 문서를 만든다 |
| **실사용 피드백** | 프로덕션 화면을 직접 써 보고 디테일을 지적한다 |

## 다루는 것

- `docs/doing/*.md` — 로드맵·설계 마스터(현재 기준의 정본)
- 팀 공유 PDF(인프라 의사결정 보고서, 정산 프로세스, 3층 검색 로드맵, 규범 세무사 검토본)
- 운영 계정(owner·auditor·admin)으로 프로덕션 화면을 직접 사용

## 다른 포지션과의 계약

- **→ AI·지식 엔지니어**: 정책은 **이름과 정의**로 넘긴다(예: 세목 17개와 각각의 설명 문장). 엔지니어가 그 설명을 프롬프트와 화면에 옮겨 적으면 분류 기준과 화면 기준이 갈리지 않는다.
- **← AI·지식 엔지니어**: 판단의 근거로 **실측 분포와 천장**(커버리지, 벤치 점수, 오라클 상한)을 받는다. 천장을 모르고 목표를 잡으면 오지 않을 회차를 기다리게 된다.
- **→ 백엔드**: 운영 규칙은 **DB에서 강제될 수 있는 모양**으로 정한다(예: pool은 계산 전용·수정 불가, 대기 제안은 1건만).
- **→ 프론트엔드**: 화면은 실제로 써 보고 지적하는 방식으로 다듬는다. 대개 한 번에 여러 건이 나온다.

## 이 자리에 필요한 역량

세법의 큰 지형에 대한 감각(판정형 질문과 자문형 질문의 차이), 운영 규칙을 숫자와 상태 전이로 말하는 능력,
그리고 **"지금 안 한다"를 분명히 적는 습관**.
