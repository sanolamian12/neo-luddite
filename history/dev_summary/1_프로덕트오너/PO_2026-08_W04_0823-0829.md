# 프로덕트 오너 — W04 · 2026-08-23 ~ 08-29

> **이번 주 요지** — 운영 모델의 빈칸 두 개를 메웠다. 첫째, **KB를 수정해도 크레딧은 원작성자에게 남는다.** 둘째, **정산 pool은 총수익 × 분배비율에서만 나오고 손으로 덮어쓸 수 없다.** 도메인 쪽에서는 **세목 17개**를 확정했다. 대회 인프라 조사에는 "GPU 미신청, 200GB"로 답했다. 가장 값진 개입은 질문을 고친 것이다. 팀이 "GraphRAG로 검색 엔진을 바꿀까"를 검토하고 있을 때, 이 로드맵은 "세무사가 KB를 보고 고치는 중간층"을 만들려고 시작한 것이라고 바로잡았다. 주 후반에는 프로덕션 화면을 직접 써 보며 지적 9건을 냈다.

## 운영 모델

### 기여 정책 — 수정해도 크레딧은 원작성자에게 (08-27)
세무사가 기존 KB passage를 수정하면 크레딧을 누구에게 어떻게 줄지 AskUserQuestion으로 정했다. 선택지 4개 중에서 **"원작성자 유지 + 수정 이력만 기록"** 을 골랐다.
- 크레딧이 이동하거나 분할되지 않는다.
- 정산 로직(`contribution_counts`, 활성 passage 수를 auditor_id로 센다)을 전혀 건드리지 않아도 된다.
- 제안은 즉시 반영되지 않는다. pending 동안 원문이 그대로 검색되고, admin이 승인할 때 반영된다. 승인 화면에 "존속기간 기여는 원작성자에게 그대로 남는다"를 적었다.

### 정산 — 수익과 연결된 pool (08-27)
요청은 "관리자가 수익을 입력하면 세무사에게 정산·입금확인이 가는 프로세스"였다. ledger, 정산 회차, 인앱 메일은 이미 PoC로 돌고 있었고, 빠진 것은 pool이 수익과 연결되지 않은 임의 숫자("cr")라는 점 하나였다. 정한 것은 셋이다.

| 정한 것 | 내용 |
|---|---|
| pool 산식 | `pool = floor(총수익(원) × 분배비율(%) / 100)` → 세무사별 활성 기여 비율로 분배(분배 방식은 종전과 같다) |
| pool은 계산 전용 | 관리자가 pool이나 개별 분배액을 덮어쓸 수 없다. 합계를 검증하는 로직이 없어도 분배 합이 항상 pool과 같도록(AskUserQuestion으로 확인) |
| 범위 밖 재확인 | 실제 은행 연동, 실제 이메일·SMS 발송. 7/14에 이어 **두 번째로 같은 결론** |

## 우선순위 · 범위

### 질문을 고치다 — GraphRAG가 아니라 "중간층" (08-28)
팀은 로드맵 §3.5를 "GraphRAG로 검색 엔진(`match_passages`)을 교체할지"로 읽고 비채택을 재확인했다. PO가 정정했다.

> 이 로드맵을 시작한 진짜 동기는 검색 엔진 교체가 아니라, **세무사와 RAG/KB 사이에 중간층을 두어 KB가 어떻게 구성되는지 시각적으로(거미줄 그래프, 줌인·줌아웃) 확인하고 필요하면 직접 수정할 수 있게 하는 것**이다.

"검색 엔진 교체 비채택"은 여전히 맞는 결론이었다. 다만 애초에 묻던 질문이 아니었다. 정정 뒤 두 가지를 확인했다.
- edge는 **배치로 미리 계산해 저장**한다. 전체 KB를 한 화면에 그리기 위해서이고, 나중에 exact scan을 완화할 때도 재사용할 수 있다.
- 렌더는 **d3-force + 커스텀 SVG**로 한다. 기존 방사형 상세뷰와 스타일을 맞추고, 무거운 그래프 라이브러리는 들이지 않는다.

또 "기존 루트로 새 지식이 배선될 때마다 재계산이 필요하지 않겠냐"는 질문으로 edge 신선도 문제를 짚었다. 이 지적은 4개 적재 경로의 즉시 재계산으로 반영됐다.
