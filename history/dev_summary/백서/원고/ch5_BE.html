백엔드·인프라 엔지니어

DB 규칙·권한·외부 LLM 호출·배포·서버를 맡는 사람

이 장은 DB 스키마와 권한 정책을 짜는 사람, 외부 LLM API를 부르는 서버를 운영하는 사람, 배포 경로와 서버 한 대를 책임지는 사람을 위한 것이다. 사례는 한 AI 세무 상담 챗봇에서 나왔다. 사장님이 세무 질문을 하면 LLM이 근거 지식을 찾아 답한다. 이렇게 검색한 근거를 프롬프트에 넣어 답하게 하는 방식을 RAG(검색 증강 생성)라고 한다. 세무사는 그 답을 검수하고, 검수 결과는 다시 지식으로 들어간다. 모델은 국내 LLM API 하나만 썼다. 프론트는 호스팅 서비스에, 파이썬 백엔드는 클라우드 VM 한 대에, 데이터와 인증은 관리형 Postgres(Supabase)에 있다. 이 자리의 실수는 대개 성공 응답을 낸다. 권한에 막힌 쓰기는 오류 대신 「0행 갱신」으로 끝난다. 권한 없는 삭제 API는 200을 돌려준다. 프론트만 배포된 날에도 화면은 잘 뜬다. 두 번 재시도한 호출은 「느린 성공 한 건」으로 기록된다. 모두 그럴듯하다. 그래서 이 장은 매번 같은 질문으로 돌아간다. 이것이 그럴듯하게 틀렸다면, 누가 언제 알아챌까? 첫 태그가 백엔드인 교훈 48개 가운데 모든 직무 공통인 21개는 1장이 주인이다. 여기서는 나머지 27개를 일곱 갈래 25개 원칙으로 묶고, 공통 교훈은 필요한 자리에서만 짧게 짚는다. 일곱 갈래는 DB가 강제하는 규칙, 데이터를 바꾸는 경로와 상태값, 오류 없이 비는 SQL, 외부 LLM API 운영, 둘 이상의 배포 자리, 인프라의 수요와 비용, 장시간 작업의 환경이다.

이 장의 원칙

  1. 「한 번에 하나만」 같은 운영 규칙은 앱 코드가 아니라 DB 제약에 맡긴다
  2. 보안·정합 불변식은 DB 함수와 트리거 하나로 몰고, 표시는 화면이 정한다
  3. 권한 축소는 정책만이 아니라 권한을 여는 데이터의 수명까지 본다
  4. 권한 정책이 부르는 함수는 비로그인에서도 실행되게 두고 거짓을 돌려준다
  5. 쓰기·삭제의 성공은 응답 코드가 아니라 대상의 실제 상태로 판정한다
  6. 파생 데이터는 모든 쓰기 경로에서 즉시 갱신하고, 주기 작업은 안전망으로 둔다
  7. 데이터를 바꾸는 경로는 늘리지 않는다 — 조회는 넓게, 기본 선택은 좁게
  8. 상태값을 새로 만들면 그 값을 걸러야 할 쿼리를 전부 함께 본다
  9. 연결 칼럼을 믿지 말고 실제 채움 상태와 대상 밖 겹침을 센다
  10. 순번은 그것을 매기는 쪽이 하나일 때만 순서를 말한다
  11. 상태 전이는 마이그레이션 승인 전에 실DB 롤백 트랜잭션에서 끝까지 돌린다
  12. 암묵 상태에 기대지 말고 문장을 나누거나 즉시 변수로 잡는다
  13. 외부 LLM 호출은 호출 단위 번호표 게이트로 막고, 혼잡은 정상 응답으로 알린다
  14. 스레드를 붙이면 SDK가 늦게 불러오는 모듈을 미리 불러 둔다
  15. 처리 경로는 실행한 컴포넌트에서 기록하고, 전환 전후는 시각으로 가른다
  16. 새 경로는 스위치로 끌 수 있게 하고, 끄면 기존 경로와 똑같게 만든다
  17. 계약 변경은 서버가 옛·새 클라이언트를 함께 받는 중간 단계를 거친다
  18. 배포·설정 자리가 둘 이상이면 「조용한 반쪽」을 점검 목록에 넣는다
  19. 브랜치를 올릴 때는 딸려 가는 커밋과 그것이 부를 배포를 먼저 본다
  20. 같은 앱을 한 번 더 띄우기 전에 프로세스 안 싱글톤을 목록으로 뽑는다
  21. 스모크가 실패하면 요청이 서버 로직에 닿았는지부터 본다
  22. 인프라 수요는 코드의 실제 의존성과 실측 병목으로 답한다
  23. 클라우드 비용은 무료 한도를 먼저 빼고, 견적이 아니라 실측으로 확정한다
  24. 다른 설정이 참조하는 값을 먼저 확정하고, 콘솔 표시보다 실상태를 믿는다
  25. 장시간 작업은 낮에 돌리고, 진행은 작업 전체를 합산해 센다

5.1 규칙은 DB가 강제한다

이 제품에는 사장님·세무사·관리자 세 역할이 있고, 화면마다 보이는 범위가 다르다. 그런데 화면이 보여 주지 않는 것과 DB가 막는 것은 다르다. Supabase는 브라우저가 DB에 거의 직접 붙는 구조라서, 화면을 건너뛰고 API를 부르면 DB가 허락한 만큼 다 보인다. 그래서 행마다 「이 사용자가 이 행을 보거나 바꿀 수 있는가」를 DB가 판정하는 행 수준 보안(RLS, Row Level Security)이 실제 경계가 된다. 이 절의 원칙은 하나의 뿌리에서 나온다. 클라이언트가 규칙대로 부르는 동안에는 어느 층에 규칙을 두든 똑같이 동작한다. 차이는 누군가 규칙을 건너뛸 때만 난다. 접근 범위를 역할별 토큰으로 직접 불러 세는 일 자체는 모든 직무의 원칙이다→ 1.5.

「한 번에 하나만」 같은 운영 규칙은 앱 코드가 아니라 DB 제약에 맡긴다

운영 규칙 가운데 「대기 중인 제안은 하나만」「같은 대화에 확정은 한 번만」처럼 개수와 유일성을 말하는 것은 DB 제약으로 적을 수 있다. 앱 코드로 막으면 두 요청이 거의 동시에 들어오는 순간 둘 다 통과한다. 이런 경합은 드물어서 화면 검사로는 안 나온다. 생기면 어느 쪽이 반영될지 아무도 모른다. 부분 유일 인덱스(조건을 만족하는 행 사이에서만 유일성을 거는 인덱스)는 이런 규칙에 잘 맞는다. 지식을 바꾸는 일은 큐를 거치게 하고, 승인 전까지는 원문이 그대로 검색되게 둔다.

사례 · 지식 수정 제안

세무사는 지식 조각(검색 단위가 되는 짧은 글. 이하 「지식 조각」)을 화면에서 보다가 고칠 점을 제안할 수 있다. 무슨 일이 제안을 대기 큐 테이블로 받고, 관리자가 승인할 때 다시 임베딩(글을 검색용 숫자 벡터로 바꾸는 일)하게 했다. 같은 지식 조각에 대기 제안이 둘 쌓이면 어느 쪽이 이길지 정해져 있지 않았다. 왜 몰랐나 두 세무사가 같은 조각을 동시에 고치는 일은 데모에서 한 번도 일어나지 않았다. 잡은 방법 구현 단계에서 미리 막았다. 부분 유일 인덱스로 지식 조각당 대기 제안을 1건으로 묶었다. 실DB에서 제안 → 반려, 제안 → 승인(실제 재임베딩) → 원복까지 돌려, 검토자와 원작성자 기록이 그대로임을 확인했다.

보안·정합 불변식은 DB 함수와 트리거 하나로 몰고, 표시는 화면이 정한다

「이 메시지를 보낸 사람은 누구인가」「이 방은 수락 뒤에만 열린다」 같은 불변식은 클라이언트가 보낸 값을 믿지 않는 자리에 둔다. 보낸 사람·역할·시각은 트리거가 호출자에게서 정하고, 클라이언트 값은 무시한다. 여러 단계가 함께 일어나야 하는 일(비식별 마스킹, 동의, 공용 풀 등재)은 DB 함수 하나로 묶어 중간에 끊길 자리를 없앤다. 내부 함수는 사용자가 직접 부를 수 없게 막는다. 반대로 「무엇을 그릴지」는 화면이 정한다. 권한은 DB가, 표시는 화면이 맡고 두 층을 섞지 않는다. 그리고 판정은 함수 하나에 모은다. 열람 판정이 정책마다 흩어져 있으면 한 곳만 고쳐진다.

사례 · 인앱 상담 방

사장님이 세무사에게 직접 상담을 신청하면, 세무사가 수락한 뒤 둘만의 대화 방이 열린다. 대화는 비식별을 거쳐 다른 세무사도 참고할 수 있는 공용 풀에 올라갈 수 있다. 무슨 일이 설계 단계에서 「원문을 풀로 빼낼 경로」와 「다른 사람 이름으로 메시지를 보낼 경로」를 하나씩 따졌다. 클라이언트가 보낸 사람 id를 적어 보내게 두면 누구든 남을 사칭할 수 있었다. 왜 몰랐나 우리 화면은 늘 자기 id를 보낸다. 규칙을 지키는 클라이언트만 있으면 어느 설계든 똑같이 동작한다. 잡은 방법 마스킹·동의·등재를 DB 함수 하나로 묶었다. 방 개설은 수락 전이 안에서만 일어나는 함수로만 하게 하고, 동시 방 수 상한을 넘으면 수락까지 되돌리게 했다. 보낸 사람·역할·시각은 트리거가 정한다. DB 시험에 「사칭 불가」와 「내부 함수 직접 실행 불가」를 넣었다. 한편 관리자에게는 RLS상 본문 열람이 열려 있지만, 사적 대화라는 대표의 판단으로 화면이 본문을 그리지 않게 했다. 권한은 DB, 표시는 화면이라는 분업의 실례다.

권한 축소는 정책만이 아니라 권한을 여는 데이터의 수명까지 본다

RLS 정책은 대개 「이 사용자가 이 데이터와 어떤 관계인가」를 다른 테이블에서 찾는다. 그러면 권한의 실제 범위는 정책 문장과 그 관계 데이터의 곱이 된다. 정책을 좁혀도, 관계 데이터가 닫히지 않고 쌓여 있으면 범위는 그대로다. 축소 전에 기대 효과를 숫자로 계산해 두고, 적용 뒤 실측과 맞춘다. 숫자가 덜 줄었으면 정책이 아니라 데이터를 본다. 권한을 여는 데이터에는 닫히는 절차를 둔다. 닫기는 일회성 SQL(또 쌓인다)도 자동 실행(운영자가 못 막는다)도 아닌, 데이터 손실이 없고 되돌리기 쉬운 운영 버튼으로 만든다.

사례 · 대화 열람 축소

세무사에게는 검수할 대화를 묶음으로 배정하는데, 이 묶음을 「일감」이라고 불렀다. 무슨 일이 세무사 토큰으로 API를 직접 불러 보니 대화 218건 전부를 본문까지 읽을 수 있었다→ 1.5. 정책을 좁혀 「검수 이력이 있거나, 열린 일감에 실린 대화」만 보이게 했다. 그런데 실측은 218 → 206건으로 거의 그대로였다. 왜 몰랐나 정책은 맞게 바뀌었다. 문제는 정책이 참조하는 데이터였다. 마감이 7월에 지났는데 열린 채 남은 100건짜리 일감 2개(와 진행 중 4개)가 「열린 일감」 조건으로 대부분을 열어 주고 있었다. 일감에는 「마감이 지나면 닫는다」는 절차가 아예 없었다. 잡은 방법 축소 때 「일감 조건을 빼면 170~194건」이라는 기대값을 계산해 둔 덕에 차이를 바로 알아봤다. 일감을 닫는 운영 버튼을 만들어 닫자 정확히 그 값(170/193/194)이 나왔다.

권한 정책이 부르는 함수는 비로그인에서도 실행되게 두고 거짓을 돌려준다

Supabase Realtime은 DB 행이 바뀔 때 구독한 클라이언트에게 이벤트를 밀어 주는 기능이다. 이벤트를 누구에게 보낼지는 RLS로 거른다. 이때 정책은 구독을 건 시점의 토큰으로 평가된다. 그래서 로그인 전 비로그인(anon) 상태로 붙은 채널은 로그인한 뒤에도 그 사람의 행을 받지 못한다. 더 나쁜 함정은 반대쪽에 있다. 정책이 부르는 함수에서 anon 실행 권한을 빼면, anon 구독자에 대한 평가가 권한 오류를 낸다. 그러면 그 이벤트가 그 구독자뿐 아니라 모두에게서 통째로 사라진다. 「권한을 줄이는 쪽이 안전하다」는 직관이 다른 구독자 전체를 끊는다. 정책 함수는 anon 실행 권한을 남기고, 호출자가 없으면 거짓을 돌려주게 짠다. 인증 상태가 바뀔 때마다 채널을 새 토큰으로 갈아 끼운다.

사례 · 실시간 메시지

무슨 일이 상담 방에서 사장님이 보낸 메시지가 세무사 화면에 오지 않았다. 모든 페이지가 로그인 전에 anon으로 한 번 구독하는데, 메시지 정책이 부르는 「방 구성원인가」 함수에서 anon 실행 권한을 빼 두었다. 왜 몰랐나 오류가 화면 어디에도 나오지 않았다. 서버 쪽 Node 클라이언트 하나로 시험하면 이벤트가 잘 왔다. 잡은 방법 anon 구독자를 하나 붙였을 때와 안 붙였을 때를 나란히 돌려, anon 하나가 붙으면 로그인한 세무사도 못 받는다는 것을 확정했다. 함수 권한을 되돌리고, 함수 안에서 호출자가 없으면 거짓을 돌려주게 했다. 구독 상태 신호가 「연결됨」이어도 실제 수신이 시작되지 않는 문제 같은 화면 쪽 이야기는 → 6장.

쓰기·삭제의 성공은 응답 코드가 아니라 대상의 실제 상태로 판정한다

권한 층은 막을 때 오류를 내지 않는 경우가 많다. RLS 아래의 UPDATE는 「0행 갱신」으로 끝나고→ 1.6, 어떤 스토리지 API는 권한이 없어도 200과 빈 배열을 돌려준다. 그래서 권한 정책은 SQL이 아니라 실제 사용자가 지나는 API 경로로, 역할별로 실측한다. 삭제가 성공했는지는 응답이 아니라 대상이 사라졌는지로 본다. 파일을 교체 업로드할 때는 새 파일 저장이 확정된 뒤에만 옛 파일을 지운다.

사례 · 프로필 사진 저장소

무슨 일이 세무사 프로필 사진을 저장하는 버킷에 「본인 폴더만 쓰고 지운다」는 정책을 걸었다. 그런데 스토리지의 일괄 삭제 API는 권한이 없어도 200과 빈 배열을 돌려줬다. 저장소 객체 테이블에 SQL DELETE를 하면 트리거가 막아서, 정책을 SQL로 검증할 수도 없었다. 왜 몰랐나 응답 코드가 성공이었다. 남의 사진을 지우려다 실패해도, 내 사진을 지우는 데 성공해도 똑같아 보였다. 잡은 방법 역할별로 실제 스토리지 API 경로를 불러 7항목을 실측했다(남의 폴더 업로드 403, 본인 삭제 200 뒤 실제로 사라짐 등). 교체 업로드는 새 객체가 저장된 뒤에 옛 객체를 지우게 했다.

5.2 데이터를 바꾸는 경로와 상태값

이 제품의 지식은 계속 바뀐다. 세무사의 코멘트가 확정되면 지식 조각이 생기고, 철회되면 빠지고, 수정이 승인되면 다시 임베딩된다. 그 위에 지식 사이의 연결 그래프, 기여 집계, 분류 같은 파생 데이터가 얹힌다. 데이터를 바꾸는 경로가 여럿이면 후속 처리가 한 경로에서만 빠진다. 새 상태값을 만들면 그 값을 몰라야 할 쿼리가 다른 파일에서 그 값을 집어 간다. 이 절의 실수는 만든 자리에서는 잘 동작한다는 공통점이 있다. 틀린 것은 늘 다른 자리에 있다.

파생 데이터는 모든 쓰기 경로에서 즉시 갱신하고, 주기 작업은 안전망으로 둔다

파생 데이터를 주기 작업만으로 갱신하면 「언젠가는 맞는다」. 낡은 구간이 짧아서 테스트에서는 안 보이지만, 방금 확정한 지식이 화면에 안 보이는 순간 사용자는 기능이 고장 났다고 읽는다. 원본을 바꾸는 쓰기 경로를 전부 나열하고, 각 경로의 응답 직전에 갱신을 부른다. 이 갱신은 실패해도 본 동작을 막지 않는다(best-effort). 수동 DB 조작처럼 경로 밖에서 일어난 변경은 주기 작업이 잡는다. 둘은 대체 관계가 아니라 역할 분담이다.

사례 · 지식 연결 그래프

세무사가 지식 전체를 거미줄 그래프로 보고 직접 고칠 수 있게, 지식 조각 사이의 연결선을 DB에 저장했다. 무슨 일이 연결선은 DB의 예약 작업 기능(pg_cron)으로 5분마다만 다시 계산했다. 그래서 지식이 적재된 직후 최대 5분 동안 그래프가 낡았다. 왜 몰랐나 주기 작업이 돌고 있으니 결국 맞았다. 테스트는 5분을 기다리지 않았다. 잡은 방법 대표가 「새 지식이 붙을 때마다 다시 계산해야 하지 않느냐」고 물었다. 수백 건 규모에서 전체 재계산이 1초도 안 걸리는 것을 확인하고, 지식 상태를 바꾸는 네 경로(코멘트 적재, 총평 적재, 철회, 수정 승인) 모두에서 응답 직전에 재계산을 부르게 했다. 5분 주기 작업은 안전망으로 남겼다.

데이터를 바꾸는 경로는 늘리지 않는다 — 조회는 넓게, 기본 선택은 좁게

일괄 정리 같은 새 작업에 전용 삭제 API를 만들면 처음에는 편하다. 그러나 기존 경로에 붙어 있던 후속 처리(그래프 재계산, 기여 집계)를 빠뜨리기 쉽다. 데이터를 바꾸는 경로를 최소로 유지해 후속 처리가 한 곳에 붙게 한다. 위험한 일괄 작업은 서버가 후보를 넓게 보여 주고, 화면의 기본 선택만 보수적으로 둔다. 사람이 「비슷하지만 정당한」 경우까지 훑어볼 수 있어야 하기 때문이다. 같은 일을 하는 로직이 두 경로에 따로 있으면 한쪽이 조용히 데이터를 버린다는 일반 원칙은 → 1.5에서 다룬다.

사례 · 중복 지식 정리

무슨 일이 같은 내용의 지식 조각이 여러 번 쌓인 것을 소급해 정리해야 했다. 새 삭제 경로를 만들지 않고 기존 철회 API를 재사용했다. 백엔드의 중복 후보 조회는 의미 유사도로 넓게 두고, 프론트의 기본 체크만 「같은 대화의 같은 구간을 다시 제출한 것」으로 좁혔다. 왜 몰랐나 전용 API를 만들었어도 삭제 자체는 잘 됐을 것이다. 빠지는 것은 연결 그래프와 기여 집계뿐이고, 그것은 다른 화면에서 한참 뒤에 드러난다. 잡은 방법 구현 판단으로 막았다. 관리자는 넓은 후보를 훑어보고, 기본 체크된 것만 확정했다.

상태값을 새로 만들면 그 값을 걸러야 할 쿼리를 전부 함께 본다

새 status 값은 만든 자리에서는 잘 동작한다. 그 값을 걸러야 할 WHERE는 다른 파일에 있다. 상태값을 새로 만들거나 기존 값을 재사용할 때는 세대교체·복구·상태 전환 쿼리를 전부 함께 읽는다. 기존 값에 이미 다른 뜻이 있으면 재사용하지 않는다. 재사용하면 그 뜻에 걸린 모든 동작이 새 데이터에도 걸린다. 화면 키도 뜻이 다르면 나눈다.

사례 · 지식 사전의 세대교체

한때 검수 지식을 세목별로 묶어 문장 단위로 다시 쓴 「지식 사전」을 따로 두었다. 이 사전은 재구조화할 때마다 통째로 새로 만들고, 옛 세대는 「보관」 상태로 내린다. 무슨 일이 어느 세목에도 들어가지 않는 잔여물을 담을 「기타」를 새로 만들어야 했다. 세대교체 함수는 「활성」 상태만 보관으로 내린다. 그래서 「기타」를 그 함수에 넣지 않으면 회차마다 죽은 「기타」가 쌓일 판이었다. 반대로 「기타」에 기존의 「끊김(사람이 내린)」 상태를 재사용하면, 세목 재연결 버튼 한 번에 182건이 검색에 들어오고 「사람이 끊었다」는 이력 배지가 기계가 만든 문서로 오염될 판이었다. 왜 몰랐나 두 실수 모두 「기타」를 만드는 코드 안에서는 보이지 않는다. 잡은 방법 설계 단계에서 상태 전환 쿼리를 훑었다. 분류 쪽에서 같은 모양의 잔해(활성 분류 31개 대 실제 17개)를 이미 실측으로 잡은 적이 있었다. 「기타」에는 새 상태값을 주고, 세대교체 함수에 넣었다.

연결 칼럼을 믿지 말고 실제 채움 상태와 대상 밖 겹침을 센다

스키마에 외래키 칼럼이 있으면 그 칼럼으로 연쇄 삭제하면 될 것처럼 보인다. 그런데 그 칼럼이 실제로 채워져 있는지는 스키마가 말해 주지 않는다. 값이 전부 NULL이면 연쇄 삭제는 조용히 0건을 지운다. 그래서 다른 키 조합으로 매칭하면, 이번에는 그 조합이 대상 밖 레코드와 겹쳐 남의 데이터를 함께 지운다. 연쇄 삭제 전에 연결 칼럼의 채움 상태를 실측하고, 대체 키로 매칭할 때는 대상 밖 겹침을 따로 센다. 프로덕션 삭제의 전체 절차(영향 재확인 → 백업 → 행 수 검증 → 커밋)는 모든 직무의 원칙이다→ 1.6.

사례 · 미확정 검수 삭제

무슨 일이 프로덕션에서 미확정 검수 기록을 지우면서, 검수 한 건에 딸린 문장별 코멘트를 함께 지워야 했다. 코멘트 테이블에는 검수 id 칼럼이 있었다. 그런데 567건 전부가 NULL이었다. 설계상 코멘트는 「대화 id + 평가자 id」로만 검수와 이어져 있었다. 왜 몰랐나 칼럼 이름이 연결을 약속하고 있었다. 그 칼럼으로 지웠다면 에러 없이 0건이 지워졌을 것이다. 잡은 방법 삭제 전 사전 안전 확인 네 가지 중 하나로 칼럼 값을 실측했다. 대상 검수들의 (평가자, 대화) 쌍으로 매칭하고, 그 쌍이 대상 밖 검수와 겹치는 경우가 0건임을 따로 센 뒤에 지웠다.

순번은 그것을 매기는 쪽이 하나일 때만 순서를 말한다

메시지 순번처럼 정렬에 쓰는 값을 두 쪽이 따로 매기면 언젠가 같은 값이 나온다. 그때 「순번이 가장 큰 것이 직전 메시지」라는 가정이 깨진다. 안정 정렬(같은 키끼리는 들어온 순서를 지키는 정렬)이 우연히 순서를 지켜 주는 동안에는 드러나지 않는다. 여러 쪽이 매기는 순번은 믿지 말고 목록 위치로 순서를 찾는다. 이런 결함은 2턴짜리 시험에서는 안 보이니, 여러 턴에 걸친 기능은 3턴 이상 시나리오로 시험한다.

사례 · 되묻기 상태

새 상담 흐름에서는 질문을 받은 앞단 모델이 판단에 필요한 사실이 빠졌으면 사장님에게 되묻는다. 「지금 무엇을 되묻는 중인가」는 직전 메시지에 실어 둔다. 무슨 일이 프론트는 사용자 메시지에 대화 길이를, 서버는 답변 메시지에 「최대 순번 + 1」을 매겼다. 그래서 2턴부터 두 메시지가 같은 순번이 됐다. 「순번 최대값 = 직전 메시지」로 상태를 찾다가 3턴째에 되묻기 상태가 사라졌다. 왜 몰랐나 기존 흐름도 순번으로 정렬했지만 안정 정렬이라 우연히 맞았다. 2턴 시험은 통과했다. 잡은 방법 3턴 시나리오에서 상태가 사라지는 것을 보고 찾았다. 직전 메시지는 순번이 아니라 목록의 마지막 위치로 찾게 바꿨다.

5.3 오류 없이 비는 SQL — 마이그레이션과 상태 전이

마이그레이션(스키마를 바꾸는 SQL 묶음)과 상태 전이 로직의 실수는 대개 문법 오류가 아니다. 문장은 실행되고, 갱신 대상만 빈다. 단위 테스트와 가짜 저장소로는 실제 스키마·제약과의 충돌이 안 보인다. 그렇다고 프로덕션에서 시험하면 시험이 곧 운영 데이터 변경이 된다. 이 절의 원칙은 그 사이에 실DB 롤백 트랜잭션이라는 시험대를 두는 것이다. 쓰기만 막고 진짜 함수를 부르는 드라이런, 이름과 날짜 상수를 카탈로그로 조회하는 습관은 모든 직무의 원칙이다→ 1.4 · 1.6.

상태 전이는 마이그레이션 승인 전에 실DB 롤백 트랜잭션에서 끝까지 돌린다

상태를 바꾸는 기능은 시험이 곧 운영 데이터 변경이다. 그렇다고 가짜 저장소로만 시험하면 실제 제약·트리거·스냅샷 규칙과의 충돌을 놓친다. 데이터 접근 층의 트랜잭션·커넥션 함수를 단일 커넥션과 세이브포인트로 바꿔 끼운다. 그 위에서 마이그레이션과 로직을 실DB에 적용하고, 시나리오를 끝까지 돌린 뒤 되돌린다. 끝나면 트랜잭션 밖에 변화가 0인지 확인한다. 마이그레이션 승인은 이 시험을 통과한 뒤에 받는다.

사례 · 규범 확정

모든 답변의 시스템 프롬프트에 상시로 들어가는 짧은 규칙 묶음을 「규범」이라고 불렀다. 세무사가 초안을 내고, 공개 기간 동안 이의를 받고, 승인이 모이면 확정되며, 관리자는 롤백할 수 있다. 무슨 일이 확정·이의 기간·관리자 롤백은 모두 상태를 바꾸는 기능이었다. 왜 몰랐나 단위 테스트는 가짜 저장소 위에서 전부 통과했다. 실제 스키마와 부딪히는 자리는 거기서 보이지 않았다. 잡은 방법 트랜잭션 함수를 세이브포인트 하나로 바꿔 끼우고, 마이그레이션과 로직을 실DB에서 돌린 뒤 되돌렸다. 이의 기간 22항목, 관리자 브레이크 12항목, 확정 시나리오 전체를 돌렸고 트랜잭션 밖 변화 0을 확인했다. 이 시험대에서 다음 원칙의 결함 하나가 잡혔다.

암묵 상태에 기대지 말고 문장을 나누거나 즉시 변수로 잡는다

SQL에는 코드에 드러나지 않는 상태가 있다. PostgreSQL에서 한 문장 안의 CTE(WITH로 잇는 하위 쿼리)는 모두 같은 스냅샷을 본다. 그래서 앞 CTE가 넣은 행을 같은 문장의 본 쿼리가 읽지 못한다. PL/pgSQL의 FOUND는 「직전 쿼리가 행을 찾았나」를 담는데, 그 뒤에 어떤 쿼리든 돌면 덮어써진다. 둘 다 문법 오류 없이 실행되고 결과만 빈다. 앞서 넣은 행을 읽어야 하는 갱신은 문장을 나눈다. 암묵 상태 변수는 조회 바로 다음 줄에서 지역 변수로 옮겨 두고 쓴다.

사례 · CTE 스냅샷

무슨 일이 규범 확정 함수가 한 문장에서 새 문서를 넣고, 새 버전을 넣고, 문서의 「현재 버전」 칸을 그 버전으로 갱신했다(with d as (insert…), v as (insert…) update … from v). 현재 버전 칸이 걸리지 않았다. 왜 몰랐나 문법 오류 없이 실행되고 갱신 대상만 비었다. 잡은 방법 앞의 롤백 트랜잭션 시험에서 결과가 비는 것을 보고 찾았다. 문장을 나눴다.

사례 · FOUND

무슨 일이 상담 방을 여는 함수가 방을 조회한 뒤 개수를 세는 count(*)를 한 번 더 돌렸다. 그 쿼리가 FOUND를 참으로 덮어써, 없는 방을 「다시 열기」 갈래로 보냈다. 왜 몰랐나 코드에서는 FOUND 검사 줄이 조회 바로 뒤에 있는 것처럼 읽혔다. 잡은 방법 드라이런 DB 시험에서 드러났다. 조회 직후 결과를 지역 변수에 담게 고쳤다.

5.4 외부 LLM API를 운영한다

이 제품의 답변·임베딩·분류는 전부 외부 LLM API 호출이다. 서버는 그 호출을 기다리는 시간이 대부분이다. 외부 API는 우리가 고칠 수 없는 이유로 느려지고, 같은 키에 요청이 몰리면 더 느려진다. SDK는 우리 모르게 재시도한다. 모든 LLM 호출에 명시적 상한을 거는 일, 재시도와 계측을 같은 층에 두는 일, 긴 지연을 분포 모양으로 판독하는 일은 모든 직무의 원칙이다→ 1.1. 동시 호출과 자동 도구 선택에서 지연이 폭발하는 모델 쪽 이야기는 → 3장. 이 절은 그 위에서 서버가 해야 할 일을 다룬다.

외부 LLM 호출은 호출 단위 번호표 게이트로 막고, 혼잡은 정상 응답으로 알린다

동시 접속이 몰릴 때 외부 API를 보호하는 게이트는 사용자 턴이 아니라 외부 호출 하나하나에 건다. 한 턴이 여러 번 호출하기 때문이다. 게이트 슬롯은 SDK 재시도까지 감싼다. 멈춘 호출도 자리를 차지하기 때문이다. 세마포어는 순서를 보장하지 않으니, 먼저 온 호출이 먼저 들어가는 번호표(FIFO)를 쓴다. 대기 상한은 호출마다가 아니라 턴 합계로 둔다. 상한을 넘으면 오류가 아니라 「지금 붐빈다」는 평범한 안내를 HTTP 200으로 돌려준다. 500으로 내면 프론트가 오류 화면으로 처리한다. 혼잡 예외가 중간의 폴백 코드에 삼켜지지 않게 다시 던진다. 게이트가 프로세스 안에 있으면 실제 동시 상한은 k × 워커 수다. 끝으로, 「멈춤 0」이 게이트 덕인지 시간대 차이인지는 표본만으로 가를 수 없다고 적어 둔다.

사례 · 전시회 대비

전시회에서는 비로그인 방문자가 한꺼번에 챗을 쓴다. 모두 같은 API 키를 쓴다. 무슨 일이 배포 전 동시 4 조건에서 48턴 중 1턴이 120초 동안 멈췄다. 그 전 주에 이미 긴 지연이 120초 타임아웃 + 재시도 1회 모양으로 군집한다는 것, 그리고 순차 64회에서는 멈춤이 0이라 동시 호출의 산물이라는 것을 확인해 두었다. 왜 몰랐나 개발자 혼자 쓰는 조건에서는 한 번도 멈추지 않는다. 잡은 방법 프로세스 안에 번호표 게이트(k=3)를 두고, 모든 외부 LLM 호출이 지나는 한 자리에 걸었다. 챗 한 턴의 대기 합계가 30초를 넘으면 HTTP 200 혼잡 안내를 돌려준다. 배포 뒤 동시 4·6·8 × 12턴, 모두 216턴에서 멈춤 0, 혼잡 안내 0이었다.

스레드를 붙이면 SDK가 늦게 불러오는 모듈을 미리 불러 둔다

요즘 SDK는 시작 속도를 위해 하위 모듈을 처음 쓰는 순간에 불러온다(지연 import). 단일 스레드에서는 처음 건드리는 쪽이 하나뿐이라 문제가 없다. 그런데 두 스레드가 서로 다른 하위 모듈을 동시에 처음 건드리면, 파이썬의 import 잠금이 서로 엇갈려 교착 오류가 날 수 있다. 서버에서는 기동 직후 첫 요청에서만 날 수 있어 드물고, 그래서 재현이 어렵다. 병렬을 붙일 때는 쓰는 하위 모듈을 모듈 로드 때 미리 import한다. 콜드스타트 경로는 따로 스모크한다.

사례 · 대조 스레드

새 답변 단계에서는 LLM이 판정을 내리고, 기존 규칙 엔진은 대조용으로 옆에서 함께 돈다. 무슨 일이 엔진 대조 스레드와 본 스레드가 채팅 호출 모듈과 임베딩 호출 모듈을 동시에 처음 건드리자 _DeadlockError가 났다. 왜 몰랐나 단일 스레드 경로에서는 한 번도 나지 않았다. 서버에서는 기동 직후에만 날 수 있다. 잡은 방법 로컬 스모크에서 드러났다. 두 하위 모듈을 모듈 로드 때 미리 불러 두게 했다.

처리 경로는 실행한 컴포넌트에서 기록하고, 전환 전후는 시각으로 가른다

「이 답변은 어느 지식 경로로 만들었나」는 나중에 품질을 비교할 때 가장 먼저 쓰이는 칼럼이다. 이 값을 결과의 모양에서 거꾸로 추정하면, 경로가 하나일 때는 늘 맞다가 경로가 섞이는 순간 틀린다. 실행한 컴포넌트(어떤 검색기를 돌렸나)에서 기록한다. 같은 이유로 「무엇을 요청했나」 칼럼은 디폴트 전환을 보여 주지 못한다. 요청값을 비워 둔 사용자는 전환 전후 모두 비어 있기 때문이다. 디폴트를 바꾸는 날은 전환 시각을 기록해 두고, 실제 처리 경로 칼럼과 시각으로 가른다. 계정 이름 같은 식별자도 짐작하지 말고 조회해서 쓴다.

사례 · 융합 검색

무슨 일이 답변 기록의 「사용한 지식 경로」 칸을, 검색 결과 1위 지식 조각의 출처 종류로 채우고 있었다. 여러 지식 묶음을 한꺼번에 검색해 순위를 합치는 융합 검색을 붙이면, 1위가 어느 묶음에서 왔느냐에 따라 경로가 잘못 기록될 자리였다. 왜 몰랐나 지식 묶음이 하나뿐일 때는 결과에서 추정해도 늘 맞았다. 잡은 방법 융합 검색 착수 전에 문서를 정정하다가 미리 찾았다. 검색기 종류에서 기록하게 바꿨다.

사례 · 디폴트 전환 계측

무슨 일이 프로덕션 기본 검색 경로를 융합 검색으로 바꾼 뒤 전후를 비교하려 했다. 계측의 「요청한 경로」 칸은 명시 요청값만 담아서, 전환 전후 둘 다 null이었다. 비교할 데모 계정 이름도 짐작한 것과 실제가 달랐다. 왜 몰랐나 요청 칸이 있으니 경로를 가를 수 있을 것처럼 보였다. 잡은 방법 실제 처리 경로 칸과 전환 시각으로 갈랐다. 계정은 목록을 조회해 확인했다.

새 경로는 스위치로 끌 수 있게 하고, 끄면 기존 경로와 똑같게 만든다

실험 경로가 기존 경로에 섞이면 회귀가 조용히 들어온다. 새 경로는 설정 스위치나 파라미터로 붙이고, 값이 없거나 모르는 값이면 기존 코드를 그대로 타게 한다. 꺼진 상태에서 기존 프로덕션 경로의 코드가 한 줄도 안 바뀌었는지 diff로 확인하고, 같은 입력으로 결과가 같은지 증명한다. 이 원칙의 일반형은 → 1.6에서 다룬다. 스위치가 있어야 운영 중에 되돌릴 수 있다. 10월에 프로덕션 챗을 새 지식 묶음 단독으로 바꿀 때도 되돌리기는 설정값 하나였다.

사례 · 새 지식 묶음의 쿼터

세무 심판례와 질의회신 원문으로 새 지식 묶음을 만들어 융합 검색에 붙였다. 무슨 일이 새 묶음을 적재하기 전부터 새 검색 경로 코드는 배포되어야 했다. 왜 몰랐나 해당 없음. 예방 설계다. 잡은 방법 새 묶음의 쿼터가 0이면 그 갈래를 아예 붙이지 않게 했다. 쿼터 0이 곧 「적재 전 상태」다. 기존 융합 검색 분기는 diff로 한 줄도 바뀌지 않았음을 확인했다.

5.5 배포 — 둘 이상의 자리가 따로 성공한다

이 제품은 배포 자리가 둘이다. 프론트는 메인 브랜치에 올리면 호스팅 서비스가 자동으로 빌드한다. 백엔드는 배포용 브랜치에 올린 뒤 서버에서 배포 스크립트를 돌려야 반영된다. 한쪽만 하면 반쪽만 바뀐다. 그리고 두 자리는 저마다 「성공」을 보고한다. 서버 저장소가 부분 체크아웃 상태로 한 달 넘게 멀쩡히 돈 일, 새 요청 필드가 있으면 백엔드를 먼저 내야 하는 일은 모든 직무의 원칙이다→ 1.6. 응답 스키마가 프론트 검증기에 조용히 지워지는 일은 → 6장.

계약 변경은 서버가 옛·새 클라이언트를 함께 받는 중간 단계를 거친다

클라이언트와 서버가 따로 배포되면, 둘 사이의 계약을 바꾸는 순간 어느 순서로 내도 한쪽이 깨지는 창이 생긴다. 서버를 「옛 클라이언트와 새 클라이언트를 둘 다 받는」 중간 상태로 먼저 낸다. 그다음 클라이언트를 바꾸고, 마지막에 서버를 새 계약만 받게 조인다. 다 끝나면 중간 단계용 우회 플래그는 남기지 않는다. 이 순서는 백엔드만 보면 설정 한 줄이라 한 번에 바꾸고 싶어지는 자리에서 특히 필요하다.

사례 · 쓰기 API 인증

무슨 일이 규범 확정이 모든 답변을 바꾸게 되자, 쓰기 API 전체에 토큰 인증을 걸어야 했다. 그때까지 신원은 요청 본문으로 받고 있었다. 그 위에 「2명 승인」을 얹으면 본문만 바꿔 위조할 수 있다→ 1.5. 백엔드를 한 번에 「필수」로 바꾸면, 아직 토큰을 안 붙이는 구 프론트가 쓰기마다 깨질 판이었다. 왜 몰랐나 백엔드 쪽에서는 인증 모드 설정값 하나였다. 잡은 방법 백엔드를 「선택」(토큰이 있으면 검증, 없으면 통과)으로 먼저 내고, 프론트에 토큰 부착을 배포하고, 마지막에 「필수」로 바꿨다. 전환 뒤 토큰 없는 쓰기는 401, 챗은 토큰 없이 정상인 것을 확인했다. 전시회 방문자는 로그인 없이 챗을 쓰므로 챗은 처음부터 인증 대상에서 뺐다. 이후 스크립트는 개발용 토큰 발급 모듈을 거쳐 쓰기를 한다.

배포·설정 자리가 둘 이상이면 「조용한 반쪽」을 점검 목록에 넣는다

배포 자리, 환경변수 자리, 빌드 산출물이 따로 있으면 각 자리는 저마다 성공을 보고한다. 그래서 「반쪽만 반영됨」은 실패가 아니라 정상처럼 보인다. 인프라를 옮긴 뒤에는 배포 스크립트·환경변수·배포된 번들 안의 주소를 전수 대조한다. 빌드 시점에 주입되는 환경변수는 값을 바꿔도 재배포해야 반영된다. 열어 볼 수 없는 비밀값은 값을 확보하기 전에는 지우지 않는다.

사례 · 서버 이전 직후

무슨 일이 백엔드를 새 VM으로 옮긴 직후, 배포 스크립트는 여전히 구 서버를 가리키고 있었다. 프론트 호스팅 쪽에서는 브라우저에 노출되는 공개 환경변수를 비밀값으로 저장하는 길이 정책 변경으로 막혀 있었다. 다시 만들 때 적용 환경(프로덕션 + 프리뷰)을 둘 다 잡지 않으면 프리뷰가 조용히 깨진다. 왜 몰랐나 구 서버가 아직 살아 있어서, 스크립트가 구 서버에 배포해도 「배포 성공」이 떴을 것이다. 잡은 방법 첫 배포 전에 스크립트를 교정했다. 이전 뒤 배포된 번들 24개를 스캔해 새 주소 2곳, 구 주소 0곳을 확인했다. 인증 키처럼 값을 다시 볼 수 없는 공개 환경변수는 건드리지 않았다.

브랜치를 올릴 때는 딸려 가는 커밋과 그것이 부를 배포를 먼저 본다

작업 트리를 건드리지 않고 원격 브랜치의 참조만 올리는 것은 편하고 안전해 보인다. 그러나 참조 갱신은 내용을 보여 주지 않는다. 그 사이 쌓인 다른 커밋이 함께 가고, 그 안에 마이그레이션 파일이나 프론트 변경이 있으면 자동 빌드나 다음 배포가 그것을 실어 나른다. 올리기 전에 함께 가는 커밋 목록을 뽑고, 각 커밋이 일으킬 배포·마이그레이션을 확인한다.

사례 · 메인 브랜치 갱신

무슨 일이 다른 세션이 고치던 파일 때문에 브랜치 전환이 막혔다. 그래서 배포 브랜치를 원격 메인으로 직접 밀고, 로컬 메인 참조를 받아 오는 식으로 전환 없이 메인을 올렸다. 커밋 4개(새 지식 묶음 작업 둘과 미적용 마이그레이션 파일)가 함께 갔다. 왜 몰랐나 명령은 한 줄로 성공했고, 무엇이 함께 갔는지는 출력에 없었다. 메인에 올라간 프론트 변경은 곧바로 자동 배포된다. 잡은 방법 딸려 간 커밋에 프론트 변경이 없는지, DB 적용이나 백엔드 배포가 따라가지 않았는지 사후에 확인했다. 다음부터는 올리기 전에 확인한다.

같은 앱을 한 번 더 띄우기 전에 프로세스 안 싱글톤을 목록으로 뽑는다

워커 하나, 인스턴스 하나로 운영하면 「프로세스는 하나」라는 전제가 코드 어디에도 적히지 않은 채 늘 참이다. 스케줄러, 멈춘 작업을 회수하는 리퍼, 프로세스 안 게이트가 모두 이 전제에 기댄다. 워커를 늘리거나 병행 유닛을 띄우는 순간 이 전제가 깨진다. 띄우기 전에 프로세스 안 싱글톤을 목록으로 뽑는다. 병행 유닛은 백그라운드 작업을 끄고, 외부 호출의 합계 상한은 각 프로세스 상한의 합으로 계산하고, 킬 스위치는 애플리케이션이 아니라 서비스 관리자 층에 둔다. 원복할 때도 새 쪽을 먼저 멈춘다. 기동 시 멈춘 작업을 회수하는 일반 원칙은 → 1.6에서 다룬다.

사례 · 병행 유닛

새 상담 흐름을 기존 서버 옆에 두 번째 서비스로 띄워 시험하려 했다. 무슨 일이 새 유닛도 같은 앱이라 기동하면 백그라운드 폴러를 띄웠다. 그 첫 순회의 리퍼가 기존 유닛이 돌리던 작업을 「멈춘 작업」으로 보고 죽일 수 있었다. 프로세스 안 번호표 게이트는 두 프로세스가 공유하지 못해 실제 동시 상한이 두 배가 됐다. 환경변수 킬 스위치는 쿼리 파라미터에 우선순위가 밀렸다. 격리 설계는 셋 다 몰랐다. 왜 몰랐나 그때까지 싱글톤 전제는 늘 참이라 코드에 드러날 일이 없었다. 잡은 방법 리퍼를 부르는 곳이 하나뿐인 것을 코드로 추적했다. 전날 서버 이전에서 「워커는 1로 유지한다」는 규칙을 정리해 둔 덕에 같은 모양을 알아봤다. 새 유닛은 백그라운드 작업을 끈 채 띄우고, 평소에는 서비스 관리자에서 꺼 둔다.

스모크가 실패하면 요청이 서버 로직에 닿았는지부터 본다

배포 뒤 스모크 요청이 422나 400을 내면 서버 오류처럼 보인다. 그런데 요청이 서버 로직에 닿지도 않았을 수 있다. 셸과 요청 도구는 비ASCII 문자를 조용히 다른 인코딩으로 바꾼다. 한글 페이로드 스모크는 인코딩을 통제하는 스크립트로 보낸다. 실패하면 먼저 그 요청이 파이프라인 기록에 남았는지 본다.

사례 · 한글 질문 스모크

무슨 일이 Windows 셸의 curl로 한글 질문 JSON을 보내자 422와 400이 났다. 파이프라인 기록에는 아무것도 없었다. 왜 몰랐나 응답 코드만 보면 방금 배포한 서버 코드가 깨진 것처럼 보였다. 잡은 방법 같은 페이로드를 파이썬 표준 라이브러리로 보내 정상 처리를 확인했다. 한글이 든 명령은 셸 인라인 대신 파일로 쓰는 습관은 → 1.7에서 다룬다.

5.6 인프라 — 수요, 비용, 이전

인프라 결정에는 그럴듯한 숫자가 늘 먼저 와 있다. 큰 GPU를 주겠다는 제안, 단가표로 곱한 월 비용, 계획 문서에 적힌 콘솔 절차. 모두 틀린 숫자는 아니다. 다만 우리 코드가 그것을 실제로 쓰는지, 무료 한도를 뺐는지, 콘솔이 정말 그 흐름을 지원하는지는 아직 확인하지 않은 숫자다. 서버 이전을 「같은 결과」로 판정하고 라이브러리 업그레이드와 섞지 않는 원칙은 모든 직무의 원칙이다→ 1.6.

인프라 수요는 코드의 실제 의존성과 실측 병목으로 답한다

자원 신청에는 「받아 두면 손해 없다」는 유혹이 따른다. 그 유혹이 실제 병목을 가린다. 신청서는 의존성 목록과 실측 병목으로 근거를 댄다. 앞으로의 고도화 계획이 그 자원을 실제로 쓰는지도 방식별로 표를 만들어 확인한다. 상태가 어디에 있는지도 함께 본다. 상태가 전부 외부 DB에 있으면 서버 이전에 데이터 이관이 필요 없다.

사례 · 대회 인프라 조사

무슨 일이 대회 운영 측이 GPU 서버 지원 여부를 물었다. 코드를 전수 확인하니 LLM·임베딩·벡터 검색이 모두 외부 API와 관리형 DB였고, GPU 라이브러리는 하나도 없었다. 실제 병목은 GPU가 아니라 서버 메모리 1GB였다. 왜 몰랐나 큰 GPU 질문이 메모리 문제를 가렸다. 「언젠가 쓸지도」가 근거처럼 보였다. 잡은 방법 의존성 파일과 백엔드 API의 로컬 파일 의존을 검색했다. 계획 중인 고도화 방식들도 API 조합으로 된다고 판정했다. GPU는 신청하지 않고 스토리지만 신청했다. 메모리 병목은 뒤에 서버 증설로 풀었다.

클라우드 비용은 무료 한도를 먼저 빼고, 견적이 아니라 실측으로 확정한다

단가표의 숫자는 맞다. 틀리는 것은 계산 순서다. 무료 한도 → 단가 순으로 계산하고, 생성 화면 견적이 아니라 비용 분석 화면의 실측 청구로 확정한다. 예산 알림은 정상 청구의 몇 배로 잡는다. 그래야 알림이 울리는 것 자체가 이상 신호가 된다.

사례 · 서버 증설

무슨 일이 메모리 병목을 풀려고 서버를 2코어·12GB로 늘리는 계획을 세웠다. 계획서의 월 비용은 37,000원이었다. 실제로는 컴퓨트 0달러에 부트 볼륨 월 2.76달러였다. 10배 넘게 과대였다. 2코어·12GB가 그 클라우드의 상시 무료 한도(4코어·24GB) 안에 통째로 들어갔다. 왜 몰랐나 단가표는 맞는 숫자였다. 무료 한도를 빼는 단계가 계획에 없었다. 잡은 방법 생성 화면 견적에 컴퓨트 항목이 아예 없었고, 사용량 지표가 0이었다. 예산 알림은 정상 청구(약 3.7싱가포르달러)의 몇 배인 월 10싱가포르달러로, 50%와 100%에 걸었다.

다른 설정이 참조하는 값을 먼저 확정하고, 콘솔 표시보다 실상태를 믿는다

공인 IP나 도메인처럼 다른 설정이 줄줄이 참조하는 값은 바뀌면 연쇄 재작업이 생긴다. 그 값을 먼저 확정하고, 그다음에 리버스 프록시·프론트 설정 같은 의존 설정을 바꾼다. 계획 문서에 적힌 콘솔 흐름은 가정일 수 있다. 작업 뒤 판단은 콘솔의 부가 표시가 아니라 리소스 상태와 실제 접속으로 한다.

사례 · 고정 IP

무슨 일이 계획은 「새 서버에 처음부터 고정 IP를 할당한다」였다. 콘솔에는 그 경로가 없었다. 임시 IP로 생성 → 고정 IP 발급 → 네트워크 인터페이스에서 교체의 3단계였고, 그 사이 공인 IP가 한 번 더 바뀌었다. 교체 뒤에도 콘솔은 IP 수명을 「임시」로, 인터페이스 칸을 빈칸으로 보였다. 왜 몰랐나 계획 문서가 콘솔 흐름을 가정으로 썼다. 교체 뒤의 표시는 실패처럼 보였다. 잡은 방법 리소스 상태가 「할당됨」인 것과 실제 접속으로 판단했다. IP를 확정하기 전에는 리버스 프록시와 프론트 설정을 건드리지 않았기에, IP가 한 번 더 바뀌었어도 재작업은 0이었다.

5.7 장시간 작업의 환경 — 밤, 절전, 재시작

세무 판례와 질의회신 원문 수천 건을 공공 사이트에서 모으는 수집, 158문항을 여러 경로로 채점하는 벤치는 몇 시간에서 하루가 넘게 돈다. 이런 작업의 실패는 코드가 아니라 환경에서 온다. PC가 절전에 들어가고, 외부 서버가 밤에 느려지고, 공유 DB 연결이 끊긴다. 그런데 실패는 코드 결함과 똑같은 모양으로 보인다. 감시를 감시받는 작업과 같이 죽지 않는 곳에 두는 일, 프로덕션 DB에 쓰기 전에 메모리 안에서 재는 일은 모든 직무의 원칙이다→ 1.6.

장시간 작업은 낮에 돌리고, 진행은 작업 전체를 합산해 센다

외부 서버와 공유 DB에는 시간대별 상태가 있다. 대량 수집과 무거운 벤치는 낮에 돌리고, 밤의 실패를 코드 결함으로 단정하지 않는다. 장시간 작업 전에는 절전 같은 공통 정지 원인을 끄고, 끝나면 되돌릴지 사용자에게 확인한다. 진행 감시는 파일 하나가 아니라 그 작업의 산출 전체를 합산해 센다. 재시작하거나 나눠 돌리면 산출 파일이 늘기 때문이다. 감시가 「진행 없음」을 말하면 작업이 멈췄을 수도, 감시가 엉뚱한 것을 세고 있을 수도 있다.

사례 · 밤의 수집과 벤치

무슨 일이 밤에는 수집 쪽의 2MB 응답이 연속으로 실패했다. 낮에는 문서당 1~3초면 받던 것이다. 같은 날 23시께 벤치를 돌리는 중 프로덕션 DB 연결이 반복해 끊겼다. 2문항에 545초, 접속만 21.8초가 걸렸다. 왜 몰랐나 낮에는 같은 코드가 문제없이 돌았다. 밤의 원인(동시에 돈 4096차원 벡터 전수 비교일 가능성)은 끝내 확정하지 못했다. 잡은 방법 실패와 지연을 보고 멈췄고, 벤치는 다음 낮으로 미뤘다. 원인을 확정하지 못했다는 사실도 그대로 적었다.

사례 · 수집 진행 감시

무슨 일이 질의회신 수집은 하루 넘게 돌면서 PC 절전으로 두 번 멈췄고, 그때마다 다시 시작했다. 재시작하면 원본 파일 이름의 날짜가 바뀌는데, 감시는 옛 파일만 세고 있었다. 왜 몰랐나 옛 파일 수는 그대로라 「진행 없음」처럼 보였고, 새 파일의 진행은 보이지 않았다. 잡은 방법 감시가 오탐을 한 번 내고서야 알았다. 감시를 그 작업의 전 파일 합산으로 바꿨다. 결국 질의회신 1,995건(2018년 이후)을 모았다.
