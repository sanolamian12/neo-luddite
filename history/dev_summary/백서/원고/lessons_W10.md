## L-10-09 | AIE,KE | 입력 거름 게이트는 분명한 경우에만 믿어라
- 상황: 작문 전에 Upstage 1회로 카드와 질문의 쟁점을 대조하는 게이트(same/related/different)를 넣었다. C48 5건 전부 different → off_issue 5/5, 같은 입력 3/3 동일. 그러나 solar 는 related 를 거의 안 쓰고 이분으로 기울었다. C30 의 같은 심판례 2건이 fusion 에선 different, KB3 단독에선 same 이었다.
- 왜 조용했나: 분명한 사례에서는 판정이 안정적이라 게이트 전체가 믿을 만해 보였다.
- 잡은 방법: 다듬기 2안(사실관계 추가, 제도명 먼저 적기)을 시험했다. 경계 사례가 회차마다 뒤집혀 원복했다. different 만 빼고, 전부 빠지면 지어내지 않고 `off_issue` 로 "직접 다룬 자료가 없다"고 말하게 했다. PO 는 경계 흔들림을 모델 성능 몫으로 감수했다.
- 규칙: LLM 판정 게이트는 가장 분명한 클래스만 행동에 쓴다. 경계 판정은 함께 들어온 입력에 따라 바뀔 수 있으니 재현성을 따로 잰다. 다 걸러지면 솔직한 "자료 없음" 출구를 둔다.

## L-10-12 | AIE,KE,ALL | "근거에 있다"는 "맞다"가 아니다 — 인용은 적합성을 따로 골라라
- 상황: 세무사가 "AI 가 단 관련 법령이 부정확·부적절하다"고 지적했다. 재 보니 법령 인용 58개 중 54개가 근거 카드에 실제로 있던 조문이었다. 그런데 인용한 26턴 중 10턴 안팎이 무관하거나 설명이 틀렸다. 남의 사건 카드(당시 법 기준)의 조문을 질문에 맞는지 보지 않고 옮긴 것이다.

- 잡은 방법: 인용을 하나씩 출처와 대조했다. 현행 조문 DB(`laws.articles` 8,498행)를 세우고, 후보 중 고르기만 하는 LLM3 를 작문 앞에 뒀다. 작문 뒤 번호 붙이기(뒷단)는 라벨만 고치고 틀린 설명은 못 고쳐 기각했다. 시민 48 "자료 없음" 18 → 1, 현행 DB 에 없는 조문 인용 0.
- 규칙: 출처 대조 가드는 "실재"만 보장한다. 인용의 질문 적합성은 작문 전에 별도 단계로 고른다. 모델에게는 번호를 만들게 하지 않고 후보 중 고르게 하며, 정확성은 법령명 + 조(+항) 키 조회로 확인한다.
- 날짜: 10-07

- 왜 조용했나: 빈 객체는 "아무것도 없음"처럼 무해해 보인다. 화면 코드는 실제 모양만 가정했다.
- 잡은 방법: 3자 방 시험 중 화면이 깨져 알았다. `{"messages":[]…}` 로 넣었다.
- 규칙: 운영에 시험 행을 넣을 때는 실제 데이터와 같은 모양으로 넣는다. 화면이 읽는 필드는 빠짐없이 둔다.
- 날짜: 10-06

## L-10-30 | KE,BE | 범위 검색 인자는 연결 확인이 있는 경로에만 열어라
- 상황: 세무사 사례는 초안 / 게시(그 세무사의 연결 대화) / 공용 승인 세 범위로 검색된다. `run_clinic` 에 세무사 범위 인자를 더했다.
- 왜 조용했나: 해당 없음. 설계 판단이다.
- 잡은 방법: BE 가 `/api/chat` 에는 범위를 열지 않았다. 열면 아무나 다른 세무사의 비공개 게시분을 검색할 수 있다. 연결 확인이 있는 3자 방에서만 열었다. 승인된 공용 사례는 내용이 바뀌면 초안으로 돌아가게 했다.
- 규칙: 지식 범위를 고르는 인자는 서버가 관계(연결·소유)를 확인하는 경로에서만 받는다. 승인을 거친 공용 지식은 수정되면 다시 승인을 거치게 한다.
- 날짜: 10-06

## L-10-31 | PO,KE | 받은 데이터는 이름이 아니라 실체를 실사한 뒤 쓸 것과 뺄 것을 갈라라
- 상황: 팀이 새로 만든 RAG 데이터를 받았다. "한국법률정보 키워드 검색"으로 알려진 자료의 실체는 조세심판원 결정 기반 LLM1 되묻기 세트였고, 신규 725건에 "충분" 사례가 0 이었다. 5000건 json 은 질문 100개 템플릿 × 50 반복에 문장 오류 100% 였다. 쓸 것은 심판례 전문 3,533건이었다.
- 왜 조용했나: 건수가 많고 이름이 그럴듯했다.
- 잡은 방법: KE 가 자료마다 실체를 열어 표로 정리했다. PO 가 5000건을 빼고 심판례만 쓰기로 정했다(D1~D12).
- 규칙: 넘겨받은 데이터는 이름·건수가 아니라 표본을 열어 실체(출처, 중복, 오류율, 용도)를 확인한 뒤 쓴다. 다른 용도의 데이터를 RAG 재료로 섞지 않는다.
- 날짜: 10-05

## L-10-32 | PO,KE | 규정상 모델 사용 범위는 파이프라인 단계별로 선을 그어라
- 상황: 대회는 국내 AI 를 써야 한다. 심판례 카드를 만들면서 어디까지 개발 도구(Claude)가 해도 되는지 정해야 했다.
- 왜 조용했나: 해당 없음. 정책 결정이다.
- 잡은 방법: PO 가 대회 규정을 평가해 D9 를 정했다. Claude 는 원문 수집·코드까지, 포맷팅부터는 Upstage. 세무사 사례 카드에는 `formatted_by='expert'` 로 세무사 원문임을 남겼다.
- 규칙: 모델 사용 제약이 있으면 데이터 파이프라인의 단계(수집·코드·포맷팅·생성)마다 허용 주체를 정하고, 산출물에 누가 만들었는지를 기록한다.
- 날짜: 10-05

## L-10-33 | PO | 동의는 고객의 말이 실제로 흘러드는 경로에만 받아라
- 상황: 세무사가 가르친 사례에 고객 동의가 필요한지 정해야 했다(팀장 프로토타입의 '상담에서 가르치기' 병합 결정 D-C). 처음 안을 사용자가 고쳐서 확정했다.
- 왜 조용했나: 해당 없음. 정책 결정이다.
- 잡은 방법: 확정안은 이렇다. 세무사가 직접 타이핑·붙여넣기한 사례는 동의가 필요 없다(고객은 스튜디오를 못 본다). 채팅방 원문을 그대로 불러올 때만 방 단위로 1회 받는다.
- 규칙: 동의 절차는 데이터 흐름을 따라 정한다. 당사자의 원문이 그대로 들어가는 경로에 받고, 그렇지 않은 경로에 절차를 덧씌우지 않는다.
- 날짜: 10-06

## L-10-34 | PO,FE | 버릴 기능은 이름을 붙여 선언하라
- 상황: 화면 흐름 20장을 그리기 전에 범위를 정했다. 세무사 '참고' 9개, 관리자 13개(모델개선 6 · 정산 · RAG · 지식망 추이 · 소급 중복 정리 · 수정 제안 승인 · KB2 · 규범)를 "앞으로 안 쓸 기능"으로 뺐다. 8~9월에 만든 검수 흐름 화면 대부분이다. 같은 날 "사례 추가 UI 가 안 보인다, 프로토타입 브랜치라서?"라는 질문도 있었는데 원인은 브랜치가 아니라 숨김 스위치였다.
- 왜 조용했나: 쓰지 않는 메뉴도 화면에 남아 있으면 살아 있는 기능처럼 보인다.
- 잡은 방법: PO 가 제외 목록을 명시했다. 옛 메뉴는 맨 아래 접힌 "참고" 그룹으로 내렸다. 관리자 '메시지' 존치는 미결로 적었다.
- 규칙: 방향이 바뀌면 남길 것만이 아니라 버릴 것을 이름 단위로 적는다. 버릴 것과 숨긴 것(스위치)을 구분해 기록한다. 미결은 미결이라고 적는다.
- 날짜: 10-05

## L-10-35 | FE,ALL | dev 서버가 떠 있는 폴더에서 build 하지 말라
- 상황: `npm run build` 가 `.next` 를 덮어써 사용자가 띄워 둔 dev 서버가 깨졌다.
- 왜 조용했나: 빌드 확인은 무해한 읽기 작업처럼 보인다.
- 잡은 방법: 사용자 dev 서버가 깨져 알았다.
- 규칙: 공유 산출물 폴더를 쓰는 명령은 다른 프로세스가 그 폴더를 쓰는지 먼저 본다. 빌드 확인은 dev 를 끈 뒤에 하고, 운영 E2E 는 배포된 화면으로 한다.
- 날짜: 10-09

## L-10-36 | ALL | 여러 줄 코드 수정은 셸 heredoc 이 아니라 편집 도구로 하라
- 상황: heredoc 안 파이썬 문자열의 `\n`·`\d` 이스케이프가 깨져 파일이 망가진 일이 두 번 있었다.
- 왜 조용했나: 셸이 이스케이프를 한 번 더 해석해도 명령은 성공으로 끝난다.
- 잡은 방법: 망가진 파일을 보고 알았다.
- 규칙: 이스케이프가 든 소스는 셸을 거치지 않는 편집 도구로 고친다.
- 날짜: 10-05, 10-08
