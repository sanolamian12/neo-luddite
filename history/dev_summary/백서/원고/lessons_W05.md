- 상황: admin "완료" 화면에 07-16~21 미확정 검수 항목이 쌓여 있었다. PO는 이를 ICTC 2026 논문 실험 데이터로 기억했다. 실제로는 제품 개발 작업(100건 일괄감사, RAG 재검증)이 남긴 검수 대기열이었다. 논문이 DB에 남긴 흔적은 `rag.passages` 168건의 07-27 상태변경 하나뿐이었고, 그것도 이미 복구돼 있었다.
- 왜 조용했나: 정황이 들어맞았다. 같은 주에 RAG on/off A/B 리포트가 연달아 나왔고, 07-29 커밋이 그 리포트들을 논문 실험 기록으로 묶었다. 기억과 정황이 서로를 받쳐 가설이 의심받지 않았다.

- 규칙: 데이터의 정체를 판단하기 전에 같은 질문을 전에 조사한 문서가 있는지부터 찾는다. 조사 결론은 다음 세션이 찾을 수 있는 자리에 남긴다. 정체가 확정돼야 지울지 말지를 논한다.

## L-05-02 | RS,AIE,ALL | 데이터 출처는 계정·화면 이름이 아니라 실제 생산 주체로 적어라
- 상황: 원문은 "논문 데이터" 오인을 바로잡으면서 결론을 다시 "세무사들이 실작업으로 남긴 검수 대기열"이라고 적었다. auditor·auditor2·auditor3의 코멘트와 세션 평가는 감사 모드 Claude 산출물이다. 사람(세무사)이 개입한 자리는 승인 게이트와 인용·원문 대조뿐이다.
- 왜 조용했나: 계정 이름이 "auditor"이고 화면도 세무사용 검수실이다. 첫 오독을 바로잡은 직후라 새 결론이 맞아 보였다. 정정은 검증을 거친 것처럼 느껴져 다시 의심받지 않는다.
- 잡은 방법: 주간 재구성에서 감사 데이터 출처 규칙에 따라 고쳐 적었다.
- 규칙: 데이터를 누가 만들었는지는 계정 이름이나 화면 용도로 추정하지 않고 생성 경로로 적는다. 정정 문장도 같은 기준으로 한 번 더 확인한다. 논문 인용에도 같은 출처 표기를 쓴다.
- 날짜: 08-31

## L-05-03 | BE,FE,ALL | 화면의 것을 지우려면 화면→컴포넌트→소스 테이블부터 추적하라
- 상황: "완료" 화면의 미확정 항목을 치우려고 `session_evaluations` 확정분 39건을 지웠다. 그 화면(`/audit/results`)은 `audits`+`reviews`+`line_feedback`을 읽고 있었다. 세션 총평은 다른 탭 몫이었다. 2차에서 타깃을 바로잡아 `submitted` audits 52건, reviews 16건, line_feedback 186건을 지웠다.
- 왜 조용했나: 1차 삭제 자체는 안전했다. RAG 손실 0건, 에러 0건이었다. DB 검증은 "지운 것이 안전한가"만 답했고 "지운 것이 맞는 것인가"는 답하지 않았다.
- 잡은 방법: 사용자가 auditor로 재로그인했는데 화면이 그대로였다. 그 뒤 화면 컴포넌트의 소스 테이블을 추적했다.
- 규칙: 화면 문제를 데이터로 고칠 때는 먼저 그 화면이 읽는 테이블을 코드에서 확인한다. 고친 뒤에는 검증 쿼리만 믿지 말고 그 화면을 다시 연다. 안전성 검증과 타깃 검증은 별개의 확인이다.
- 날짜: 08-31

## L-05-04 | BE,ALL | RLS 아래 UPDATE는 갱신 행 수를 보고, 0행은 실패로 다뤄라
- 상황: `session_evaluations`에 admin 쓰기 RLS가 없어서 관리자의 결정이 "0행 갱신"으로 끝났다. 이것이 7월 미확정 항목이 쌓인 근본 원인이었다(7월에 `0015`로 수정, 이번 주 재확인).
- 왜 조용했나: 권한에 막힌 UPDATE는 에러가 아니라 0행 갱신으로 끝난다. 화면에서는 실패로 보이지 않았다.
- 잡은 방법: 7월에 원인을 찾아 고쳤고, 이번 주 미확정의 정체를 캐다 다시 확인했다.
- 규칙: 행 수준 보안 아래에서 쓰기를 할 때는 영향받은 행 수를 확인한다. 기대가 1행 이상인데 0행이면 실패로 올린다. 조용한 권한 실패는 데이터를 미완 상태로 쌓아 몇 주 뒤 다른 모습으로 나타난다.
- 날짜: 08-31

## L-05-05 | BE,KE,ALL | 프로덕션 삭제는 영향 재확인→백업→rowcount 검증→커밋으로 하라
- 상황: 프로덕션 DB에 직접 DELETE를 두 번 실행했다. 스크립트는 RAG 영향을 재확인해 0건이 아니면 멈추고, non-draft 리뷰가 섞이면 멈추게 했다. JSON으로 백업하고, 자식부터(`line_feedback` → `reviews` → `audits`) 지우며 단계마다 rowcount를 검증했다. 삭제 전후 `rag.passages` 수치(feedback active 287, session_eval active 120)가 같았다.
- 왜 조용했나: 직접 DELETE는 되돌릴 길이 없다. 사람이 확인을 건너뛰어도 아무것도 경고하지 않는다.
- 잡은 방법: 구현 판단으로 절차를 스크립트 안에 넣었다. 조건이 어긋나면 사람이 아니라 스크립트가 스스로 멈춘다.
- 규칙: 운영 데이터 삭제는 이 순서를 표준으로 재사용한다. 안전 조건은 사람의 확인이 아니라 스크립트의 자동 중단 가드로 건다. 삭제 전후로 하류 지식(RAG) 수치를 대조한다.
- 날짜: 08-31

## L-05-06 | BE,KE | 외래키 칼럼을 믿지 말고 실제 연결 값과 교차 겹침을 확인하라
- 상황: `line_feedback.audit_id`가 전체 567건 전부 NULL이었다. 설계상 `conversation_id`+`auditor_id`로만 연결됐다. 그래서 대상 audits의 (auditor_id, conversation_id) 쌍으로 매칭했고, 그 쌍이 대상 밖 audit과 겹치는 경우가 0건임을 확인했다.
- 왜 조용했나: 스키마에 `audit_id` 칼럼이 있으니 그것으로 연쇄 삭제하면 될 것처럼 보인다. 값이 전부 NULL이면 조용히 0건을 지우거나, 다른 키로 매칭할 때 남의 데이터를 함께 지운다.
- 잡은 방법: 삭제 전 사전 안전 확인 4가지 중 하나로 칼럼 값을 실측했다.
- 규칙: 연쇄 삭제 전에 연결 칼럼의 실제 채움 상태를 본다. 대체 키로 매칭할 때는 그 키가 대상 밖 레코드와 겹치지 않는지 따로 센다.
- 날짜: 08-31

## L-05-07 | PO,KE,ALL | 지워도 되는 근거가 있는 것만 지우고, 한 단계 더 나간 상태는 남겨라
- 상황: 확정 세션 평가 39건은 `rag.passages`에 독립 사본(텍스트 복사)이 39건 전부 active로 있어서 지웠다. 검수실은 RAG에 반영되지 않은 `submitted`만 지웠고, 한 단계 더 진행된 `reviewed`(검수저장, 이의가능) 2건은 범위에서 뺐다.
- 왜 조용했나: "미확정 항목 정리"라는 한 덩어리 요청 안에 진행 단계가 다른 데이터가 섞여 있었다. 날짜 구간으로만 자르면 이의 절차가 걸린 데이터까지 함께 사라진다.
- 잡은 방법: PO가 범위를 "검수실 '제출됨'만"으로 못 박고, 구현은 RAG 사본 매칭과 리뷰 상태로 근거를 확인했다.
- 규칙: 삭제 범위는 날짜가 아니라 상태와 하류 반영 여부로 정한다. 지식이 다른 곳에 독립 사본으로 남는지, 다른 절차(이의 등)가 걸려 있는지 확인한다. 애매한 상태는 남기고 별도 결정으로 넘긴다.
- 날짜: 08-31
