## 1. RAG 구조 분석 · 지식망 1차 시각화 (08-27)

**결과** — 출발점은 "세무사가 KB를 직접 보고 이해할 수 있는 UI를 만들어 달라"는 요청이었다. 화면부터 그리지 않고 **KB 구조부터 코드로 분석**했다. 실체는 이렇다.
- `rag.passages` 단일 테이블에 edge가 없다.
- 임베딩 단위는 문장이 아니라 **질문 + AI 답변 + 코멘트를 묶은 번들**이다.
- 4096차원이라 pgvector ANN 인덱스 상한(2000)을 넘는다. 그래서 매 질문 **active 526건 전체를 exact scan** 한다.
- `occupation="clinic"`이 하드코딩돼 있어서 필터가 사실상 전부를 통과시킨다.

이 구조에 맞춰 시각화를 정했다. 거미줄 전체 대신 **저장된 메타데이터 클러스터를 기본 축**으로 두고, 유사도는 조회 시점에 국소적으로만 계산해 보여 준다.

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 지식 엔지니어 | KB 구조 분석(번들 임베딩, 비대칭 임베딩, exact scan, top-k 5, 컷 0.50), `store.neighbors()` 조회 시점 이웃 |
| 백엔드 | `GET /api/rag/passages/{id}/neighbors` 신설 |
| 프론트엔드 | `/audit/kb-map` 클러스터 그리드, `/audit/kb-map/[passageId]` 방사형 상세, `/admin/pipeline/timeline` 기여 순위·존속기간 간트 |
| 프로덕트 오너 | 요청자. "코사인 유사도로 순차 계산하는 거냐"는 질문에 코드 근거로 답을 받았다 |

**맞물린 자리** — 지식 엔지니어가 "저장된 관계는 메타데이터뿐"이라고 확인한 결과가 곧 화면의 기본 축이 됐다. 기여 = 존속기간이라는 PO의 운영 개념은 관리자 타임라인에서 처음으로 시간축 그림이 됐다.

**검증** — 프론트(Vercel)와 백엔드 모두 배포 후 확인했다. **남은 것** — exact scan 비용은 KB 규모 트리거(5,000~10,000건)까지 모니터링만 한다.

## 2. KB 중복 — 사전검토와 소급 정리 (08-27)

**결과** — 다이어그램을 그리던 중 같은 Q&A("병원 명의 종신보험 / 배우자 수익자")에 코멘트 3건이 중복 적재된 것을 발견했다. 원인은 `dedupe_key`가 콘텐츠가 아니라 원본 ID 기준이라는 데 있었다. 대응은 두 갈래였다.
- **앞으로**: 검수실 두 화면에 85%+ 유사 경고를 띄운다(자동 병합·거절은 하지 않는다).
- **이미 들어간 것**: KB 전체를 훑는 클러스터 조회를 만들었다.

0.85 의미 클러스터만으로는 오탐이 압도적이었다(104개 클러스터, 390건 = KB의 74%). 그래서 **같은 `conversationId` + `segmentId`** 만 "진짜 재제출"로 자동 체크하도록 좁혔다(286건 → 45건, 41개 그룹). admin이 프로덕션 화면에서 직접 확정해 **active 526 → 413건**이 됐다(113건 retired). 정리 후 같은 segment 재제출 그룹은 0개이고, "비슷하지만 정당한" 75개 클러스터(232건)는 남겼다.

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 지식 엔지니어 | `find_similar`, 번들 조립 함수 공유(`session_eval_bundle_text`), `find_duplicate_pairs` / `find_duplicate_clusters`(union-find), 오탐 원인 분석 |
| 백엔드 | `POST /api/rag/dedup-check-*` 2종, `GET /api/rag/duplicate-clusters`. 정리는 기존 `/api/rag/retract` 재사용 |
| 프론트엔드 | 검수실 ⚠ 칩과 주황 경고 카드, `/admin/pipeline/duplicates` 화면과 **기본 선택 로직 정제** |
| 프로덕트 오너 | "기여 정책이 없으니 자동 처리는 위험하다"는 판단으로 경고 방식을 골랐다. admin으로서 최종 정리를 확정했다 |

**맞물린 자리** — 백엔드는 클러스터 조회를 **그대로** 두고 프론트의 기본 체크만 좁혔다. 유사하지만 정당한 항목도 admin이 훑어볼 수 있어야 해서다. 오탐의 근원(번들 임베딩이 질문 텍스트에 끌려간다)은 KE의 구조 분석에서 이미 예고돼 있었다.

**검증** — 3중복 사례로 사전검토 API 94%대를 확인했고, 시뮬레이션으로 286 → 45건을 확인했다. → [EV](../7_평가검증/EV_2026-08_W04_0823-0829.md). **결정** — 경고만 하고 자동 처리는 하지 않는다. 진짜 중복의 신호는 segment 일치다. → [DL](../8_결정교훈/DL_2026-08_W04_0823-0829.md)

## 4. 정산 — 총수익 × 비율 pool, 크레딧/원화 분리 (08-27)

**결과** — 요청은 "관리자가 수익을 입력하면 세무사에게 정산·입금확인이 가는 프로세스"였다. 조사해 보니 ledger, 정산 회차, 인앱 메일은 이미 PoC로 동작하고 있었다. 빠진 것은 **pool이 실제 수익과 연결되지 않은 임의 숫자("cr")** 라는 점이었다. 이를 **총수익(원) × 분배비율(%) → pool 자동 계산**으로 바꿨다. 그 과정에서 크레딧(추상 포인트)과 정산액(원화)이 같은 누적 잔액에 더해지는 구조적 버그를 찾아 함께 고쳤다.

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 프로덕트 오너 | pool은 계산 전용·수정 불가, 개별 분배 덮어쓰기 불가. 은행 연동과 실제 메일·SMS는 범위 밖(7/14에 이어 두 번째로 같은 결론) |
| 백엔드 | `0016_settlement_revenue_ratio.sql`(`revenue` bigint, `distribution_ratio` numeric). 라이브 적용 |
| 프론트엔드 | `settlement.ts`의 preview/publish/markPaid 원화화, `ledger.ts`의 `settlement_round`를 잔액에서 제외, 관리자·세무사 화면 5곳의 단위 분기 |

**맞물린 자리** — 정산 로직이 `frontend/services`에 있어서 운영 규칙이 프론트를 지났다. PO의 "수정 불가" 결정은 합계를 검증하는 로직이 없어도 분배 합이 항상 pool과 맞게 하는 장치다.

**검증** — Playwright로 실 Supabase E2E를 돌렸다(2,000,000원 × 25% = 500,000원, 3명에게 228,764 / 140,926 / 130,308원). 테스트 타이밍 착시가 하나 있었다. → [EV](../7_평가검증/EV_2026-08_W04_0823-0829.md). **남은 것** — 정산 테이블들과 `rag.passages`에 RLS가 실제로 적용됐는지 확인해야 한다.

## 6. KB 거미줄 그래프 — GraphRAG 재검토에서 진짜 목적으로 (08-28)

**결과** — 로드맵 순번대로 GraphRAG를 "검색 엔진을 교체할지"의 관점에서 재검토했고, 비채택을 유지했다. 근거는 넷이다.
- `Retriever` Protocol 경계가 이미 있어서 나중에 바꿔도 된다.
- 그래프가 풀 뻔했던 오탐 문제는 segment 휴리스틱으로 이미 풀었다.
- 제품 논지가 "품질"이 아니라 "범위"다.
- 413건 규모에서는 이득이 없다.

그런데 PO가 정정했다. 이 로드맵의 진짜 동기는 **"세무사와 KB 사이에 중간층을 두어 KB 구성을 거미줄 그래프로 보고(줌인·줌아웃) 직접 고칠 수 있게 하는 것"** 이었다. 그 목적대로 전체 KB 그래프를 구현·배포했다(413 노드, 3,304 edge).

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 프로덕트 오너 | 질문 정정. edge는 **배치로 미리 계산해 저장**하고, 렌더는 **d3-force + 커스텀 SVG**로 하기로 확인 |
| 지식 엔지니어 | GraphRAG 재검토(비채택 유지, 재오픈 신호 3개 명시), `list_passage_edges` / `rebuild_passage_edges(k)` |
| 백엔드 | `0018_rag_passage_edges.sql`(self-join top-k 재계산 함수 + pg_cron 5분), KB를 바꾸는 4개 경로에서 best-effort 동기 재계산 |
| 프론트엔드 | `kb-graph-view.tsx`(300틱 수렴 후 정적 SVG, 휠 줌, 팬, 노드 크기 = degree), 탭 토글, passive 리스너 버그 수정 |

**맞물린 자리** — PO의 "새 지식이 배선될 때마다 재계산이 필요하지 않냐"는 질문에 백엔드가 응답 직전 동기 호출로 답했다. pg_cron은 안전망으로 남겼다. 지금 규모에서 전체 재계산이 1초 미만이라 가능했다.

**검증** — Playwright 스모크로 407 노드 렌더, 줌 라벨, 노드 → 상세 이동을 확인했다. → [EV](../7_평가검증/EV_2026-08_W04_0823-0829.md). **교훈** — 맞는 답이라도 묻던 질문이 틀리면 소용이 없다. → [DL](../8_결정교훈/DL_2026-08_W04_0823-0829.md)

## 7. 세목 분류 정책 17개 · 자동분류 · 소급 재분류 (08-28)

**결과** — 그래프 스모크 중 PO가 "왜 전부 미분류냐"고 물었다. UI 폴백이 아니라 **데이터 자체**의 문제였다. `frontend/services/conversation.ts:76`이 스냅샷을 복원할 때 `taxCategory`를 늘 `"미분류"`로 하드코딩했고, 그 값이 적재까지 흘러 **KB 전량(521건)** 이 미분류였다. 이에 세 가지를 했다.
