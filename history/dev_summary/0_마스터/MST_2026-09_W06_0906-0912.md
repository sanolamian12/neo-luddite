## 1. KB2 설계·구축 — 문장 단위 사전, 합성, 검색 A/B (09-09)

**결과** — 출발점은 메뉴 요청이었다. 세무사(auditor) 쪽에는 확인·수정이 되는 "지식베이스2", admin 쪽에는 읽기 전용 "지식베이스2"를 두고 싶다는 것이다. 설계 중에 PO가 "지금 KB도 코사인 유사도로 찾아오냐, 백서 형식에도 통하냐"고 물었다. 코드를 보니 `ingest_kb_document()`가 title+body 전체를 통째로 임베딩하고 있었다. **문서 전체를 벡터 하나로 만들면 길어질수록 여러 주제의 평균이 되어 정보가 희석된다.** 기존 `kb_documents`도 같은 결함을 안고 있었다.

그래서 KB2를 정의했다. RAG 번들을 원재료로 Solar Pro가 **문장(조항) 단위**로 응축한 별도 정책 사전이다. 검색·크레딧·수정 이력의 최소 단위가 문서에서 문장으로 내려간다. 로드맵 1~4단계를 하루에 구현했다.
- 스키마(`0019`): `kb2.documents` · `kb2.sentences` · `kb2.sentence_versions` + `kb2.match_sentences()`
- admin 전용 합성 트리거: 부가가치세 세목(원천 28건) → 독립 완결형 조항 14문장
- 검색 A/B: `?ragSource=rag|kb2|hybrid`. 기본값 `rag`는 기존과 100% 같다
- 세무사의 문장 직접 수정: 즉시 반영, 버전 이력, 재합성에서 잠금 보호

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 프로덕트 오너 | 메뉴 구조(auditor 수정 / admin 읽기 전용), 합성 트리거 admin 전용, 문장 수정은 승인 큐 없이 즉시 반영. "코사인으로 찾냐"는 질문이 문장 단위 설계의 계기가 됐다 |
| 지식 엔지니어 | 데이터 모델, `kb2_synthesis.py`(잠긴 문장 보호), `Kb2Retriever`·`HybridRetriever`, `KB2_MIN_SCORE=0.35` 분리 |
| 백엔드 | `0019_kb2_schema.sql` 적용, `kb2_store.py`, 합성·조회·수정 라우트, `ChatMeta.ragSource` |
| AI 엔지니어 | `synthesize_kb2_sentences()` — tool 강제 출력, "이 경우/위와 같이" 없는 독립 완결형 강제 |
| 프론트엔드 | `/admin/kb2` 합성 화면, `/audit/kb2`(수정·출처 보기·버전 히스토리) |

**맞물린 자리** — 지식 엔지니어가 "회귀 없음"을 설계 제약으로 걸었다. 그래서 `source`가 없거나 모르는 값이면 기존 코드 경로를 그대로 탄다. 이 제약 덕분에 3방향 비교(무RAG / 기존 RAG / KB2)가 나중에 구조적으로 가능해졌다(→ §8). `sentence_versions.editor_type`에는 설계 당시부터 `auditor_edit`가 들어 있었지만, 잠금 컬럼을 `true`로 세우는 코드 경로는 4단계 전까지 없었다.

**검증** — 같은 질문으로 3방향 호출을 해서 기본값이 `rag`와 완전히 같음을 확인했다. kb2 매치가 0.4985로 기존 컷 0.50에 근소하게 걸려 소리 없이 잘리는 것을 이때 잡았다. → [EV](../7_평가검증/EV_2026-09_W06_0906-0912.md). **결정** — 문장 단위 임베딩, 크레딧 2종 모델, 수정 즉시 반영. → [DL](../8_결정교훈/DL_2026-09_W06_0906-0912.md)

## 2. AI 동적 카테고리 재구조화 (09-09)

**결과** — PO가 더 근본적인 질문을 던졌다. "이 구조를 Upstage AI가 이해하고 구축할 수 있어야 한다." 국내 AI 트랙 대회인데, KB2의 최상위 구조(17세목)가 `taxonomy.py`에 박제돼 있었다. 그래서 버튼 한 번에 Solar Pro가 그 시점 RAG 전체를 다시 읽고 **목차 자체를 새로 제안**하게 바꿨다(로드맵 4.5단계). 발견(map-reduce) → 분류 → 이전 세대 archive → 카테고리별 합성 순서다. 버그 두 개를 고친 뒤 3차 실행에서 **20/20 카테고리, 17문서, 141문장**을 약 35분에 만들었다.

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 프로덕트 오너 | 트랙 취지 제기. 매번 전체 재생성 + 이전 세대 archive(연속성 매칭 안 함), 진행 UX는 job id + 폴링 |
| AI 엔지니어 | `propose_categories_batch()`(맵) · `merge_categories()`(리듀스), 상한 20개를 코드 슬라이스로 강제 |
| 지식 엔지니어 | `kb2_taxonomy.py` 신설, "배치에 실제로 넣은 id 집합과의 교집합만 신뢰" 필터(레거시 경로도) |
| 백엔드 | `0020`(`kb2.categories`로 레이블과 정체성 분리, `kb2.synthesis_jobs`), 재구조화·폴링·보관함 API |
| 프론트엔드 | "AI로 카테고리 재구조화" 섹션(3초 폴링, 단계 라벨, 보관함) |

**맞물린 자리** — 레이블이 매번 바뀌면 `tax_category` unique가 기본키 노릇을 하던 문서가 고아가 된다. 백엔드가 `kb2.categories`(안정 UUID)를 들여 레이블(표시용)과 정체성(category_id)을 갈랐다. 사이드바 트리 UI는 이번엔 보류하고 동적 재구조화를 먼저 했다.

**교훈** — 상한을 프롬프트로만 요청했더니 카테고리가 149개로 폭주했다. Solar가 출처 id를 한 글자 다르게 지어내 37분째 크래시가 났다. → [DL](../8_결정교훈/DL_2026-09_W06_0906-0912.md)

## 3. KB2 편집 화면 — 2단 트리·편집 락·이동·연결 끊기 (09-09 ~ 09-10)

**결과** — 재구조화 결과를 화면에서 보던 PO가 두 가지를 요청했다. 하나는 기존 지식베이스처럼 왼쪽 트리 + 오른쪽 패널, 그것도 대목→세목 2단 트리다. 다른 하나는 여러 세무사가 동시에 고칠 때 나중 저장이 덮어쓰는 문제를 막는 것이다. 그 결과 이렇게 됐다.
- **2단 트리**: 대목(`kb2.groups`, AI 파이프라인과 무관한 정리 계층) → 세목
- **편집 락**: 문장 단위 비관적 락, 서버 TTL 5분, 60초 무입력 자동저장
- **문장 이동**: 다이얼로그 피커. 크레딧은 유지
- **대목 자동배정**: Solar Pro가 세목 17개를 대목 6개로 묶었다(16/17)
- **연결 끊기/재연결**(`0022`): 사유 필수, 삭제 아님
- 9/10: **세목은 연결 끊기, 대목은 삭제**로 수단을 갈랐다(`0024`, `kb2.document_events`)

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 프로덕트 오너 | 기존 세목도 그룹 편입, 락 해제는 서버 TTL, 그룹 이동은 [확정] 버튼형, 끊기는 사유 필수. 실사용 피드백(롱프레스, UI 4건) |
| 프론트엔드 | `kb2-view.tsx` 대개편, 첫 롱프레스 훅 → 클릭 방식으로 교체·삭제, 다이얼로그 4곳, 락 배지, Playwright 첫 실브라우저 검증 |
| 백엔드 | `0021`(groups·locks·moved), `0022`(문장 status), `0024`(세목 `retired`, `document_events`), 락·이동·상태 API |
| AI 엔지니어 | `propose_document_groups()` — 세목 제목만 넣고, id를 실존 enum으로 묶어 환각 차단 |
| 지식 엔지니어 | `auto_group_ungrouped_documents()` — 미분류만 대상이라 다시 누르면 재시도 |

**맞물린 자리** — 이 레포의 기존 "락"(0012/0013 검수 확정 잠금)은 영구 상태 전이형이라 성격이 달랐다. 그래서 TTL형을 새로 설계했다. 이동·이름 수정·그룹 지정은 원자적 단발 작업이라 락 대상에서 뺐다. 9/10에 문서 단위 락도 검토했지만 단일 UPDATE라 불필요하다고 결론 냈다. 대신 락으로는 못 막는 **대목 삭제 × 세목 이동 레이스**를 찾아 "죽은 참조는 미분류로 표시"로 막았다.

**검증** — curl로 락 A/B/C 시나리오와 TTL 회수, Playwright로 롱프레스 700ms/100ms와 UI 4건, 9/10에 Playwright 22건을 확인했다. → [EV](../7_평가검증/EV_2026-09_W06_0906-0912.md)

## 4. 재구조화 운영화 — 야간 예약·호출 상한 전수·stale 회수 (09-10)

**결과** — PO의 우려가 출발점이었다. **"세무사가 버튼 한 번으로 큰 작업에 들어가면 안 된다."** 세 가지를 했다.
- **분류 배치화**: 20건 묶음으로 바꿔 분류 시간을 약 5.6분에서 약 2.8분으로 줄였다. 이 과정에서 SDK 기본 타임아웃(600초×재시도 2회)이 한 배치에 1250초를 먹는 것을 발견했다.
- **야간 예약**: 기본 액션이 `[오늘 밤 03:00 실행 예약]`이다. DB에 예약을 남기고 백엔드 폴러가 1분마다 집는다. pg_cron은 쓰지 않았다.
- **잔해 정리**: 활성 카테고리 31 vs 활성 문서 17이었다. `0023`으로 14개를 보관 처리했다.

## 6. 재구조화 안전장치 — 실패를 세고, 나쁜 회차를 막는다 (09-11)

**결과** — 재구조화는 새 목차를 만든 뒤 **멀쩡한 세대를 먼저 내리고** 새로 쌓는다. 나쁜 회차에 걸리면 좋은 KB가 나쁜 KB로 바뀐다. 야간 예약은 아무도 안 보는 중에 그 일을 한다. 그래서 가드를 세 겹으로 넣었다.

| 가드 | 자리 | 중단 조건 | 근거 |
|---|---|---|---|
| 나쁜 회차(분류) | archive 직전 | 호출 실패율 > 2%, 또는 배정률 < `max(35%, 직전×0.75)` | 순차 4회 편차 상대 3.8%, 실패 0/600 |
| 합성 0개 | archive 뒤 | 문장 0개면 이전 세대를 원래 status로 복구 | 0은 재볼 필요가 없는 유일한 값 |
| 유실 청크 | 합성 뒤 | 유실 청크 비율 > 10% | 관측 0~4%의 2.5배 |

그보다 먼저, **실패가 데이터로 둔갑하던 자리 둘**을 찾았다.
- 분류: "회차가 통째로 무너진다(미분류 40/38/75%)"의 정체는 8워커 병렬 측정의 `RateLimitError`였다. `except: return "미분류"`가 429를 분류 판정으로 접었다.
- 합성: 인용률 하락(93.1% → 87.4%)은 편차(상대 7.9%) 안이었다. 그 편차는 전부 `APITimeoutError`에서 왔다. 실패 세목을 빼면 0.9%다.

| AI 엔지니어 | 분류·합성 함수가 `(결과, 실패사유)`를 반환, 재시도 1→2, `_dedup_labels`(merge가 같은 레이블 30개를 돌려줄 때) |

## 8. KB2 완성 기준 G1~G3 · 타임아웃 60초 · G3 계측 배선 (09-12)

**결과** — PO가 로드맵 현황을 정리했다. 계층 1(원본 RAG `rag.passages`)은 끝났다. 남은 것은 규모 모니터링(413 / 트리거 5,000~10,000)뿐이다. 계층 2(KB2)는 기능 1~19를 전부 배포했다. 그래서 지금은 "더 만들 것"이 아니라 **"작동하고 자란다는 증명"** 단계다. 완성 기준을 셋으로 정했다.

> "세무사가 하루 쓰면 KB2가 그만큼 좋아져 있고, 다음 회차가 그걸 지우지 않으며, 지표가 편차 안에서 재현된다."

| 기준 | 뜻 | 이 주 끝 상태 |
|---|---|---|
| **G1 재현성** | 지표가 편차 안에서 재현되고 차이를 계측으로 분해할 수 있다 | **마감** — `TIMEOUT_SYNTHESIZE` 240 → 60초 |
| **G2 축적성** | 사람이 손댄 것이 세대교체를 살아남는다 | **성립**(2회 재현) |
| **G3 임팩트** | kb2 경로의 되묻기율이 내려간다 | **계측 배선** — `rag.chat_turns`(0027), 표본 0 |

G1의 마지막 조각은 타임아웃 값이었다. 원시 소요값을 남기고 합성 호출의 SDK 내부 재시도를 걷어낸 뒤 한 회차를 더 쟀다. 정상 호출 48건이 전부 15초 이하였다(진짜 p90 4.87초). 어느 상한 후보도 정상 호출을 자르지 않았다. **완주가 35분에서 16분**이 됐다.

| 포지션 | 맡은 몫 (결과) |
|---|---|
| 프로덕트 오너 | 계층 정리, G1~G3 정의, "커버리지는 계기판", 남은 3가지 후 일단락 → 논문, 60초 결정, G3 결정 3건, 커버리지 하락은 기록만 |
| 백엔드 | 원시값 저장, 합성 호출만 SDK 재시도 0, 상한 60초, `0027_rag.chat_turns`, 적재 실패는 응답을 막지 않음 |
| AI 엔지니어 | 파이프라인 각 return 자리에 `outcome`을 손으로 붙임, `rag_searched` nullable |
| 지식 엔지니어 | KB2 기능 1~19 연표, 트리 가독성 조건(접은 만큼 리필) |
| 리서치 | 3방향 벤치마크는 논문 세션 사안. curl 벤치도 남도록 백엔드 테이블 적재를 요구 |

**맞물린 자리** — G3에 필요한 값(`ragSource`/`ragHits`/`followUp`)은 `ChatMeta`에 이미 다 있었다. 문제는 아무 데도 안 남는다는 것이었다. 프론트 payload에 얹으면 curl로 도는 논문 벤치가 통째로 유실된다. 그래서 백엔드 전용 테이블로 갔다. "요약만 남기고 원시값을 버리지 말라"는 타임아웃 쪽 교훈이 같은 날 G3 설계(분모를 스키마에 박지 않음)로 옮겨 갔다.

**남은 것** — 커버리지가 53.3%로 내려갔다. 목차까지 새로 뽑는 전체 파이프라인의 편차는 한 번도 잰 적이 없어서 기록만 했다. → [EV](../7_평가검증/EV_2026-09_W06_0906-0912.md) · [DL](../8_결정교훈/DL_2026-09_W06_0906-0912.md)
