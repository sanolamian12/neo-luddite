# 지식 엔지니어 — W06 · 2026-09-06 ~ 09-12

> **이번 주 요지** — KB의 두 번째 모양, **KB2** 를 만들었다. 기존 RAG는 [질문 / AI 답변 / 검수 코멘트] 번들을 통째로 임베딩한다. 길어질수록 벡터 하나가 여러 주제의 평균이 된다. KB2는 그 번들을 원재료로 Solar Pro가 **문장(조항) 단위**로 응축한 별도 정책 사전이다. 9/9에 데이터 모델·합성·검색 A/B를 기존 경로를 건드리지 않고 나란히 얹었다. 같은 날 목차도 AI가 매번 새로 만들게 했다. 9/10에 처음 돌려 보니 원본 413건 중 **20%** 만 담겨 있었다. 그 뒤 이틀은 **"원문이 어디서 버려지나"** 를 깔때기 계측으로 쫓는 일이었다. 합성 절단, 배치 분류, 목차 크기, merge 미실행, 인용 누수, 분류 입력이 차례로 드러났고 커버리지는 **63.9%** 까지 왔다. 9/12에는 세대교체가 사람의 정리를 지우던 구조를 **보존 + 의미 기반 재부착**(임계값 0.70)으로 끊었다. 주 끝 결론은 **"커버리지는 계기판이고, 자동 경로 천장은 63~65%"** 다.

## KB2 구조

### 왜 문장 단위인가 (09-09)
PO가 "지금 KB도 코사인으로 찾냐, 백서 형식에도 통하냐"고 물었다. 코드를 보니 `ingest_kb_document()`가 title+body 전체를 통째로 `embed_passage()`한다. 문서 전체 임베딩은 길어질수록 정보를 희석한다. 기존 `kb_documents`도 이미 이 결함을 안고 있었다. 검색은 작동하니 결함이 드러나지 않았던 것이다. 결론은 **청킹 단위를 문장/조항으로 낮춘다**였다.

| 테이블 | 역할 |
|---|---|
| `kb2.documents` | 세목 컨테이너(처음엔 `tax_category` 1:1) |
| `kb2.sentences` | 검색·크레딧·수정 이력의 최소 단위. 문장별 임베딩(vector 4096) |
| `kb2.sentence_versions` | 전체 이력. 관리자 번복의 근거 |
| `kb2.match_sentences()` | `rag.match_passages`와 대칭인 exact scan |

설계에는 두 확장이 함께 적혔다. 둘 다 이 주에는 구현하지 않았다.
- **배선실 폐루프**: KB2 문장이 수정·삭제되면 그 출처 `rag.passages`를 배선실의 "끊김 후보"로 표시한다(5단계).
- **크레딧 2종**: RAG 크레딧과 KB 크레딧을 독립 축으로 둔다(6단계). → [DL](../8_결정교훈/DL_2026-09_W06_0906-0912.md)

### 합성 오케스트레이션과 검색 A/B (09-09)
- `backend/api/rag/kb2_synthesis.py`: 세목별로 active passage → 합성 → 문장별 임베딩 → `locked_by_auditor=true` 문장은 보호하고 나머지만 교체.
- `retriever.py`: `Kb2Retriever`(kb2 검색), `HybridRetriever`(kb2 우선, 결과 없으면 rag 폴백). `get_retriever(force_enabled, source)` 확장. **`source`가 없거나 `"rag"`이거나 모르는 값이면 기존 코드 경로를 그대로 탄다.** 회귀 없음이 핵심 제약이었다.
- **`KB2_MIN_SCORE`(기본 0.35)를 분리했다.** kb2 문장은 번들보다 짧고 응축돼 코사인 분포가 낮다. 명백히 관련 있는 매치가 0.4985로 기존 `RAG_MIN_SCORE=0.50`에 근소하게 걸려 소리 없이 잘렸다. `RAG_MIN_SCORE`는 rag 전용으로 그대로 뒀다.

생성 문장의 `source_passage_ids`로 원 passage를 추적할 수 있고, `attribution`에는 원 검수 계정이 자동으로 채워진다. 이 번들의 검수 코멘트는 감사 모드 Claude 산출물이다(README 규칙 1).

### 목차를 AI가 만든다 — 동적 재구조화 (09-09)
하드코딩 17세목(원래 Solar Pro가 초기 RAG를 분석해 도출한 산출물)을 버튼 한 번에 다시 만들게 했다. `backend/api/rag/kb2_taxonomy.py`를 새로 만들었다.
1. 발견: 맵(배치당 30~40건) → 리듀스(목차 확정)
2. 분류: 기존 `classify_tax_category` 재사용(1건 = 1콜 순차)
3. 이전 활성 문서 전체 archive
4. 카테고리별 합성: 기존 `synthesize_kb2_sentences` 재사용

설계 문제 하나를 풀었다. `kb2.documents.tax_category`가 unique 제약으로 기본키 노릇을 했다. 레이블이 매번 바뀌면 이전 문서가 고아가 된다. `kb2.categories`(안정 UUID)를 들여 **레이블(표시용)과 정체성(category_id)을 갈랐다.**

안전장치도 코드로 확인했다. `rag.passages.tax_category`는 DB 제약 없는 순수 text 컬럼이다. `retriever.py`의 `_rag()`는 `kb2_store`를 import조차 하지 않는다. 이 작업이 RAG 전용 모드(A/B 기준선)에 영향을 줄 수 없다.

2차 실행 37분째, Solar가 출처 id를 한 글자 다르게 지어내(`"152ea4c-..."`, 첫 세그먼트가 7자리) `uuid[]` insert가 깨졌다. `kb2_taxonomy.py`와 레거시 `kb2_synthesis.py` 양쪽에 **그 배치에 실제로 넣은 id 집합과의 교집합만 신뢰**하는 필터를 넣었다. 같은 버그가 레거시 경로에도 잠재해 있었다. 3차 실행은 20/20 카테고리, 17문서(3개는 배정 0건), 141문장, 약 35분이었다. 결과 카테고리는 "개원 전 비용 인정 시점", "중고 의료장비 증빙 부족" 같은 실제 상담 주제로 세분됐다.

## 커버리지 — 원문이 어디서 버려지나 (09-11)

### 깔때기 계측
`kb2.synthesis_jobs.result`가 이미 jsonb라 **마이그레이션 없이** 넣었다.
```
passagesTotal → assigned / unclassified → fed / truncated → cited
+ classifyCalls, synthesisChunks, sentences, hallucinatedIdsDropped
+ categoryStats[] (세목별 assigned/fed/truncated/chunks/sentences/cited)
```
세 지점을 나란히 둔 이유가 있다. 미분류가 크면 목차가 좁은 것이고, 미투입이 크면 세목이 커서 예산에 밀린 것이다. **처방이 정반대다.** 그리고 두 결함은 맞물려 있었다. 맵만 고쳐 카테고리를 넓히면 세목당 건수가 늘어 합성 절단에 더 걸린다. 유실 지점이 옮겨갈 뿐이다.

### 원인 넷 — 2×2 실측 (표본 100건, seed 11)

| 분류 방식 | 프롬프트 | 목차 | 미분류 |
|---|---|---|---|
| 배치 20건 | 기존 | 14 | 98% |
| 배치 20건 | 기존 | 30 | **84%** ← 프로덕션 |
| 배치 20건 | 강화 | 30 | 59% |
| 건별 | 기존 | 30 | 45% |
| 건별 | 강화 | 14 | 47% |
| 건별 | 강화 | 30 | **28%** |

1. **분류 배치화**(가장 큼): 84% vs 45%. 건별로 되돌렸다.
2. **프롬프트 불일치**: 레거시 17세목 설명이 박힌 프롬프트로 동적 목차를 골랐다. 전용 프롬프트로 45% → 28%. → [AIE](../2_AI엔지니어/AIE_2026-09_W06_0906-0912.md)
3. **목차 크기**: 14개 47% vs 30개 28%. **작을수록 갈 곳 없는 상담이 늘어난다.** 413건의 병의원 세무 상담은 14개 비용 항목으로 덮이지 않는다. 로드맵의 "카테고리가 좁아서"라는 진단은 레이블의 *성격*(주제형 vs 질문형)과 목차의 *크기*를 뒤섞은 것이었다. 넓은 주제명을 쓰되 목차는 촘촘해야 한다. 탐색성은 2단 트리가 감당한다.
4. **merge 미실행**: 1201초 = 600초 타임아웃 + 600초 재시도. 목차를 정한 것은 배치 순서였다. `tally_candidates`로 19초. → [AIE](../2_AI엔지니어/AIE_2026-09_W06_0906-0912.md)

합성 쪽도 고쳤다. `_synthesize_members`가 예산 단위로 나눠 여러 번 합성하고 이어붙인다. 청크 경계의 중복 문장은 정규화 후 일치하면 **출처 id 합집합으로 병합**한다(`_dedup_sentences`).

결과(job `7493247e`, 2247초): 413 → 배정 236(57%) → 투입 236(절단 0) → 인용 154(**37.3%**). 문장 256, 카테고리 30, 환각 id 15. DB의 `source_passage_ids` distinct = 154로 일치했다.

예측(미분류 28%)에는 못 미쳤다. 실제 43%(177건)였다. 실제 merge가 낸 30개에는 여전히 질문 하나짜리 레이블(`1세대1주택비과세`·`수도권공공기관이전`·`가족직원급여`는 배정 0건)과 의미 중복(`복리후생비` 32 / `인건비·복리후생` 9 / `헬스장복리후생비` 5)이 섞였다. **개수는 스키마로 강제했지만 품질은 강제하지 못했다.** 계측은 새 손실 지점도 드러냈다. 투입 236 중 인용 154(65%)다.

### 합성 인용 누수 — 공유 함수와 측정 그룹 (09-11)

## 세대교체 축적성 — G2 (09-12)

### 왜 커버리지보다 먼저인가
재구조화의 `archive_all_active_documents()`는 활성 세대를 통째로 내린다. 9/11 브라우저 실사용 검증(Playwright 자동화)에서 '기타'에서 빼내 `1세대1주택비과세`에 넣은 문장 `fc17e2f6`이 **정확히 한 회차 만에 원상복귀**했다. 옮긴 문장은 archived 문서 안에서 검색 밖으로 나갔고, 같은 원문은 새 세대에서 새 문장으로 다시 '기타'에 담겼다. `locked_by_auditor`는 레거시 재합성 경로만 막아서 여기엔 효과가 없었다. **KB는 자라지 않고 회차마다 다시 만들어지고 있었다.** G2(축적성 — 사람이 손댄 것이 세대교체를 살아남는다)가 커버리지보다 큰 이유다.

### 보존 + 의미 기반 재부착
사람이 손댄 문장은 archive하지 않는다. 새 세대 목차 중 **레이블 임베딩이 가장 가까운** 세목에 다시 붙인다. 맞는 자리가 없으면 '기타'로 내리고 센다.

문자열 매칭을 안 쓰는 것은 측정 때문이다. 목차 레이블은 세대를 넘어 **33~67%만 남는다**(최근 4회 67/33/47/60%). 그런데 의미는 남는다. `1세대1주택비과세`→`양도소득세비과세`, `감가상각`→`감가상각비`, `부가가치세`→`부가가치세신고`.

**임계값 0.70** 을 쌍 목록 전수 판독으로 그었다. 카테고리 7세대 201개(고유 레이블 106개)를 전부 임베딩했고(실패 0), 세대 N→N+1 최근접 쌍 171건(정확일치 84 + 비일치 87)을 점수순으로 읽었다.
```
0.7399  1세대1주택비과세 → 양도소득세비과세   정탐
0.7003  현금결제적격증빙미제출 → 현금결제영수증미수령비용처리  정탐 ← 0.70 이상 전수 정탐
0.6883  가족인건비 → 인건비·복리후생        거칠다(2위 가족직원급여 0.6833이 맞다)
0.6303  개인차량비용인정 → 접대비인정       첫 오탐('인정' 접미사)
```
- 0.635는 선이 아니다. 정탐 6건을 더 건지지만 첫 오탐과 간격이 0.006뿐이다.
- 0.70은 첫 오탐까지 0.07 여유가 있다. 전날 근사 동의어 병합에서 **다른 방법으로** 도달한 0.70과 독립적으로 일치했다.
- 이 선의 재부착 성공률은 80.7%(138/171), 나머지 19.3%가 '기타'행이다.
- 덤: `가족인건비`처럼 1위가 틀린 경우도 둘 다 0.70 아래라 '기타'로 간다. 틀린 자리에 붙는 것보다 낫다.

구현은 `kb2_taxonomy.REATTACH_MIN_SIMILARITY=0.70`, `_reattach_preserved`다. 순서를 두 가지 정했다.
1. `_reattach_preserved`는 **합성 가드를 통과한 뒤** 돈다. 가드가 회차를 되돌리는 경로에서는 여기까지 오지 않으므로, 곧 삭제될 문서로 사람 문장을 옮겨 놓는 일이 없다.
2. 보존 대상은 archive **직전**에 집는다. "내려가기 전에 건졌다"는 의도가 코드 순서로 읽힌다.

**소급 보정은 하지 않았다.** 보존 쿼리가 문서 상태를 보지 않으므로 archived에 갇힌 3건이 다음 회차에 자동으로 따라온다. 정의 그대로다. "사람이 손댄 문장은 어디에 있든 새 세대로 따라온다." 스키마·store는 → [BE](../4_백엔드인프라/BE_2026-09_W06_0906-0912.md), 결정 6건은 → [PO](../1_프로덕트오너/PO_2026-09_W06_0906-0912.md).

## 주 끝 정리 — 계기판과 천장 (09-12)
KB2 기능 1~19의 연표를 정리했다(스키마 · 재구조화 · 2단 트리 · 야간 배치 · 커버리지 규명 · 인용 누수 · 가드 · '기타' · 합성 편차 · G2). 커버리지는 63.9% → 59.3% → 66.3%로 움직였지만 **분해되어 읽힌다.** 배정 변동은 분류 회차 편차 안(상대 3.6% < 3.8%)이고, 인용 변동은 유실 청크가 설명한다(1청크 ≈ 3%p). 자동 경로 천장은 63~65%다.

남은 지식 쪽 일은 **트리 가독성**이다. 근사 동의어 병합은 **접기만 하면 안 된다.** A/B/C에서 접고 채우면(B) 중립, 접기만 하면(C) 나빴다. 접은 만큼 리필해야 하고, 리필에 LLM 호출이 하나 더 붙는다. 도구는 `g1_labels.py`(사라진 `build_taxonomies.py`의 대체)다. 목록은 재구조화로 낡았으니 새 세대(30개)에서 다시 뽑는다.

계층 1(원본 RAG)은 모니터링만 남았다. `kbPassages` 413 / 트리거 5,000~10,000. GraphRAG 검색 엔진 교체는 비채택 유지다.
