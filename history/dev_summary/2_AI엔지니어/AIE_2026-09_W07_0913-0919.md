**처방은 입력을 바꾸는 것이었다.** 무엇이 이미 덮였는지는 모델이 알 수 없고 파이썬은 공짜로 안다. 덮이지 않은 후보만 코드가 걸러 넘기자(72 → 20, → [KE](../3_지식엔지니어/KE_2026-09_W07_0913-0919.md)) 2차에서 LLM 리필 8 · 거부 0이 됐다.

**정직하게 적은 것.** LLM은 "넓은 주제로 묶기"를 하지 않았다. 덮이지 않은 후보 20개가 전부 1회 관찰이었고, 모델은 그 목록을 관찰 순서대로 거의 그대로 골랐다. 결과가 코드 리필과 같다. B 방식은 커버리지 중립이 측정된 방식이라 위험하지 않지만, 가독성 이득은 **중복 제거분뿐**이다. 이 사실을 `refill_categories` docstring에 적었다. 프로덕션 회차에서도 리필 5개(현금매출증빙 / 카드비용구분 / 접대성지출 / 기부금 / 의료봉사비용)가 1회 관찰 후보를 옮겼다.

### 대목 자동 그룹화 — 도구 스키마가 진짜 결함이었다 (09-16)
대목 재사용 버그를 고치고 드라이런을 돌렸더니 재사용은 완벽했는데(생성 0 · 재사용 6) 배정이 엉망이었다. 29개 중 23개가 한 대목에 몰리고, 3건 중복, 2건 누락. 그래서 조건을 갈랐다. 같은 29개 세목, `temperature=0`이다.

| 조건 | 배정 | 누락 | 중복 | 결과 |
|---|---|---|---|---|
| ① 기존(그룹→세목 배열, 기존 레이블 없음) | 20/29 | 9 | 1 | 한 대목에 17개 |
| ② ① + 기존 레이블 제공 | 30/29 | 2 | 3 | 한 대목에 23개 |
| ③ 스키마 뒤집기(세목→대목 1:1) | 29/29 | 0 | 0 | **대목 17개로 파편화** |
| ④ 2단(대목 확정 → enum 배정) | 29/29 | 0 | 0 | 한 대목에 10~14개 |

- ①이 기존 구현이다. 원래부터 9건을 빠뜨리고 있었다.
- **누락·중복은 프롬프트로 못 고친다.** ①②는 "모든 세목은 정확히 하나의 대목에"라고 써 두고도 매번 어겼다. 도구 스키마가 그룹마다 독립적인 `documentIds` 배열이라 빠뜨리거나 두 번 내는 것을 막을 방법이 없었다.
- ③은 누락·중복을 구조적으로 막았지만 대목 수 상한(3~8)을 안 지켜 17개로 파편화했다. 모델이 세목 제목을 그대로 대목 이름으로 복사했다(`복리후생비 정책 사전`이 대목 이름이 된 사례). **개수 제약도 프롬프트로는 안 지켜진다.**
- ④는 이 코드베이스가 이미 쓰는 패턴이다. `merge_categories`(목차 확정) → `classify_dynamic_category`(그 목차 안에서만 고름).

**구현** — `llm.propose_document_groups(documents, existing_labels)`를 2패스로 바꿨다. 패스1이 `minItems`/`maxItems`로 대목 개수를 확정하고, 패스2는 그 목록을 enum으로만 고른다. 새 이름 창작이 불가능하다. 반환 형식은 예전 그대로라 호출측을 건드리지 않았다. LLM 호출은 회차당 2회다.

**남은 것** — 개수는 스키마로 강제했지만 "대목다움"(패스1 규칙 6: "세목 하나만 담을 이름이면 대목이 아니다")은 여전히 프롬프트 의존이다. 프로덕션에서 세목 1개짜리 대목이 3개 나왔고, 다음 회차에서는 승계 잔여분만 들어가 5개가 됐다. → [KE](../3_지식엔지니어/KE_2026-09_W07_0913-0919.md)

**거짓 세무사 귀속.** 사전만 근거인 질문 4개 × 6회. 1회차에서 P4가 오히려 거짓 귀속이 많았다(HEAD 5 vs P4 6). 원인은 시스템 프롬프트가 그 문장을 어조 예시로 **직접 지시**한 것이었다. 규칙 ③ + 예시 한정 뒤 2회차는 HEAD 4 / 35 / 94 → P4 **2 / 19 / 100**(거짓 귀속 / 단정 / 유보)이다. 남은 2건도 같은 형태("세무사가 확인한 유사 사례에서는")다.

**반복 루프는 P4 원인이 아니다.** 초기 표본에서 P4 쪽에 루프가 몰려 보였다(1/64 vs 6/64). 변형 4 × 근거 2 × 32로 분해하니 누적 HEAD 6/128 vs P4 10/128로 구분이 안 됐다. **solar-pro3 도구 출력의 기저 현상(~5~8%)** 으로 판정했다. 반복 제거 가드는 화면 보호용이고, 루프 회차의 지연(15~24초)은 남는다. 원인 치료는 미착수다.

측정 상세는 → [EV](../7_평가검증/EV_2026-09_W07_0913-0919.md).

### P5 — 규범 로더를 DB용으로 (09-17)
규범 원본이 DB(`norms.*`)로 올라가면서 로더를 바꿨다. **`llm.py`는 한 줄도 바뀌지 않았다**(P1 경계 약속 이행).
- `_read_sources()` → `(원문, 'db'|'md')`. DB 확정본, 실패하면 md. `build_norms()`와 예산 규칙은 그대로(절단 없음).
- `lru_cache`를 없애고 `_State` + 락으로 바꿨다. `NORMS_CHECK_SEC`(기본 60) 동안은 메모리 블록을 돌려준다. 지나면 `active_token()`(active_version_id 조합 문자열)을 한 번 조회해 같으면 유지, 다르면 재빌드한다. **매 턴 DB 왕복은 없다.**
- 실패 모드는 3단이다. DB 순단(지문 조회 실패) → 기존 블록 유지. 콜드스타트 DB 장애 → md. DB 확정본이 빌드 불가(예산 초과 등) → md. md도 불가 → None(하드코딩 문안).
- `invalidate_norms()`(확정 API가 호출해 같은 프로세스는 즉시 반영), `norms_status()`(`/rag/health`와 편집 화면용).

### KB2 합성 입력 — 오류 지적 [AI 답변]을 뺀다 (09-18, P8 A)
KB2 문장 가운데 오류로 지적된 [AI 답변]을 옮겨 적은 것이 최소 30건 있었다(→ [KE](../3_지식엔지니어/KE_2026-09_W07_0913-0919.md)). 후보 출처 13문서 × 2회 드라이런(DB 쓰기 0)으로 수정안을 골랐다.

| 변형 | 성공 | 문장 | 오류 지적 AI 답변 옮김 | 인용률 |
|---|---|---|---|---|
| old(HEAD 프롬프트) | 26/26 | 230 | **30.9%** | 89.5% |
| new(규칙 6·7만) | 23/26 | 210 | 20.0% | 90.1% |
| label([AI 답변] 머리말에 "오류 지적 초안" 표시) | 20/26 | 195 | 17.4% | 83.8% |
| drop(오류 지적 번들의 [AI 답변] 절 제거) | 25/26 | 214 | 0.9% | 93.2% |
| **최종(drop + 규칙 6 문구 수정)** | **26/26** | 185 | **1.1%** | 86.5% |

- **규칙만으로는 solar-pro3가 따르지 않는다. 입력에서 빼야 옮기지 않는다.**
- `_synthesis_view()` — 코멘트에 `법적 해석 오류|문법적 오류|법률적 정확성 [12]/5`가 있으면 [AI 답변] 절을 뺀다(`_AI_ANSWER_FLAGGED`). '제안' 태그는 제외한다. AI 답변이 틀렸다는 뜻이 아니기 때문이다. 이 태그와 점수는 감사 모드 Claude가 단 검수 데이터다.
- `_synthesis_block()`이 이 보기를 쓰므로 투입량 계산(`fit_passages_for_synthesis`)과 실제 입력이 일치한다.
- drop 출력을 눈으로 확인했다. 승용차 "운행기록부 미작성 시 1,500만 원 정액, 작성 시 실제 비율"(정답), 카드 "건별 사업 관련성"(코멘트 정답). 남은 흠은 "AI 답변에서 … 오류가 발생했으므로" 같은 **메타 문장**이었다. 규칙 6 문구를 "AI 답변·시스템의 잘못은 서술하지 말고 세무 처리 기준만"으로 바꿔 최종 회차에 반영했다.
- 질문자 개별 사실("포르쉐 카이엔은 5인승 SUV")은 규칙 7로 줄였지만 0은 아니다.
- 옮김 지표는 근사다. drop은 원문을 못 보니 낮게 나오는 면이 있어서, 출력 표본을 읽어 내용이 코멘트를 따르는지 따로 확인했다.

### 날조 수치 가드 `numeric_guard` (09-18, P8 C, `eb7636d`)
판정형 답변에서 "질문·엔진·근거·규범 어디에도 없는 수"를 쟀다. 접대비 한도를 64회 중 23회 근거 없이 말했고, 값이 회차마다 달랐다(1,000만/1,200만/1천만/100만/300만원/"1인당 10만원", 비례율 0.1/0.2/10/20%). 서로 모순이라 대부분은 틀렸다. 자문 경로도 기존 규칙 2("수치를 지어내지 마세요")가 있는데 11/96이었다.

| 붙은 것 | 자리 |
|---|---|
| `drop_unsourced_numbers(raw, sources, derive_from)` — 출처 없는 수치가 든 세그먼트를 빼고, 하나라도 뺐으면 "한도·세율·기한 같은 기준 수치는 … 세무사 확인이 필요합니다." caveat 1문장. 다 빠지면 원문 유지 | `backend/api/numeric_guard.py` |
| `_number_sources()` — sources = 질문·**이전 사용자 발화만**·엔진 블록·규범·근거, derive_from = 질문·사용자 발화·엔진 블록. 판정형·자문 둘 다 | `pipeline.py` |
| `_WRITE_SYSTEM` 규칙 5 — 판정·근거·규범에 없는 수치(한도액·세율·비율·기한·연도)나 사용자가 말하지 않은 인원·금액 금지 | `llm.py` |

- **문장 단위 제거**: 숫자만 지우면 "기본 한도( )와" 같은 깨진 문장이 남는다. 조문 번호와 달력 날짜의 '일'은 토큰이 아니다.
- **이전 사용자 발화만 출처**: 앞선 답변의 날조가 다음 턴 근거로 되살아나지 않게 한다.
- **값을 고치지 않는다**: 어느 값이 맞는지는 세무사 몫이다. 가드는 문장을 빼고 확인 안내를 붙인다(PO 확정).
- 결과: 판정형 날조 답변 **29/192 → 10(규칙만) → 0(규칙 + 가드)**, 자문 11/96 → 0. 상세는 → [EV](../7_평가검증/EV_2026-09_W07_0913-0919.md).
- **한계**: 우연히 맞는 틀린 산술은 놓칠 수 있다. 출처에 있는 수를 엉뚱하게 쓴 것(혼입)은 대상이 아니다. 정당한 법정 수치도 출처에 없으면 빠진다. 필요한 법정 수치는 **L0 규범(세무사 승인)** 으로 넣는 게 제품 구조상 올바른 길이다. 가드는 규범에 들어간 수치를 자동으로 통과시킨다.
