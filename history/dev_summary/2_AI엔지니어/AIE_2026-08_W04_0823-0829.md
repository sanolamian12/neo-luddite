# AI 엔지니어 — W04 · 2026-08-23 ~ 08-29

> **이번 주 요지** — LLM에게 처음으로 **분류** 일을 맡겼다. `classify_tax_category()`는 solar-pro3 function-calling으로 KB passage를 세목 17개 중 하나로 고른다. 불확실하면 강제로 배정하지 않고 `'미분류'`를 돌려준다. 카테고리 이름만 나열한 첫 버전은 미묘한 경우를 놓쳤고, **카테고리마다 설명 문장을 붙이자** 바로잡혔다. 인프라 쪽에서는 "Agentic RAG와 GraphRAG도 API 오케스트레이션으로 된다"고 판정해 GPU 미신청의 근거를 댔다.

## 분류기

### `classify_tax_category()` (08-28)

| 붙은 것 | 자리 |
|---|---|
| `classify_tax_category(content, categories)` — Upstage `solar-pro3` function-calling, `tool_choice`로 강제 호출 | `backend/api/llm.py` |
| 시스템 프롬프트 `_CLASSIFY_SYSTEM` — 카테고리별 설명 문장 | `backend/api/llm.py` |
| 실패 또는 불확실 → `'미분류'` 반환(**강제 배정 금지**) | 같은 함수 |

- **국내 AI 트랙 준수** — 외산 모델을 쓰지 않는다. 제품 경로 안의 호출이라 Upstage만 쓴다.
- **튜닝** — 첫 버전(카테고리명만 나열)은 상속·증여, 매출관리, 기타 같은 미묘한 경우를 자꾸 놓치고 미분류로 흘렸다. 실측 예시로 종신보험 수익자 지정과 자녀명의 펀드 증여가 미분류로 나왔다. `engine_adapter.py`가 9종 지출유형에 1줄씩 힌트를 주는 방식을 그대로 가져와 카테고리별 설명 문장을 넣었다. 재테스트에서 **종신보험 → 상속·증여, 증여펀드 → 상속·증여, 현금매출누락 → 매출관리, 기부금 → 기타**로 바르게 갈렸다.
- 이 설명 문장은 프론트의 클러스터 설명(`TAX_CATEGORY_DESC`)으로 그대로 옮겨졌다. 분류기가 쓰는 기준과 세무사가 화면에서 읽는 기준이 같은 글이다. → [FE](../5_프론트엔드/FE_2026-08_W04_0823-0829.md)
- 적재 경로 배선과 소급 재분류는 → [KE](../3_지식엔지니어/KE_2026-08_W04_0823-0829.md). 결과 분포는 → [EV](../7_평가검증/EV_2026-08_W04_0823-0829.md).
- 정확도가 낮다고 느끼면 `_CLASSIFY_SYSTEM`의 힌트 문장을 다듬고 재분류 엔드포인트를 다시 돌리면 된다(재임베딩 없음).

## 고도화 방식 판정

### GPU 없이 되는가 (08-27)
대회 인프라 조사에 답하려고 고도화 방식별로 GPU 필요 여부를 판정했다. `backend/api/rag/retriever.py`에는 확장 인터페이스 경계만 있고 구현은 아직 없다.

| 방식 | GPU |
|---|---|
| Agentic RAG(쿼리 분해, 재귀 검색, self-critique를 Upstage API로 오케스트레이션) | 불필요 |
| GraphRAG(그래프 DB + Upstage 임베딩) | 불필요 |
| 로컬 리랭커 / 로컬 그래프 임베딩 | 있으면 유리(미계획) |
| 로컬 LLM 파인튜닝 / 로컬 추론 서빙 | 필수 — 국내 트랙 위반 소지라 미채택 |

결론: 고도화는 **API 오케스트레이션 확장 범위 안에서** 진행한다. CPU 인프라로 충분하다. 신청안은 → [PO](../1_프로덕트오너/PO_2026-08_W04_0823-0829.md).
