# 프론트엔드 엔지니어 — W08 · 2026-09-20 ~ 09-26

> **이번 주 요지** — 사흘 동안 아홉 번 배포했다. 사장님에게는 채팅방·연결 요청 카드·사이드바 탭이, 세무사에게는 비식별 풀·채팅방·원 대화 열람이, admin에게는 상담 운영 탭 넷이 생겼다. 그러나 이 주의 진짜 상대는 **Realtime**이었다. `sync.ts` 하나를 다섯 번 고쳤다. 구독 순서를 뒤집고, 인증 이벤트마다 채널을 갈고, 준비 신호를 기다리고, 이중 구독을 없애고, 마지막에 15개 컬렉션을 채널 하나로 묶었다. 그 과정에서 **내가 적은 해석 하나가 틀렸다.** "준비 신호는 채널당 ~250ms"가 아니라 바인딩당 ~60~90ms였다. "간헐 잡음"이라고 적어 둔 화면 하나도 진짜 버그였다. 원칙 하나가 끝까지 따라다녔다. **id를 이름 대신 비추지 않는다.**

## Realtime — `frontend/lib/supabase/sync.ts`

### ① 구독 → 적재 → 버퍼 (09-21)
`makeCollectionSync`가 "전체 fetch → setAll → 구독" 순서였다. fetch 스냅샷 시점과 구독 시작 사이에 들어온 INSERT는 어느 쪽에도 잡히지 않아 **다음 재적재까지 영구 유실**됐다. 대화만이 아니라 모든 컬렉션 공통이었다.
- 고친 순서: **구독(SUBSCRIBED 확인) → fetch → setAll → 버퍼 적용.** 적재 중 도착한 이벤트는 버퍼에 쌓았다가 스냅샷 뒤에 순서대로 적용한다. 유실은 회복할 수 없지만 겹침은 upsert가 멱등이라 무해하다. 겹치는 쪽을 택했다.
- 인증 이벤트(SIGNED_IN/OUT/TOKEN_REFRESHED)가 오면 채널 자체를 새 토큰으로 갈아끼운다. `postgres_changes`의 RLS는 join 시점 토큰으로 평가되므로, anon으로 붙은 채널은 로그인 뒤에도 본인 행을 못 받는다.
- 구독 확정은 5초 타임아웃으로 풀어 준다. Realtime이 막혀 있어도 적재는 진행한다.
- `conversation-store.fetchConversationRecord` 폴백은 그대로 뒀다. 특정 대화를 꼭 열어야 하는 화면(상담 상세, `?c=`)의 안전망이라 성격이 다르다.
- 커밋 `672d16b`. 재현 방법은 → [EV](../7_평가검증/EV_2026-09_W08_0920-0926.md).

### ② 준비 신호를 기다린다 — 채팅방·메시지만 (09-21)
방 INSERT는 오는데 메시지 INSERT가 세무사 화면에 오지 않았다. 원인은 anon 정책 평가 오류였다(→ [BE](../4_백엔드인프라/BE_2026-09_W08_0920-0926.md)). 그것을 고친 뒤에도 **페이지를 연 지 몇 초 안에 생긴 방·닫힘이 유실**됐다. 웹소켓 프레임을 찍어 보니 `SUBSCRIBED`는 join 응답일 뿐이고, 서버가 "Subscribed to PostgreSQL"을 보내야 변경이 흐른다. 그 틈이 로그인 직후 2.5~3초, 채널이 많은 새 페이지에서 7초였다. ①의 순서도 이 틈은 막지 못했다.
- `makeCollectionSync`에 `waitForPostgresReady` 옵션: 준비 신호 뒤 적재하고, 준비가 5초 타임아웃보다 늦으면 **준비 시점에 한 번 더 적재**한다.
- 채팅방·메시지만 켰다. 전면으로 켜면 모든 화면 첫 적재가 2.5초 늦어지므로 별도 판단으로 넘겼다.
- 방어 fetch: `[채팅방 열기]`는 방이 안 보이면 직접 조회(0 · 1.5 · 4초), 방 화면은 탭 복귀·전송 실패 때 다시 당긴다.

### ④ "보이게 됨"엔 이벤트가 없다 — `useEnsureConversations` (09-22)
0040으로 세무사는 관계있는 대화만 읽는다. 새 대화는 세무사에게 안 보인 채 생기고, 뒤에 일감·신청·방이 생겨 보이게 돼도 **대화 행 자체는 안 바뀌니 이벤트가 오지 않는다.** 설계는 "빈 제목"을 걱정했지만, 실제로 숨는 12건을 참조하는 행이 없어서 그것은 깨지지 않았다. 깨지는 것은 운영 흐름이었다. 페이지를 연 채 있으면 큐 상세 미리보기가 "—", 픽업하면 워크스페이스에 "대화 데이터를 찾을 수 없습니다", 신청·방 목록엔 사장님 이름 대신 `viewer`.

### ⑤ 허브 채널 하나 — 바인딩당이었다 (09-23)
15개 컬렉션의 바인딩을 채널 하나(`rt:hub#<epoch>`)에 걸었다. **채널 13 → 1, 준비 신호 1회**(로컬·운영 모두).

깨면 안 되는 규칙.
- **새 채널이 준비된 뒤 옛 채널을 버린다.** 먼저 버리면 그 틈의 변경이 전 컬렉션에서 유실된다.
- 늦게 합류한 컬렉션만 깨우려고 `hubReadyTables`에 이미 준비를 본 테이블을 기억한다(`scope: "new" | "all"`).
- 인증 이벤트로 채널을 갈아끼우는 일은 허브가 한 번만 한다. 같은 사용자 SIGNED_IN 재구독 금지는 그대로이고, **첫 합류가 예약만 된 상태(`hubJoinedAs === null`)도 건너뛴다.** 이 가드가 없으면 세션 복원의 SIGNED_IN이 첫 합류와 겹쳐 채널이 2개가 된다(실측으로 잡음).
- 실패하면 채널 단위 지수 백오프(0.4 → 3.2초)로 재구독하고 다시 붙으면 전 컬렉션을 재적재한다.

**뒤집힌 전제.** 바인딩/채널 조합을 바꿔 가며 재 보니(→ [EV](../7_평가검증/EV_2026-09_W08_0920-0926.md)) 서버는 준비 신호를 채널마다 한 번 보내되, 그 채널의 바인딩을 하나씩 설정한 뒤에 보낸다. **바인딩당 ~60~90ms + 연결 바닥값 ~1.0초.** (c) 때는 컬렉션 = 채널이라 채널 수와 바인딩 수가 구별되지 않았을 뿐이다. 채널을 묶어도 바인딩 수가 그대로라 시간은 크게 줄지 않았다. 얻은 것은 "마지막 준비 2.5 → 2.0초"다.

admin 첫 화면은 4,827 → 4,392ms로 목표 2,500ms에 못 미쳤다. 나머지는 로그인 요청(~1.0초)과 `conversations` fetch(`select=*`, 1.3~1.7MB)였다. 더 줄이는 길(역할별 바인딩 줄이기, 목록용 컬럼만 select)은 범위 밖이다. 앞의 길은 ④의 함정이 걸리고, 뒤의 길은 스토어가 `select=*` 전제로 짜여 있다.

**부작용(고장 아님) — 몰림.** 15개 fetch가 한 신호에 동시에 출발한다. 제일 큰 `conversations`가 꼴찌로 도착해서, 대화 제목에 기대는 화면은 완성이 늦다. `/admin/packaging`이 제목 대신 id로 잠깐 그려지다 채워진다(본문 6,015 → 10,009자, 매번 수렴).
