## 교훈 — 밟은 지뢰

### 맞는 답도 묻던 질문이 아니면 쓸모없다 — GraphRAG 재검토 (08-28)
- **무슨 일**: 로드맵 §3.5를 "검색 엔진을 GraphRAG로 바꿀까"로 읽고 성능·가치 두 관점에서 꼼꼼히 재검토해 비채택을 결론지었다. PO가 정정했다. 이 로드맵을 시작한 동기는 "세무사가 KB를 거미줄 그래프로 보고 직접 고치는 중간층"이었다.
- **왜 조용했나**: 로드맵 항목 이름이 "GraphRAG"였다. 이름이 기술(검색 엔진)을 가리켜서, 목적(세무사의 이해와 수정)이 문서에서 흐려져 있었다. 재검토 결론 자체는 논리적으로 맞았다.
- **어떻게 잡았나**: PO가 결론을 듣고 바로 정정했다.
- **이제의 규칙**: 로드맵 항목을 재검토하기 전에 **"이 항목을 왜 시작했나"를 한 문장으로 PO에게 확인**한다. 항목 이름이 기술 이름이면 특히 그렇다.

### 우연히 무해한 합산 — 크레딧과 원화가 한 잔액에 (08-27)
- **무슨 일**: `ledger_entries.balance_after`가 기여 포인트(+10)와 정산 지급액을 구분 없이 더했다.
- **왜 조용했나**: v1의 pool은 작은 추상 숫자("cr")라 섞여도 눈에 띄지 않았다. 원화(수십만 단위)로 바꾸는 순간 터지는 구조였다.
- **어떻게 잡았나**: pool을 원화로 바꾸는 작업 중에 단위를 따라가다 발견했다.
- **이제의 규칙**: 단위가 다른 두 값은 같은 컬럼에 있어도 **`kind`로 집계에서 갈라 놓는다.** 한쪽의 단위나 규모를 바꿀 때는 그 값을 더하는 모든 자리를 찾는다.

### 괄호 하나 — `"(미분류)"`와 `"미분류"` (08-28)
- **무슨 일**: 프론트의 빈 메타데이터 플레이스홀더 상수가 `"(미분류)"`였고, 백엔드(`taxonomy.py`)가 저장하는 값은 `"미분류"`였다. 그래서 미분류 설명이 뜨지 않았고, 직전 커밋에서 넣은 "맨 뒤 정렬"도 동작하지 않았다.
- **왜 조용했나**: 미분류가 우연히 건수순으로도 뒤쪽이라 정렬 실패가 보이지 않았다.
- **어떻게 잡았나**: PO가 "미분류 설명이 안 뜬다"고 지적했다.
- **이제의 규칙**: 프론트가 백엔드의 값과 비교하는 문자열은 **백엔드가 실제로 저장하는 값을 그대로** 쓴다. 표시용 꾸밈은 비교가 끝난 뒤에 한다.

### 하드코딩된 플레이스홀더가 KB 전량을 덮었다 — "미분류" 100% (08-28)
- **무슨 일**: `conversation.ts:76`이 스냅샷 복원 시 `taxCategory`를 늘 `"미분류"`로 채웠고, 그 값이 적재까지 흘러 521건 전부가 미분류였다.
- **왜 조용했나**: UI에는 "미분류" 클러스터 하나로 정상처럼 보였다. 세목으로 묶는 화면이 생기기 전까지 아무도 이 값을 읽지 않았다.
- **어떻게 잡았나**: 그래프 스모크에서 PO가 "왜 전부 한 색이냐"고 물었다. UI 폴백을 의심하기 전에 데이터를 확인했다.
- **이제의 규칙**: 화면이 한 덩어리로만 보이면 **렌더보다 데이터를 먼저** 본다. 플레이스홀더는 서버가 적재 시점에 덮어쓰게 하고, 실제 값은 존중한다.

### 의미 유사도 클러스터는 번들 임베딩에서 오탐을 증폭한다 (08-27)
- **무슨 일**: 0.85 클러스터가 KB의 74%를 잡았다. 그대로 자동 정리했다면 286건이 지워질 뻔했다(대부분 정당한 기여).
- **왜 조용했나**: 의심했던 3건이 정확히 잡혀서 방법이 맞아 보였다. 진짜 중복과 정당한 별개 코멘트가 같은 클러스터에 섞여 있다는 것은 클러스터를 하나하나 까 봐야 드러났다.
- **어떻게 잡았나**: 의심 클러스터 하나(6건)를 segment와 대화 ID로 대조했다.
- **이제의 규칙**: 번들 임베딩(Q+A+C)은 질문 텍스트에 끌려간다. union-find의 transitive 묶음은 오탐을 키운다. **삭제 후보는 의미 유사도가 아니라 구조적 신호**(같은 segment, 짧은 간격)로 고르고, 의미 유사도는 "사람이 볼 목록"에만 쓴다.

### 부분 체크아웃 — push했는데 서버는 이상한 상태 (08-27)
- **무슨 일**: 7/18 이후 서버의 `git pull`이 root 소유 파일 때문에 중간에 실패했다. HEAD는 그대로인데 파일 내용은 새 버전이 된 상태로 한 달 넘게 남아 있었다.
- **왜 조용했나**: 파일 내용이 이미 최신이라 서버가 정상으로 동작했다. git 상태만 어긋나 있었다.
- **어떻게 잡았나**: 다음 `git pull`이 "로컬 미커밋 변경 다수"로 충돌하는 것을 보고, 전 파일을 origin과 diff해서 내용이 같음을 확인했다.
- **이제의 규칙**: 서버에서 sudo로 저장소 파일을 만지지 않는다. 충돌이 나면 덮어쓰기 전에 **diff로 내용이 같은지부터** 본다(같으면 `stash -u → pull → stash pop`). 세션을 시작할 때 로컬과 origin의 동기화를 확인한다.

### React `onWheel`은 passive라 `preventDefault`가 무시된다 (08-28)
- **무슨 일**: 그래프 휠 줌은 됐지만 페이지 스크롤이 같이 움직였다.
- **왜 조용했나**: 기능(줌)은 동작했고, 콘솔 경고로만 드러났다.
- **어떻게 잡았나**: 브라우저 스모크의 콘솔을 확인했다.
- **이제의 규칙**: 스크롤을 막아야 하는 휠·터치 핸들러는 `useEffect`로 `{ passive: false }` 네이티브 리스너를 붙인다. 스모크에서는 콘솔 경고도 결과로 본다.

- **무슨 일**: 18개 라벨 중 hue 간격 1~5°인 쌍이 다섯이었다.
- **왜 조용했나**: 세목이 전부 미분류였을 때는 색이 하나뿐이라 충돌할 일이 없었다. 재분류 뒤에야 드러났다.
- **어떻게 잡았나**: PO가 "전부 다른 색인지 체크해 달라"고 했고, 실제로 계산해 봤다.
- **이제의 규칙**: 알려진 범주 색은 **미리 배정**한다(골든 앵글). 같은 색 공식을 화면마다 따로 두지 말고 공용 모듈 하나로 둔다. 범주가 추가되면 그 모듈을 갱신한다.

### 테스트가 기다리지 않으면 앱 버그처럼 보인다 (08-27)
- **무슨 일**: 정산 E2E에서 3건 중 1건만 처리된 것처럼 보였다.
- **왜 조용했나(반대로 시끄러웠나)**: 결과가 그럴듯한 부분 실패라서 앱의 경합 버그로 읽혔다.
- **어떻게 잡았나**: DB로 직접 다시 확인했다. 스크립트가 `publish()` 완료를 기다리지 않고 강제로 페이지를 옮긴 것이었다.
- **이제의 규칙**: E2E가 부분 실패하면 화면 대신 **DB 상태로 판정**한다. 스크립트는 사용자처럼 완료를 기다리게 짠다.
