## 교훈 — 밟은 지뢰

### 받아 온 코드의 기본값이 프로토타입이었다 (10-04)
- **무슨 일**: 프로토타입 코드는 `NEXT_PUBLIC_DATA_MODE !== "live"` 이면 프로토타입이 기본값이었다(프로덕션 빌드 포함). `isPrototype` 은 "샘플 데이터"와 "새 UX" 두 뜻을 겸했다. 새 게스트 챗은 live 에서도 키워드를 보고 0.45초 뒤 고정 문장을 냈다.
- **왜 조용했나**: 데모 저장소에서는 그게 정상 동작이었다. 화면은 그럴듯하게 답했다.
- **어떻게 잡았나**: live 연결 작업 중 코드를 읽어 찾았다. 그대로 main 에 올렸다면 프로덕션이 가짜 주소로 API 를 쏘고 인증을 건너뛰었다.
- **이제의 규칙**: 받아 온 코드는 **환경 변수가 없을 때 무엇이 되는지**부터 본다. Vercel 변수를 먼저 넣고 push 한다.

### 프로토타입이 저장본에 가짜 판정을 씌우고, 관리자 화면을 열어 두었다 (10-06 밤)
- **무슨 일**: 새 답변 UI 코드는 저장된 대화를 불러올 때 **모든 답에 가짜 '판정 표시 예시'** 를 씌웠다. 새 관리자 기여 검토 화면은 막혀 있지 않았다.
- **왜 조용했나**: 프로토타입 시연에서는 샘플 답이라 예시가 자연스러웠다. 관리자 화면도 시연용이었다.
- **어떻게 잡았나**: 병합 충돌 10파일을 손으로 풀면서 읽었다.
- **이제의 규칙**: 프로토타입 병합은 "샘플 장식이 live 데이터에 닿는 자리"와 "권한 확인이 없는 새 화면"을 따로 찾는다. 막은 자리에는 시험을 더한다.

### "세무사 검수 선례"라는 라벨이 모든 근거에 붙어 있었다 (10-05)
- **무슨 일**: `llm.py`·`pipeline.py` 가 kbdict 가 아닌 근거를 전부 "세무사 검수 선례"로 표시했다. 심판례·질의회신을 넣으면 세무사가 확인한 것처럼 보일 자리였다.
- **왜 조용했나**: 그때까지 그 자리에 들어오는 것은 정말 검수 선례뿐이었다. 갈래가 늘어나자 뜻이 틀어지는 구조였다(9월 W09 의 "거짓 출처 문구"와 같은 성질).
- **어떻게 잡았나**: 적재 세션이 끝날 때 다음 세션의 함정으로 미리 적었고, 배선 때 층별 라벨로 나눴다.
- **이제의 규칙**: 근거 갈래를 더할 때는 **그 근거를 부르는 모든 문구**(라벨, 머리 문구, 도구 설명, 폴백 문구)를 같이 바꾼다.

### solar 는 규칙 서열 문구를 그대로 끌어다 썼다 (10-06)
- **무슨 일**: 세무사 사례로 답하면서 "검수 선례에 따르면"이라고 불렀다. 규칙에 적힌 서열("검수 선례 > 세무사 사례 …")을 그대로 가져왔다.
- **어떻게 잡았나**: 운영 흐름 시험의 답을 읽었다.
- **이제의 규칙**: 프롬프트에는 **실제로 들어온 층만** 적는다. 없는 층의 이름을 적으면 모델이 쓴다.

### fusion 쿼터 0 ≠ 갈래 끔 (10-06)
- **무슨 일**: KB2 를 빼려고 쿼터를 0 으로 두려 했다. fusion 은 남는 자리를 아무 갈래에서나 채워 KB2 가 되살아났다.
- **왜 조용했나**: 쿼터라는 이름이 "그 갈래 몫"처럼 읽힌다. 빈자리 채우기는 다른 줄(retriever L304)에 있었다.
- **어떻게 잡았나**: KB3 단독 측정에서 kb2 근거가 섞여 나왔다.
- **이제의 규칙**: 갈래를 빼려면 숫자가 아니라 **검색 경로 자체**를 바꾼다.

### 말로 부탁한 제약은 이번 주에도 하나도 지켜지지 않았다 (10-05 ~ 10-08)
- **무슨 일**: 원문 복사(어미 48% 수정), 쟁점 규칙 3줄(효과 0), 법인세법 제외(3회 연속 실패), 7문장·반복 금지(23문장·같은 결론 5번). 분류 게이트도 related 를 거의 안 쓰고 이분으로 기울었다. temperature 0 에서도 경계 판정이 흔들렸다.
- **어떻게 잡았나**: 매번 같은 문항으로 전후를 쟀다.
- **이제의 규칙**: solar 에게는 **처음부터 코드로** 강제한다. 입력에서 빼고(게이트·후보 제외), 출력을 자른다(번호 추출·반복 제거·`max_tokens`). 프롬프트는 효과를 잰 것만 남긴다.

### 앞 기록의 해석이 틀렸다 — "추출 흔들림" (10-06)
- **무슨 일**: 오전 기록은 P8 판정형의 undecided 를 "추출(LLM1) 흔들림"이라 적었다. 추출을 고친 뒤에도 P8 run_clinic 은 6/6 undecided 였다. 실제 원인은 추출 뒤의 `verify_decisive`/`missing_decisive` 단계였다.
- **왜 조용했나**: 증상(미판정)이 같았고, 추출 흔들림이 실제로 시민 질문에서 크게 보였다.
- **어떻게 잡았나**: 원인을 고친 뒤에도 증상이 남는 것을 측정이 보여 줬다.
- **이제의 규칙**: 원인을 적을 때는 **그 원인을 고치면 증상이 사라지는지**까지 확인한 뒤에 적는다. 틀린 기록은 다음 기록에서 틀렸다고 명시한다.

### 법령 오류는 지어낸 조문이 아니었다 (10-07)
- **무슨 일**: 세무사가 "관련 법령이 부정확·부적절하다"고 지적했다. 재 보니 인용 58개 중 54개가 근거 카드에 실제로 있던 조문이었다. 남의 사건 카드(당시 법 기준)의 조문을 질문에 맞는지 보지 않고 옮긴 것이었다.
- **왜 조용했나**: 날조 가드와 화이트리스트는 "근거에 있는 조문"을 통과시킨다. 형식은 맞고 맥락이 틀렸다.
- **어떻게 잡았나**: 인용을 하나씩 출처와 대조했다(세무사 판정이 아니라 진단).
- **이제의 규칙**: "근거에 있다"는 "맞다"가 아니다. 인용은 **질문 적합성**을 따로 골라야 한다(LLM3).

### 지연은 추측 말고 계측부터 — 병목은 Solar 가 아니었다 (10-08)
- **무슨 일**: 느린 이유를 LLM 으로 짐작하기 쉬웠다. 단계별로 재 보니 DB 벡터 전수 비교가 절반이었다. 꼬리는 반복 루프였고, 헤지로는 못 막았다(두 요청이 같은 확률로 루프).
- **이제의 규칙**: 지연은 단계별로 먼저 잰다. 새 작문 호출에는 `hedged_create` + `max_tokens` + `parse_segments` 를 붙인다. 재적재 뒤에는 서버를 재시작한다.

### 마이그레이션 번호가 두 저장소에서 겹쳤다 (10-08)
- **무슨 일**: 팀장 PR #5 의 `0046_social_registration` 과 그날 운영에 적용한 `0046_laws_articles` 가 같은 번호였다.
- **어떻게 잡았나**: PR 을 들이기 전 진단에서 찾았다. PR 마이그레이션은 운영 미적용이라 0047 로 바꿔 들였다.
- **이제의 규칙**: 외부 PR 을 받을 때는 **운영에 적용된 마지막 번호**와 대조한다.

### 운영 역할 탈취 구멍 — 판정이 두 군데, 한 군데도 막지 않았다 (10-08)
- **무슨 일**: 가입 트리거가 메타데이터의 role 을 믿었고, 자기 프로필 수정 정책이 role 열을 막지 않았고, 이메일 가입이 열려 있었다. 누구나 admin 이 될 수 있었다.
- **왜 조용했나**: 운영 계정이 데모 8개뿐이었다. live 프론트의 로그인 역할도 하드코딩 데모 목록으로 정해졌다.
- **어떻게 잡았나**: 소셜 가입 PR 을 진단하다 찾았다. 운영 Auth 의 이메일 가입이 이미 열려 있어 실제로 쓸 수 있는 구멍이었다. 0047 로 PR 보다 먼저 막았다.
- **이제의 규칙**: 가입·역할은 **서버 쪽 값(app_metadata)만** 믿는다. 역할 열은 트리거로 막는다. 가입 경로를 여는 배포 전에 역할 결정 경로를 전부 읽는다.

### 처리방침을 사실대로 쓰려다 결함 둘이 드러났다 (10-08)
- **무슨 일**: 탈퇴 기능이 없었다(domain_id 가 텍스트 키라 auth.users 를 지우면 대화가 고아로 남는다). KB 에 회원 질문 원문이 저장되고 있었다(마스킹은 공개 풀에만).
- **왜 조용했나**: 아무도 탈퇴하지 않았고, KB 원문을 사람이 읽을 자리가 없었다.
- **어떻게 잡았나**: 12개 법정 항목을 채우려고 저장 위치·보관·파기를 하나씩 확인했다.
- **이제의 규칙**: 개인정보 문서는 **코드 조사로** 쓴다. "무엇을 어디에 얼마나 두는가"를 적다 보면 결함이 나온다.

### 모든 로그인 사용자가 세무사 연락처를 읽고 있었다 — P1 (10-08 밤)
- **무슨 일**: `auditors_read` 가 로그인 사용자 전원이었다. 고객 화면 3곳이 registry 구독으로 세무사 이메일·전화·관리자 메모까지 받았다. 화면에는 이름만 썼다.
- **왜 조용했나**: 화면에 보이지 않았다. 데이터는 네트워크 응답에만 있었다.
- **어떻게 잡았나**: 가입 승인 설계 진단에서 RLS 를 읽었다.
- **이제의 규칙**: 고객에게는 **쓰는 칸만 주는 함수**(`list_expert_names`)를 둔다. 표 전체 읽기 권한은 본인·관리자로 좁힌다.

### role 만 바꾸면 domain_id 쪽 권한이 남는다 (10-09)
- **무슨 일**: 권한 판정이 역할 기준과 domain_id 기준 둘로 갈려 있었다. 강등하면 역할 기준 권한은 끊기지만 domain_id 기준(방 읽기, **메시지 쓰기**, 검수 CRUD 등)은 남았다. 강등자가 열린 방에 "세무사"로 글을 쓸 수 있었다.
- **왜 조용했나**: 강등이라는 상태 전이가 이전엔 없었다. domain_id 는 "본인 것" 판정이라 안전해 보였다.
- **어떻게 잡았나**: 강등 설계 진단에서 정책을 기준별로 갈라 표로 만들었다.
- **이제의 규칙**: domain_id 로 권한을 주는 정책을 새로 만들 때는 세무사 쪽에 `is_staff()` 를 붙인다. 상태 전이를 새로 만들면 **두 기준의 정책을 모두** 다시 본다.

### 탈퇴 경로가 새 표를 몰랐다 — P2 · 고아 (10-08 ~ 10-09)
- **무슨 일**: 0048 의 탈퇴가 `auditors`·`expert_profiles` 를 몰라 세무사 카드가 남았다. `expert_agents` 는 auth FK 가 없어 고아가 됐고, 세무사 사례는 set null 이라 이름째 남았다.
- **왜 조용했나**: 탈퇴 함수는 만든 날의 표 목록만 안다. 그 뒤에 생긴 표는 자동으로 들어가지 않는다.
- **어떻게 잡았나**: 다음 날 진단에서 차례로 찾았다(0049 · 0051 에서 보강).
- **이제의 규칙**: 사용자 데이터를 담는 표를 새로 만들면 **`_purge_account` 를 같이 고친다.**

### 꺼 둔 동안의 메시지에 늦게 답했다 — 0045 (10-06 밤)
- **무슨 일**: 상대 쪽 10초 백업 호출이, 스위치를 꺼 둔 동안 쌓인 메시지에 스위치를 켠 뒤 답했다.
- **왜 조용했나**: 단위 시험은 스위치 하나의 상태만 봤다. OFF → ON 전이는 운영 시나리오에서만 생겼다.
- **어떻게 잡았나**: 운영 확인(시험 방)에서 봤다.
- **이제의 규칙**: 스위치가 있는 기능은 **전이(OFF → ON) 순간**을 따로 시험한다.

### 시험 데이터 `{}` 하나가 화면 전체를 깨뜨렸다 (10-06 밤)
- **무슨 일**: 시험 대화 payload 를 `{}` 로 넣었더니 사장님 사이드바가 `payload.messages.length` 를 읽다 화면 전체가 깨졌다.
- **이제의 규칙**: 운영에 넣는 시험 데이터는 **실제 모양**(`{"messages":[]…}`)으로 넣는다.

### 로컬 `.env` 가 프로덕션 DB 를 가리킨다 (10-05)
- **무슨 일**: 로컬 서버로 챗을 보내면 운영 `rag.chat_turns` 에 기록된다.
