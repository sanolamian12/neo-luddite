# 결정 · 교훈 — W05 · 2026-08-30 ~ 09-05

> **이번 주 요지** — 결정은 둘 다 **"지워도 되는 근거가 있는 것만 지운다"** 는 쪽이었다. RAG에 독립 사본이 있는 것, RAG에 반영되지 않은 `submitted`만 지웠고, 한 단계 더 나간 `reviewed`는 남겼다. 교훈은 둘 다 **"그럴듯해서 의심받지 않은 것"** 이다. 하나는 정황이 들어맞던 "논문 데이터"라는 기억이고, 다른 하나는 에러도 손실도 없던 엉뚱한 삭제다. 여기에 하나를 더한다. 정정한 원문조차 데이터 출처를 "세무사 실작업"으로 다시 잘못 적었다.

## 결정

### 삭제 범위: 검수실 `submitted`만, `reviewed` 2건은 제외 (08-31, PO 확정)
- **무엇을**: "검수실(문장단위)에서 '제출됨'으로 표시된 데이터를 지워서 admin·auditor 양쪽에서 다 안 보이게". `status='submitted'` audits 52건과 딸린 reviews 16건·line_feedback 186건을 지웠다.
- **왜**: `reviewed`(검수저장, 이의가능)는 한 단계 더 진행된 상태다.
- **남은 것**: `reviewed` 2건을 지울지는 별도로 확인한다.

### finalized `session_evaluations` 39건 삭제 — RAG 사본이 있으므로 (08-31, 구현 판단)
- **무엇을**: 확정된 세션 평가 원본 39건을 지웠다.
- **왜**: `rag.passages`에 `source_kind='session_eval'` 독립 사본(텍스트 복사)이 `dedupe_key='session_eval:<id>'`로 39건 전부 active로 매칭됐다. 원본을 지워도 지식은 사라지지 않는다.
- 이 삭제는 안전했지만 사용자가 보던 화면과는 무관한 테이블이었다(→ 아래 교훈).

### 프로덕션 삭제의 안전 절차 표준 (08-31, 구현 판단)
- **무엇을**: RAG 매칭 재확인 → 백업 → rowcount 검증 → 커밋. 연쇄 삭제는 자식부터(`line_feedback` → `reviews` → `audits`) 지운다.
- **왜**: 프로덕션 Supabase에 직접 `DELETE`를 실행하는 작업이다. RAG 영향이 0이 아니거나 non-draft 리뷰가 섞이면 스크립트가 스스로 멈추게 했다.
- 원문은 향후 비슷한 작업에서 이 절차를 그대로 재사용하라고 적었다.

## 교훈 — 밟은 지뢰

### 기억과 실제가 달랐다 — "논문 때 쌓인 데이터" (08-31)
- **무슨 일**: admin 화면의 07-16~21 미확정 검수 항목을 PO는 ICTC 2026 논문 실험 데이터로 기억했다. 실제로는 제품 개발 작업(100건 일괄감사, RAG 재검증)이 남긴 검수 대기열이었다.
- **왜 조용했나**: 정황이 들어맞았다. 같은 주에 A/B 리포트가 연달아 나왔고, 07-29 커밋이 그 리포트들을 논문 실험 기록으로 묶었다. 그래서 가설이 의심받지 않았다.
- **어떻게 잡았나**: 선행 조사 문서(`docs/academic paper/db_backup_260806/README.md`)를 찾아 읽었다. 이전 세션이 같은 질문에 이미 답을 남겨 두었다. `history/260718`을 다시 읽어 진짜 원인(RLS 버그)도 확인했다.
- **이제의 규칙**: **기억보다 히스토리 문서와 DB 실측이 우선한다.** 같은 질문을 전에 조사한 문서가 있는지부터 찾는다.

### 원문의 정정도 출처를 다시 잘못 적었다 — "세무사 실작업" (08-31)
- **무슨 일**: 원문은 "논문 데이터"를 정정하면서 결론을 "세무사들이 실작업으로 남긴 검수 대기열"이라고 적었다. auditor·auditor2·auditor3의 코멘트와 세션 평가는 감사 모드 Claude 산출물이다.
- **왜 조용했나**: 계정 이름이 "auditor"(검수자)이고 화면도 세무사용 검수실이다. 첫 오독을 바로잡은 직후라 결론이 맞아 보였다.
- **어떻게 잡았나**: 이 재구성에서 README 규칙 1(감사 데이터 출처)에 따라 고쳐 적었다.
- **이제의 규칙**: auditor 계정의 산출물은 "검수 코멘트(감사 모드 Claude 산출물)"로 적는다. 사람(세무사)이 개입한 자리는 승인 게이트와 인용·원문 대조뿐이다. 논문에서 인용할 때도 같다.

### 안전한 삭제가 엉뚱한 테이블이었다 (08-31)
- **무슨 일**: "완료" 화면의 미확정 항목을 치우려고 `session_evaluations` 39건을 지웠다. "완료" 화면(`/audit/results`, `results-table.tsx`)은 `audits`+`reviews`+`line_feedback`을 읽는 화면이었다. 세션 총평은 별개의 "배선실(정성평가)" 탭 몫이다.
- **왜 조용했나**: 삭제 자체가 안전했다. RAG 손실이 없었고 에러도 없었다. DB 쪽 검증은 "지운 것이 안전한가"만 확인했다.
- **어떻게 잡았나**: 사용자가 auditor로 재로그인했는데 화면이 그대로였다.
- **이제의 규칙**: 화면에 보이는 것을 지우려면 **삭제 전에 화면 → 컴포넌트 → 실제 소스 테이블을 먼저 추적**한다. 삭제 뒤에는 그 화면을 다시 연다.

### (과거 원인) RLS에 막힌 갱신은 "0행"으로 조용히 실패한다 (7월, 08-31 재확인)
- **무슨 일**: `session_evaluations`에 admin 쓰기 RLS가 없어서 관리자의 결정이 "0행 갱신"으로 끝났다. 미확정 항목이 쌓인 근본 원인이다.
- **왜 조용했나**: 에러가 아니라 0행 갱신이라 화면에서는 실패로 보이지 않았다.
- **어떻게 잡았나**: 7월에 `0015_session_eval_review.sql`로 고쳤다. 이번 주에는 원인을 다시 확인만 했다.
- **이제의 규칙**: RLS 아래의 UPDATE는 갱신 행 수를 확인한다. 0행은 실패로 다룬다.
