## 결정

### KB2

#### 근사 동의어 접기: 코사인 0.75 ∪ 문자열 규칙(3자 이상) (09-13, PO 확정)
- **무엇을**: merge가 쪼갠 레이블을 분류 직전에 접는다. 문자열 규칙은 부분문자열 / `·` 토큰 / 공통 접두이고 3자 이상만 본다. 재부착 임계값 0.70은 그대로 둔다.
- **왜**: 0.70은 세대 내부 접기에서 오탐(0.7166)을 끌어들여 무관한 세목 셋을 뭉쳤다. 0.75와 0.80은 결과가 같다(안정 구간). 진짜 동의어 일부가 코사인 선 아래(0.6954, 0.6326)라 문자열 규칙과 합집합으로 쓴다. 두 글자 조각(`리스`, `개인`)이 무관한 세목을 잇지 않게 3자 이상으로 한다.
- **기각**: 0.70(오탐).

#### 리필: LLM 1회, 모자라면 관찰 횟수순 코드 리필 (09-13, PO 확정)
- **왜**: 접기만 하면 A/B/C 실험의 C(46.4%, 커버리지 하락)다. 코드 리필만 하면 1회 관찰 레이블(72개 중 52개)이 돌아와 가독성을 해친다.
- **기각**: 접기만 / 코드 리필만.

#### 대표 레이블 = 맵 관찰 횟수 최다 (09-13, PO 확정)
- 분류기는 레이블만 본다(tool enum). 대표가 곧 묶음의 유일한 이름이다.

#### 접기에 화면 단계를 새로 만들지 않는다 (09-13, 구현 판단)

#### 0.70~0.74 구간에서 임계값을 낮추지 않는다 (09-13, 구현 판단)
- 리필이 이 구간의 근사 중복 셋(0.7348 · 0.7201 · 0.7047)을 들였지만, 같은 구간에 오탐(0.7166)이 있어 선을 그을 수 없다. 알려진 한계로 둔다.

#### 대목 자동 그룹화: 2단 스키마(대목 확정 → enum 배정) (09-16, 구현 판단)

#### 승계는 이전 세대의 오배정도 물려받는다 (09-16, 구현 판단)

#### 코드로 '기타'류 후보를 자동 제외하지 않는다 (09-16, PO 확정)
- 세무사가 쓰는 대목을 코드가 임의로 빼는 것이라서다(사용자와 합의).

#### 몰림에 선을 긋지 않는다 — 가드보다 계측 (09-16, 구현 판단)

### KB 3층 검색 — 설계

#### 3층 구조 + RRF 순위 융합 (09-16, PO 확정)
- **무엇을**: L0 규범(상시 주입) / L1 사전(검색, doc2query) / L2 KB2. 점수 대신 순위로 합산하고 쿼터로 독식을 막는다. 권위 서열은 엔진 판정 > L0 > L2 > L1이다.
- **왜**: 시드 6종은 성격이 다른 두 덩어리라 한 코퍼스로 뭉치면 둘 다 망가진다. 지금의 하드 폴백(`HybridRetriever`)은 융합이 아니라 경쟁이고, 코퍼스마다 임계값을 따로 튜닝하는 것이 그 증상이다.
- 「후일담」 10/6 L2를 포함한 KB 구조가 교체되고 프로덕션 챗은 KB3 단독이 됐다.

#### L0는 검색하지 않고 system prompt에 상시 주입 (09-16, PO 확정)
- 해석 원칙은 질문마다 top-k로 뽑을 성질이 아니라 어떤 질문에든 적용되는 판단 규칙이다. 부수 효과로 "세무사가 KB를 고치면 AI의 사고방식이 바뀐다"가 성립한다.

#### 단계 순서 P1 → P2 → P3 → P4 (09-16, PO 확정)
- 융합기 없이 사전층을 먼저 만들면 KB2와 경쟁만 한다. 그릇을 먼저 만든다.
- **불변 원칙**: 디폴트 `?ragSource=rag`는 바꾸지 않고 병렬로 얹어 A/B로 비교한다(→ 9/18에 갱신, 아래).

#### P1 원본 = (c) 백엔드 md + `load_norms()` 경계 (09-16, PO 확정)
- **왜**: 규범 시드 전문 17.4k자는 시스템 프롬프트(1,028자)의 17배라 요약이 필수다. 요약이 붙으면 (a)의 유일한 편익인 자동 동기화가 사라진다. LLM 요약은 비결정적이라 규범이 될 수 없다. (b)는 P3에서 거의 공짜다.
- **기각**: (a) 빌드 시 JSON 내보내기(비용은 내고 편익은 못 받음), (b) DB 이관(P3로 이월).
- **재오픈 신호**: L0를 요약 없이 전문 주입하는 설계로 바뀌면 (a)가 되살아난다.

#### "두 원본" 문제는 역할 분리로 푼다 (09-16, 구현 판단)
- 프론트 시드 = 사람이 읽는 해설(길다, 표·예시), 백엔드 md = AI가 따르는 규범(짧다, 명령형). 역할이 다른 두 문서라 동기화 의무가 없다.

#### `master`는 L1이 아니라 L0 (09-16, 구현 판단 — 정정)
- 문서가 스스로 "본 지식 베이스는 당신의 시스템 프롬프트다"라고 말한다. 확정 배치는 L0 = master·frameworks·pitfalls / L1 = glossary·cases·occupations.

#### doc2query 채택, HyDE 보류 / 외산 리랭커 금지, BM25·pg_trgm은 무관 (09-16, 구현 판단)
- doc2query는 오프라인 1회 비용에 런타임 0이다. HyDE는 턴마다 LLM 1회 지연이 붙는다. BM25·pg_trgm은 모델 호출이 아니라 국내 AI 트랙과 무관하다.

#### 코퍼스 확장 6규칙 (09-16, PO 확정)
- ① 계측 먼저 ② precision 감시 ③ 한 번에 한 소스 ④ 라이선스 ⑤ 권위 등급 ⑥ 소급 가능(status 전환). 계측 없이 넣으면 품질이 왜 변했는지 영영 모른다.

#### 청킹: 짧은 절 병합, 링크·메타 절 제외, `ingest_kb_document()` 미사용 (09-17, 구현 판단)

#### doc2query 프롬프트에서 예시 문장 제거 (09-17, 구현 판단)

- P5 규범 테이블이 옆에 설 수 있게, `origin='seed'`로 소스 단위 되돌리기가 되게.

#### 규범 md는 그대로, 라벨 규칙은 코드 문구로 (09-17, 구현 판단)

## 교훈 — 밟은 지뢰

### LLM에게 "이미 있는 것은 빼라"고 시키지 말고, 뺀 목록을 줘라 (09-13)
- **무슨 일**: KB2 리필 드라이런에서 모델이 1.8초 만에 후보 목록 머리를 베꼈다. 11개 전부가 기존 레이블과 겹쳐 거부됐다. 프롬프트에 "겹치는 건 내지 말 것"이 있었다.
- **왜 조용했나**: 오류 없이 코드 리필로 넘어갔다. 결과 목차는 30칸이 다 차 있었다.
- **어떻게 잡았나**: `refillFromLlm`과 `refillFromTally`를 따로 센 계측이 드라이런에서 LLM 0 / 코드 8을 보여 줬다.
- **이제의 규칙**: 무엇이 덮였는지처럼 규칙이 명확한 판정은 코드가 하고, 모델에게는 코드가 할 수 없는 판단만 남긴다. 폴백이 있는 경로는 **주 경로와 폴백을 따로 센다.**

### 같은 임계값이라도 쓰이는 구조가 다르면 다시 잰다 (09-13)
- **무슨 일**: 재부착(세대 간)에서 전수 정탐이던 0.70이 접기(세대 내부)에서 오탐 한 건으로 세목 셋을 뭉쳤다.
- **왜 조용했나**: 같은 KB2, 같은 임베딩, 같은 레이블 축이라 같은 값이 통할 것처럼 보였다.
- **어떻게 잡았나**: 새 세대 30개의 세대 내부 쌍을 전수로 다시 뽑았다.
- **이제의 규칙**: 임계값은 값이 아니라 **"그 선 위에서 무엇을 하느냐"와 한 쌍**이다. 최근접 1위 선택과 모든 쌍 추이적 묶음은 다른 구조다.

### 세대는 시각이 아니라 상태로 가른다 (09-13)
- **무슨 일**: `g1_labels.py`가 `created_at` 간격 1시간으로 세대를 갈라, 붙어 있던 두 회차를 합쳐 "최신 세대"를 60개로 잡았다.
- **어떻게 잡았나**: 세대 내부 쌍을 다시 뽑는 출발점에서 걸렸다. `status='active'`로 직접 뽑았다.
- **이제의 규칙**: 세대 경계는 `status`로 가른다.

### 회차 상승을 개선으로 읽지 않는다 (09-13, 09-16)
- **무슨 일**: 접기 회차의 배정이 64.4% → 78.7%로 올랐다. 대목 첫 실증에서 최대 묶음이 43% → 32%로 내려갔다.
- **왜 위험했나**: 둘 다 원하던 방향이라 효과로 읽고 싶어진다. 그러나 A/B/C 실험은 "중복 제거는 커버리지를 안 올린다"였고, 전체 파이프라인 회차 편차는 미측정이다. 대목 쪽은 목차가 통째로 바뀐 회차였다.
- **이제의 규칙**: 1회 측정으로는 "떨어지지 않았다"까지만 주장한다. 비교하기 전에 **같은 축인지**부터 본다(`largestGroup`은 잔여분 기준이라 이전 회차와 축이 달랐다).

### "세대를 건너야 하는 것" 목록이 불완전했다 — 대목 배치가 매일 밤 사라졌다 (09-16)
- **무슨 일**: 재구조화가 새 세대 문서를 `group_id=null`로 만들어 대목 배치가 회차마다 100% 소실됐다. 세무사가 손으로 배치해도 그날 밤 예약 회차가 지웠다.
- **왜 조용했나**: 9/12에 G2로 문장 승계를 고쳤기 때문에 "세대 승계는 해결됐다"고 여겨졌다. 대목은 이름만 남아 화면에 보였다.
- **어떻게 잡았나**: DB 실측 — group_id를 가진 16건이 전부 archived였다.
- **이제의 규칙**: 세대교체 코드를 고칠 때는 **세대를 건너야 하는 것의 목록을 전수 점검**한다(문장, 대목 배치, 사람의 손댐).

### 말로 부탁하는 제약은 스키마로 옮긴다 (09-16)
- **무슨 일**: "모든 세목은 정확히 하나의 대목에, 대목은 3~8개"를 프롬프트로 부탁했다. 모델은 누락 9·중복 1을 냈고, 스키마를 1:1로 뒤집자 이번엔 개수 제약을 어겨 17개로 쪼갰다.
- **왜 조용했나**: 기존 구현이 원래부터 9건을 빠뜨리고 있었지만 화면에는 "미분류"로만 보였다.
- **어떻게 잡았나**: 같은 29세목, temperature 0으로 조건 4개를 나눠 쟀다.
- **이제의 규칙**: "빠짐없이 / 정확히 하나 / n개"는 **출력 형식으로 실패를 불가능하게** 만든다(목록 확정 → enum 배정). "대목다움" 같은 판단만 프롬프트에 남긴다.

### 정상 회차가 "실패했습니다"를 띄웠다 (09-16)
- **무슨 일**: 자동 그룹화가 기존 대목을 재사용하면 생성 0이 되고, 화면은 생성 0을 실패로 읽었다.
- **이제의 규칙**: 성공 판정은 목적(배정된 수, `documentsGrouped`)으로 한다. 부산물(생성 수)로 하지 않는다.

### "한 번 더 누르면 된다"는 틀린 조언이었다 (09-16)
- **무슨 일**: 자동 그룹화 결과가 몰렸을 때 재실행을 권했다. `auto_group`은 `group_id is null`인 세목만 처리하므로 재실행은 남은 1건만 건드린다.
- **어떻게 잡았나**: 세션 중에 코드를 다시 보고 정정했다.
- **이제의 규칙**: 몰림의 처방은 재실행이 아니라 **흡수원 제거**다. 조언하기 전에 그 함수가 무엇을 입력으로 받는지 확인한다.

### 드라이런 계측이 거짓말하는 자리 — 최종 dict로 중복을 세면 늘 0 (09-16)
- **이제의 규칙**: 중복·누락은 **모델 원응답 기준**으로 센다. 최종 매핑은 이미 중복을 지운 결과다.

### 숫자는 근거 SQL로 판정한다 — `groupsCreated 6` (09-16)
- **무슨 일**: 첫 실증에서 신규 대목 6개가 재사용 버그처럼 보였다.
- **어떻게 잡았나**: 활성 대목 중 이름이 겹치는 것을 조회하니 0행이었다. 새 세목용 새 이름이었다.
- **함께**: `embedFailures`가 비었다는 것은 "물어봤는데 낮음"이지 "못 물어봄"이 아니다. 두 실패를 섞어 읽지 않는다.

### 질문의 전제부터 코드로 확인한다 — "매칭률"이 아니라 "검색 경로 밖" (09-16)
- **무슨 일**: PO는 사전형 KB의 매칭률을 걱정했다. 실제로는 그 KB가 프론트 정적 시드라 검색에 아예 쓰이지 않았다(품질 기여 0). 적재 함수는 있었지만 호출자가 없었다.
- **왜 조용했나**: 세무사 화면에는 KB가 멀쩡히 보였다. 화면에 있으면 쓰이고 있다고 여기게 된다.
- **어떻게 잡았나**: 백엔드 grep 결과가 없었다.
- **이제의 규칙**: 질문에 답하기 전에 **질문의 전제가 코드에서 성립하는지** 먼저 본다.

### 코퍼스마다 임계값을 따로 튜닝하고 있다면 그것이 증상이다 (09-16)
- 하드 폴백 구조에서는 두 임계값의 상대값이 승자를 정한다. 순위 융합으로 바꾸면 스케일 차이가 사라진다. 코퍼스가 늘기 전에 **융합기부터** 만든다.

### 문서가 자기 정체를 말하고 있었다 — master 오분류 (09-16)
- 처음에 master 시드를 L1(사전)로 분류했다. 문서가 스스로 "당신의 시스템 프롬프트"라고 적고 있었다. 분류할 때는 문서의 머리말부터 읽는다.

### 라벨을 결과로 추정하지 않는다 — `rag_source_used` (09-16)
- **무슨 일**: `rag_source_used`를 `passages[0].source_kind`로 추정했다. fusion에서는 1위 코퍼스에 따라 'kb2'/'rag'로 오기록될 자리였다.
- **어떻게 잡았나**: P2 착수 전 문서 정정 단계에서 미리 찾았다.
- **이제의 규칙**: 경로 라벨은 **검색기 타입**으로 붙인다.

### RRF는 겹치지 않는 코퍼스에서 교차 배치로 퇴화한다 (09-16)
- 같은 문서가 두 갈래에 동시에 나오지 않으면 합산이 일어나지 않는다. RRF의 이득은 같은 코퍼스를 두 방식으로 찾을 때 난다. 이득을 기대하기 전에 갈래들이 겹치는지 본다.

### 채점 절대치는 회차마다 움직인다 (09-16, 09-17)
- 같은 검색 결과에 4-way는 +4~6pp, 5-way는 기본 ±1pp·엄격 ±2~5pp가 이동했다. **판정은 같은 회차 안의 순위로만** 한다.

### 기본 채점기는 일반론에 관대하다 (09-17)
- **무슨 일**: 사전 청크 27개짜리 kbdict 단독이 far 문항 useful 60.8%를 받았다. 점수 구간과 상관없이 등급2가 약 40%로 평평했다.
- **왜 조용했나**: 점수는 그럴듯했고 fusion_kbdict의 useful도 크게 올랐다.
- **어떻게 잡았나**: 원문을 열었다. "의료장비 업그레이드는 수선비?"에 차량유지비 인용 청크가 2점이었다.
- **이제의 규칙**: 사전형(일반 원칙) 코퍼스는 **엄격 채점**으로 잰다. 채점기가 평평하면 원문부터 본다.

### 프롬프트의 어조 예시도 지시로 작동한다 (09-17)
- **무슨 일**: P4 1회차에서 거짓 세무사 귀속이 오히려 6건으로 늘었다. 시스템 프롬프트의 어조 예시("유사 사례에서 세무사들은 ~로 보았습니다")가 그 문장을 직접 지시하고 있었다.
- **어떻게 잡았나**: 걸린 문장의 모양이 예시와 같았다.
- **이제의 규칙**: 예시 문장은 **언제 쓰는지 조건을 붙여** 넣는다(검수 선례가 근거일 때만).

### 라벨만, 규칙만으로는 효과가 없다 (09-17)
- 분해 실험에서 라벨만 29/32, 규칙만 29/32, 둘 다 9/32였다. 출처 구분은 **라벨과 사용 규칙을 함께** 넣는다.

### 소표본 착시 — 루프가 P4 쪽에 몰려 보였다 (09-17)
- 1/64 vs 6/64로 보였지만, 변형 4 × 근거 2 × 32로 분해하자 6/128 vs 10/128로 구분이 안 됐다. 기저 현상이었다. 처방을 만들기 전에 분해한다.

### 데이터 변경 CTE가 넣은 행은 같은 문장의 본 쿼리에 안 보인다 (09-17)
- `with d as (insert…), v as (insert…) update … from v` 한 문장에서 active_version_id가 걸리지 않았다. 문장을 나눈다.

### epoch 계산은 연도부터 확인한다 (09-17)
- 확정 시각을 2025년 기준으로 계산했다가 1789516800000(2026-09-16 00:00 UTC)으로 정정했다.

### 점검 CLI와 런타임이 다른 설정을 읽었다 (09-17)
- **무슨 일**: 첫 배포 로그가 `출처 md`였다. CLI는 `api/main.py`를 안 거쳐 `.env`를 안 읽었다.
- **왜 조용했나**: 런타임은 db를 읽고 있어서 서비스는 정상이었다.
- **이제의 규칙**: 점검 도구는 **런타임과 같은 설정 경로**로 띄운다.

### 측정 경로가 그 기능을 지나는지 먼저 본다 (09-17)
- **무슨 일**: 규범 v2 효과를 기본 경로에서 쟀더니 전후 8/8 동일이었다. 그 질문은 고정 안내문으로 끝나 작문 LLM을 타지 않았다(무효 측정).
- **이제의 규칙**: 규범 효과는 **작문 경로(fusion 자문)** 에서 잰다. 측정 전에 질문이 측정 대상 코드를 지나는지 확인한다.

### 거버넌스 규칙보다 신원이 먼저다 (09-17)
- **무슨 일**: P5까지 신원을 요청 본문으로 받았다. "N명 승인"을 얹어도 본문만 바꾸면 위조된다.
- **어떻게 잡았나**: P5 후속에서 PO가 다세무사 확정 위험을 열린 과제로 제기했고, 그 전제로 백엔드 인증이 기록됐다.
- **이제의 규칙**: 승인·이의 같은 거버넌스는 **인증된 신원 위에만** 세운다. 본문 신원 위의 N명 승인은 장식이다.

### 토큰 필수화는 2단계로 배포한다 (09-17)
- 백엔드 `optional`(검증하되 없으면 통과) → 프론트 → `required`. 한 번에 바꾸면 구 프론트가 깨지는 창이 생긴다.

### 마이그레이션 승인 전에 상태 전이를 롤백 트랜잭션에서 돌린다 (09-17)
- `_tx`/`_get_conn`을 단일 커넥션·savepoint로 바꿔 스키마 + 로직을 실DB에서 돌리고 되돌렸다(22 + 12항목).

### 제약 이름은 추정하지 않고 조회한다 (09-17)
- `pg_constraint`로 `versions_status_check`를 확인한 뒤 교체했다.

### 브라우저 테스트는 새 빌드인지부터 확인한다 (09-17)
- Vercel 반영을 기다리는 동안 옛 UI로 절반만 실행되는 사고를 막으려고, 화면 문구로 빌드를 확인하고 아니면 변경 없이 중단하게 짰다. 탭 패널은 비활성 탭도 DOM에 남으니 선택자를 `tabpanel` 안으로 좁힌다.

### Windows 셸 curl의 한글 JSON은 422/400이 난다 (09-16, 09-17)
- 파이프라인에 도달하지 않는다. 스모크는 Python urllib로 한다. 챗 페이로드는 `{"userInput": {"text": …}}`다.

### 기록된 혼입원이 틀렸다 — 이전 결론도 원문으로 다시 본다 (09-18)
- **무슨 일**: P4와 로드맵은 "rag 단독 혼입원 = 번들 속 옛 [AI 답변]"이라고 적었다. P4의 고정 근거 다섯 건은 전부 `[질문]`에도 같은 수치가 있었다. 전수 정규식으로 보니 남의 사안 수치는 세 섹션에 흩어져 있었다.
- **왜 조용했나**: P4 측정은 그 결론과 모순되지 않았다. 다른 설명을 시험하지 않았을 뿐이다.
- **어떻게 잡았나**: 재적재를 결정하기 전에 PO가 혼입원부터 특정하라고 했다.
- **이제의 규칙**: 큰 작업(재적재)의 근거가 되는 **이전 결론은 섹션별 전수로 다시 확인**한다.

### 수치를 지우는 처방은 날조를 부른다 (09-18)
- **무슨 일**: 전 섹션 마스킹이 근거 코멘트의 "경조사비 20만원 기준"까지 가렸다. 모델은 30만원, 3만원을 지어냈다(20만원 22 → 0/32).
- **왜 조용했나**: leak 지표로는 혼입이 줄어 보였다.
- **어떻게 잡았나**: 기준액 서술을 값별로 분포표로 만들었다.
- **이제의 규칙**: 정규식은 "남의 사안 수치"와 "법정 기준 수치"를 가를 수 없다. **수치를 지우는 처방은 쓰지 않는다.**

### 긴 지연을 루프로 추정했다 — 실제는 120초 멈춤 (09-18)
- **무슨 일**: 긴 꼬리를 반복 루프 탓으로 봤다. 실제로는 60초 초과 35회 중 루프가 2회였고, 지연이 124~129초·241초에 군집했다.
- **왜 조용했나**: SDK 재시도는 로그를 남기지 않는다. 재시도가 즉시 성공해서 오류도 없었다.
- **어떻게 잡았나**: 지연 분포의 군집 모양을 읽고, 순차 64회로 재현해 멈춤 0을 확인했다.
- **이제의 규칙**: 지연은 **분포 모양**으로 판독한다. 동시와 순차를 나눠 재현해 원인이 동시성인지 가른다.

### 규칙만으로는 모델이 따르지 않는다 — 입력에서 뺀다 (09-18)
- **무슨 일**: KB2 합성에 "오류로 지적된 [AI 답변]을 옮기지 말 것"(규칙 6·7)을 넣어도 20%가 옮겨졌다. 입력에 남아 있으면 커버 압력(규칙 5) 때문에 뽑는다.
- **어떻게 잡았나**: 드라이런에서 변형 다섯을 나란히 비교했다.
- **이제의 규칙**: 모델이 따르지 않을 규칙 대신 **입력에서 뺀다.**

### 수동 은퇴는 원인을 고치지 않는다 (09-18)
- 은퇴한 문장은 재구조화 뒤에도 유지되지만, 같은 주장이 새 `system_synthesis` 문장으로 다시 생긴다. 원인(합성 입력)을 고쳐야 한다.

### 1차 정규식은 과대 집계한다 — 걸린 문장을 전부 본다 (09-18)
- 판정형 혼입 1차 정규식이 엔진 근거 문구와 올바른 문장까지 잡았다. 걸린 문장을 눈으로 다 본 뒤 규칙을 좁혀 재분류했다.

### 혼입처럼 보인 것이 엔진 잔재였다 — "회원권 명의" (09-18)
- 복리후생 답변의 "회원권 명의"는 근거에서 온 것이 아니라 엔진 필요증빙 목록(헬스장 사안 잔재)에서 왔다. 근거 코퍼스의 검수 코멘트가 이미 "환각 증빙"으로 지적해 두었다. 이상한 문구는 **엔진 출력부터** 거슬러 본다.

### 스캔 수치는 하한이다 (09-18)
- 확인된 오류 1건이 태그 없는 세션 평가 출처라 스캔에 안 걸렸다. 그래서 30건은 하한이다. 스캔 조건이 놓치는 출처를 함께 적는다.

### 전환 전후는 요청값이 아니라 시각으로 가른다 (09-18)
- `rag_requested`는 명시 요청값만 담아 디폴트 전환 전후가 같은 `null`이다. 데모 계정 이름도 확인하고 쓴다(`auditor1`은 없고 `auditor`·`auditor2`가 있다).

### "수치를 지어내지 마세요"가 있어도 지어냈다 — 사후 가드를 병행한다 (09-18)
- **무슨 일**: 자문 경로에 규칙 2가 있었는데 11/96이 날조했다. 판정형은 접대비 한도를 64회 중 23회, 회차마다 다른 값으로 말했다.
- **왜 조용했나**: 날조된 한도는 그럴듯한 숫자였고, 판정 카드는 맞았다.
- **어떻게 잡았나**: "질문·엔진·근거·규범 어디에도 없는 수"를 세는 지표를 만들었다.
- **이제의 규칙**: 수치는 **규칙 + 출력 가드**로 막는다. 가드는 문장 단위로 빼고(숫자만 지우면 문장이 깨진다), 출처에는 이전 **사용자** 발화만 넣는다(앞선 답변의 날조가 다음 턴 근거로 되살아나지 않게).

### 측정 도구의 산술 허용이 틀린 답을 통과시켰다 (09-18)
- 1차판은 "20명 = 5+15" 같은 우연을 derived로 봤다. 2차판은 남의 사안 "1인당 10만원"으로 틀린 "20명"을 통과시켰다. 피연산자를 **사용자·엔진 수로 한정**했다.

### 카드와 본문이 충돌하면 엔진 근거 문구를 의심한다 (09-18)
- 카드는 "복리후생비 인정"으로 계정을 단정했고, 본문은 "급여성 상여"라 반박했다. 원인은 엔진 근거 문구였다. 맞는 쪽(판정·금액)을 남기고 문구를 고쳤다.

### 내부 문서의 출처 표기가 바깥으로 나가면 안 된다 (09-18)
- **무슨 일**: 내부 md가 검수 코멘트의 출처를 "세무사 코멘트"라고 적었다. 실제로는 감사 모드 AI 산출물이다.
- **어떻게 잡았나**: 세무사에게 보낼 PDF·엑셀을 만들면서 표기를 점검했다.
- **이제의 규칙**: 외부 전달본에는 **"검수 코멘트(AI 평가 도구 작성, 참고용)"** 로 쓴다. 제품용 검토 요청과 논문 맹검 표본(KIIS)은 한 표로 섞지 않는다.

### 게이트 k는 워커 수만큼 곱해진다 (09-18)
- 게이트는 프로세스 안에 있다. 전제는 `uvicorn --workers 1`이다. 워커를 늘리면 k를 다시 잰다.

### 학회 공식 사이트가 메일보다 상위다 (09-16)
- **무슨 일**: 채택 메일은 6페이지, 학회 공식 페이지는 4페이지였다. 메일을 근거로 6p판 주력을 정해 두었었다.
- **왜 조용했나**: 메일은 학회가 보낸 명문 근거라 믿을 만해 보였다. 메일 본문은 여러 학회에서 재사용되는 템플릿이라 틀릴 수 있다.
- **어떻게 잡았나**: 제출 직전에 공식 제출 안내 페이지를 다시 열었다.
- **이제의 규칙**: 마감 직전에 **공식 페이지를 한 번 더 연다**(비용 5분, 안 열었을 때 비용은 게재 실패).

### EDAS 저자명은 각자의 프로필에서 온다 (09-16)
- 논문 화면의 저자 편집으로는 남의 이름을 못 바꾼다. 4명이 각자 고쳐야 했다. eCF는 EDAS 정정 **뒤에** 연다(틀린 이름으로 서명되면 proceedings에서 빠진다). PDF eXpress는 User profile이 아니라 Dashboard → Create New Title로 간다. Travel Grant처럼 마감이 급해 보이는 항목은 자격부터 본다(해외 소속 대상이라 비대상이었다).
