이름·그룹·상태 변경은 전부 **단일 UPDATE**라 "읽고 → 몇 분 고치고 → 저장" 구간이 없다. 마지막 쓰기가 이겨도 잃는 것은 이름 한 줄이다. 문서 단위 락은 넣지 않았다.

### 야간 예약 — pg_cron이 아니라 DB 예약 + 백엔드 폴러 (09-10)
로드맵은 pg_cron(0006 하차장 스냅샷)을 선례로 지목했지만 맞지 않았다. 스냅샷은 순수 SQL 함수라 DB 안에서 끝난다. 재구조화는 **Upstage API 호출(Python)이 본체**라 DB가 스스로 못 한다. pg_cron이 할 수 있는 것은 pg_net으로 백엔드를 깨우는 것뿐이고, 그건 폴러 하나보다 부품이 는다.

| 붙은 것 | 내용 |
|---|---|
| 예약 상태 | `kb2.synthesis_jobs.status='scheduled'` + `scheduled_at` |
| 폴러 | `backend/api/rag/kb2_scheduler.py`, FastAPI lifespan에서 기동, 1분마다 만기분(`scheduled_at <= now`)을 집는다 |
| claim | 단일 `UPDATE … WHERE status='scheduled'` + `FOR UPDATE SKIP LOCKED`. 폴러가 겹치거나 워커가 늘어도 같은 job을 두 번 실행하지 않는다. 현재 배포는 `uvicorn --workers 1` |
| 엔드포인트 | `POST /admin/kb2/restructure`(body에 `scheduleAt` 있으면 예약), `GET .../scheduled`, `POST .../{id}/cancel` |

- 예약의 진실이 DB라 백엔드가 재시작·크래시해도 예약은 남는다. 지난 예약은 다음 기동 때 곧바로 집힌다.
- **라우트 순서**: `/scheduled`(9/11의 `/latest`도)가 `/{jobId}`보다 위에 있어야 job id로 안 잡힌다.
- 시각은 서버가 아니라 브라우저(KST)에서 계산한다. 서버가 도쿄 박스라 서버 로컬 시간으로 "새벽 3시"를 해석하면 어긋난다.

9/10 후반에 프로덕션에서 처음 실제로 발화시켰다. +0초 `scheduled` 생성(2분 뒤 예약) → +178초 `running`. 폴러가 예약시각 +60초에 집었다. 파이프라인은 Oracle 서버 프로세스 안에서 돌고 로컬 스크립트는 관찰자일 뿐이라 컴퓨터를 꺼도 무관하다.

### 맵 21분 교착 → 상한 전수 감사 (09-10 후반)
예약 첫 발화에서 `discovering_categories`가 21분간 갱신이 없었다. 서버는 정상 가동 중이었고 에러 로그도 없었다. 죽은 게 아니라 LLM 호출 하나에 물린 상태였다. 분류에만 상한을 걸었고 맵에는 SDK 기본값(최대 30분)이 살아 있었다. **진단이 21분이나 걸린 것은 맵이 배치마다 job을 갱신하지 않아서**였다. "정상 진행 중"과 "한 배치 폭주 중"이 화면에서 구분되지 않았다.

전수 조사하니 상한 없는 호출이 **10곳**이었다. `llm.bounded_client(timeout, retries=1)` 헬퍼를 두고 전부 적용했다.

| 대상 | 상한 |
|---|---|
| 맵 / 리듀스 / 분류 배치 / 대목 배정 | 90초(리듀스는 이후 600초로 상향) |
| 단건 분류(배치 폴백) | 30초 |
| 합성 | 240초 |
| 임베딩 | 30초 |
| 챗 경로: 추출 / 판정문 / 자문 / 검증 / 되묻기 | 60 / 120 / 120 / 60 / 90초 |

10곳 모두 `try/except` 폴백이 있어 상한 초과가 500이 아니라 점진적 저하로 흡수됨을 확인하고 적용했다. **상한은 정확도를 깎지 않고 최악 시간만 자른다.** 커밋은 `84463c3`.

### stale job 회수 — 배포가 job을 영구 `running`으로 만든다 (09-10)
파이프라인은 백엔드 프로세스 안의 백그라운드 작업이다. `deploy.sh`(= `systemctl restart`)나 크래시로 프로세스가 내려가면 job이 `running`인 채로 영원히 남는다. 화면은 끝나지 않는 "재구조화 중…"을 보여 준다. 두 갈래로 정리했다.
- **기동 직후 1회**: 그 시점의 `running`은 정의상 이전 생의 잔해다(전제: `--workers 1`).
- **평시**: 일정 시간 갱신 없는 `running`을 `error`로.

실전에서 확인됐다. 교착된 판을 배포로 끊자 로그에 "`[kb2_scheduler] 재시작으로 중단 — job 1건 정리`"가 찍혔다. 활성 문서 17개는 손상이 없었다(보관 처리는 분류 이후 단계라서).

merge 상한을 600초로 올리려고 계산하다 **리퍼가 살아 있는 job을 죽이는 버그**를 찾았다.
- 예약 경로: 폴러가 `await asyncio.to_thread(...)`에서 막혀 있어 리퍼가 못 돈다 → 안전
- 즉시 실행 경로: `background_tasks`가 별도 스레드로 돌리고 폴러 루프는 계속 돈다 → 심장박동 간격이 stale 기준을 넘으면 리퍼가 일하는 job을 죽인다

당시 기준 15분에 위험 구간이 둘 있었다. merge 600×2(20분 무소식), 그리고 분류 배치 실패 후 건별 폴백 20건(배치 단위로만 심장박동, 최악 20분)이다. `STALE_JOB_MS`를 15 → **30분**으로 올리고 폴백 루프에 건별 심장박동을 넣었다. 값 선정 원칙을 주석에 적었다. **"정상 진행 중 가능한 최장 침묵보다 넉넉히."** 불변식 `최악 침묵(20분) < stale 기준(30분)`도 코드로 확인했다.

### 나쁜 회차 가드 (커밋 `58a981f`)
`kb2_taxonomy._assess_run`을 `archive_all_active_documents()` **직전**에 둔다. 되돌릴 수 있는 마지막 지점이다. 카테고리 생성도 archive 뒤라, 중단 시점엔 아무것도 안 건드린 상태다.

| 조건 | 값 | 근거 |
|---|---|---|
| 호출 실패율 | > 2% | 순차 실측 0/600이라 평시값이 0. 실제 사태는 16%로 자릿수가 다르다 |
| 배정률 | < `max(35%, 직전×0.75)` | 상대 25% 하락 = 관측 편차(3.8%)의 6배 |

- 기준선은 `kb2_store.get_latest_generation_job()`(신설)이다. `status='done'`이면서 coverage가 있는 job만 본다. 기존 `get_latest_finished_job`은 error를 포함해서, **가드가 한 번 중단시키면 그 error job이 기준선이 되어 가드가 스스로를 무력화**한다.
- 애매하면 중단 쪽으로 기운다. 좋은 회차를 놓치는 비용은 "내일 밤 다시"지만, 나쁜 회차를 통과시키는 비용은 "세대가 사라졌다"다.
- 중단된 회차는 `stage='aborted'` + 계측을 남긴다. 스케줄러는 `status='error'`를 재시도하지 않는다(새벽에 조용히 API 예산을 태우지 않는다).

### 합성 0개 가드 — 되돌리기
분류 가드는 archive 직전이라 멈추면 아무것도 안 건드린 상태다. 그 뒤에 합성이 전량 실패하면 **빈 세대**가 남는다. 트랜잭션으로 묶는 길은 막혀 있었다. 커넥션이 모듈 캐시 하나(autocommit)이고, archive부터 적재까지 LLM 호출로 십수 분이 흐른다. 십수 분짜리 트랜잭션은 그 커넥션을 쓰는 다른 요청까지 붙잡는다.

그래서 되돌리기를 준비한다. archive 직전에 내려가는 세대의 `(id, status)`를 찍어 둔다. 합성이 문장 0개로 끝나면 이번 회차의 껍데기를 지우고 기존 세대를 **원래 status로** 복구한다. `unsorted`는 `unsorted`로 돌린다. `active`로 일괄 복구하면 '기타'가 검색에 들어간다.

판정선은 **문장 0개뿐**이다. 합성 단계의 회차 편차를 아직 재 본 적이 없어서다. 0은 재 볼 필요가 없는 유일한 값이고 오탐이 원리적으로 불가능하다. `archive_all_active_documents()`의 범위도 `status in ('active','unsorted')`로 넓혔다. 안 넓히면 회차마다 죽은 '기타'가 쌓인다(0023이 카테고리에서 고친 것과 같은 모양).

### 유실 청크 가드 (커밋 `af1c013`)
- `CHUNK_ATTEMPTS = 3`(빈 청크 재시도 1 → 2). 같은 세목이 다른 회차엔 한 번에 성공하므로 Upstage 쪽 산발 정체로 봤다. 한 번 더 묻는 비용(타임아웃 1회)이 원문 ~10건보다 싸다.
