# 백엔드·인프라 엔지니어 — W11 · 2026-10-11 ~ 10-17

> **이번 주 요지** — 비용 사고 하나를 원인부터 막고, 지식층 하나를 지우고, 고객과 세무사를 한 번에 잇는 DB 함수를 만든 주다. Supabase egress 293%의 원인은 **재시작마다 벡터 전량을 텍스트로 받는 것**이었다. 이 로드맵 세션의 로컬 서버도 원인 제공자였다. 지문 한 줄과 서버 디스크 캐시로 바꿔 재시작 적재를 12 → 1.4초, egress를 사실상 0으로 만들었다. KB2는 코드 스위치로 먼저 끊고 스키마를 지웠다(0053). R3에서는 0054·0055와 세무사 AI 첫 인사 API로 "가상 세무사 즉시 연결"을 DB 쪽에 세웠다. 주 중반부터는 Solar Pro 4 운영 전환과 매 배포 측정이 이어졌다. 로컬과 운영이 같은 DB를 나눠 쓰면서 생긴 지뢰가 여럿이었다.

## 비용 · 용량

### Supabase egress 대응 (10-12)
- **원인** — egress 293%(14.63/5GB)의 원인은 `vec_memory`였다. 재시작마다 4096차원 벡터 전량(법령 7,613 + KB3 5,101행)을 텍스트로 받아 1회 674MB가 나갔다. 배포 restart와 로컬 uvicorn이 원인이었다. **이 로드맵 세션의 로컬 서버도** 원인이었다. `LAW_STORE=file`로 띄워도 vec_memory는 운영 DB에서 받는다.
- **처방** — `api/rag/disk_cache.py`.

| 장치 | 내용 |
|---|---|
| 지문 한 줄 | 행 수 · max updated_at · md5. 지문이 같으면 서버 디스크 캐시(`VEC_CACHE_DIR`, 기본 `backend/.cache/vec`)를 쓴다 |
| 미스일 때 | 바이너리 커서(텍스트의 1/3) |
| 쓰기 | 원자적 기록. 지문 파일을 마지막에 쓴다. 깨졌거나 쓰다 만 캐시는 버린다 |
| 법령 원문 | `law_select.warm`(약 24MB/회)도 같은 캐시 |

- **운영 확인** — 첫 기동은 db에서 받아 캐시를 만들었다(laws 125MB · kb3 84MB · 원문 25MB). 그 뒤 재시작은 전부 `cache 0.1초`였고, 적재가 12초 → 1.4초가 됐다.
- **0052** — `cron.job_run_details`를 15.7만 → 1.2만 행으로 줄이고, 매일 7일 지난 이력을 정리한다.
- `egress_audit.py`(읽기 전용)에 DB 크기와 cron 절을 더했다.
- **이제의 규칙** — 로컬 백엔드는 `VEC_MEMORY=off`로만 띄운다. 디스크 캐시가 있어도 `--reload` 연속 재시작 중에는 쓰다 만 캐시로 다시 받을 수 있다. 배포는 모아서 한다. → [DL](../8_결정교훈/DL_2026-10_W11_1011-1017.md)
- **남은 것** — 다음 날 Supabase Usage의 일별 egress가 수십 MB인지 확인, `vacuum full cron.job_run_details`(약 25MB, 사용자), `rag.passages` 전량 조회 427회(21만 행)의 경로(egress 잔여 후보).

### KB2 삭제 — 스위치 먼저, 스키마는 그다음 (10-12)
- `kb2_store.kb2_enabled()`를 새로 두었다(KB2=on일 때만, 기본 off). kb2 API 23개, 재구조화 폴러, 합성, Kb2Retriever를 이것으로 막는다.
- `is_configured()`는 건드리지 않았다. kb3·법령·규범 저장소도 이 함수를 'DB 있음'으로 쓰기 때문이다.
- 의존 0 확인과 텍스트 백업(→ [KE](../3_지식엔지니어/KE_2026-10_W11_1011-1017.md)) 뒤에 **0053 `drop schema kb2 cascade`**. DB가 421.6 → 336.8MB가 됐다.

이 주에 같은 종류의 지뢰가 네 번 나왔다.

|---|---|---|
| 10-12 | 로컬 서버의 vec_memory가 운영 DB에서 벡터 전량을 받아 egress를 키웠다 | 로컬은 `VEC_MEMORY=off` |
