### 계획이 틀렸던 것 셋
1. **비용이 10배 과대였다.** 계획의 월 37,000원은 A1 단가를 그대로 곱한 값이었다. 실제 견적은 Compute 항목 없음($0) + 부트 볼륨 $2.76이다. 2/12가 A1 Always Free 한도(4/24) 안에 통째로 들어간다. 셰이프의 Always Free 뱃지가 유지되고 A1 Usage가 0이었다. 견적 면책 문구를 끝까지 읽지 못해 며칠 뒤 Cost Analysis 실측으로 확정하기로 했다.
2. **Reserved IP를 처음부터 붙일 수 없다.** 생성 마법사는 Ephemeral 여부만 묻는다. 실제는 ① Ephemeral로 생성 ② Reserved IP 별도 발급 ③ VNIC의 사설 IP 행에서 교체, 3단계다. 게다가 Ephemeral이 붙어 있으면 Reserved 선택지가 목록에 안 나온다. "No public IP"로 한 번 저장한 뒤 다시 Edit해야 한다. 공인 IP가 한 번 더 바뀌었지만, **IP 확정 전에 Caddy·Vercel을 건드리지 않아 재작업은 0**이었다. 교체 뒤에도 콘솔은 `IP lifetime`을 Ephemeral로, Reserved 목록의 VNIC 칸을 빈칸으로 보인다. 판단 근거는 Reserved IP의 State = `Assigned`와 실제 SSH 접속이다.
3. **의존성이 조용히 드리프트한다.** `requirements-api.txt`가 전부 `>=` 하한이라 새 박스는 그날 최신을 받았다. `openai` 2.44.0 → 3.19.2(메이저, HTTP 스택 교체), `starlette` 1.3.1 → 1.7.0. 이전과 SDK 메이저 업그레이드가 섞이면 동작 차이의 원인을 박스와 라이브러리로 가를 수 없다. 구 박스 `pip freeze`를 `backend/requirements-api.lock.txt`로 커밋하고(`7d9af47`) venv를 다시 만들어 35개 완전 일치를 확인했다. SDK 업그레이드는 별도 과제다.

systemd 유닛 주석에 "향후 큰 박스로 옮기면 `--workers 2~4`로"라고 적혀 있었다. 워커가 둘 이상이면 나중에 뜬 워커가 `kb2_store.py:781-801` 리퍼를 돌려 **다른 워커의 살아 있는 job을 전부 error 처리**한다. 12GB 박스로 옮기면서 그 주석을 따라갈 위험이 실재했으므로 정반대로 뒤집고 코드 근거와 journal 실측을 같이 적었다. 같은 이유로 **백엔드 인스턴스 두 대를 동시에 켜면 안 된다.**

journal을 7/9 기동부터 9/24까지 훑으니, HTTP 로그를 빼면 스케줄러 줄은 둘뿐이었다(9/10 kb2_scheduler 재시작으로 job 1건 정리, 9/17 norms_scheduler 디폴트 승인 1건). 두 가지를 알 수 있었다.
- **KB2 배치는 Oracle 서버에서 돈 적이 없다.** 재구조화·합성은 로컬에서 돌았다. "1GB로 복귀하면 KB2 배치를 못 돌린다"는 걱정에 근거가 없다.
- 9/10 줄은 **리퍼가 실제로 도는 코드임을 관측**으로 보여 준다. 두 인스턴스 동시 기동 금지가 추론에서 관측으로 올라섰다.

### 단계 0.5 — 꺼진 v2 자리

| 무엇 | 값 |
|---|---|
| 코드 | v1 checkout의 **git worktree**(브랜치 `agentic-v2`). `deploy.sh`가 만지지 않아 손으로 pull |

| `.env` | v1 `.env`로의 심볼릭 링크(비밀값 원본은 하나) |
| 유닛 | `neo-luddite-api-v2` — 8788, `--workers 1`, `BACKGROUND_JOBS=off`, `UPSTAGE_MAX_CONCURRENCY=1`, **disabled / inactive** |
| Caddy | `/api/chat?pipeline=v2`만 8788 → 8787(`lb_policy first`, `lb_try_duration 2s`, `fail_duration 30s`). 그 밖은 전부 8787. 넣기 전 Caddyfile 백업 |

v1 영향 0을 확인했다. `/health`·`/rag/health`(kbPassages 418) 정상, CORS 200, 실제 채팅 200, `?pipeline=v2` 요청은 꺼진 8788을 건너 **v1이 0.3초에** 응답했다.

**격리 설계가 틀렸던 것 셋.**
1. **게이트 공유 불가.** `upstage_gate`는 프로세스 안의 FIFO다. "두 파이프라인이 같은 게이트 줄을 선다"와 "프로세스를 나눈다"는 동시에 성립하지 않는다. v2를 동시 1로 둬 합계 상한을 4로 묶었다. 진짜 공유는 프로세스 밖 줄(DB advisory lock 등)이 필요하고, 트래픽이 붙는 단계 5에서 판단한다.
2. **두 번째 프로세스는 리퍼를 들고 뜬다.** 같은 `api.main:app`이라 lifespan이 kb2 폴러를 띄우고, 폴러의 첫 패스가 `reap_stale_running_jobs(all_running=True)`로 v1의 running job을 죽인다. 호출처가 `kb2_scheduler.py:39` 하나뿐임을 확인하고 `BACKGROUND_JOBS=off` 가드와 "지우지 말 것" 주석을 넣었다.
3. **환경변수 킬 스위치는 약하다.** `?pipeline=v2`가 env를 이긴다. 실질 킬 스위치는 `systemctl disable --now neo-luddite-api-v2`다(Caddy가 v1로 흘린다). `CHAT_PIPELINE`은 서버 `.env`에 넣지 않았다.
