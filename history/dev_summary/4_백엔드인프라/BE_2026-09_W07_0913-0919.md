> **이번 주 요지** — 백엔드가 KE·AIE에 붙어 있던 자리에서 **갈라져 나온 주**다. 계기는 둘이다.

### P5 — `norms.*`와 저장소 API (09-17)
**0030 설계**
- `documents`(name unique, order_index, origin, active_version_id, status) / `versions`(version_no, content, status draft|confirmed|discarded, base_version_id, note, author_id, updated_by, confirmed_by/at, discarded_by/at).
- **문서당 초안 1개** — `unique (document_id) where status='draft'`. 두 초안이 경쟁하는 확정 충돌이 원천적으로 없다. 그래서 "초안 뒤에 다른 확정이 끼었나" 검사는 뺐다.
- `version_no`는 확정 때 부여한다. 확정 이력 번호에 구멍이 없다. 되돌리기는 과거본으로 새 초안을 만들어 같은 게이트를 지난다(v3 식으로 누적).
- 시드는 md에서 **생성**했다(손 전사 금지). 관리 주석을 뺀 본문을 `$norm$` 달러 인용으로 넣었다.
- 헛걸음 둘: 데이터 변경 CTE로 넣은 행이 같은 문장의 본 쿼리에 안 보여 active_version_id가 안 걸렸다(문장을 나눴다). 확정 시각을 2025년 epoch로 계산했다(1789516800000으로 정정). → [DL](../8_결정교훈/DL_2026-09_W07_0913-0919.md)

**저장소·API(`api/prompts/store.py`, `main.py`, `schema.py`)**
- 읽기는 모듈 캐시 커넥션, **쓰기는 호출마다 새 커넥션 + 트랜잭션**(`_tx`). 캐시 커넥션을 스레드풀 요청이 공유하면 여러 문장 트랜잭션에 다른 요청의 문장이 섞일 수 있다. `connect_timeout=5`.
- 역할 판정은 `public.profiles.domain_id → role`이다. 초안·폐기 = admin|auditor, 확정 = auditor. 이 시점 백엔드는 인증이 없고 신원을 본문으로 받는 관례였다(kb2·rag edits와 같다).
- 검사: 예산(이 문서만 바꾼 주입 블록으로 `build_norms`), 빈 본문, 낙관적 잠금(`expectedUpdatedAt`), 확정 사유 필수, 확정본과 동일 내용 거절, 동시 첫 초안(UniqueViolation) → 문구, 잘못된 UUID → "버전을 찾을 수 없음".
- 거절은 HTTP 오류가 아니라 `ok=false + error`다.
- 엔드포인트: `GET /api/norms` · `GET /api/norms/{name}/versions` · `POST /api/norms/{name}/draft` · `POST /api/norms/drafts/{id}/discard` · `POST /api/norms/drafts/{id}/confirm`. 확정 성공 시 경고 로그 `L0 규범 확정 — …`.

### P6 ② — 이의 기간 (09-17, `62e5596`, 0031)
상태는 `draft → pending → confirmed`(+ discarded)다. 문서당 열린 제안(draft|pending) 하나로 부분 유니크 인덱스를 바꿨다.
- `versions`에 `published_by/at`, `deadline_at`, `applied_via`(direct|approvals|deadline). 기존 확정본은 `direct`.
- `norms.decisions`(approve|object, reason, withdrawn_at/by/reason) — 삭제 없는 이력, 유효 결정은 1인 1개.
- `publish_draft`: 운영자·세무사, 사유 필수, 확정본과 동일·예산 초과 거절, `deadline = now + 1일`.
- `decide`: 세무사만, `expectedUpdatedAt` 일치 필요, 이의 사유 필수, 작성자·공개자 자기 승인 거절, 이전 결정은 `changed`로 철회 후 기록.
- `_try_apply`: **이의가 하나라도 있으면 무조건 불가** → 승인 ≥ 문턱이면 `approvals` → 기한이 지났으면 `deadline`(confirmed_by `system:deadline`).
- `withdraw_decision`: 이의를 거두면 그 자리에서 조건을 재평가한다(기한이 이미 지났으면 즉시 반영).
- 공개 중 수정 → `draft`로 복귀, 결정 전부 `reset:edited`, 기한 제거. 공개 중 폐기는 작성자·공개자만(나머지는 이의로).
- 승인 문턱은 `NORMS_FAST_APPROVALS` 설정값, 2명(PO가 3에서 낮춤).

**자동 반영 트리거를 pg_cron에서 백엔드 폴러로 바꿨다(구현 판단).** `api/prompts/scheduler.py`가 lifespan에서 60초마다 `apply_due`를 돌리고 반영 시 `invalidate_norms()`를 부른다. 반영 직전 예산 검사(`build_norms`)가 Python이라 SQL만으로는 같은 검사를 못 한다(kb2_scheduler 모듈 주석의 판단과 같다). 진실은 `deadline_at`이라 서버가 재기동해도 안전하다.

### P6 ③ — admin 사후 브레이크 (09-17, `01e6a2e`, 0032)
- status `rejected`, applied_via `rollback`, `versions.admin_reason`. 별도 이력 테이블 없이 versions 행이 이력이다.
- `reject_proposal`: pending만, 사유 필수, 결정 `reset:rejected`, `discarded_by/at` 재사용.
- `rollback_active`: `expectedActiveVersionId` 일치 필요 → 직전 번호 확정본 내용으로 **새 확정본**을 insert(번호 증가, base_version_id = 대상, note "롤백 vX → vY 내용") → active 교체 → 즉시 invalidate. 열린 제안은 건드리지 않는다.
- 긴급 단독 확정은 두지 않았다(PO 확정).
- 0030의 status check 제약은 이름을 추정하지 않고 `pg_constraint`로 `versions_status_check`를 확인한 뒤 교체했다.

**현재 상태** — pitfalls 확정본 v7(내용 = v1 = md), master·frameworks v1. 버전 이력에 테스트 흔적(v2~v7, 거부 1건, 폐기 초안)이 사유 `[기능 테스트 260917]`로 남아 있다. 프로덕션 쓰기 API는 토큰 필수다. 검증 시나리오는 → [EV](../7_평가검증/EV_2026-09_W07_0913-0919.md).

### 120초 멈춤은 동시 호출의 산물 (09-18, P7 C)
실사용 턴이 0건이라(`rag.chat_turns` 47행 전부 `smoke-`, `journalctl` 30일 `segment 반복 제거` 2건도 둘 다 스모크) 실사용 규모는 잴 수 없었다. 대신 P7 B 측정 576회(4워커 동시)의 부산물을 봤다.
- 60초 초과 35회 중 루프는 2회뿐이었다. 지연이 124~129초(32회)와 241초(3회)에 군집했다. `TIMEOUT_WRITE_ADVISORY=120` + `DEFAULT_RETRIES=1`의 모양, 즉 **120초 멈춤 후 재시도 즉시 성공**이다. SDK 재시도는 로그를 안 남겨서 지연 모양으로 판정했다.
- 단일 요청 재현(제품 `write_advisory` 그대로, workers=1 순차 64회): 120초 이상 **0**. 동시 조건의 멈춤률(약 6%)이 순차에서도 같다면 64회 중 0회일 확률은 0.94^64 ≈ 2%다. 그래서 **같은 API 키에 요청이 몰릴 때의 레이트리밋·혼잡**으로 판정했다.
- PO 결정: 재현까지만 한다. 단일 사용자 조건에서 멈춤이 없으니 타임아웃 단축의 근거가 없다.
- **전시회 경고**: 비로그인 방문자가 동시에 몰리면 같은 Upstage 키에 호출이 쌓인다. 4워커 조건이 그 축소판이었다. `/api/chat` 무인증 결정과는 무관한 용량 쪽 과제로 남겼다.

### Upstage FIFO 게이트 (09-18, P8 B, `4613f1a`)
배포 전 프로덕션 `/api/chat` 동시 N=1~4를 쟀다. 120초 멈춤은 N=4에서만 1/48 나왔고, N≤3은 0/76, 순차 0/64였다. k=3은 "관측된 무사고 최대치"다(3과 4의 차이는 표본이 작아 통계적으로 확정은 아니다).

| 붙은 것 | 내용 |
|---|---|
| `backend/api/upstage_gate.py` | 프로세스 내 **FIFO 번호표 게이트**(Condition + deque). k = `UPSTAGE_MAX_CONCURRENCY`(기본 3, env로 재배포 없이 조정) |
| `llm._Gated` / `bounded_client()` | `.create()`마다 `slot()`. 호출 지점 14곳 + 임베딩을 한 자리에서 잡고, 새 호출도 자동으로 줄에 선다 |
| `turn_budget` | 스레드 로컬 예산. **챗 턴 대기 합계 30초**. 예산 없는 스레드(백그라운드)는 무기한 대기 |
| `pipeline.congested_response()` | HTTP 200 + "지금 상담 요청이 몰려 답변을 드리지 못했습니다. 잠시 후 같은 질문을 다시 보내 주세요." + `meta.congested=true`, `rag.chat_turns.outcome='congested'`(outcome에 check 제약이 없어 마이그레이션 불요) |
| `/health`의 `upstageGate` | capacity·active·waiting·peakWaiting — 전시 중 줄 길이 확인용 |

설계 판단은 넷이다(구현 판단).
- **단위 = Upstage 호출**(턴이 아니다). 슬롯은 SDK 재시도까지 감싼다. 멈춘 호출도 실제로 Upstage 자리를 쓰고 있기 때문이다.
- `threading.Semaphore`는 기각했다. 새치기가 돼 순서가 보장되지 않는다.
- 호출마다 대기 상한을 두는 안은 기각했다. 한 턴이 3~4배를 기다린다. 그래서 상한은 턴 합계다.
- 혼잡 예외가 폴백에 삼켜지지 않게 `write_advisory`·`verify_decisive`·retriever 4곳(`_shared_query_vector` 포함)의 except 앞에서 다시 던진다.

PO가 정한 것: 혼잡은 500이 아니라 HTTP 200 안내다. 프론트(`services/chat.ts`)는 비정상 status를 오류로 던지기 때문에, 200이면 평범한 말풍선이 된다. 백그라운드 Upstage 호출(KB2 재구조화·분류·적재 임베딩)도 같은 게이트에 우선순위 없이 FIFO로 선다. 쓰기 타임아웃 단축은 하지 않는다(게이트 후 216턴 멈춤 0으로 근거가 사라졌다).

**배포 후 N=4·6·8 × 12턴 = 216턴: 멈춤 0 · 오류 0 · 혼잡 0.** 게이트 로그는 1초 이상 기다린 호출 361건, 대기 중앙 1.9s · 최대 5.7s, 줄 최대 6이었다. 메모리 여유는 약 490MB(E2.1.Micro)다. 상세는 → [EV](../7_평가검증/EV_2026-09_W07_0913-0919.md).

**전제: `uvicorn --workers 1`.** 워커를 늘리면 k가 워커 수만큼 곱해진다. 인프라 이전(Oracle A1 2OCPU/12GB)은 PO가 다음 주 이후로 보류했고, 이전하면서 워커를 늘리면 k를 다시 잰다. → 이어서: 인프라 이전은 9/24에 이뤄졌다(W08).

**전시 당일 모니터링 메모**: `/health` `upstageGate`, `rag.chat_turns where outcome='congested'`, journal `[upstage_gate]`·`출처 없는 수치`.
