# 백엔드·인프라 엔지니어 — W04 · 2026-08-23 ~ 08-29

> **이번 주 요지** — 마이그레이션 셋을 프로덕션에 적용했다. `0016`은 정산 수익·비율, `0017`은 수정 제안 큐, `0018`은 저장 edge + pg_cron이다. KB를 바꾸는 엔드포인트 4개에는 edge 재계산을 **best-effort 동기 호출**로 붙이고, pg_cron은 안전망으로 남겼다. 대회 인프라 조사를 위해 실태를 코드로 확인했다. 결론은 **CPU-only이고, 병목은 RAM 1GB이고, 백엔드에는 로컬 파일 의존이 없다**는 것이다. 그리고 7/18부터 서버의 `git pull`이 **부분 체크아웃**으로 깨져 있던 것을 발견해 복구했다.

### `0018_rag_passage_edges.sql` + pg_cron (08-28)

| 붙은 것 | 내용 |
|---|---|
| `rag.passage_edges` 테이블 | 저장 edge |
| `rag.rebuild_passage_edges(k)` | 전체 삭제 후 self-join top-k 재계산 |
| pg_cron 5분 주기 | 0006 스냅샷 캡처와 같은 패턴 |
| `GET /api/rag/edges` · `POST /api/rag/edges/rebuild` | 전체 edge 조회, 수동 즉시 재계산 |

프로덕션에 적용했고 수동 실행 결과 `edgeCount: 3304`였다.

**edge 신선도** — pg_cron만으로는 적재 직후 최대 5분간 그래프가 낡는다(PO 지적). KB의 active·embedding 상태를 바꾸는 **4개 경로** 모두에서 응답 직전에 `rebuild_passage_edges()`를 동기 호출하도록 붙였다(`_rebuild_edges_best_effort`).
1. `/api/rag/ingest`(문장 코멘트 적재)
2. `/api/rag/ingest-session-eval`(세션 총평 적재)
3. `/api/rag/retract`(소급 정리, active ↔ retired 전환)
4. `/api/rag/edits/{id}/approve`(수정 승인, embedding 갱신)

- 지금 규모(수백 건)에서 전체 재계산이 **1초 미만**이라 요청 경로에 넣어도 부담이 없다.
- best-effort다. 재계산이 실패해도 원래 동작은 막지 않는다.
- pg_cron 5분 주기는 이 경로를 타지 않는 변경(수동 DB 조작 등)의 안전망으로 남겼다.

### 프로덕션 서버 git — 부분 체크아웃 복구 (08-27)
1. `git pull`을 다시 시도하다 `frontend/e2e/` 파일이 root 소유인 것 때문에 실패했다(7/18 이후 다른 세션이 sudo로 건드린 흔적).
2. `chown -R ubuntu:ubuntu` 후 다시 시도하자, 이번에는 **로컬 미커밋 변경사항 다수**(main.py, store.py, schema.py, 프론트 다수, history 11개, migration 0016 등)와 충돌했다.
3. **원인**: 이전 `git pull`이 소유권 문제로 중간에 실패하면서, git이 HEAD를 옮기지 못한 채 파일 내용만 새 버전으로 받아 놓은 상태였다.
4. **복구**: "수정됨·추적 안 됨" 파일을 전부 origin 최신 커밋과 diff해서 **완전히 같음**을 확인했다. 그다음 `git stash -u` → `git pull`(clean fast-forward) → `git stash pop`(이미 존재해서 충돌 없이 확인만) 순서로 복구했다.
5. 서버에만 있던 history 메모 11개(7/15~8/27)는 untracked라 보존됐고, 저장소에 편입됐다.

교훈은 → [DL](../8_결정교훈/DL_2026-08_W04_0823-0829.md). 이 사고는 로드맵 §3.6(배포 파이프라인 수리)으로 이어졌다. 이후 백엔드 배포는 두 브랜치(`import-credigraph`, `main`) push + `backend/deploy/deploy.sh` + `/health`·`/rag/health` 확인이 표준이 됐다. 이 주 08-28의 모든 배포가 그 순서로 이뤄졌다. 프론트만 바뀐 날은 `deploy.sh`를 생략하고 `/rag/health`(`kbPassages: 413`, 무변화)로 백엔드가 정상인지만 확인했다.
