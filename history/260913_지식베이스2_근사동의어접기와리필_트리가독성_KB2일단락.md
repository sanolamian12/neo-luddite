```

cos ≥ 0.80 ∪ 문자열 → 30 → 22  6덩어리 (0.75 와 동일 — 안정 구간)

## 2. L2 결정 (전부 사용자 확인)

| 항목 | 결정 | 이유 |
|---|---|---|
| 접기 임계값 | 코사인 **0.75** ∪ 문자열 규칙 | 0.70 은 오탐, 0.75=0.80 결과 동일. 재부착 0.70 은 그대로 |
| 문자열 규칙 | 부분문자열 / `·` 토큰 일치 / 공통 접두 — **3자 이상** | 두 글자 조각(`리스`·`개인`)이 무관한 세목을 잇지 않게. `리스~리스·렌탈` 은 토큰 규칙이 건진다 |
| 리필 | **LLM 1회**, 모자라면 관찰 횟수순 코드 리필 | 아래 §2.1 |
| 대표 레이블 | **맵 관찰 횟수 최다**, 동률은 merge 순서 | 분류기는 **레이블만** 본다(tool enum) — 대표가 곧 묶음의 유일한 이름 |

### 2.1 왜 리필이고, 왜 LLM 인가

항목 16 A/B/C 실험(같은 150건·순차 3회):
```
A 현행 30개·중복 有 : 평균 51.8%
B 접고 30개로 채움  : 평균 53.6%   ≈ A (편차 안, 중립)
C 접고 22개로 축소  : 평균 46.4%   (편차 밖, 나쁨)
```
**접기만 하는 구현은 기각된 C 그 자체다.** 채워야 중립이다.

B 는 코드가 맵 후보를 관찰 횟수순으로 채웠는데, 캐시된 맵 후보를 세어보니
**72개 · 고유 59개 중 52개가 1회 관찰**이었다. 코드 리필은 곧 1회짜리 좁은 레이블을
되돌려놓는 일이라 **가독성이 목적인 작업이 가독성을 해친다** → 좁은 후보를 넓은 주제로
묶는 판단을 LLM 에 맡기기로 했다.

### 2.2 화면 단계명은 새로 만들지 않았다

프론트가 job `stage` 를 레이블 맵으로 표시한다(`kb2-synthesis-view.tsx`). 새 단계를 만들면
Vercel 배포가 딸려오므로, 개념상 통합의 일부인 접기는 **`merging_categories` 단계 안에서**
돈다. 프론트 변경 0.

## 3. 구현 (`14989b9`)

`backend/api/rag/kb2_taxonomy.py` — merge 직후, 분류 직전:

1. 모든 쌍을 `코사인 ≥ 0.75 ∪ 문자열 규칙` 으로 잇고 union-find 로 묶는다.
2. 묶음 대표 = 관찰 횟수 최다. 대표는 **묶음의 가장 앞 멤버 자리**를 이어받는다(merge 의
   중요도순 유지).
3. 빈 칸만큼 리필. 새 레이블은 **원래 목차 전부(접힌 멤버 포함)** 와 대조한다 — 대표하고만
   대조하면 접힌 멤버가 '새 주제'인 척 돌아온다(A/B/C 실험에서 밟은 함정).
4. 그래도 `MERGE_MIN_CATEGORIES`(20) 아래면 **접기를 통째로 포기**하고 원래 목차를 쓴다.
5. 예상 못 한 예외도 원래 목차로 되돌린다 — 가독성 작업이 회차를 죽이면 안 된다.

`backend/api/llm.py` — `refill_categories()` 추가, `_finalize_categories_tool` 이
`min_items/max_items` 를 받게 함(리필은 `need ~ need+3`, 일부가 걸러질 여분).

계측 `result.labelFold`:
`clusters`(대표·멤버·관찰 횟수·연결 근거) · `refillProposed` · `refillFromLlm/FromTally` ·
`refillRejected` · `candidatesUncovered` · `refillError` · `refillMs` · `embedFailures` ·
`skipped` · **`candidatesTally`(맵 후보 원시값)**.

마지막 것은 "요약만 남기고 원시값을 버리지 말 것" 교훈의 세 번째 적용이다 — 맵 후보는
결정적이지 않아 회차가 끝나면 다시 못 만든다. 이게 있어야 접기 규칙을 바꿨을 때 같은
입력으로 되짚을 수 있다.

## 4. 드라이런에서 밟은 것 — LLM 은 무엇이 이미 덮였는지 모른다

### 4.1 1차 — LLM 리필 0건

```

오류가 아니었다. 모델이 **1.8초 만에 후보 목록 머리를 그대로 베껴** 냈고 11개 전부가 기존
레이블과 겹쳐 거부됐다:
```

프롬프트에 "확정 목차·접힌 레이블과 겹치는 건 내지 말 것"을 줬는데도 그랬다.

### 4.2 처방 — 덮이지 않은 후보만 코드가 걸러 넘긴다

**무엇이 이미 덮였는지는 모델이 알 수 없고 파이썬은 공짜로 안다** — `tally_candidates` 가

먼저 걷어내고(72 → 20), LLM 리필과 코드 리필이 **같은 목록**에서 고르게 했다.

### 4.3 2차

```
30 → 30  접힘 8  LLM 리필 8  거부 0  코드 리필 0
결과를 다시 접기 → 0건 (멱등, 리필이 새 중복을 안 들였다)

⚠️ **정직하게**: LLM 은 "넓은 주제로 묶기"를 하지 않았다. 덮이지 않은 후보 20개가 전부

## 7. 교훈

**LLM 에 "이미 있는 것은 빼라"고 시키지 말고, 뺀 목록을 줄 것.** 금지 목록을 프롬프트에
넣어도 모델은 후보 목록 머리를 그대로 베꼈다. 무엇이 덮였는지 판정하는 건 규칙이 명확한
일이라 코드가 공짜로 한다 — `tally_candidates`(관찰 횟수), 이번의 `uncovered` 필터가 같은
수법이다. 모델에게는 코드가 할 수 없는 판단만 남긴다.

**같은 임계값이라도 쓰이는 구조가 다르면 다시 재야 한다.** 재부착(최근접 1위 선택)에서
전수 정탐이던 0.70 이, 접기(모든 쌍 연결 + 추이적 묶음)에서는 오탐 한 건으로 세목 셋을
뭉쳤다. 임계값은 값이 아니라 **"그 선 위에서 무엇을 하느냐"와 한 쌍**이다.

**드라이런은 진짜 함수로 — 이번에도 값을 했다.** 1차 드라이런이 LLM 리필 실패를 배포 전에
잡았다. 오류 없이 조용히 코드 리필로 넘어갔기 때문에, `refillFromLlm/FromTally` 를 따로
세지 않았다면 "LLM 리필이 돌았다"고 오독했을 자리다.
