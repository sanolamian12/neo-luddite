> **로드맵 §4를 이어받아 §3.2/3.3(확장성)·§3.5(GraphRAG)를 재확인했다가, 사용자 정정으로 §3.5의 진짜 목적("세무사가 KB를 거미줄 그래프로 보고 직접 수정할 수 있는 중간층")을 다시 파악하고 실제로 구현·배포했다. 그 과정에서 KB `tax_category`가 전량 "미분류"였던 근본 원인을 발견해, 17개 세목 taxonomy + Upstage 자동분류 정책을 도입하고 기존 데이터까지 소급 재분류했다.**

## 1. 배경 — 세션 시작 시점

## 2. §3.2/§3.3 확장성 — 재확인 (변화 없음)

- `/rag/health` 실측: active passage 413건 — 트리거(5,000~10,000건)까지 여유 큼.
- `backend/api/pipeline.py`: `occupation="clinic"` 하드코딩 그대로, 새 직업군 지원 없음.
- **결론**: 개발 항목 없음, 계속 모니터링.

## 3. §3.5 GraphRAG — 첫 재검토는 잘못 짚은 질문이었음

처음엔 "GraphRAG로 RAG 검색 엔진(match_passages)을 교체할지"를 성능/가치 두 관점에서 재검토해 **비채택 유지**로 결론지었다. 그런데 사용자가 정정: 이 로드맵을 시작한 진짜 동기는 검색 엔진 교체가 아니라 —

> **세무사와 RAG/KB 사이에 중간층을 놓아서, KB가 어떻게 구성되는지 시각적으로(거미줄 그래프, 줌인/줌아웃) 확인하고 필요하면 직접 수정할 수 있게 하는 것.**

"검색 엔진 교체 비채택"은 여전히 유효한 결론이지만(재오픈 신호: §3.2 트리거 도달 / occupation 교차참조 필요 / UI 실패사례), 그건 애초에 묻던 질문이 아니었다.

## 4. §3.5 진짜 목적 — KB 거미줄 그래프 시각화 구현

### 4.1 설계 결정 (사용자와 확인)

- **edge 확보 방식**: 조회 시점 실시간 계산이 아니라 **배치로 미리 계산해 저장** — KB 전체를 한 화면에 그릴 수 있고, 덤으로 향후 §3.2(exact-scan 완화) 검토 시 재사용 가능한 구조가 되도록.
- **렌더링 방식**: 새 무거운 그래프 라이브러리 대신 **d3-force + 커스텀 SVG** — 기존 `kb-passage-detail-view.tsx`의 순수 SVG 방사형 그래프 스타일과 통일.

### 4.2 구현

- `supabase/migrations/0018_rag_passage_edges.sql`: `rag.passage_edges` 테이블 + `rag.rebuild_passage_edges(k)` SQL 함수(self-join top-k 재계산) + pg_cron 5분 주기 스케줄(0006 스냅샷 캡처와 같은 패턴).
- `backend/api/rag/store.py`: `list_passage_edges()`, `rebuild_passage_edges(k)`.
- `backend/api/main.py`: `GET /api/rag/edges`, `POST /api/rag/edges/rebuild`.
- `frontend/components/audit/kb/kb-graph-view.tsx`(신규): d3-force 시뮬레이션을 300틱 수렴시킨 뒤 정적 SVG 렌더. 휠 줌(줌인 시 라벨 노출), 드래그 팬, 노드 크기=연결수, 색=세목/직업군 해시. 노드 클릭 → 기존 상세뷰(유사도 이웃+§3.4 수정 제안)로 이동.
- `frontend/components/audit/kb/kb-map-view.tsx`: "클러스터"/"전체 그래프" 탭 토글 추가.
- `frontend/package.json`: `d3-force`, `@types/d3-force` 추가.

프로덕션 실측: 413 active passage → 3,304 edge. 배포 완료(두 브랜치 push + `deploy.sh`).

### 4.3 브라우저 스모크 테스트

로컬 백엔드(uvicorn, 프로덕션과 동일 Supabase)+프론트(`next start` — `next dev`가 이 Windows 환경에서 Turbopack CSS 워커 `0xc0000142` DLL 초기화 실패로 죽는 환경 이슈가 있어 프로덕션 빌드로 우회)를 띄우고 Playwright로 auditor 계정 로그인 → `/audit/kb-map` "전체 그래프" 탭 구동.

- 407개 노드+edge 렌더 확인, 줌인 시 라벨 노출 확인.
- 노드 클릭 → 기존 상세뷰 이동 → 유사도 방사형+원문 렌더까지 확인(전체 "그래프 탐색→상세→수정 제안" 플로우 검증 완료).
- **버그 발견·수정**: 휠 줌의 `e.preventDefault()`가 React의 passive 리스너 등록 때문에 무시됨(콘솔 경고) — `useEffect`로 `{ passive: false }` 네이티브 리스너를 직접 붙이는 방식으로 교체. 재배포 완료.

### 4.4 edge 신선도 — 사용자 지적 반영

"기존 루트로 새 지식이 배선될 때마다 재계산이 필요하지 않겠냐"는 질문에 — 맞는 지적. pg_cron 5분 주기만으로는 배선 직후 최대 5분 지연이 생긴다. KB의 active/embedding 상태를 바꾸는 4개 경로(`/api/rag/ingest`, `/api/rag/ingest-session-eval`, `/api/rag/retract`, `/api/rag/edits/{id}/approve`) 전부에서 응답 직전에 `rebuild_passage_edges()`를 동기 호출하도록 배선(`_rebuild_edges_best_effort`, best-effort — 실패해도 원래 동작은 안 막힘). pg_cron 5분 주기는 안전망으로 유지.

## 5. §3.7 — tax_category "미분류" 원인 발견 + 세목 분류 정책

스모크 테스트 중 클러스터/그래프 뷰가 전부 "미분류" 한 덩어리로만 보이는 걸 사용자가 지적. 조사 결과 UI fallback이 아니라 **데이터 자체** 문제 — `frontend/services/conversation.ts:76`이 라이브 채팅을 정지 스냅샷에서 복원할 때 `topic.taxCategory`를 실제 분류 없이 항상 `"미분류"`로 하드코딩. KB 전량(521건)이 이 값이었다.

### 정책 (사용자 확정)

규칙엔진 9종 지출유형(`clinic_expense_engine.ExpenseType`)을 포함하되, KB 407건 실측 샘플링에서 관찰된 자문형(판정 없는, 실측 55%) 주제를 더한 **17개 카테고리**를 `backend/api/rag/taxonomy.py`에 확정: 업무용승용차·임차료·접대성지출·광고선전비·통신비·복리후생비·출장비·소프트웨어구독·가사관련비(기존 9종) + 인건비·가족직원·퇴직금·4대보험·시설·인테리어·부가가치세·상속·증여·소득세·법인전환·개원폐업·매출관리·기타(신규 8종).

### 구현

- `backend/api/llm.py`: `classify_tax_category()` — Upstage(solar-pro3) function-calling(국내 AI 트랙 준수, 외산 모델 미사용). 실패/불확실 시 '미분류' 반환.
- **튜닝**: 카테고리명만 나열한 첫 버전은 상속·증여/매출관리 같은 미묘한 케이스를 자꾸 놓치고 미분류로 흘렀다. `engine_adapter.py`의 9종 지출유형 힌트 패턴처럼 카테고리별 설명 문장을 시스템 프롬프트에 추가하니 정확도가 크게 개선.
- `backend/api/rag/ingest.py`: `_resolve_tax_category()` — 프론트값이 없거나 플레이스홀더면 서버가 분류해 덮어씀. 이후 신규 배선은 자동으로 실제 카테고리를 받는다.
- `backend/api/main.py` + `store.py`: `POST /api/rag/reclassify-tax-categories` — 기존 active passage 전체 소급 재분류(재임베딩 없음, 재실행 가능한 관리자 엔드포인트).
