## 4. 설계가 틀렸던 것 / 새로 안 것

### 4-1. "두 파이프라인이 같은 게이트 줄을 선다"는 두 프로세스로는 불가능

`upstage_gate` 는 프로세스 안의 FIFO 다. 격리 설계 §1(프로세스 층)과 §2(게이트 공유)는 **동시에 성립하지 않는다.**
→ v2 유닛을 k=1 로 둬 합계 상한을 4 로 묶었다. 진짜 공유가 필요하면 프로세스 밖 줄(DB advisory lock 등)이 필요하다 — 트래픽이 붙는 단계 5 에서 판단.

### 4-2. 두 번째 프로세스는 리퍼를 들고 뜬다

v1 유닛 주석의 `--workers 1` 경고와 **같은 사고가 v2 유닛으로도 난다** — 같은 `api.main:app` 이라 lifespan 이 kb2 폴러를 띄우고,
폴러의 첫 패스가 `reap_stale_running_jobs(all_running=True)` 로 v1 의 running job 을 죽인다. 격리 설계는 이걸 몰랐다.
→ `BACKGROUND_JOBS=off` 가드 + 유닛 파일에 "지우지 말 것" 주석. 리퍼 호출처는 `kb2_scheduler.py:39` 하나뿐임을 확인.

### 4-3. 원복 1단계(env)는 두 프로세스 위상에서 약하다

`?pipeline=v2` 가 env 를 이기므로(rag 관례) env 는 v2 프로세스 안 디폴트일 뿐이다. **실질 킬 스위치 = `systemctl disable --now neo-luddite-api-v2`**
(Caddy 가 v1 로 흘린다). 격리 설계 §3 표는 한 프로세스 전제로 쓰였다.

### 4-4. 로컬 스모크의 한글 본문

Windows Git Bash 에서 `curl -d '한글'` 은 본문이 깨져 FastAPI 가 400 을 낸다. 서버 쪽 검증은 **서버에서 파일로(`--data-binary @f`)** 보냈다.

## 5. O-2 확정 (사용자 결정)

- **턴 간 상태 = assistant `Message.askState` 선택 필드**(서버 무상태, history 왕복).
- **"이대로 답변 받기" = `ChatRequest.action: "proceed_with_gap"`** + 텍스트는 버튼 문구.
- 결정 근거가 된 코드 사실: 프론트 Zod `messageSchema` 가 **모르는 키를 조용히 지운다**(`services/chat.ts:41`) → 백엔드와

- 기각한 안과 이유는 설계 마스터 §6.
