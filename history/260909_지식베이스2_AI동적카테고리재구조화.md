# 260909 · 지식베이스2(KB2) AI 기반 동적 카테고리 재구조화 (로드맵 4.5단계)

## 배경

KB2 로드맵 4단계(auditor의 문장 직접 수정)를 마친 뒤, `/audit/kb2` 화면 UX를 기존 지식베이스
(문서 트리 + 사이드바)와 통일할 수 있는지 검토하다가, 사용자가 더 근본적인 질문을 던졌다:
"이 구조를 Upstage AI가 이해하고 구축할 수 있어야 한다" — 대회가 국내 AI 트랙([[project_korean_track_compliance]])
이라, KB2의 최상위 구조(17개 세목)가 지금은 `backend/api/rag/taxonomy.py`에 하드코딩돼 있는데,
사용자 확인으로는 이 17개도 원래 Solar Pro가 초기 RAG 데이터를 분석해 도출한 결과였다 — 지금은
그 산출물이 코드에 박제돼 있을 뿐. 그래서 "재구조화" 버튼을 누르면 그 시점 RAG 전체를 Solar
Pro가 다시 분석해 카테고리 자체를 새로 제안하도록 바꾸기로 했다.

## 설계 — Plan 모드, Explore 에이전트 4개로 조사 후 확정

**두 가지 사용자 결정**:
1. 카테고리 연속성 — 재구조화를 다시 돌리면 카테고리 이름/개수가 달라져도 AI가 매칭 판단을
   하지 않는다. **매번 전체 재생성** + 이전 `kb2.documents`는 `status='archived'`로 보관
   (삭제 아님, 세무사가 잠근 문장도 보존되지만 검색·auditor 화면 노출에서는 빠짐).
2. 진행 UX — map-reduce라 수 분 걸릴 수 있어 **작업(job) id + 폴링**으로 진행률을 보여준다
   (새 인프라지만 UX가 낫다는 결정, 이 레포에 처음 생기는 job/폴링 패턴).

**조사로 확인한 안전장치**: `rag.passages.tax_category`는 DB 제약 없는 순수 text 컬럼이고,
`?ragSource=rag`(일반 RAG, A/B 비교 기준선)는 `kb2.*` 스키마를 전혀 참조하지 않음
(`retriever.py:get_retriever`의 `_rag()`는 `kb2_store` import조차 안 함) — 구조상 이 작업이
RAG-only 모드에 영향을 줄 수 없음을 코드로 확인.

**해결한 설계 문제**: `kb2.documents.tax_category`가 `unique` 제약으로 기본키 역할을 하고
있어서, 카테고리 레이블이 매번 바뀌면 이전 문서가 고아가 되는 구조였다 → `kb2.categories`
테이블(안정적 UUID)을 새로 도입해 레이블(표시용)과 정체성(category_id)을 분리.

## 구현

- **스키마** (`supabase/migrations/0020_kb2_dynamic_taxonomy.sql`): `kb2.categories`(id/label/
  description/status), `kb2.documents.category_id` FK 추가 + `tax_category` unique 제약 제거,
  `kb2.synthesis_jobs`(진행상황 폴링용). 프로덕션 Supabase에 적용 완료.
- **map-reduce** (`backend/api/llm.py`): `propose_categories_batch()`(맵 — 배치당 30~40건,
  각 200자만 사용해 후보 카테고리 제안) + `merge_categories()`(리듀스 — 후보 label+description
  만 다시 LLM에 넣어 통합, `MAX_CATEGORIES=20` 코드에서 강제 상한).
- **오케스트레이션** (`backend/api/rag/kb2_taxonomy.py` 신설): 발견→분류(기존
  `classify_tax_category` 재사용)→이전 활성 문서 전체 archive→카테고리별 합성(기존
  `synthesize_kb2_sentences` 재사용). `kb2_store.py`에 `create_category`/`list_categories`/
  `archive_all_active_documents`/`create_document`(순수 insert)/`create_job`/`update_job`/
  `get_job` 추가, `list_documents(status=...)` 파라미터 추가(auditor 화면 기본 `active`만).
- **API** (`backend/api/main.py`): `POST /admin/kb2/restructure`(FastAPI `BackgroundTasks`로
  즉시 jobId 반환, DB에 job 기록), `GET /admin/kb2/restructure/{jobId}`(폴링), `GET
  /admin/kb2/documents?status=archived`(보관함).
- **프론트**: `frontend/components/admin/kb2-synthesis-view.tsx`에 "AI로 카테고리 재구조화"
  섹션 추가(job 폴링 3초 간격, stage별 라벨, 완료 시 요약, 보관함 접기/펼치기). 기존 고정
  세목 트리거는 "레거시"로 표시만 하고 코드는 안 건드림. `frontend/services/kb2.ts`에
  `startKb2Restructure`/`getKb2RestructureJob`/`listArchivedKb2Documents` 추가.

## 실제 실행 검증 — 버그 2개 발견·수정

1차 시도(FastAPI `BackgroundTasks`를 통한 실행)에서 `updated_at`이 멈춘 것처럼 보여 스레딩
문제를 의심했으나, 실제로는 **파이프라인 자체가 그만큼 느렸을 뿐**이었다(413건 활성 passage,
분류 단계가 기존 `classify_tax_category` 패턴을 그대로 재사용해 1건씩 순차 호출 — 이 레포에
배치 분류 유틸이 없어 기존 관례를 그대로 씀). FastAPI 밖에서 스크립트로 직접 실행해 동일하게
느린 것을 확인, 스레딩이 원인이 아님을 배제.

**버그 1 — 카테고리 개수 폭주**: `merge_categories`가 "최대 20개"를 프롬프트로만 요청했더니
1차 실행에서 149개가 나옴(맵 단계 배치 12개 × 배치당 다수 후보가 그대로 통과). `llm.py`에
`MAX_CATEGORIES=20` 상수를 추가해 LLM 성공 경로·폴백 경로 양쪽 다 코드에서 슬라이스하도록
수정 — 프롬프트 지시만으로는 모델이 안 지킬 수 있다는 교훈.

**버그 2 — sourcePassageIds 환각으로 uuid[] insert 실패**: 2차 실행(37분 소요, 20개 카테고리
중 11번째에서 크래시) — Solar Pro가 문장의 `sourcePassageIds`를 실제 id와 한 글자 다르게
생성(`"152ea4c-..."`, 8자리여야 할 첫 세그먼트가 7자리)해서 `insert ... uuid[]`가
`invalid input syntax for type uuid` 로 실패. `kb2_taxonomy.py`와 레거시 `kb2_synthesis.py`
양쪽에 **그 배치에 실제로 넣은 id 집합과의 교집합만 신뢰**하는 필터를 추가(같은 버그가 레거시
경로에도 잠재해 있어서 같이 고침) — LLM 출력의 참조 필드는 실제 존재 여부를 검증 없이 DB에
넣으면 안 된다는 일반 교훈.

3차 실행(두 버그 모두 수정 후): **20/20 카테고리 성공, 17개 문서 생성(3개는 분류된 passage
없어 문서 없음, 정상), 141개 문장 합성, 에러 없음**, 총 소요 약 35분. 결과 카테고리가 이전
고정 17개와 확연히 다른 실제 상담 주제로 세분화됨(예: "개원 전 비용 인정 시점", "중고 의료장비
증빙 부족", "현금결제 적격증빙 미제출" 등) — AI가 실제로 새 구조를 도출했음을 확인.

HTTP 레벨 검증: `GET /api/kb2/documents`(auditor용)가 archived 필터링으로 정확히 17건만 반환,
`GET /admin/kb2/documents?status=archived`가 11건(레거시 1 + 1차 크래시 잔여 9~10) 정상 반환,
`POST /api/chat?ragSource=kb2`로 실제 질문("개원 전 인테리어 비용") 호출 시 새로 합성된 문장을
실제로 인용함을 확인, `?ragSource=rag`는 그대로 4건 히트로 정상 동작(회귀 없음, A/B 기준선
보호 확인). 프론트 `tsc --noEmit` + `next build` 통과.

## 다음 세션 후보

- **분류 단계 배치화**: 지금 413건 순차 호출(1건=1LLM콜)이 전체 소요시간의 대부분을 차지함.
  `propose_categories_batch`처럼 여러 건을 한 번에 분류하도록 바꾸면 호출 수가 크게 줄어든다.
  사용자가 직접 제기한 우려: "서비스 규모가 커지면 세무사가 클릭 한 번으로 큰 작업에
  들어가면 안 된다" — (1) 배치 분류로 절대 시간 단축, (2) 트리거를 "즉시 실행"이 아니라
  "다음 새벽 배치에 반영" 같은 예약 실행(이 레포에 이미 pg_cron 선례 있음, [[project_snapshot_pool]])
  으로 전환, 두 가지를 함께 검토할 것.
- **`kb2.categories` 테이블 정리**: 지금은 문서만 archive 처리하고 카테고리 레이블 자체는
  archive 안 해서 재실행할 때마다 `kb2.categories`에 예전 레이블이 계속 쌓인다(기능엔 영향
  없지만 지저분함) — 문서 archive와 같이 카테고리도 archive하도록 보완 필요.
- `/audit/kb2` 사이드바 트리 UI(기존 지식베이스처럼 문서 트리+콘텐츠 패널 레이아웃)는 이번
  세션에서 검토만 하고 보류 — 이번 동적 재구조화가 먼저 필요하다고 판단해 순서를 바꿈. 다음
  세션에서 이어서 진행 가능.
- 브라우저 수동 스모크(관리자 계정으로 `/admin/kb2`에서 버튼 클릭 → 진행률 UI 실시간 갱신
  확인)는 아직 미실시 — API 레벨 검증만 완료.
