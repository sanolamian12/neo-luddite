# RAG ON/OFF 100건 A/B — 성능 측정보다 먼저 나온 것은 오염 전파 버그였다

날짜: 2026-07-19
브랜치: `import-credigraph` (커밋 없음 — 실험 스크립트 + KB 3건 은퇴)
산출물: `upstage bulk 답변.csv` (4열 완성), `backend/bulk_ask_rag.py` (신규)

---

## 0. 먼저 읽을 것 — 이 숫자는 "정확도 향상"이 아니다

100건 중 **98건의 질문이 KB passage 안에 그대로 들어 있다.** KB 는 바로 이 질문들을
감사해서 만들어졌기 때문이다. 그래서 이 실험이 측정한 것은:

> ✅ **폐루프 반영률** — 세무사가 교정한 내용이 다음 답변에 실제로 반영되는가
> ❌ 일반화 성능 — 처음 보는 질문에서 RAG 가 더 정확한가

본선 자료에 "RAG 로 정확도가 올랐다"고 쓰면 leakage 반박을 그대로 맞는다.
쓸 수 있는 문장은 **"세무사 1회 교정이 동일 질문군에서 재현된다"** 까지다.

## 1. 설계 — 변수를 RAG 하나로 묶기

`bulk_ask.py`(C열 생성기)의 `SYSTEM_PROMPT` · `solar-pro3` · `temperature=0.3` 을
그대로 import 해서 `bulk_ask_rag.py` 를 만들었다. 두 스크립트의 유일한 차이:

```
bulk_ask.py     : [system, user(question)]                → C열 (RAG OFF)
bulk_ask_rag.py : [system, user(교정된 사례 + question)]   → D열 (RAG ON)
```

검색 경로는 제품과 동일(`embedding-query` → `rag.match_passages` → `RAG_MIN_SCORE=0.50`,
top-5). 제품 파이프라인을 통째로 태우지 않은 건 라우팅·후처리가 섞이면 차이를 RAG 에
귀속시킬 수 없어서다.

검색 실적: **hits=0 은 1건(no.1)뿐**, 5건 만점이 64건. 채택 score 중앙 0.648.
출처는 `feedback` 280 · `session_eval` 151.

## 2. 1차 실행에서 나온 버그 — KB 가 오류까지 같이 주입하고 있었다

### 2-1. 증상

RAG ON 답변에 **가짜 판례가 살아 돌아왔다.** no.55 예:

```
RAG ON v1: "조심2025구1960: … (조세심판원 결정례, 판례 아님)"
```

세무사가 "그건 실재 여부도 확인 안 된다"고 지적한 사건번호를, 지적을 괄호로만 흡수한 채
근거로 재인용했다.

### 2-2. 원인 — `build_bundle_text` 의 [AI 답변] 블록

`ingest.build_bundle_text()` 가 만드는 KB 번들은 이 형식이다:

```
[질문] …
[AI 답변] …        ← 세무사가 "틀렸다"고 지적한 바로 그 답변
[세무사 코멘트] …   ← 교정 의견
(태그: …)
```

이걸 **통째로** 프롬프트에 넣으면 모델은 두 블록의 극성을 구분하지 못한다. KB 전수 조사:

| 토큰 | ✗[AI 답변] 블록 | ✓[세무사 코멘트] 블록 |
|---|---:|---:|
| 소득세법 §35 | 70 | 18 |
| 조심2025구1960 | 11 | 14 |

즉 **교정 지식을 넣으면서 오류도 같이 넣고 있었다.**

### 2-3. 고침 — 추론에 맡기지 말고 데이터 층에서 라벨을 박는다

`reshape_passage()` 가 주입 직전 번들을 파싱해 극성을 명시한다:

```
■ 유사 사례: {질문}
  [✗ 잘못된 답변 — 세무사가 오류로 지적한 내용입니다.
     여기 등장하는 조문·판례·수치는 실재하지 않을 수 있으니 절대 인용하지 마세요]
  {AI 답변}
  [✓ 세무사 교정 의견 — 이것만을 근거로 삼으세요]
  {코멘트}
```

파싱 실패 시 원문 그대로 통과(graceful). 코멘트 없는 `case_seed`/`kb_document` 는 미변경.

### 2-4. v1 → v2 효과

| 지표 | OFF | ON v1 | ON v2 |
|---|---:|---:|---:|
| 가짜근거(§35·조심1960) | 0 | 3 | **0** |
| 스캐폴딩 누출(`[질문]` 등) | 0 | 7 | **0** |
| "참고 지식에 따르면" 인용체 | 0 | 61 | **1** |
| 길이 중앙값(자) | 3,889 | 1,479 | 736 |

### 2-5. ⚠️ 제품에는 아직 이 구멍이 그대로 있다

`backend/api/llm.py` 의 `write_segments` / `write_advisory` 는 **`p.content` 를 원문 그대로
주입**한다. 실험에서 증명된 오염 경로가 프로덕션에 살아 있다. → §6

## 3. KB 안의 나쁜 데이터 3건 (사용자 승인 후 은퇴)

`session_eval` passage 3건이 **가짜 사건번호를 "실존 케이스"로 추천**하고 있었다:

```
▷ RAG 개선: … 조심2025구1960(가족 인건비 부인) 계열 실존 케이스로 치환
```

권위 있는 블록(세무사 코멘트) 안에 있어서 `reshape_passage()` 로도 걸러지지 않는다.
사용자 승인을 받아 `set_status(..., 'retired')`:

```
active 529 → 526 · retired 0 → 3 · session_eval 167 → 164
auditor 기여 240 → 237
ledger_entries 무변동 (contribution_accepted 270 / rejected 6)
```

**ledger 가 안 움직인 게 설계대로다.** 적립된 크레딧은 남고 "살아 있는 기여"만 감소한다.
은퇴는 삭제가 아니라 status 플립이라 감사 추적도 보존된다.
영향받은 no.11 · no.43 은 은퇴 후 KB 로 재생성했다.

## 4. 채점 결과 (100건 전수, 문장력·법률정확성 각 5점)

파일럿 5건으로 루브릭을 잡고(기존 260712 세무사 점수와 3/5 정확 일치·2/5 ±1),
나머지 95건은 8개 병렬 에이전트가 동일 루브릭 + 검증된 법령 미니 KB로 채점.

| | RAG OFF | RAG ON | Δ |
|---|---:|---:|---:|
| 문장력 | 2.29 | **3.85** | +1.56 |
| 법률정확성 | **1.00** | **4.03** | +3.03 |
| 우세 판정 | 1건 | **99건** | |

분포:
```
OFF 문장력   2:71  3:29                 OFF 법률   1:100   ← 전건 최하점
ON  문장력   2:1  3:14  4:84  5:1       ON  법률   1:1  2:1  3:14  4:62  5:22
```

**OFF 법률정확성이 100건 전부 1점**이다. 이건 바닥 효과(floor effect)라 Δ+3.03 을
"3배 향상"처럼 읽으면 안 된다. 정확한 서술은 **"OFF 는 예외 없이 법적 근거가 무효였다"**.

### 4-1. 가장 단단한 객관 지표 — 가짜 근거 인용

에이전트가 답변마다 환각 인용을 열거하게 했다 (사건번호 형식·조문 표제 불일치·미상 예규):

| | RAG OFF | RAG ON |
|---|---:|---:|
| 가짜 근거 인용 **총량** | **359건** | **8건** |
| 하나라도 포함한 답변 | **99 / 100** | **2 / 100** |

전형적 OFF 환각: `대법원 2015다12345`, `대법원 2005다12345` — 일련번호가 `12345`,
`1234` 같은 자리표시자다. `국세청 예규 2022-12-01`, `한국세무학회 '세무실무 가이드 2023'`
처럼 출처 자체가 없는 것도 반복된다.

### 4-2. P1–P12 패턴

| | OFF | ON |
|---|---|---|
| | P5:100 P7:50 P2:28 P9:28 P8:13 P10:7 P6:7 P3:4 P12:4 P4:2 | P2:5 P12:4 P10:3 P5:2 P7:2 P8:2 P9:1 |

**P5(가짜 조문·판례) 100/100 → 2/100.** 260712 에서 정의한 반복오류 사전이 A/B 축으로
그대로 작동했다.

> 참고: 초기에 만든 키워드 자동 집계(`ab_tally.py`)는 **결론이 뒤집혀 나왔다.**
> "'적격증빙 미보유 → 손금부인' 논리는 성립하지 않습니다" 같은 **교정 문장**을
> 오류로 세기 때문이다(극성 맹목). 정성 채점의 대체가 될 수 없어 교차검증용으로만 남겼다.

## 5. RAG ON 이 진 유일한 건 — no.1

**hits=0 인 1건이 정확히 그 1건이다.** 0.50 컷을 넘는 passage 가 없어 순수 생성으로
떨어졌고, 가짜 조문 4개 + 가짜 판례 3개에 자기모순(P12)까지 냈다. OFF 보다 나빴다.

> **RAG 는 검색이 실패한 자리에서 RAG OFF 보다 안전하지 않다.** 오히려 "근거가 있다"는
> 프롬프트 틀만 남고 내용이 비어 환각을 부른다. hits=0 일 때는 주입 문구 자체를 빼거나
> "확인 필요"로 강제하는 분기가 필요하다.

### 5-1. 남은 약점 — 내용은 맞는데 조문 번호가 없다

에이전트들이 공통으로 지적한 ON 의 감점 사유 1위가 **"조문 미인용"**이다. 환각을 막느라
인용 자체를 눌러버린 부작용이다. 법률정확성 3점대(14건)가 대부분 여기 걸린다.
KB 코멘트에 조문 번호가 있으면 그건 인용하도록 허용하는 규칙 완화를 검토할 것.

## 6. 남은 것

- **제품 반영 (P0)** — `backend/api/llm.py` 의 `write_segments`/`write_advisory` 에
  `reshape_passage()` 동등 처리를 넣는다. 지금은 실험 스크립트에만 있고, 프로덕션은
  §2-2 오염 경로가 열려 있다.
- **hits=0 분기** — 검색 미스 시 주입 틀 제거 + "확인 필요" 강제 (§5).
- **조문 인용 허용 규칙** — ✓ 블록에 있는 조문은 인용하게 (§5-1).
- **미학습 질문 세트** — leakage 없는 20~30건으로 일반화 성능을 따로 측정해야
  본선에서 "정확도 향상"을 주장할 수 있다 (§0).

## 7. 배운 것

1. **성능을 재려다 버그를 먼저 잡았다.** 사용자 판단("구조 문제를 잡고 비교해도 된다")이
   맞았다. v1 그대로 측정했으면 "RAG 가 가짜 판례를 늘린다"는 결론이 나왔을 것이다.
2. **KB 에 오류를 넣는 건 의도된 설계다 — 문제는 극성을 안 알려준 것.** 틀린 답변은
   지워야 할 게 아니라 "틀렸다"고 라벨링해서 넣어야 하는 자산이다.
3. **키워드 집계는 교정 문장을 오류로 센다.** 비판 어휘와 오류 어휘가 같아서다.
   반복오류 사전은 사람(또는 읽는 모델)이 극성을 판단해야 작동한다.
4. **권위 블록 안에도 나쁜 데이터가 있다.** 세무사 코멘트라고 무조건 참이 아니다.
   §3 은 구조적 필터로는 못 걸러 사람 승인이 필요했다.
5. **바닥 효과를 그대로 배수로 말하지 않는다.** OFF 법률 100건 전부 1점이라는 사실이
   Δ+3.03 보다 정직하고 강한 문장이다.
