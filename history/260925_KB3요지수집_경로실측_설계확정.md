## 1. 결과 한 줄

> **국세법령정보시스템 판례 '요지'를 사람 손 없이 모으는 3단계 경로를 실제 호출로 확인했고, 수집 범위·키·용어를 사용자와 정했다. 코드는 0줄.**

## 2. 왜 지금

"다음 단계" 질문에 **LLM2 데이터 수집을 먼저** 권했다 — 남은 일 중 리드타임이 가장 길고(수집→검수→적재), 정본 S2(LLM2 판정)의
전제가 KB3 라 데이터 없이는 W5 를 한 줄도 못 쓴다. 지금 v2 답변 단계는 판정 없는 자문 임시라 v2 유닛을 먼저 켜도(단계 5) 얻는 게 적다.
LLM1 단계 4(턴 단위 평가)는 KB3 와 무관한 작은 데이터 작업이라 병행 가능.

세무사 추천(사용자 전달): law.go.kr 판례 검색 → 국세법령정보시스템 문서의 **'요지'를 RAG 에**.

## 3. 실측한 것

| 확인 | 결과 |
|---|---|
| law.go.kr Open API 검색 | `search=2`(본문)로 "병의원" 53건. 사건명 검색(기본)은 0건 |
| 출처 섞임 | 53건 대부분 대법원 의료법 형사·특허·손해배상 — `데이터출처명=국세법령정보시스템` 필터가 핵심 |
| law.go.kr Open API 상세 | 국세법령정보시스템 판례엔 "일치하는 판례가 없습니다" → 요지 못 받음(기존 `law_prec.py` 요지 57/740 의 원인) |
| law.go.kr 웹 판례 페이지 | `precInfoP.do?precSeq=…` 가 **302 로 taxlaw `ntstDcmId`** 를 준다 — 연결 고리 |
| taxlaw 상세 페이지 | JS 껍데기. 데이터는 `POST /action.do` actionId `ASIQTB002PR01` JSON — `ntstDcmGistCntn` = 요지 |
| robots | law.go.kr 전면 Allow · taxlaw 는 통합검색 두 페이지만 Disallow → **검색은 law.go.kr, taxlaw 는 상세만** |
| 요지 수신 | `대법원-2025-두-34754`(사용자 예시) · `서울고등법원-2015-누-631`(② 경유) 둘 다 성공. 본문은 "붙임과 같습니다"(첨부) |
| 기존 수집본 | 5월 1,301건 중 의료 관련 ~67건 — 주 재료로 부족 |

사용자가 준 URL 조각 `#licPrec205636` 은 클릭한 문서가 아니었다(205636 = 특허법원 손해배상). 화면 상태가 조각에 안 남는다.

## 4. 사용자와 정한 것

- **범위 확장**: 병의원 한정은 양 걱정 때문이었다 → **전시회 시민이 물을 법한 키워드까지 확장 OK**. 양은 키워드당·전체 상한으로.
- **OC 키 `choiyoojin`** = 팀장 **최유진**의 open.law.go.kr 이용자 ID, 대량 수집 OK. **LLM 키가 아니다**(Solar·Claude 무관, 수집에 AI 호출 0).
- **용어**: 내가 쓴 "상세"는 문서 1건을 여는 호출 이름이었고, 가져오는 건 그 안의 **요지 칸** — 세무사가 말한 "두세 문장" 정보와 같다.
- **정본 A6 정정**: "KB3 는 외부에서 유입, 우리가 수집하지 않는다" → **우리가 수집한다**(LLM1 데이터 때 9/24 "우리 몫"과 같은 전환).
