## 0. 한 줄 요약

세무사가 손댄 문장이 재구조화 한 회차 만에 사라지던 것을 끊었다 — archive 하지 않고
**새 세대 목차 중 레이블 임베딩이 가장 가까운 세목에 다시 붙인다**. 임계값 0.70 은
세대 간 레이블 쌍 171건을 전부 찍어 오탐이 시작되는 지점 위에 그었다. G2 축적성
0% → 성립.

## 1. 왜 이것이 커버리지보다 먼저인가

KB2 의 제품 논지는 "KB 는 세무사 코멘트로 **자란다**"인데, 직전 세션 §8.2 에서 그게
사실이 아님이 실물로 드러났다: 세무사 계정으로 '기타'에서 빼내 진짜 세목에 넣은 문장
`fc17e2f6` 이 **정확히 한 회차 만에 원상복귀**했다. 옮긴 문장은 archived 문서 안에서
검색 밖으로 나갔고, 같은 원문은 새 세대에서 새 문장으로 **다시 '기타'** 에 담겼다.

`archive_all_active_documents()` 가 활성 세대를 통째로 내리기 때문이다.
`locked_by_auditor` 는 레거시 재합성 경로만 막아서 여기엔 효과가 없었다.

즉 **KB 는 자라지 않고 회차마다 다시 만들어지고 있었다.** 커버리지를 몇 %p 올리는 것
보다 이쪽이 크다 — 완성 목표에서 G1 재현성 다음이 G2 축적성인 이유다.

## 2. 전략: 보존 + 의미 기반 재부착 (문자열 매칭이 안 되는 이유)

사람이 손댄 문장을 archive 하지 않고, 새 세대 목차 중 **레이블 임베딩이 가장 가까운**
세목에 다시 붙인다. 맞는 자리가 없으면 '기타'로 내리고 계측에 남긴다.

문자열 매칭을 안 쓰는 건 취향이 아니라 **측정된 사실** 때문이다:

- 목차 레이블은 세대를 넘어 **33~67% 만 남는다**(최근 4회 67/33/47/60%).
  하필 `fc17e2f6` 의 목적지 `1세대1주택비과세` 가 이번에 사라진 12개 중 하나였다.
- 그런데 **의미는 남는다**: `1세대1주택비과세`→`양도소득세비과세`,
  `감가상각`→`감가상각비`, `부가가치세`→`부가가치세신고`.

문자열은 불안정하고 의미는 안정적이므로 재부착은 임베딩으로 해야 성립한다.

## 4. L2 결정 6건 (사용자 확정)

### ② 중복 정책 — **둘 다 둔다**

근거는 추측이 아니라 실측이다. 현 세대 **안에서도** 원문 1건이 여러 문장에 들어가 있다:

```
1문장 251건 · 2문장 46 · 3문장 27 · 4문장 12 · 5문장 9 · … · 12문장 1
```

**크레딧 중복은 보존이 만드는 새 문제가 아니라 지금도 매 회차 일어나는 일이다.**
보존이 더하는 건 "세대를 넘는 중복" 하나뿐이다.

### ③ 기여·정산 — 충돌 없음

기여 = RAG 존속기간 모델은 **원문 passage 의 생존**에 걸려 있고 문장 수와 무관하다.
재부착은 attribution 을 건드리지 않는다(move_sentence 와 같은 이유 — 분류 정리이지
내용 수정이 아니다).

### ④ 보존 범위 — `auditor_edit` + `moved` + `retired` 전부

`retired` 는 "이 문장은 쓰지 말라"는 사람의 판단이다. 그것도 세대교체가 지우면 같은
문장이 매 회차 되살아난다 → **보존하되 status 를 유지한 채** 따라오게 한다.

### ⑤ 스키마 — 마이그레이션 0026

`sentence_versions.editor_type` 에 `regenerated_reattach` 추가(CHECK 확장만).
**별도 플래그 컬럼을 두지 않았다** — 사람이 손댄 흔적은 이미 `sentence_versions` 에
전부 있고, 플래그를 두면 이력과 플래그가 어긋날 자리가 하나 더 생긴다.

`moved` 와 editor_type 을 나눈 이유: 재부착은 사람이 고른 이동이 아니라 세대교체가 한
자동 재배치다. 이력에서 둘이 구별되지 않으면 나중에 "세무사가 여기로 옮겼다"를 잘못
읽는다. `meta` 에 from/to 레이블과 유사도 점수를 남겨 오탐을 사후에 되짚을 수 있게 했다.

### ⑥ 계측 정의 — **분리 계상** (지표가 스스로를 속이지 않게)

`coverage.cited` 는 지금처럼 **'이번 회차 합성이 인용한 원문'만** 센다. 보존분을 더하면
분자가 세대를 넘어 섞여 커버리지가 **누적치로 변하고**, "이번 합성이 얼마나 잘했나"를
더는 못 읽는다. 보존분은 `preservedSentences` / `reattached` /
`reattachFailedToUnsorted` / `reattachEmbedFailures` 로 따로 남기고 **화면에서만** 합쳐
보여준다.

### ⑦ 재부착 실패율 — coverage 에 남긴다

매칭이 없어 '기타'로 내려간 건수. 계속 크면 임계값이 빡빡하거나 목차가 회차마다 너무
많이 뒤집힌다는 신호다.

## 5. 구현

| 파일 | 내용 |
|---|---|
| `0026_kb2_preserve_human_sentences.sql` | `editor_type` 에 `regenerated_reattach` 추가 |
| `kb2_store.py` | `list_human_touched_sentences` · `reattach_sentence` · `get_or_create_unsorted_document` |
| `kb2_taxonomy.py` | `REATTACH_MIN_SIMILARITY=0.70` · `_reattach_preserved` · `_duration_summary` · coverage 분리 계상 |
| `kb2_synthesis.py` | 합성 호출별 소요 계측(성공/실패 분리) |
| 프론트 | coverage 필드·단계 레이블·소요 분포 표시 |

**두 가지 순서 결정**:

1. `_reattach_preserved` 는 **합성 가드를 통과한 뒤**에 돈다. 가드가 회차를 되돌리는
   경로(`restore_generation`)에서는 여기까지 오지 않으므로, 되돌려진 회차가 사람 문장을
   엉뚱한(그리고 곧 삭제될) 문서로 옮겨놓는 일이 없다.
2. 보존 대상은 archive **직전**에 집는다. 쿼리가 문서 상태를 안 보므로 값은 같지만,
   "내려가기 전에 건졌다"는 의도가 코드 순서로 읽히는 편이 낫다.

**소급 보정을 안 한 이유**: 보존 대상 쿼리가 **문서 상태를 보지 않는다.** 그래서 지금
archived 에 갇힌 3건이 다음 회차에 자동으로 딸려 올라온다. 이건 편의적 예외가 아니라
정의 그대로다 — "사람이 손댄 문장은 어디에 있든 새 세대로 따라온다". 재부착된 문장은
새 세대 활성 문서로 옮겨가므로 이 집합은 회차마다 커지지 않는다(같은 문장이 따라올 뿐).

지난 회차와 결정적으로 다른 점 — 문장이 **active 로 '기타'에 살아 있고 이력이 온전하다**:

```

          sent=active  문서='기타'(unsorted)
```

세무사가 다시 옮길 수 있다. 직전 회차엔 archived 로 검색 밖에 나가고 같은 원문의
복제본이 조용히 새로 생겼다.

**정직하게 적어둘 것**: G2 는 **"문장을 안 지운다"를 달성했고**, **"사람이 고른 세목을
지킨다"는 목적지 개념이 목차에서 통째로 사라지면 못 지킨다.** 이번 회차는 2/3 이다.
이 비율이 곧 목차 안정성의 함수이므로, 회차가 쌓이기 전에는 임계값 탓으로 읽지 말 것.

**중복 정책이 실제로 보이는 모양**: 보존 문장마다 같은 원문의 다른 활성 문장이 1개씩
있다(`fc17e2f6`+`8277addb` 둘 다 '기타', `acdb99cb`+`7f89e3ae` 둘 다 '6세이하자녀').
결정("둘 다 둔다")대로지만, **같은 세목 안에 비슷한 두 문장이 나란히 보인다**는 뜻이라
트리 가독성 관점의 후속거리다(→ §9⑤).


**"모델이 느리다"가 아니다.** 진짜로 느린 생성이면 분포가 연속적이어야 하는데, 3.5초에서
**240초 벽에 딱 붙어** 두 덩어리로 갈라진다(243~248초 = `TIMEOUT_SYNTHESIZE` 240초를
치고 SDK 내부 재시도가 성공한 모양). 실패 1건이 정확히 480초인 것이 재시도를 확증한다.

산수:

```
TIMEOUT_SYNTHESIZE 240s = p50(3.54s) 의 68배
정상 호출 48회를 p50 로 다 돌면            2.8분
실제 합성 단계 벽시계 (21:23→21:58)        35분
→ 호출의 ~10%(p90 기준 5회쯤)가 벽시계의 ~85% 를 먹었다
```

처방은 **상한 하향 + 백오프** 쪽이지 청크 재분할이 아니다(청크 크기와 인용률은 이미
단조 관계 없음으로 기각됐고, 여기서도 느린 건 크기가 아니라 정체다).

⚠️ **단, 1회 측정이다.** 그리고 요약 분위수만 남겨서 "5회쯤"은 p90 에서 **추정**한
값이다 — 원시 소요 목록을 저장하지 않았다. 값을 바꾸기 전에 원시값을 남기도록
바꾸고(한 줄) 한 회차 더 재는 편이 싸다.

## 8. 함께 넣은 것 — 합성 호출 소요 계측 (G1 의 마지막 조각 준비)

`TIMEOUT_SYNTHESIZE`(240초)를 **감으로 낮추지 않기 위해** 먼저 분포를 잰다. 직전 회차
9be87b52 에서 합성 호출의 12.7%(7/55)가 `APITimeoutError` 였고, 한 번에 240초를 붙들어
회차가 3002초까지 늘었다. 정상 호출이 몇 초인지 알아야 **상한 하향·백오프·청크 재분할**
중 무엇이 처방인지 정할 수 있다.

`ChunkFailures` 에 `successMs`/`failedMs` 를 더하고(성공과 실패를 **나눠** 담는다 —
섞으면 타임아웃이 평균을 끌어올려 정상 호출이 원래 느린 것처럼 보인다),
`coverage.synthesisSuccessMs/FailedMs` 에 p50/p90/p99/min/max 로 요약한다.
**이번 회차가 그 값을 준다** — 별도 측정 비용 0.

## 9. 다음 세션 작업 목록

### ① 합성 타임아웃 처방 (G1 의 마지막 조각) — **분포는 나왔다**

§7.3 이 답이다: p50 3.54초 vs 상한 240초(68배), 호출 ~10% 가 벽시계 ~85% 를 먹는다.
처방 후보는 **상한 하향 + 백오프**. 다만 (a) 1회 측정이고 (b) 원시 소요 목록을 안
남겨 "5회쯤"이 p90 추정이다 → **원시값 저장을 한 줄 더하고 한 회차 더 재고 나서**
값을 바꾸는 것이 이 프로젝트의 규율에 맞다. 상한을 낮출 때 정상 호출(p90 이 이미
240초 벽에 붙어 있으므로 **벽 아래의 진짜 p90 을 모른다**)을 자르지 않는지가 관건.

### ② 근사 동의어 병합 — **접기만 하면 안 된다**

직전 세션 A/B/C 실험을 다시 읽으면 조건이 하나 붙어 있다:

```
B 채움 30개·중복 無 : 53.6%  ≈ A(51.8%, 편차 안)   ← 접고 **다시 채움** = 커버리지 중립
C 축소 22개·중복 無 : 46.4%  < B (편차 밖)          ← 접기만 함 = 분명히 나쁨
```

즉 **접은 만큼 목차를 다시 채워야** 커버리지 중립이고, 접기만 하는 구현은 그대로
기각된 C 다. 리필에 LLM 호출이 하나 더 붙는다. 효과는 **트리 가독성**이지 커버리지가
아니다. 도구는 `docs/doing/kb2_측정자료_260912/scripts/g1_labels.py`
(사라진 `build_taxonomies.py` 의 대체).

### ③ 미인용의 '분모' 판단 (후순위 유지)

직전 세션 §9 그대로. 태그만으로는 안 된다(태그가 있는데 인용된 46건이 있다).

### ④ 재부착 임계값 재평가 — 회차가 쌓인 뒤에

`reattachFailedToUnsorted` 와 `reattachDetails` 의 점수가 회차마다 쌓인다. 실패가
계속 크면 0.70 이 빡빡한 것인지 목차가 너무 뒤집히는 것인지 그 데이터로 가른다.
**1회로 판단하지 말 것.**
