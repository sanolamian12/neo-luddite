# 지식베이스2 커버리지 20% — 원인 규명 · 분류 건별 복원 · 계측 도입

**날짜**: 2026-09-11
**세션 성격**: 제품 코드 전용(논문·벤치마크는 다른 세션 — `docs/doing/HF_사용정책_국내AI트랙.md` §5)
**커밋**: `f113d04` (import-credigraph, main 동일)

## 0. 한 줄 요약

커버리지 20% 의 원인은 **맵 단계 프롬프트가 아니었다.** 분류 배치화(9/10), 프롬프트
불일치, 목차 크기, merge 타임아웃 — 네 가지가 각각 독립적으로 원문을 버리고 있었고,
그중 제일 큰 것은 **직전 세션에 성능 개선이라고 넣은 분류 배치화**였다.

## 1. 들어갈 때의 가설과 그 결말

로드맵 §7 과 직전 세션 기록은 원인을 이렇게 적어뒀다:

> 맵 단계(`llm.propose_categories_batch`)가 `'업무용승용차'` 같은 주제 대신
> "사립학교사무직원육아휴직수당과세" 같은 질문 하나짜리 레이블을 뽑는다. 카테고리가
> 지나치게 좁아 나머지 80% 가 어느 곳에도 안 붙는다.

**틀렸다.** 좁은 레이블은 실재했지만 그건 증상이지 원인이 아니었고, 실제 인과는 정반대
방향이었다 — **목차가 작을수록 커버리지가 나빠진다**(§5). 사용자가 "인과를 단정하기 전에
대조군부터"라고 못박은 것이 이번에도 맞았다.

## 2. 계측 먼저 (사용자 지시 ①)

분류 결과를 아무 데도 저장하지 않아 "미분류가 몇 건인지" 측정 자체가 불가능한 상태였다.
`kb2.synthesis_jobs.result` 가 이미 `jsonb` 라 **마이그레이션 없이** 깔때기를 넣었다.

```
passagesTotal → assigned / unclassified → fed / truncated → cited
+ classifyCalls, synthesisChunks, sentences, hallucinatedIdsDropped
+ categoryStats[] (세목별 assigned/fed/truncated/chunks/sentences/cited)
```

admin 화면(`kb2-synthesis-view.tsx`)에 `CoverageFunnel` 로 노출, 세목별 표는 접기/펼치기.
세 지점을 나란히 둔 이유: **미분류가 크면 목차가 좁은 것이고, 미투입이 크면 반대로
세목이 커서 프롬프트 예산에 밀린 것이라 처방이 정반대**다.

## 3. 발견 — 합성 프롬프트가 세목당 ~17건에서 포화

`llm.synthesize_kb2_sentences` 가 bundle 을 통째로 `[:12000]` 으로 잘랐다. 문장 중간에서
끊겨 근거가 훼손되고, 몇 건이 버려졌는지 아무도 몰랐다. 실제 passage 길이(n=413, 평균
642자, 중앙값 352자)로 시뮬레이션:

| 세목 크기 | 프롬프트 투입 | 유실 |
|---|---|---|
| 10건 | 10.0 | 0% |
| 21건 | 16.9 | 19% |
| 40건 | 17.1 | **57%** |
| 60건 | 17.1 | **71%** |

여기서 중요한 건 **두 결함이 서로 맞물린다**는 점이다. 맵 프롬프트만 고쳐 카테고리를
넓히면 세목당 건수가 늘어나 이 절단에 더 크게 걸린다 — 유실 지점이 '미분류'에서
'미투입'으로 옮겨갈 뿐 커버리지는 그대로다. 그래서 사용자에게 범위를 물어
**합성 청크화 + 맵 프롬프트를 함께** 하기로 했다.

조치: `llm.fit_passages_for_synthesis` (건 단위 포장, 버린 수 반환) +
`kb2_taxonomy._synthesize_members` (예산 단위로 나눠 여러 번 합성 후 이어붙임,
청크 경계 중복 문장은 정규화 후 출처 id 합집합으로 병합).

## 4. 대조군 — merge 는 그동안 **한 번도 실행된 적이 없었다**

새 맵 프롬프트로 전체 맵+리듀스를 오프라인 실행(적재 없음)한 결과:

```
후보 237개 -> 최종 20개 (merge 1201s)
 6자  장비유지보수    장비 유지보수 계약 비용 전액 비용처리 여부
 4자  업종추가        피부과와 비만·다이어트 클리닉 동시 운영 시 …
 7자  추석복리후생비  추석 직원 떡값 지급 시 비용처리 및 소득세 처리
```

**1201초 = 600초 타임아웃 + 600초 재시도.** 즉 예외로 빠져 파이썬 폴백(첫 등장 순 dedup)이
목차를 정했다. 설명이 전부 "상담 한 건"인 이유가 이것이다 — 목차를 정한 건 LLM 이 아니라
**배치 순서**였고, 최종 목록은 사실상 1번 배치의 원본 레이블이다.

직전 세션이 "9/9 판도 같은 목록이었으니 merge 탓이 아니다"라고 정정했던 그 관찰도 이제
설명된다: 9/9 는 상한 90초라 186초에서, 9/10 은 상한 600초라 1201초에서 — **두 판 모두
같은 폴백으로 빠졌다.** 같은 목록이 나온 건 merge 출력이 안정적이어서가 아니라 둘 다
merge 를 안 썼기 때문이다.

조치: `llm.tally_candidates` — 후보를 레이블 기준으로 접어 **관찰 횟수**와 함께 넘긴다.
맵은 배치마다 독립이므로 반복 관찰 = 넓은 주제다(실측: 업무용승용차·복리후생비 5회,
인테리어비용 4회인 반면 질문 하나짜리는 전부 1회). 이전에는 평평한 목록을 주고
"관찰 빈도순으로 정리하라"고 요구했다 — **모델이 알 수 없는 것을 요구한 셈**이다.
세는 건 파이썬이 공짜로 한다.

결과: **1201초 → 19초.** 폴백도 첫 등장 순에서 빈도순으로 바꿔, 폴백으로 빠져도
최소한 자주 나온 주제가 살아남게 했다.

부수 발견: 개수를 산문으로만 요구하면 모델이 압축을 아예 안 한다 — "8~14개"라고 썼는데
155개 후보에 **128개**를 그대로 돌려줬다. 도구 스키마 `minItems`/`maxItems` 로 박으니
바로 지켜졌다(4초). 스키마 제약이 프롬프트 문장보다 강하게 먹는다.

## 5. 본체 — 2×2 실측으로 진짜 원인 분리

같은 표본 100건, 같은 후보 집합. 재구조화를 돌리지 않고 오프라인으로만 측정:

| 분류 방식 | 프롬프트 | 목차 | 미분류 | 사용된 세목 |
|---|---|---|---|---|
| 배치 20건 | 기존 | 14 | **98%** | 2 |
| 배치 20건 | 강화 | 14 | 60% | 3 |
| 배치 20건 | 기존 | 30 | **84%** ← 프로덕션 | 10 |
| 배치 20건 | 강화 | 30 | 59% | 14 |
| 건별 | 기존 | 30 | 45% | — |
| 건별 | 강화 | 14 | 47% | — |
| 건별 | 강화 | 30 | **28%** | 24 |

세 가지가 독립적으로 작동한다.

### ① 분류 배치화 (가장 큰 원인, 직전 세션에 도입)

84% vs 45%. 20건 × 700자를 한 번에 넣으면 모델이 **앞쪽 몇 건만 성실히 읽고 나머지를
미분류로 흘린다** — 100건에 서로 다른 세목을 2개만 쓴 조합까지 나왔다. 배치화의 명분은
"정확도는 그대로 두고 시간만 줄인다"였는데 성립하지 않았다.

절약분도 다시 재보니 작았다: 건당 0.83초, 413건에 **5.7분** — 배치 2.6분 대비 3분 차이다
(도입 당시 근거였던 "건별이면 35분"은 실측과 맞지 않는다). **14분 파이프라인에서 3분을
아끼려고 코퍼스 절반을 버린 셈**이라 되돌렸다.

### ② 프롬프트 불일치 (구조적 버그)

kb2 가 `llm.classify_tax_category` 를 그대로 빌려 썼는데, 그 `_CLASSIFY_SYSTEM` 은
**레거시 17개 고정 세목**을 이름·설명까지 박아둔 프롬프트다. kb2 는 그 시점에 새로 만든
동적 목차를 `enum` 으로 넘기므로, 모델은 "업무용승용차·임차료·접대성지출…"을 설명받고
**전혀 다른 목록 중에서** 고르라는 지시를 받고 있었다. (레거시 호출자 2곳은
`TAX_CATEGORIES` 를 넘기므로 그쪽은 정합했다 — kb2 만 어긋나 있었다.)

`classify_dynamic_category` 신설로 45% → 28%. 고정 목차 설명을 걷어낸 것과,
**'미분류'를 최후의 수단으로 격하**한 것 두 가지다. 이전 문구("안 맞으면 미분류, 억지로
끼워맞추지 마세요")를 모델이 성실히 따르느라 웬만한 상담을 전부 미분류로 보냈다.
kb2 에서 비용은 대칭이 아니다 — 가까운 세목에 넣으면 세무사가 옮길 수 있지만,
미분류는 어느 문서에도 안 실리고 **화면에 나타나지도 않는다.**

### ③ 목차 크기 — 직관과 반대

14개 47% vs 30개 28%. **작을수록 갈 곳 없는 상담이 늘어난다.** 413건의 병의원 세무 상담은
14개 비용 항목으로 덮이지 않는다. 로드맵의 "카테고리가 좁아서 커버리지가 낮다"는 진단은
레이블의 *성격*(주제형 vs 질문형)과 목차의 *크기*를 뒤섞은 것이었다 — 넓은 주제명을
쓰되 목차 자체는 촘촘해야 한다. 목차가 커져도 탐색성은 2단 트리(대목/세목)가 이미 감당한다.

`MERGE_MIN/MAX_CATEGORIES = 20/30`, `MAX_CATEGORIES = 30`.

## 6. 맵 프롬프트 (원래 이 세션의 주제)

개정은 유지했다 — 3~6개/배치, 12자 이내 명사구, "이 묶음에서 최소 3건 이상 속할 주제만",
실제 산출물을 좋은 예/나쁜 예로 제시. 대조군 3배치에서 2배치는 확실히 넓어졌다
(`인건비·복리후생`, `부가가치세 신고`). 다만 **개수 지시는 안 지킨다**(한 배치가 18~32개).

그리고 이것만으로는 아무것도 바뀌지 않았을 것이다 — 맵 출력은 어차피 타임아웃으로
폴백되는 merge 에 들어갔고, 최종 목차는 배치 순서가 정하고 있었기 때문이다. 지금은
빈도 집계가 그 다변량을 흡수하므로 맵이 수다스러워도 해롭지 않다.

## 8. 다음 (우선순위순)

1. **합성 인용 누수 — 투입 236 / 인용 154 (65%)**. 절단이 사라진 지금 가장 큰 누수이고,
   이번 계측으로 처음 보이게 된 것이다. 합성 프롬프트가 "모든 묶음을 최소 한 문장의
   근거로 쓰라"고 요구하지 않는다. 세목이 클수록 심하다(`가족인건비` 27투입/6인용).
2. **미분류 43% (177건)** — 두 갈래다. (a) merge 가 여전히 질문 하나짜리 레이블과 의미
   중복을 내보낸다(배정 0건 세목이 3개). 개수는 스키마로 강제했지만 품질은 못 했다 —
   merge 에 세목 후보의 *예시 상담*을 같이 주거나, 배정 0건 세목을 사후 정리하는 방향.
   (b) 그래도 남는 건 '기타' 세목으로 받아 버려지는 대신 세무사에게 보이게 하기.
3. 맵 단계 개수 지시 미준수(배치당 18~32개) — merge 에서 통한 `maxItems` 를 맵 도구
   스키마에도 적용.
4. 합성 32분 — 30세목 순차라 가장 긴 단계가 됐다. 병렬화 여지.
5. 합성 청크 2개 이상인 세목이 2개뿐(`복리후생비` 32건, `중고의료장비증빙` 25건) —
   세목이 더 커지면 청크 간 중복 문장이 늘어날 수 있다. 지금은 정규화 일치만 접으므로
   표현이 다른 중복은 남는다. 실사용에서 눈에 띄면 그때 볼 것.

## 9. 계측이 안 보이던 문제 (세션 후반 발견·수정)

깔때기를 붙여놓고 보니 **정작 기본 실행 경로에서는 볼 수 없었다.** `job` 은 "실행을 건
탭이 폴링하는 동안"에만 화면에 있었는데, 기본 액션은 새벽 3시 예약이라 그 탭이 없다.
`GET /admin/kb2/restructure/latest`(마지막으로 끝난 done/error job)를 신설하고 화면
진입 시 복원하도록 했다. 라우트는 `/{jobId}` 보다 위 — `scheduled` 와 같은 이유.

**브라우저 검증(Playwright, 실제 조작)**: admin 로그인 → `/admin/kb2` 진입 →
**재구조화를 걸지 않은 상태에서** 깔때기가 뜨는 것 확인.

```
FUNNEL: 커버리지 37% — 원본 413건 중 154건이 KB2 문장의 근거로 반영됨
  원본 활성 passage 413건 / 세목에 배정 236건(57%) / 미분류로 유실 177건(43%)
  합성 프롬프트 투입 236건(57%) / 예산에 밀려 미투입 0건(0%) / 문장 근거로 인용 154건(37%)
  세목별 상세 표 30행, 콘솔 에러 없음
```

메모: 프로덕션 백엔드의 CORS 는 `localhost:3000` 만 허용한다(3001·3111 은 400
"Disallowed CORS origin"). 로컬에서 프로덕션 백엔드를 보며 검증할 땐 **반드시 3000**.
`next dev --webpack` 은 이전 세션 메모대로 유지(Turbopack 은 이 환경에서 크래시).

이 함정이 고약한 이유: 프론트가 fetch 실패를 조용히 삼키는 자리(계측 복원의
`.catch(() => {})`)라 **에러도 없이 화면만 비어 보인다** — 컴포넌트 버그로 오진하기 쉽다.
실제로 이번에 3111 로 띄웠다가 그 경로를 한 번 밟았다. 메모리
`project_deploy_git_workflow` 에 추가해뒀다.

1. `rag.passages(active)` 에서 `random.seed(11); random.sample(rows, 100)` — 시드를 고정해야
   조건 간 비교가 성립한다(이번 세션 수치는 전부 이 표본이다).
