## 무엇이 바뀌었나
세무사는 이제 **자기와 관계있는 대화만** 원문으로 읽는다. 전에는 계정만 세무사면 전체 대화 218건이 payload 째 읽혔다(9/21 실측).
열리는 조건은 넷이다. ① 내가 픽업한 검수 건 ② 열린 일감에 실린 대화(큐에서 픽업 전 미리보기) ③ 나와 채팅방이 있는 대화
④ 내 앞으로 온 상담 신청(거절·취소 포함). admin 은 전체, 사장님은 본인 것 — 둘 다 그대로.
연결 요청(경로 B)만으로는 열리지 않고, 사장님이 승인해 방이 생기면 ③으로 열린다.

운영 실측(세무사 토큰으로 PostgREST 직접): **218 → 206건**. admin 218, 사장님 57/53, 비로그인 0 그대로.

## 결정 (사용자, 착수 전)
- 조건 ② **유지** — 큐의 픽업 전 미리보기가 필요하다. 열린 일감이 많으면 넓은 열람이 되는 한계는 알고 둔다.
- 조건 ④ **상태 무관** — 세무사가 자기 신청 이력의 대화를 다시 볼 수 있게.
- `/audit/chat-logs` **그대로** — 확인해 보니 목록은 DB 가 아니라 번들된 정적 데모 3건이라 축소와 무관했다.

## 설계를 따르며 잡은 것
1. **판정은 함수 하나로**(지시서의 최대 함정). 정책은 `using (can_staff_read_conversation(id))` 뿐이고, 함수는 security definer·비로그인 실행 허용·
   로그인 전 false. 비로그인 페이지의 Realtime 구독자가 정책을 평가하다 권한 오류를 내면 그 이벤트가 사장님에게서도 사라진다((b)에서 겪음) —
   교체 뒤 **비로그인 브라우저·비로그인 채널을 띄운 채로** 서버에서 대화를 넣고 사장님 사이드바에 새로고침 없이 뜨는 것을 E2E 로 확인했다.
2. **조건 ②에 역할 검사가 필요했다.** "열린 일감에 실린 대화"를 그대로 쓰면 사장님도 일감에 실린 **남의** 대화를 읽는다 → 함수 안에서 세무사가 아니면 false.
3. **"보이게 됨"엔 Realtime 이벤트가 없다** — 이번 단계에서 가장 컸던 발견. 설계는 "목록에 있는데 대화가 없다(빈 제목)"를 걱정했지만,
   실제 데이터에선 숨는 12건을 참조하는 행이 하나도 없어서 그대로는 아무것도 안 깨진다. 깨지는 건 **운영 흐름**이다:
   새 대화는 세무사에게 안 보인 채 생기고, 뒤에 일감·신청·방이 생겨 보이게 돼도 대화 행 자체는 안 바뀌니 이벤트가 안 온다.
   페이지를 연 채 있으면 큐 상세 미리보기 "—", 픽업하면 워크스페이스 "대화 데이터를 찾을 수 없습니다", 신청·방 목록엔 사장님 이름 대신 `viewer`.
   → `conversation-store` 에 `useEnsureConversations(ids)`(스토어에 없는 id 를 한 번에 DB 에서, 같은 id 는 10초에 한 번) 를 두고 8화면에서 부른다.
   이 수정은 0040 전에도 무해하므로 **프론트를 먼저 배포하고** 마이그레이션을 적용했다.
4. **효과가 생각보다 작은 이유**: 마감이 7월에 지났는데 `full` 로 남은 100건짜리 일감 2개가 조건 ②로 대부분을 연다. ②를 빼도 이미 픽업한 검수 건(①)만으로
   170~194건. 이번 축소가 실제로 막는 건 **앞으로 생길 새 대화**다. 오래된 일감을 닫는 절차가 생기면 효과가 커진다(남은 일).
