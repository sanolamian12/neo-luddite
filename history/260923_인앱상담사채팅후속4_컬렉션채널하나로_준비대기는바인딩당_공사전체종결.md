## 1. 이번 단계에서 한 일

컬렉션마다 Realtime 채널을 따로 쓰던 것을 **채널 하나(`rt:hub#<epoch>`)** 로 모았다. 바인딩 15개를 한 채널에 건다.
**채널 13 → 1, `"Subscribed to PostgreSQL"` 준비 신호 1회**(로컬·운영 둘 다 확인).

착수 전 사용자 결정 4가지:

| 물음 | 답 |
|---|---|
| 묶는 범위 | **15개 전부 한 채널** |
| 실패 처리 | **채널 단위 지수 백오프 재구독(0.4 → 3.2초 상한) + 다시 붙으면 전 컬렉션 재적재** |
| 목표값 | **admin 로그인 직후 첫 화면 2.5초 이하** |
| 설계 마스터 | **README 약속대로 `history/` 로 접는다** |

구현에서 지킨 규칙(다시 건드릴 때 깨면 안 되는 것):

- **교체는 새 채널이 준비된 뒤 옛 채널을 버린다.** 먼저 버리면 그 틈의 변경이 **전 컬렉션에서** 유실된다.
  겹치는 동안 같은 이벤트가 두 번 와도 upsert 는 멱등이라 무해하다.
- 뒤늦게 합류한 컬렉션만 깨우려고 `hubReadyTables` 로 이미 준비를 본 테이블을 기억한다(`scope: "new" | "all"`).
- **인증 이벤트로 채널을 갈아끼우는 일은 허브가 한 번만** 한다(전엔 컬렉션마다 따로 했다).
  같은 사용자 SIGNED_IN 재구독 금지는 그대로 + **첫 합류가 예약만 된 상태(`hubJoinedAs === null`)도 건너뛴다** —
  이 가드가 없으면 세션 복원이 쏘는 SIGNED_IN 이 첫 합류와 겹쳐 **채널이 2개**가 된다(실측으로 잡았다).
- 준비가 5초 타임아웃보다 늦으면 먼저 적재하고 **준비가 온 순간 한 번 더 적재**하는 규칙은 허브가 대신 지킨다.

## 2. 이번에 뒤집힌 전제 — 준비 대기는 **채널당이 아니라 바인딩당**

설계 §7 은 "Realtime 서버가 준비 신호를 **채널당 ~250ms 씩 직렬로** 보낸다"고 적혀 있었다. **틀린 읽기였다.**
(c) 때는 컬렉션=채널이라 "채널 수"와 "바인딩 수"가 구별되지 않았을 뿐이다.

바인딩/채널 수를 바꿔 가며 직접 쟀다(바인딩 15개 고정, 2회):

| 붙이는 모양 | 첫 준비 | 마지막 준비 |
|---|---|---|
| 바인딩 1 · 채널 1 | 1.0~1.3초 | 1.0~1.3초 |
| 바인딩 5 · 채널 1 | 1.1~1.5초 | 1.1~1.5초 |
| **바인딩 15 · 채널 1** (후속4) | 1.9~2.3초 | **1.9~2.3초** |
| **바인딩 15 · 채널 15** (후속4 이전) | 0.8~1.2초 | **2.4~2.8초** |
| 바인딩 15 · 채널 3 | 1.4~1.5초 | 1.9~2.0초 |

→ 서버는 준비 신호를 **채널마다 한 번** 보내되, 그 채널의 `postgres_changes` **바인딩을 하나씩 설정한 뒤**에 보낸다.
늦어지는 값은 **바인딩당 ~60~90ms**, 거기에 **연결 바닥값 ~1.0초**.
**채널을 묶어도 바인딩 수는 그대로라 그 시간은 사라지지 않는다.**

## 3. 그래서 목표는 못 채웠다 (사용자 판단: 그대로 배포·종결)

`timing.mjs` 전·후(3회 중앙값, 로그인 직후 첫 화면):

| | 전 | 후 | |
|---|---|---|---|
| admin | 4,827ms | **4,392ms** | 목표 2,500ms **미달** |
| 세무사 | 4,325ms | **3,838ms** | |
| 사장님 | 1,135ms | 1,370ms | 잡음 범위 |

묶어서 얻은 것은 **"마지막 준비 2.5 → 2.0초"** 뿐이다. admin 4.4초의 나머지는 채널 일이 아니다 —
네트워크 워터폴로 보면 **auth POST ~1.0초**(로그인 요청 자체) + **`conversations` fetch 0.9~2.0초**(`select=*` 로 payload 통째, **1.3~1.7MB**).

**첫 화면을 더 줄이려면 갈 곳은 둘이고, 둘 다 이번 범위 밖이다:**
1. **바인딩 수 줄이기** — 역할이 안 쓰는 테이블은 구독하지 않기. §7 의 "가시성이 다른 테이블로 바뀌면 이벤트가 안 온다" 함정이 걸린다.
2. **fetch 크기 줄이기** — `conversations` 를 목록용 컬럼만 select 하고 본문은 필요할 때. 스토어가 `select=*` 전제로 짜여 있다.

## 4. 함께 고친 진짜 버그 — `/admin/inspection/<id>`

이 화면이 **"Audit 을 찾을 수 없습니다"로 굳었다.** 원인은 채널 묶기가 아니라 **그 화면의 누락된 게이트**다:
`workHydrated / auditHydrated / reviewHydrated` 만 기다리고 **대화 스토어를 안 기다렸고**, `getConversation` 은
비구독 조회라 대화가 늦게 도착해도 **다시 그리지 않는다.** 전에는 `conversations` 가 자기 채널로 제일 먼저 준비돼
경합에서 이겼을 뿐이다. 채널을 묶어 15개 fetch 가 동시에 출발하자 제일 큰 `conversations` 가 꼴찌로 도착하면서
**경합이 항상 지는 쪽으로 뒤집혔다.**

세무사 워크스페이스(`audit-workspace.tsx`)가 (d)에서 고친 것과 같은 자리라 **같은 방식으로** 고쳤다 —
`useConversationHydrated()` 를 게이트에 더하고 `useConversationStore((s) => s.records)` 를 구독해 반응형으로.

> **2·3단계에 "간헐 잡음"으로 적어 둔 `/admin/inspection/<id>` 412 "찾을 수 없습니다"가 바로 이것이었다.**
> 잡음이 아니라 같은 경합이었고, 이번에 재현이 100%가 되면서 드러났다.
> **교훈: `getConversation`(비구독 조회)을 쓰는 화면은 반드시 `useConversationHydrated` + `records` 구독을 같이 둔다.**

## 5. 부작용(고장 아님) — 몰림

15개 fetch 가 한 준비 신호에 **동시에 출발**한다. 전에는 채널마다 준비가 달라 자연히 흩어졌다.
그래서 제일 큰 `conversations` 가 꼴찌로 도착하고, **대화 제목에 기대는 화면은 완성이 늦다** —

## 8. 다음에 이 근처를 건드릴 사람이 알아야 할 함정

Realtime(설계 §7 에서 넘어온 것, 이번에 하나 교정):

1. **`SUBSCRIBED` ≠ 변경 수신 시작.** 채널의 `SUBSCRIBED` 는 join 응답일 뿐이고, 서버가 `"Subscribed to PostgreSQL"` 을
   보내야 변경이 흐른다. 그 사이에 적재하면 적재 뒤·준비 전 변경이 **영구 유실**된다.
2. **준비 대기는 바인딩당 ~60~90ms + 연결 바닥값 ~1.0초**(§2 — 채널당이 아니다).
3. **anon 구독자의 정책 평가 오류가 이벤트를 모두에게서 지운다.** 비로그인 페이지도 모든 테이블을 anon 으로 구독한다.
   정책에 쓰는 함수는 **anon 실행 허용 + null 이면 false**.
4. **가시성이 다른 테이블 때문에 바뀌면 이벤트가 안 온다.** 행이 안 바뀌므로 구독자는 아무것도 못 받는다 →
   목록이 참조하는 id 는 화면이 직접 당긴다(`useEnsureConversations`).
5. (이번에 더함) **`getConversation` 같은 비구독 조회를 쓰는 화면은 `useConversationHydrated` + `records` 구독을 같이 둔다**(§4).

작업 환경(설계 §9 에서 넘어온 것):

- Bash 인라인 python/node 에 `\n`·`\b` 금지 — 정규식이 든 수정은 Write 로 스크립트 파일을 쓴 뒤 실행.
- Git Bash 에서 node 인자로 `/audit/...` 처럼 `/` 로 시작하는 값을 넘기면 경로로 바뀐다 → `MSYS_NO_PATHCONV=1`.
- 로컬 E2E: `NEXT_PUBLIC_API_BASE=http://localhost:8788 NEXT_PUBLIC_CHAT_MODE=remote npx next build && npx next start -p 3012`,
  백엔드는 `CORS_ORIGINS=http://localhost:3012 ... uvicorn api.main:app --port 8788`. 재빌드 전 3012 를 쥔 옛 `next start` 를 죽인다.
- 기준(전) 측정은 `git stash push -u -- <파일>` → 빌드·측정 → `git stash pop`(worktree 보다 간단하다).
- `regress.mjs` 의 `ONLY=` 는 경로가 아니라 **역할** 필터(`auditor`·`admin`·`owner`). `OWNER_ROOM` 에는 **방 id**.
- 감사 화면엔 `<main>` 이 둘이라 `locator("main")` 은 strict 오류 — `body` 를 쓴다.
- 로그인: 사장님 `owner`(domain_id `viewer`), 세무사 `auditor`·`auditor2`·`auditor3`, `admin`, 전부 `demo1234`.
