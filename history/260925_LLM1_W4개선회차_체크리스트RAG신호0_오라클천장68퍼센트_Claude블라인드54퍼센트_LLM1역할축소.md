## 결론 (판단 기준대로, 한 줄)
**72% 를 넘은 회차 없음 → LLM1 역할 축소: 충분 판정은 D4 상한에 맡기고 LLM1 은 추출·되묻기 생성만.**
단 원인은 solar 만이 아니다 — Claude 도 열린 과제에서 54%(반대 방향으로 틀림: 중간 질문의 78% 를 "충분"). 원본 vs 충분은
Claude 가 83% 로 가른다 = "대충 다 말했나"는 알 수 있지만 **"그 판례가 갈린 1~3개 사실"은 질문만 보고 알 수 없다.**
우리 라벨의 "충분"이 판례 의존적이라 **어느 모델이든 열린 과제로는 못 푼다** → 모델 교체로도 안 풀리는 문제였다.

## 왜 체크리스트 RAG 가 안 됐나
- 이웃 케이스 항목의 missing 비율이 정답 충분 45% · 불충분 45% 로 같다 — **판정에 쓸 신호가 없다**.
  항목의 53% not_relevant, stated 2%, top-k 같은 세목 67%. 결정적 사실이 판례마다 달라 이웃 목록이 안 맞는다. k 조정(1·5)은
  이 구조를 못 바꿔 돌리지 않았다.
- 정답 목록을 줘도(오라클) 68.6% — **닫힌 대조조차 solar 의 천장이 길이 규칙 밑.** v1 실패의 대부분은 **부정형 답을 누락으로 본 것**
  ("전입신고 한 번도 안 했어요" → missing; 정답 충분의 부정형 사실 55%, 긍정형 41%). v2 한 줄로 항목 단위 기재→stated
  50.7 → 73.2% 로 올랐지만, 중간 질문에서 없는 사실도 stated 로 보기 시작해 진짜 지표는 거의 그대로.

## 블라인드 설계 (재현용)
입력 `{id, user_question_raw}` 만, **불투명 id**(`q0001`…, 원 id 의 `_suf`/`_part` 접미사가 라벨을 누출하므로), **같은 케이스의
3형제는 서로 다른 서브에이전트로**(4개로 분할, 시드 20260925), 셔플. 대응표 `blind/key.json`. 서브에이전트에게 repo 접근·웹 검색
금지. 판정이 스크립트 휴리스틱이 아니라 항목별 수기 판정인지 산출 스크립트를 열어 확인했다(항목별 누락 사실 사전).

## 제품에 넘길 것 (구현은 제품 세션)
- **max3 조치**(결론 가르는 것만·`maxItems 3`·`max_tokens` 상한): 퇴화 잘림 37 → 0, 나열 중앙값 5 → 3, p50 1.0초. 판정 정확도엔 무효.
- 2턴부터는 LLM1 이 **자기가 물은 사실**을 안다 = 오라클과 같은 닫힌 대조. v2 프롬프트 항목 정확도(기재→stated 73%, 미기재→missing 91%)가
  `filled`/`unknown` 추출의 기대치. 틀려도 D4 상한이 멈춘다.
- 대가: **정보를 다 준 사용자도 1턴은 질문을 받는다** — 경험 저하지 고장이 아니다.
