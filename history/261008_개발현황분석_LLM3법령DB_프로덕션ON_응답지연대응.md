## 4. 진단 — 법령이 틀리는 실체 (10/7, 세무사 판정 아님)

KB3 단독 회차 시민 48문항: 법령 인용 58개 중 **54개가 근거 카드에 있던 조문**. 그런데 법령을 인용한 26턴 중 10턴 안팎이 무관하거나
설명이 틀림(C48 연기 → 국기법 §48 가산세 감면, C27 상증법 §45 를 '과세표준'으로, C43 조특법 §32 를 '세액감면 승계'로, C26·C30).
→ 지어낸 조문이 아니라 **남의 사건 카드(당시 법 기준)의 조문을 질문 적합성 확인 없이 옮긴 것**. 카드 기준 화이트리스트로는 못 잡는다.

## 7. 응답 지연 (10/8, `679a4a3`)

단계별 계측(12문항): 보통 턴 25초 = **DB 벡터 검색 2회가 절반**(laws 8.6초·kb3 6.4~7초 — 4096차원은 pgvector ANN 상한 2000 밖이라 전수 비교,
DB 왕복 자체는 0.3초) + 작문 3~9초 + LLM3 선택 2~3초 + 게이트·추출 각 1.5초. 꼬리 = **작문 반복 루프**(같은 요청 6회 중 1회 6,000토큰·44.8초,
`finish=length`) — 헤지로 다시 보내도 같은 확률이라 헤지만으로는 못 막았다(3/12 가 두 요청 모두 45초 → 폴백).

| 대응 | 효과 |
|---|---|
| `api/rag/vec_memory.py` 서버 메모리 벡터(kb3 정적 코퍼스·laws, 기동 후 백그라운드: 서버 15.8초·22.7초, +650MB). 세무사 사례만 DB | 검색 7~9초 → 0.6~1.5초 |
| `embed_query` 캐시 · LLM3 ‖ 쟁점 게이트 병렬 | 임베딩 2회 → 1회, 1~2초 |
| 작문 `max_tokens` 1,800 + 잘린 도구 JSON 에서 온전한 문장 복구(`parse_segments`) · 무응답 헤지 20초 · 챗 경로 상한 120 → 45초 | 폴백 3/12 → 0/12 |
| numpy 추가(서버 py3.10 → `numpy==2.2.6`, 2.3+ 는 3.11 이상) | — |

로컬 12문항 중앙 25 → 14.9초 · 최대 150 → 27.7초. 프로덕션 C48·C42·C27 = 10.3·7.8·11.7초.

## 8. 함정

1. **법령·KB3 를 다시 적재하면 서버 재시작해야 메모리 인덱스가 바뀐다**(deploy.sh 가 재시작). 재시작 직후 약 40초는 DB 검색(느리지만 정상). 재시작은 `/health` upstageGate active·waiting 0 일 때.
2. **팀장 PR #5(`feat/supabase-social-auth`) 의 마이그레이션도 `0046_social_registration.sql`** — 오늘 운영에 적용한 `0046_laws_articles` 와 번호 충돌. 0047 로 바꿔 들여올 것.
3. Solar 는 프롬프트 제약(개인/법인 법 구분·길이·반복)을 안 따른다 — 처음부터 코드로 강제.
4. Solar 작문은 가끔 반복 루프로 출력 상한까지 간다 — `max_tokens` 없이 부르면 45초+ 후 폴백. 새 작문 호출에도 `hedged_create` + `max_tokens` + `parse_segments`.
5. 지연은 추측 말고 계측부터 — 병목은 Solar 가 아니라 DB 전수 비교였다.
6. heredoc 안 파이썬 문자열의 `\n`·`\d` 이스케이프가 깨져 파일이 망가진 일이 두 번 — 여러 줄 코드 수정은 Edit 도구로.
7. PDF 원문은 글자 단위 줄바꿈이라 줄 끝 띄어쓰기가 사라진다(`납세자가제82조`) — 좌표로도 못 가른다.
8. 하네스 결과 파일을 이름순으로 고르면 자정 넘긴 `llm3_00…` 이 앞에 온다 — 수정 시각 기준으로.
