## 1. 분류 단계 배치화

**문제**: `kb2_taxonomy.run_dynamic_restructure` 의 분류 단계가 활성 passage 를 하나씩
`llm.classify_tax_category` 로 호출했다. 프로덕션 실측 **413건**.

**측정부터 했다**(추정으로 고치지 않기 위해):

| 방식 | 건당 | 413건 환산 |
|---|---|---|
| 건별(기존) | 0.82s | ≈ 5.6분 |
| 배치 20건 | 0.41s | ≈ 2.8분 |
| 배치 60건 | 0.34s | ≈ 2.3분 |

로드맵에 적혀 있던 "20개 카테고리 기준 실측 35분"은 이번 측정과 맞지 않는다 — 그 수치는
분류 단계만이 아니라 파이프라인 전체(맵/리듀스/합성/임베딩 포함)였던 것으로 보인다.
**분류 단계만 따지면 원래 5~6분대**이고 배치화로 2~3분대가 된다.

**배치화보다 중요했던 발견**: 배치 크기 40 실험에서 한 배치가 **1250초**를 먹었다.
20건은 8.2초, 60건은 20.1초로 도는 와중의 단발 폭주 — OpenAI SDK 기본값(타임아웃 600초 ×
재시도 2회)에 정확히 들어맞는 시간이다(600 + 600 + 50). 배치화의 목적이 절대 시간 단축인데
한 배치 폭주로 20분을 잃으면 본말전도라, 이 호출에만 **90초 상한 + 재시도 1회**를 걸고
실패분은 건별 폴백으로 넘긴다.

**구현**: `llm.classify_passages_batch(passages, categories) -> {id: category}`.
- 도구 스키마의 `id` 를 이번 배치 id 들의 enum 으로 주고, 그래도 **없는 id 를 지어내면
  걸러낸다** — 4.5단계에서 겪은 `sourcePassageIds` 환각과 같은 종류의 방어.
- 반환에서 빠진 id 는 호출측이 건별로 보충(`kb2_taxonomy._classify_all`). 배치가 통째로
  실패하면 빈 dict 라 같은 경로로 자동 폴백된다 — **정확도는 건별과 같고 시간만 준다**.
- 배치 크기 20 채택(60이 근소하게 빠르지만, 폭주·폴백 비용이 배치 크기에 비례하므로).

부수 수정: job 진행률의 단위가 단계마다 다른데(분류=배치, 합성=카테고리) 프론트가 둘 다
"카테고리"로 찍고 있었다 → 단계별 단위 표기로 교정.

## 2. 트리거를 "즉시 실행" → "야간 배치 예약"

사용자 지적: **"세무사가 버튼 한 번으로 큰 작업에 들어가면 안 된다."**

**pg_cron 을 쓰지 않은 이유**(로드맵이 선례로 지목했지만 안 맞았다): 0006 하차장 스냅샷은
순수 SQL 함수라 DB 안에서 완결된다. 재구조화는 **Upstage API 호출(Python)이 본체**라 DB 가
스스로 못 한다 — pg_cron 이 할 수 있는 건 pg_net 으로 백엔드를 깨우는 것뿐이고, 그건 폴러
하나보다 부품이 는다.

**채택**: DB 에 예약을 남기고(`kb2.synthesis_jobs.status='scheduled'` + `scheduled_at`)
백엔드 안의 폴러(`backend/api/rag/kb2_scheduler.py`, FastAPI lifespan 에서 기동)가 1분마다
만기분을 집는다. 예약의 진실이 DB 라 **백엔드가 재시작·크래시해도 예약은 남고**, 지난
예약은 다음 기동 때 곧바로 집힌다(만기 조건이 `scheduled_at <= now`).

claim 은 단일 `UPDATE … WHERE status='scheduled'`(+`FOR UPDATE SKIP LOCKED`)라 폴러가
겹쳐 돌거나 훗날 워커가 늘어도 같은 job 을 두 번 실행하지 않는다. 현재 배포는
`uvicorn --workers 1`.

**시각 계산은 브라우저(KST)에서** — 서버가 Oracle **도쿄** 박스라 서버 로컬 시간으로
"새벽 3시"를 해석하면 의도와 어긋난다. 프론트가 다음 03:00 의 epoch ms 를 계산해 보낸다.

**UI**: 기본 액션이 `[오늘 밤 2026-09-11 03:00 실행 예약]`, 즉시 실행은 확정 버튼
확인형(세목→대목 이동에서 쓴 것과 같은 패턴). 예약 중이면 "실행 예약됨 + [예약 취소]"가
뜨고, 예약이 DB 에 있으므로 브라우저를 닫았다 열어도 복원된다.

엔드포인트: `POST /admin/kb2/restructure`(body 에 `scheduleAt` 있으면 예약, 없으면 기존대로
즉시), `GET /admin/kb2/restructure/scheduled`, `POST /admin/kb2/restructure/{id}/cancel`.
라우트 순서 주의 — `/scheduled` 가 `/{jobId}` 보다 위에 있어야 job id 로 안 잡힌다.

## 4. 세목 연결 끊기/재연결 + 대목 삭제

로드맵엔 "대목/세목 삭제 UI"로 적혀 있었으나, 두 계층의 성격이 달라 **다른 수단**을 줬다
(사용자 확인 후 결정):

| 계층 | 성격 | 수단 |
|---|---|---|
| 세목 `kb2.documents` | 지식(문장·이력·기여)이 든 그릇 | **연결 끊기/재연결** (삭제 아님) |
| 대목 `kb2.groups` | 지식 없는 순수 정리 계층 | **삭제** (속한 세목은 미분류로 풀림) |

**세목 상태값을 `'archived'` 가 아니라 새 값 `'retired'` 로 둔 이유**: `'archived'` 는 이미
"재구조화로 세대교체됨"이라는 뜻으로 쓰이고 있다(0020). 사람이 의도적으로 끊은 것과
재구조화가 갈아엎은 것이 같은 값이면 화면에서도 이력에서도 구분이 안 된다.

- 사유 필수 → `kb2.document_events`(문서 수준 이력 테이블 신설). 문서 row 에 사유 컬럼을
  붙이면 마지막 사유만 남아 "왜 끊었다 다시 연결했나"를 못 따라가서 별도 테이블로.
- 목록 쿼리는 최신 이벤트 1건만 `left join lateral` 로 얹어 배지에 사유를 바로 띄운다.
- `kb2.match_sentences` 는 이미 `d.status='active'` 만 보므로 retired 세목의 문장은 검색에서
  자동으로 빠진다 — **SQL 함수 변경 불필요**(0022와 같은 이유).
- auditor 목록 API 는 `['active','retired']` 를 함께 내려준다 — 끊긴 세목이 화면에서
  사라지면 재연결할 방법이 없다. 트리에서 옅게 + 끊긴 링크 아이콘.
- 대목 삭제는 되돌리기 어려워(세목이 전부 미분류로 흩어진다) 확인 다이얼로그를 거치고,
  "안에 있는 세목과 문장은 하나도 지워지지 않는다"를 명시한다.

## 5. 문서 동시 수정 편집 락 — 결론: 불필요. 대신 진짜 구멍을 닫았다

이름/그룹/상태 변경은 전부 **단일 UPDATE** 라, 문장 편집처럼 "읽고→몇 분 고치고→저장"하는
구간이 없다. 마지막 쓰기가 이기더라도 잃는 건 방금 타이핑한 이름 한 줄이고 새로고침하면
바로 보인다. 문장 락은 몇 분치 작업 + 버전/기여 결과가 걸려 있어서 필요한 것이지, 여기엔
그 성질이 없다.

**대신 락으로는 못 막는 구멍이 하나 나왔다**: A가 대목을 삭제하는 사이 B가 그 대목으로
세목을 옮기면(삭제는 삭제 **시점**의 소속 세목만 풀어준다) 그 세목이 존재하지 않는 대목을
가리킨다. 트리는 활성 대목만 그리므로 그 세목이 **화면에서 통째로 사라진다**.
→ 살아있지 않은 `group_id` 는 "미분류"로 간주해 트리를 전사(全射)로 만들었다. 세목이
안 보이는 것보다 미분류로 보이는 편이 언제나 낫고, 그러면 사용자가 다시 옮기면 된다.

레이스 상태를 인위적으로 재현(대목을 먼저 삭제한 뒤 raw SQL 로 그 대목에 세목을 배정)해
브라우저에서 **세목이 사라지지 않고 미분류 아래에 붙는 것**까지 확인.
