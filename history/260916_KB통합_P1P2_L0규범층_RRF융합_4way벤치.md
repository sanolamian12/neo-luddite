  판정은 어떤 경우에도 규칙엔진의 권위다]` + 규범. None이면 base 그대로 = 도입 전 프롬프트.

다만 세무 규범 문안이므로 **사람(세무사) 검토를 거치지 않은 초안**이다 — 배포 전후 검토 권장.

## 3. P2 — RRF FusionRetriever

### 3.1 구현
- `FusionRetriever(arms=[(name, Retriever)], quotas, rrf_k=60, per_arm_k)`:
  갈래 ThreadPool 병렬 → `Σ 1/(rrf_k+rank)` → 정렬(동률: 갈래 순서, 그다음 순위) → 쿼터 → 백필.
- `get_retriever(source="fusion")` = kb2(0.35 컷) + rag(0.50 컷), 쿼터 `FUSION_QUOTA_KB2/RAG` 기본 3/3.
- `pipeline._rag_source_label()` — FusionRetriever면 "fusion", 그 외 종전 규칙. `schema`/`main` 주석 갱신.
  `rag.chat_turns.rag_source`는 text라 마이그레이션 불필요.
- 프론트는 `ragSource`를 안 쓴다(grep 0) — 프론트 변경 없음.

### 3.2 설계와 달라진 점
1. **코퍼스 구분 = 갈래 이름.** 로드맵은 `Passage.source_kind`로 공짜라 했지만 rag 쪽은
   feedback/case_seed/session_eval로 갈려 코퍼스 식별이 안 된다.
2. **RRF는 겹치지 않는 두 코퍼스에서 교차 배치로 퇴화한다.** 같은 문서가 두 갈래에 동시에 안 나오니
   합산이 일어나지 않고 k0, r0, k1, r1… 순이 된다. RRF 본연의 이득은 같은 코퍼스를 두 방식으로 찾을 때
   (벡터+pg_trgm) — 그 갈래를 넣을 때 다시 평가할 것.
3. **min_score는 노이즈 컷으로 남는다.** 없어진 건 "두 임계값의 상대값이 승자를 정하던" 역할.
4. **백필 추가.** 쿼터를 하드 상한으로 두니 kb2가 빈 질문에서 rag가 3건으로 잘려 rag 단독(5건)보다
   근거가 줄었다(단위 시험에서 발견). 쿼터는 독식 방지일 뿐 → 빈자리는 융합 순서대로 채운다.

### 3.3 4-way 벤치 — **기준선 (P3 이후 재현 불가, 보존)**

프로덕션 값(`RAG_TOP_K=5`, `RAG_MIN_SCORE=0.50`, `KB2_MIN_SCORE` 기본 0.35, 쿼터 3/3). 문항당 임베딩
1회 캐시. 채점: 문항별 모든 갈래 결과 합집합을 셔플·갈래표시 없이 solar-pro3에 1회(temperature 0),

### 3.4 판독
- **판정 통과**: fusion의 useful이 두 회차 모두 최고(75.5/81.8%), precision은 kb2·hybrid와 동률,
  noise 동률. "나빠지면 멈춘다" 조건에 해당 없음 → P3 진행 가능.
- 검색 결과는 두 회차가 동일한데 채점 절대치가 갈래 전반 +4~6pp 이동 — **채점기 분산**. 순위만 믿을 것.
- 이득의 출처는 near 셋: kb2가 못 채운 쟁점에 rag 번들이 들어간다(fusion 문항 중 rag 근거가 섞인 것 51/110).
  far 셋에선 rag가 0.50 컷에 거의 걸러져 fusion ≈ kb2.
- 대응 비교(1회차 useful): fusion vs hybrid 승 4(R36, T07, T15, T18) / 패 2(R32, T06); vs kb2 승 6 / 패 2;
  vs rag 승 47 / 패 0. 패배 2건은 kb2 4~5위의 등급2 문장이 rag 항목(session_eval, 등급0)에 밀린 것 —
  교차 배치의 정해진 비용.
- 쿼터 2/4는 3/3보다 약간 나쁘고(useful 74.5, noise 1.45), 4/2는 k=5 교차 배치에서 3/3과 결과가 같다.
  기본 3/3 유지.
- **kb2의 prec=2가 rag보다 낮다**(53~57% vs 62~67%) — kb2는 넓게 잡고 rag는 0.50 컷으로 좁게 잡는다.
  fusion은 이 성향을 그대로 물려받는다. precision을 올리려면 KB2_MIN_SCORE를 볼 자리지만, 이 세션은
  "나쁘지 않음" 판정이 목적이라 손대지 않았다.
