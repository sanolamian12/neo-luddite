# 정산 — 총수익×비율 pool 계산 + 크레딧/정산금액 단위 분리

날짜: 2026-08-27 · 브랜치: `import-credigraph` · 선행: [260707_정산_존속연동_살아있는RAG기여도_파생.md](260707_정산_존속연동_살아있는RAG기여도_파생.md), [260704_정산_설계_핸드오프.md](260704_정산_설계_핸드오프.md)

## 한 줄 요약
"관리자가 수익을 입력하면 세무사에게 정산·입금확인이 가는 프로세스"를 요청받아 조사했더니, ledger·정산 회차·인앱 메일 인프라는 이미 PoC 수준으로 동작 중이었다(브라우저 E2E로 확인). 다만 **분배 pool이 임의 숫자였을 뿐 실제 수익과 연결되어 있지 않았다** — 이를 **총수익(원) × 분배비율(%) → pool 자동계산**으로 교체했고, 그 과정에서 **크레딧(추상 기여 포인트)과 정산 지급액(실제 원화)이 같은 누적 잔액에 섞이는 버그**를 발견해 함께 고쳤다. 신·구 두 흐름 모두 실 Supabase에 대해 브라우저로 직접 검증(테스트 데이터는 검증 후 삭제).

## 배경 — 조사 결과 (구현 착수 전)
`frontend/services/settlement.ts`(preview/publish/markPaid), `ledger.ts`, `mail.ts`, `supabase/migrations/0001_public_schema.sql`의 `settlement_rounds`/`ledger_entries`/`mail` 테이블, 관리자 정산 화면(`components/admin/settlement-*.tsx`), 세무사 우편함(`mailbox-view.tsx`)까지 이미 구현되어 있었음을 확인. 정산 발행 시 자동으로 세무사별 ledger 기록 + "정산 안내" 메일, 관리자 입금 처리 시 "입금 완료" 메일이 나가는 흐름이 실제로 동작. 다만 **`pool`은 관리자가 그냥 타이핑하는 추상 숫자**(단위 "cr")였고 실제 수익액과 무관했다 — 이번 세션의 출발점.

## 산출물

### 스키마
- **[supabase/migrations/0016_settlement_revenue_ratio.sql](../supabase/migrations/0016_settlement_revenue_ratio.sql)** — `settlement_rounds`에 `revenue`(bigint, 원), `distribution_ratio`(numeric, %) 추가. 라이브 Supabase에 적용 완료(`schema_migrations`에 0016 기록).

### 정산 로직 (`frontend/services/settlement.ts`)
- `SettlementPreviewInput`: `pool` 파라미터 제거 → `revenue`, `distributionRatio`로 교체. `preview()` 내부에서 `pool = floor(revenue * distributionRatio / 100)` 계산 후 종전과 동일하게 세무사별 활성 기여 비율로 분배.
- `publish()`: `settlement_rounds` insert에 `revenue`/`distribution_ratio`/계산된 `pool` 저장. 정산 안내 메일 본문에 "총수익 X원 × 분배비율 Y% = 분배 pool Z원", "입금 예정액: N원" 명시(기존엔 "분배 credit: +N"이었음).
- `markPaid()` 메일 본문도 "입금액: N원"으로 원화 표기.

### 크레딧/정산금액 단위 분리 (`frontend/services/ledger.ts`)
- **버그**: `ledger_entries.balance_after`(누적 크레딧)는 `contribution_accepted`(인정 1건당 +10) 같은 추상 포인트와 `settlement_round`(이제 실제 원화, 수십만 단위)를 구분 없이 그대로 더하고 있었다. pool이 작은 추상 숫자였던 v1까지는 우연히 무해했지만, 원화로 바뀌는 순간 세무사의 "누적 크레딧" 표시가 정산액에 의해 완전히 왜곡되는 구조적 버그였다.
- **수정**: `append()`에서 `kind === 'settlement_round'`이면 `balanceAfter = prev`(불변) — 지급 이력은 `amount`/`kind`로 그대로 남기되 크레딧 잔액 합산에서는 제외.
- 연쇄 수정: `components/auditor/ledger-view.tsx`(월간 합계·엔트리별 단위 표기), `components/auditor/dashboard-view.tsx`(월간 합계), `components/admin/auditor-detail-view.tsx`(엔트리별 단위 표기) — 모두 `settlement_round` 종류는 "원"으로, 그 외는 "cr"로 분기 표시하고 월간/합계 집계에서 `settlement_round`를 제외하도록 정리.

### 화면
- **[settlement-new-form.tsx](../frontend/components/admin/settlement-new-form.tsx)** — "회차 pool" 숫자 입력란 제거 → "이번 회차 총수익(원)" + "세무사 분배 비율(%)" 입력, "분배 pool (계산됨)"은 읽기전용 표시(관리자가 직접 덮어쓸 수 없도록 의도적으로 잠금 — 사용자 확인 후 결정).
- **[settlement-detail-view.tsx](../frontend/components/admin/settlement-detail-view.tsx)** — 표에서 항상 빈 값이던 "포함 audit" 열 제거, "분배" 열은 원화 금액. 헤더에 "총수익 X원 × 분배비율 Y%" 추가.
- **[settlement-table.tsx](../frontend/components/admin/settlement-table.tsx)** — 목록의 pool 표시를 "cr"→"원".
- **[mailbox-view.tsx](../frontend/components/auditor/mailbox-view.tsx)** — "정산 내역" 박스가 입금 전/후에 따라 "입금 대기 금액"/"입금액" 라벨로 원화 표시, 죽은 필드였던 "포함 audit" 문구 제거.
- **[ledger-view.tsx](../frontend/components/auditor/ledger-view.tsx)** — 세무사 자신의 회차별 탭에 "입금 상태"(입금 완료/대기) 열 신설, "포함 audit" 열 제거.

## 설계 결정
- **pool 은 계산 전용, 수정 불가** — 총수익×비율 두 입력값에서만 파생. 개별 세무사 분배액도 자동 계산값만 표시하고 관리자가 개별 덮어쓰기 불가. (합계검증 로직 없이도 항상 pool과 일치하는 분배를 보장하기 위한 선택 — AskUserQuestion으로 확인 후 결정.)
- **크레딧과 정산금액은 같은 테이블(`ledger_entries`)에 공존하되 절대 합산되지 않는다.** `kind`로 구분하고, 화면마다 표시 단위를 분기.
- 실제 은행 연동, 실제 이메일/SMS 발송은 이번에도 범위 밖으로 재확인(7/14, 8/27 두 차례 동일 결론).

## 검증
- **정적**: `npx tsc --noEmit` 0 에러 (스키마·서비스·전 화면 변경 후).
- **라이브 E2E(Playwright, 실 Supabase)**: 관리자 로그인 → 새 회차(총수익 2,000,000원 × 25% → pool 500,000원 계산 확인) → 발행 → 세무사별 228,764/140,926/130,308원 분배 확인 → 회차 상세("포함 audit" 열 없음, "분배" 열 원화 확인) → 입금 처리(0/3→3/3) → 세무사 우편함(정산 안내 + 입금 완료 메일, 원화 표기) → 세무사 자신의 모델 기여 로그(회차별 탭에 "입금 상태" 열, 헤더의 "누적 5,530cr"이 정산액과 섞이지 않음을 실측 확인).
- 첫 시도에서 테스트 스크립트가 `publish()` 완료를 기다리지 않고 강제 네비게이션해 3건 중 1건만 처리된 것처럼 보인 적이 있었음 — DB로 직접 재확인해 **앱 버그가 아니라 테스트 타이밍 문제**였음을 규명(정상 사용에서는 버튼 클릭 후 `router.push`가 로직 완료를 기다리므로 문제 없음).
- 테스트로 생성한 회차·ledger·mail은 매번 직접 SQL로 삭제해 실 데이터에 잔여물 없음.
