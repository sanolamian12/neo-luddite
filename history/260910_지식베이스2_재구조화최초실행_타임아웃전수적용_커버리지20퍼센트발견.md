## 1. 야간 예약 경로 — 최초 실제 발화 ✅

지금까지 claim 함수 단위로만 검증했던 경로를 프로덕션에서 실제로 돌렸다.

| 시점 | 상태 |
|---|---|
| +0s | `scheduled` 생성(2분 뒤 예약) |
| +178s | `running` — **폴러가 예약시각 +60초에 집음**(폴링 주기 60초 내) |

DB에 예약을 두고 백엔드 폴러가 집는 설계가 의도대로 동작했다. **컴퓨터를 꺼도 무관**하다는
점도 확인 — 파이프라인은 Oracle 서버 프로세스 안에서 돌고 로컬 스크립트는 관찰자일 뿐이다.

## 2. 그런데 맵 단계에서 교착 — 21분 무진전

`discovering_categories` 에서 21분간 갱신이 없었다. 서버는 정상 가동 중이었고(재시작 없음)
에러 로그도 없었다 — 즉 죽은 게 아니라 **LLM 호출 하나에 물린 상태**.

원인은 어제 배치화 작업의 빠진 조각이었다. 분류 배치에만 90초 상한을 걸었고 **맵 단계는
SDK 기본값(타임아웃 600초 × 재시도 2회 = 최대 30분)이 그대로** 살아 있었다.

**진단이 21분이나 걸린 이유가 더 중요하다**: 맵 단계는 배치마다 job 을 갱신하지 않아
단계 전체가 무소식이었다. 그래서 화면에서 "정상 진행 중"과 "한 배치가 폭주 중"이
**구분되지 않았다.** 관측 불가능한 구간을 만들어두면 그 구간의 장애는 늦게 발견된다.

## 3. 상한 전수 감사 — 1곳이 아니라 10곳이었다

맵만 고치려다 전수 조사했더니 상한 없는 호출이 **10곳**이었다.

`llm.bounded_client(timeout, retries=1)` 헬퍼를 두고 전부 적용:

| 대상 | 상한 |
|---|---|
| 맵 / 리듀스 / 분류배치 / 대목배정 | 90s (리듀스는 이후 600s 로 상향, §6) |
| 단건 분류(배치 폴백) | 30s |
| 합성 | 240s |
| **임베딩** | 30s |
| 챗 경로: 추출 60 / 판정문 120 / **자문 120** / 검증 60 / 되묻기 90 | |

챗 경로까지 넣은 이유: `embed_query` 와 `write_advisory` 는 **사용자 요청 경로**라 여기서
물리면 사용자가 최대 30분 응답을 못 받는다. 10곳 모두 `try/except` 폴백이 있어 상한 초과가
500 이 아니라 점진적 저하로 흡수되는 것을 확인하고 적용했다 — **상한은 정확도를 깎지 않고
최악 시간만 자른다.**

## 4. stale job 회수 — 배포가 job 을 영구 `running` 으로 만든다

파이프라인은 백엔드 프로세스 안의 백그라운드 작업이라, `deploy.sh`(= `systemctl restart`)나
크래시로 프로세스가 내려가면 **job 이 `running` 인 채로 영원히 남는다.** 아무도 꺼내주지
않으므로 화면은 끝나지 않는 "재구조화 중…"을 보여준다.

두 갈래로 정리:
- **기동 직후 1회**: 그 시점의 `running` 은 정의상 이전 생의 잔해(전제: `--workers 1`)
- **평시**: 일정 시간 갱신 없는 `running` → `error`

실전 검증됨 — 교착된 판을 배포로 끊었더니 로그에
`[kb2_scheduler] 재시작으로 중단 — job 1건 정리: ['2e61b062-…']` 가 찍혔고 job 이
`error` 로 정리됐다. **활성 문서 17개는 손상 없음**(보관 처리는 분류 이후 단계라서).

## 5. 리퍼가 살아있는 job 을 죽이는 버그 — 값을 고르다가 발견

merge 상한을 600초로 올리려고 계산하다 나왔다.

- **예약 경로**: 폴러가 `await asyncio.to_thread(...)` 에서 막혀 있어 리퍼가 못 돎 → 안전
- **즉시 실행 경로**: `background_tasks` 가 별도 스레드로 돌리고 **폴러 루프는 계속 순회** →
  리퍼가 자유롭게 돈다 → 심장박동 간격이 stale 기준을 넘으면 **살아서 일하는 job 을 죽인다**

당시 기준 15분에 대해 위험 구간이 이미 둘 있었다:
- merge 를 600×2 로 올리면 20분 무소식(단일 호출이라 중간에 찍을 곳이 없음)
- **분류 배치 실패 후 건별 폴백 20건** — 배치 단위로만 심장박동을 찍어 최악 20분

조치: `STALE_JOB_MS` 15 → **30분**, 폴백 루프에 건별 심장박동 추가.
값 선정 기준을 주석에 명문화했다 — **"정상 진행 중 가능한 최장 침묵보다 넉넉히"**.
코드로 불변식도 확인: `최악 침묵(20분) < stale 기준(30분)`.

## 6. 재실행 — 완주 822초 (13.7분)

| 단계 | 소요 | 비고 |
|---|---|---|
| 맵 12배치 | 88초 | 이전엔 같은 단계 21분 교착 → 상한이 작동 |
| 리듀스 | 186초 | ⚠️ 90×2 에 걸려 **폴백으로 빠짐** |
| 분류 21배치 | 156초 | **배치화 실효 확인** — 413건 2.6분(건별 추정 5.6분) |
| 합성 20개 | 391초 | |

맵 진행률이 `0/12 → 12/12` 로 제대로 찍혔다. 진단을 21분 늦췄던 사각지대 해소.

결과: 카테고리 20 · 문서 20 · 문장 176 (이전 판 17문서/92문장에서 문장 수는 증가).

## 7. ⚠️ 정정 — merge 타임아웃은 카테고리 품질의 원인이 아니었다

리듀스가 폴백으로 빠진 것을 보고 "그래서 카테고리가 엉망이다, 상한 올리고 재실행하자"고
판단했으나 **틀렸다.** 9/9 판(상한이 없어 merge 가 성공했을 판)의 아카이브를 대조하니
**거의 같은 질문 제목 목록**이었다.

```
9/09판: 리스종료후장비인수회계처리 · 광고대행사수수료개인카드결제인정 · 6세이하자녀범위 …
9/10판: 리스종료후장비인수회계처리 · 광고대행사수수료개인카드결제인정 · 6세이하자녀범위 …
```

merge 를 고쳐도 같은 결과가 나온다. **재실행을 권할 뻔했고 그랬으면 시간만 버렸다.**
대조군을 확인하지 않고 인과를 단정한 것이 실수였다.

## 8. 진짜 문제 — KB2 가 원본의 20% 만 담고 있다

```
원본 rag.passages 413건 중 KB2 에 반영된 passage: 83건 (20%)
```

카테고리가 `'업무용승용차'` 같은 주제가 아니라 **질문 하나짜리 레이블**("사립학교사무직원
육아휴직수당과세")이라 지나치게 좁고, 나머지 80% 는 어느 카테고리에도 안 붙어 사라진다.
문장 분포도 극단적이다 — 상위 3개는 15문장씩인데 "1세대1주택비과세"·"유튜브콘텐츠제작비용"은
2문장뿐.

> 단서: 83건은 **하한**이다. Solar 가 환각한 출처 ID 를 걸러내는 필터(`valid_source_ids`)
> 때문에, 기여했지만 집계 안 된 passage 가 있을 수 있다. 분류 결과(assignment)는 저장하지
> 않아 "몇 건이 미분류였는지"는 직접 측정 불가 — **재실행 없이 알려면 분류 분포를 job
> result 에 남기는 계측이 먼저 필요하다.**

원인은 맵 단계(`llm.propose_categories_batch`) 프롬프트가 주제 대신 질문 요약을 뽑는 것.
KB2 전체가 다시 만들어지는 변경이라 이 세션에서 손대지 않고 다음 세션으로 넘긴다.

## 9. 세션 운영 — 논문 작업과 제품 작업 분리 (사용자 지시)

세션 중반, 3방향 성능 비교(무RAG / 기존RAG / KB2)가 구조적으로 가능한지 점검했고
**가능함을 프로덕션 실호출로 확인**했다(`?rag=` on/off 와 `?ragSource=rag|kb2|hybrid` 두 축이
직교). 이어서 벤치마크 하네스를 제안했으나, 사용자가 **논문 작업과 제품 수정을 한 세션에서
같이 맡기는 것의 위험**을 지적하고 분리를 요청했다.

- 논문·벤치마크·채점은 **별도 세션**에서. 이 세션은 제품 코드 전용.
- 정책을 `docs/doing/HF_사용정책_국내AI트랙.md` **§5** 로 신설(로컬 전용 문서).
  - 트랙 판정 대상은 **제품 구동 경로 안의 추론 호출**. 오프라인 연구는 트랙 밖이지만
    예외는 **좁게**(연구로 명시 스코프 / 대회 제출물 아님 / 런타임 미import, 셋 다 만족).
  - **제품 세션에서는 그 예외를 아예 적용하지 않는다.**
  - 감사 결과: **런타임 `backend/api/` 는 깨끗**(`OpenAI(...)` 인스턴스는 `llm.get_client()`
    하나뿐, `base_url` 이 Upstage 로 고정). 외산 호출 추적 파일은 `backend/bulk_ask_multi.py`
    (ICTC 논문 2×3 교차모델 실험) 1건 — 런타임 미import 지만 제품 레포 안에 있어 심사자
    눈엔 구분이 안 된다. **처리는 논문 세션 사안, 삭제 금지**(논문 실험 원본 기록).
  - §3 에 설계된 **CI 정적 검사는 미구현** — 현재 방어선은 문서와 사람 주의력뿐.

부수 확인: 7월 리포트·ICTC 실험의 Claude 채점은 **대회와 별개인 논문 투고용이라 문제없었다**
(사용자 정정). "LLM-as-judge = 무조건 위반"이 아니라 판단 기준은 구동 경로 여부다.

## 10. 안 한 것 / 다음

- **맵 단계 프롬프트 개선** — §8 의 본체. 다음 세션 주제.
- **분류 분포 계측** — 미분류가 몇 건인지 지금은 측정 불가. 프롬프트를 고치기 전에 이걸
  먼저 넣어야 개선 전/후를 비교할 수 있다.
- 3방향 벤치마크 — 구조는 확인됐고 실행은 논문 세션에서.
- 되묻기 분기의 `ragSource` 기록 — 그 분기는 검색 **전에** 리턴하므로 값이 없는 게 정직한
  상태다. 다만 로그만 보면 "KB2 가 0건"과 "검색 안 함"이 구분 안 되므로
  `not_retrieved` 명시가 필요. 벤치마크 계측용이라 논문 세션과 함께.
- 추출 비결정성: 같은 질문·같은 모드 5회에 `etype` 이 2/5 vs 3/5 로 갈렸다(`temperature=0`
  인데도). 벤치마크 설계에 직접 영향 — 논문 세션에서 다룰 것.
