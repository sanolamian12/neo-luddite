## 0. 한 문단 요약

auditor `/audit/kb2` 화면에서 활성 세목 29개가 **전부 "미분류"** 아래 있었다. 원인은
두 겹이었고, 고치는 과정에서 **세 번째(가장 큰) 결함**이 측정으로 드러났다.
① 재구조화가 새 세대 문서를 `group_id=null` 로 만들고 이전 세대를 archive 해서,
**회차마다 대목 배치가 100% 소실**된다(2026-09-12 에 문장 G2 로 고친 것과 같은 자리인데
대목 층이 빠져 있었다). ② 유일한 복구 수단인 [자동 그룹화] 버튼이 기존 대목을 재사용하지
않아 **누를 때마다 같은 이름의 대목이 늘어난다.** ③ 그걸 고치고 재보니 배정 자체가
나빴는데, 원인은 프롬프트가 아니라 **도구 스키마**였다 — "세목당 정확히 하나"를 부탁만
하고 구조로 강제하지 않아 누락 9·중복 1 이 났다. 재구조화 파이프라인이 이미 쓰는 2단
구조(목차 확정 → enum 배정)로 바꿔 누락·중복·파편화를 **0 으로** 만들었다. 남은 것은
**몰림**이고, 그건 스키마가 아니라 목차(대목 목록)의 문제라 회차마다 흔들린다.

## 1. 원인 — 대목 배치는 승계 대상에서 빠져 있었다

### 1.1 주원인: 세대교체가 배치를 지운다

`run_dynamic_restructure` 는 새 세대 문서를 이렇게 만들었다:

```python
doc_id = kb2_store.create_document(cat_id, cat["label"], title=f"{cat['label']} 정책 사전")
```

`group_id` 인자가 아예 없다 — 항상 null 이다. 그 직전 `archive_all_active_documents()` 가
대목이 붙어 있던 이전 세대를 통째로 내리므로, **재구조화 1회 = 대목 배치 전량 소실**이다.
세무사가 손으로 배치해도 그날 밤 3시 예약 회차가 원상복구시킨다.

2026-09-12 에 만든 G2 축적성(`_reattach_preserved`)은 **문장**만 세대를 건너게 했다.
같은 함수, 같은 archive 직전 자리에서 **세목→대목 배치**도 사라지는데 그건 승계 대상에
안 들어갔다. **"세대를 건너야 하는 것"의 목록이 불완전했던 것**이 이 결함의 정체다.

### 1.2 부차: 복구 수단 자체가 망가져 있었다

`auto_group_ungrouped_documents` 가 제안마다 `create_group(label)` 을 **무조건** 불렀다.
기존 active 대목을 후보로 주지도 않고, 같은 이름을 재사용하지도 않고, `kb2.groups.label` 에
unique 제약도 없다(0021). 즉 **버튼을 누를 때마다 같은 이름의 대목이 하나씩 늘어난다.**
실측 시점에 활성 대목 6개가 그대로 있었으니, 한 번 더 눌렀으면 12개가 됐을 상태였다.

### 1.3 DB 실측 (수정 전)

```
kb2.groups         active 6 / deleted 6(브라우저검증 잔여물)
kb2.documents      active 29 + unsorted 1 + archived 216
  └ group_id 보유  16건 — 전부 archived (9/9 세대)
  └ 현 세대 29건   전부 group_id = NULL  ← 화면의 "미분류"
```

대목 6개는 **9/9 세대 16개 세목** 기준으로 Upstage 가 만든 것이고, 그 문서들은 이후
재구조화 3회를 거치며 전부 archived 됐다. **대목은 남았는데 안이 비었고, 현 세대는 전부
밖에 있었다.** 이 비대칭이 "대목은 6개 보이는데 세목은 전부 미분류" 라는 화면을 만든다.

## 2. 진짜 결함은 도구 스키마였다 (측정)

버그를 고치고 드라이런을 돌렸더니 재사용은 완벽했는데(생성 0 · 재사용 6) **배정이 엉망**
이었다 — 29개 중 23개가 한 대목에 몰리고, 3건 중복, 2건 누락. 그래서 조건을 갈랐다.
같은 29개 세목 · `temperature=0`:

```
① 기존(그룹→세목 배열, 기존 레이블 없음)   배정 20/29 · 누락 9 · 중복 1 · 한 대목에 17개
② 기존 + 기존 레이블 제공                 배정 30/29 · 누락 2 · 중복 3 · 한 대목에 23개
③ 스키마 뒤집기(세목→대목 1:1)            배정 29/29 · 누락 0 · 중복 0 · **대목 17개로 파편화**
④ 2단(대목 확정 → enum 배정)              배정 29/29 · 누락 0 · 중복 0 · 한 대목에 10~14개
```

**읽는 법이 중요하다.**

- ①이 기존 구현이다. **원래부터 9건을 빠뜨리고 있었다** — 이 세션이 그걸 만든 게 아니다.
  (②가 ①보다 배정 수는 많다. 내 변경은 나쁜 것을 덜 나쁘게 만들었을 뿐 결함은 그대로였다.)
- **누락·중복은 프롬프트로 못 고친다.** ①②는 "모든 세목은 정확히 하나의 대목에" 라고
  프롬프트에 써 두고도 매번 어겼다. 도구 스키마가 그룹마다 독립적인 `documentIds` 배열이라
  빠뜨리거나 두 번 내는 것을 **막을 방법이 없었다.** ③처럼 `documentId` 를 enum 으로 갖는
  항목을 세목 수만큼 정확히 받으면 **구조적으로 불가능해진다.**
- 그런데 ③은 대목 수 상한(3~8)을 안 지켜 **17개로 파편화**했다 — 모델이 세목 제목을 그대로
  대목 이름으로 복사했다(`복리후생비 정책 사전` 이 대목 이름이 된 사례까지 나왔다).
  **개수 제약도 프롬프트로는 안 지켜진다.**
- ④는 그래서 이 코드베이스가 **이미 쓰는 패턴**을 그대로 가져온 것이다:
  `merge_categories`(목차 확정) → `classify_dynamic_category`(그 목차 안에서만 고름).
  패스1이 `minItems`/`maxItems` 로 대목 개수를 확정하고, 패스2는 그 목록을 **enum** 으로만
  고른다 — 새 이름 창작이 불가능하다.

> **교훈**: 모델에게 "빠짐없이 / 정확히 하나 / 3~8개"를 **말로 부탁하고 있다면 그건
> 스키마로 옮겨야 할 제약이다.** 이 프로젝트가 배치 분류에서 배운 것("모델이 앞쪽만
> 성실히 읽는다")과 같은 결이고, 처방도 같다 — 출력 형식을 바꿔 실패를 불가능하게 만든다.

## 3. 넣은 것

### A. 대목 승계 (`_inherit_groups`, LLM 0회)

archive 직전에 `{세목 레이블: group_id}` 를 찍고(`list_active_document_groups`), 새 세대
레이블에 **임베딩 최근접**으로 물려준다. 정확히 같은 이름은 임베딩 없이 바로 잇는다
(세대를 넘어 살아남는 레이블이 33~67% 라 이 지름길이 자주 쓰인다).

**임계값은 `REATTACH_MIN_SIMILARITY`(0.70) 를 그대로 쓴다.** 같은 축의 같은 문제(세대 N
레이블 ↔ 세대 N+1 레이블)라 171쌍 실측 근거가 그대로 적용되고, 따로 두면 두 층이 서로
다른 기준으로 "같은 세목"을 판정하게 된다.

드라이런(진짜 함수 + 쓰기만 스텁):

```
② 같은 목차 자신 → 승계 29/29 (정확일치 29)        ← 상한 확인
① 9/9 세대 → 현 목차 → 승계 8/29, 정확일치 1, 임베딩 실패 0
```

①은 **4세대를 건너뛴 최악 조건**이다(매 회차 승계가 걸리면 거리는 1세대). 개별값:

```
O 육아휴직수당과세   ← 사학연금육아휴직수당과세   0.8213
O 직원워크숍비용     ← 직원워크숍비용인정        0.8055
O 수도권공공기관이전  ← 수도권공공기관이전근무상형편 0.7781
O 적격증빙          ← 현금결제적격증빙미제출     0.7367
O 현금매출증빙       ← 현금결제적격증빙미제출     0.7232
O 개인카드비용       ← 사업용개인카드구분가족카드사용 0.7201
O 4대보험·임금      ← 가족직원급여지급4대보험    0.7107
──────────────────────────────────────── 0.70
. 카드비용구분       ← 사업용개인카드구분가족카드사용 0.6777   ← 정탐인데 탈락
. 업무용승용차특례    ← 개인차량업무용비용인정     0.6597   ← 정탐인데 탈락
```

**0.70 은 여기서도 놓치는 쪽으로 기운다.** 그대로 둔다 — 놓친 것은 뒤이어 도는 자동
그룹화가 받으므로, 승계 실패의 대가는 '미분류로 남는 것'이 아니라 **'사람 판단이 아닌
모델 판단으로 배치되는 것'**이다. 임계값을 1회 측정으로 건드리지 말라는 기존 결정 유지.

⚠️ **승계는 이전 세대의 오배정도 충실히 물려받는다.** 드라이런에서 `4대보험·임금` 이
`사업용 카드·비용 구분` 으로 갔는데, 9/9 auto_group 이 거기 잘못 넣어둔 것을 그대로
받은 것이다. **이건 의도된 동작이다** — 세무사가 고치면 그 고침이 이후 세대로 이어진다.

### B. 자동 그룹화 — 재사용 + 2단 스키마

- `llm.propose_document_groups(documents, existing_labels)` 를 2패스로. 반환 형식은
  예전 그대로 유지(호출측을 안 건드린다).
- `kb2_store.get_or_create_group(label)` — `norm_label`(공백·가운뎃점·대소문자 무시)로
  기존 활성 대목 재사용. `deleted` 대목은 **일부러 되살리지 않는다**(사람이 지운 판단을
  이름이 같다는 이유로 뒤집지 않는다).
- **0028** — 활성 대목 이름에 정규화 unique 인덱스. 코드 밖 경로([대목 추가] 버튼, 동시
  요청)를 막는 자리다. 이름이 겹치는 `deleted` 대목이 실재하므로 `where status='active'`
  부분 인덱스다. `POST /api/kb2/groups` 도 `get_or_create_group` 으로 바꿔 500 대신
  기존 대목을 돌려준다.
- 재구조화 파이프라인 끝(재부착 뒤)에서 **승계 잔여분만** 자동 호출. 실패해도 회차는
  안 죽인다 — 문장은 이미 다 적재됐고 대목은 지식이 없는 정리 계층이다.
- `norm_label` 을 `kb2_store` 로 올려 **대목 재사용과 세목 접기가 같은 규칙**을 쓰게 했다.

### C. 화면

- 성공 판정을 `groupsCreated` → `documentsGrouped` 로. **기존 대목을 재사용한 정상 회차가
  "실패했습니다"를 띄우고 있었다**(생성 0 이면 실패로 읽던 코드). 오히려 재사용이 바람직한
  결과다.
- `documentsUngrouped`(모델이 빠뜨린 세목 수)를 API·화면까지 올린다 — 조용히 넘기지 않는다.
- job result 에 `groupInheritance` · `documentGrouping`(`largestGroup` 포함) 계측.
  **두 숫자는 나란히 읽어야 한다** — 승계 0 인데 배정이 많으면 그 배치는 사람 판단이 아니다.

## 4. 프로덕션 결과 — 그리고 "재실행은 처방이 아니다"

배포 후 [자동 그룹화] 1회:

```
1차   생성 0 · 재사용 6 · 배정 28 · 미분류 1
      → '기타·특수 상황' 에 19/29(66%) 몰림. 복리후생비·접대비·출장비가 전부 거기로.
```

⚠️ **여기서 세션 중에 한 조언을 정정했다.** "결과가 별로면 한 번 더 누르면 된다"고 했는데
**틀렸다** — `auto_group_ungrouped_documents` 는 `group_id is null` 인 세목만 처리하므로,
재실행은 남은 1건만 건드리고 몰림은 그대로다. **재실행은 몰림의 처방이 아니다.**

진짜 처방은 **흡수원 제거**였다. `기타·특수 상황` 은 9/9 세대 유물이고, 이름이 무엇이든
빨아들이는 구조라 후보에 있는 한 계속 그리로 간다. 대목 삭제(문장 무관, 세목은 미분류로
풀려남) 후 재실행:

```
2차   생성 3 · 재사용 4 · 배정 19 · 미분류 1
      최대 묶음 19/29(66%) → 12/28(43%)
      복리후생비 · 육아휴직수당과세 · 6세이하자녀범위 → '인건비·복리후생' 으로 제자리
      업무용승용차특례 → '차량·자산 관련비'
      새 대목: 광고·경품 / 기부금 / 무형자산인식·처리
```

**가설대로 흡수원을 없애니 모델이 진짜 대목을 만들었다.** 다만 **몰림 자체는 다른 대목으로
옮겨갔다** — `공동 개원·시설 관련비` 12건에 접대비·출장비·현금매출증빙·의료봉사비용이
들어갔다(오배정). `부가가치세신고` 는 '부가가치세·적격증빙' 대목이 있는데도 미분류로
남았다(모델이 그냥 빠뜨림). 세목 1개짜리 대목 3개도 패스1 규칙 위반이다.

**여기서 멈췄다.** `공동 개원·시설 관련비` 에 같은 처방을 또 적용하면 정당한 세목
(개원전비용인정·공동개원정산)까지 풀어야 하고, 그건 이 프로젝트가 여러 번 확인한
**"회차 편차를 개선으로 착각하는"** 자리다. 남은 오배정은 **세무사가 옮기는 것이 맞고,
이제 A 승계가 들어갔으므로 그 손댐이 다음 회차에도 살아남는다** — 세션 초반 문제의
본질이 그것이었다.

**최종 상태**: 활성 세목 29개 중 **28개가 대목 아래**, 활성 대목 8개.

## 5. 남은 것 / 알려진 공백

- **몰림은 미해결이다.** 회차마다 흔들린다(드라이런 4회 최대 묶음 10/11/14/17, 프로덕션
  19→12). **선을 긋지 않았다** — 대목은 되돌릴 지식이 없고 사람이 언제든 옮길 수 있어서,
  가드보다 계측(`largestGroup`)이 맞는 처방이다.
- **원인 가설(미검증)**: 대목 목록에 '일반 경비'를 담을 이름이 없으면 가장 넓어 보이는
  대목이 흡수원이 된다. 검증하려면 패스1 출력(대목 목록)만 여러 회차 모아 비교해야 한다.
- **코드로 '기타'류를 후보에서 자동 제외하는 안은 채택하지 않았다** — 세무사가 쓰는 대목을
  코드가 임의로 빼는 것이라 권할 수 없다(사용자와 합의).
- **A 승계는 아직 프로덕션에서 한 번도 안 돌았다.** 다음 재구조화 회차가 첫 실증이다.
  볼 것: `job.result.groupInheritance.inherited` 가 0 이 아닌가(0 이면 배치가 또 날아갔다).
- 세목 1개짜리 대목 3개 — 패스1 규칙 6("세목 하나만 담을 이름이면 대목이 아니다")이
  안 지켜졌다. 개수는 스키마로 강제했지만 **"대목다움"은 여전히 프롬프트 의존**이다.

## 6. 재현 방법 (측정 자료는 스크래치패드라 세션과 함께 사라진다)

- **대목 승계 드라이런**: `kb2_taxonomy._inherit_groups(labels, previous)` 를 직접 부른다.
  입력 `previous` 는 `select tax_category, group_id from kb2.documents where group_id is
  not null and status='archived'`, `labels` 는 현 활성 문서의 `tax_category`. 쓰기 없음.
- **자동 그룹화 드라이런**: `kb2_store.create_group` / `set_document_group` 을 스텁으로
  갈아끼우고 `auto_group_ungrouped_documents()` 를 그대로 부른다 —
  **진짜 함수, 쓰기만 스텁**(프로젝트 측정 규칙).
- ⚠️ 드라이런에서 "중복 배정 수"를 최종 매핑(dict)으로 세면 **항상 0 이 나온다** — 그건
  계측이 거짓말하는 자리다. 모델 원응답 기준으로 세야 한다(이번엔 `documentsUngrouped`
  로 우회했다).
- LLM 호출은 회차당 2회(패스1+패스2). 재구조화가 도는 중에는 돌리지 말 것(429).
