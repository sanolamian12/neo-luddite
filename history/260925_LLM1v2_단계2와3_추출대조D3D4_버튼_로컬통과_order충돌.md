## 4. 설계가 틀렸던 것 / 새로 안 것

### 4-1. `order` 는 턴 순서를 말하지 않는다 (v1 부터)
프론트는 user 메시지에 `history.length`, 서버는 assistant 에 `max(order)+1` 을 매긴다 → **2턴부터 user 와 assistant 가 같은 order.**
"order 최대값 = 직전 메시지"로 찾다가 3턴에 상태가 사라졌다. → **목록 위치**로 찾는다. v1 `handoff.is_stalled` 도 order 정렬이지만 안정 정렬이라 우연히 맞는다. 고치는 건 공유 계약 변경이라 손대지 않았다.

### 4-2. 부록 B 의 "어떤 답이든 stated" 가 "모르겠어요"를 삼킨다
`unknown` 을 추가만 하니 "원가는 모르겠어요"가 stated. → unknown 을 enum·정의 맨 앞 + "모른다는 말 **말고** 어떤 답이든". 프로브 4문장 중 3 정답,
"…너무 오래돼서 모르겠어요"(문장 끝)만 stated. 부정형 "운행기록부는 따로 안 쓰고 있습니다"가 missing 1건. **단계 4 측정 대상.**

### 4-3. 누락 사실이 날조 수치를 달고 나온다
"골프 비용이 1인당 5만원 이하인지 여부" — 사실 문구가 그대로 질문이 되므로 틀린 기준액을 사용자에게 단정한다. → 출처 없는 수치가 든 사실은 뺀다(`droppedNumeric`). 결정력 높은 사실을 잃을 수 있음 → 단계 4 에서 빈도.

### 4-4. 되묻기 문안은 지시를 항목별로 줘야 한다
`[다시 묻기]` 표식만으로는 같은 질문을 되풀이. 항목별 지시로 고치니 "대략 얼마 정도로 생각하시나요?". 또 사실 2개 중 1개만 묻는 출력 → follow_up 수 < 사실 수면 결정적 문안.

### 4-5. 답변 단계 `write_advisory` 243초 1회
v1 함수가 120초×2 타임아웃 후 폴백 문안으로 끝났다(1/7 답변 턴). v1 이 알던 반복 루프·멈춤과 같은 성질로 보이나 재현 안 함. v1 파일이라 무변경 — LLM2 설계 때 max_tokens 를 걸 것.
